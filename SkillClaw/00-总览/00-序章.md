# 00 · 序章：这本书怎么读

## 写给谁

你打开了 SkillClaw 的源码——一个让 AI agent 的 skills 从真实交互中集体演化出来的 Python 项目(它由一个 OpenAI 兼容的本地代理 + 一个独立的 `evolve_server` 后台进程组成,详见 01 章)。你看到了一个 Python 包、一份 FastAPI 代理、一份 `evolve_server` 子包、一堆 SVG 图、一份论文 PDF。你想知道："这玩意到底是怎么工作的？"

你可能是：要把 SkillClaw 接入自家 agent 框架的后端工程师；要把它换成自家 LLM 的平台开发；要给它加一个全新 CLI agent 适配器的贡献者；或只是想搞清楚"agent skill 演化"这个范式到底是怎么落地的学生。

这本源码书**不是**给只想"调一下参数、跑一下命令"的人的——如果你只想跑起来，`README.md` 已经够用。**这是给"想看穿它"的人的**。

## 这本书不做什么

- **不重复 README**。`README.md` 是用户视角的快速入门（Path A / Path B / 部署手册）。本书是源码视角的内部构造。
- **不堆代码**。每一节默认禁用直接贴代码；如果某段代码被引述，会是"被精确截取、贴出来只为消除歧义"的那种。
- **不做"逐函数 API 文档"**。函数签名 / 字段默认值会列，但"这个字段解决什么问题"会展开。
- **不用"显然 / 众所周知 / 顾名思义 / 不难看出"等偷懒词跳过本该解释的地方**。如果某处读者需要回头翻前文，那是因为前文没把它讲透——跳到那一节读就行。
- **不替你做营销判断**。SkillClaw 的能力 / 局限 / 待确认项,本书会清楚标"## 待确认 / 已知限制"而不是回避,也不会用"强大""优雅"这种话术。

## 这本书做什么

本书面向**零背景读者**——读完即可建立 SkillClaw 的完整心智模型,然后按 4 条常用路径切入:

- **第一次读 / 想理解 SkillClaw 是什么**——按总览 3 章(00 → 02)+ 端到端 2 章(40 / 41)读,共 5 章读完即可建立完整心智模型;不必顺读模块层 15 章。
- **查特定功能**——直接看 INDEX 的覆盖映射,跳到对应章节。
- **排查 bug**——优先读 13(请求处理)、14(Session 簿记)、31/32(Evolve 引擎),这三章是 Bug 集中地。
- **接入新 CLI agent**——先读 17(适配器矩阵),再读 11(配置系统)。
- **部署到团队**——直接看 41(部署形态)。

- **按"数据/控制怎么流动"串讲**。不是按文件罗列,是按"一次请求从进到出"和"一次演化循环从触发到回写"两条主线,把分散在十几个文件里的逻辑重新串成线。
- **设计思路先于实现细节**。任何一段有分量的逻辑,先讲"问题是什么 → 选了什么思路 → 落到代码里是哪几步"——而不是"这个函数先调 A 再调 B 然后返回 C"。
- **术语第一次出现处必铺垫**。项目特有术语(`SKILL.md`、Claw、Two Loops、Publish Mode、Skill Backend、Session Bundle…)在首次出现时先讲定义;02 章是术语权威源,其它章的"## 术语速查"段只放"本章新引入"的术语,每条末尾指回 02 章。
- **默认值全部给具体数字,并标出"双源"位置**。完整默认值速查表见 [11 · 配置系统与字段归一化](01-客户端运行时/11-配置系统.md) §2 字段表;01 章"## 数字速查"只保留 5-10 行"心智模型级别"的非显然默认值(如 `prm_m=3` / `evolve_interval=600s` / `skill_reload_interval=30s`)。**默认值有两类来源:dataclass 声明 + 调用点运行时兜底**;具体见 11 章。
- **覆盖每条分支、每个边界、每个异常**。覆盖范围:控制流分支(if/else/match);公开 API 的错误返回 / 降级 / 重试;对象存储 / LLM 调用的网络异常;配置缺失 / 字段校验失败。**不**覆盖:操作系统层信号、未在源码里显式处理的 race condition、第三方库的内部异常。

## 学习者递进原则

本书是写给**零背景学习者**的——不是你熟悉 SkillClaw 之后再来复读的"技术参考"。每章核心讲解段按下面这套模板写,目的是让读者**沿着"为什么 → 怎么走 → 走了之后"递进建立认知**,而不是"看代码里有什么"。

### 核心讲解的"四段式"模板

每段有分量的逻辑按这四段写:

1. **场景引入**(这一段解决什么真实问题)
   - 假设读者正在用 SkillClaw 做 X,过程中遇到 Y 问题
   - 用一两句"具体场景 + 痛点"开场——而不是"这个函数是干嘛的"
   - 例:`"下午 3 点,Alice 公司的 evolve_server 刚跑完一个 cycle,把 12 个新 skill 写到了 OSS 上。现在她本机的 SkillClawAPIServer 怎么知道?"`

2. **设计思路**(用什么思路解决)
   - 作者选了 A 思路而不是 B 思路——为什么
   - 解释"设计 trade-off"——这个选择牺牲了什么、换来了什么
   - 例:`"作者选了"30 秒轮询 manifest"而不是"Nacos 长连接回调"——前者 30s 延迟但零依赖,后者实时但绑死 Nacos"`

3. **流程分步**(实际怎么走)
   - 整体流程分 N 步——每步**做什么**+**为什么这步在这**+**这一步的输出是什么**
   - 用"数据怎么流"展示输入/输出形状(可用 ASCII 框图 / JSON 形状)
   - 例:`"第 1 步 guard——`prm_scorer` 为空就早返回(为什么:配置层不报错,运行层兜底)"`

4. **关键边界 / 走了之后**(什么情况下会出问题)
   - 边界条件 / 异常路径 / 失败兜底
   - 走完这一步之后,系统的"状态"是什么(下一步从哪里接)
   - 例:`"如果 PRM 第三方 LLM 不可达——这次 turn 静默失败,`prm_score` 留 None,`effectiveness` 不变"`

### "代码翻译"的反面

下面这种讲法是**代码翻译**(应避免):

```markdown
`_apply_prm_result`(在 SkillClawAPIServer)走六步:
第一步从 `prm_result` 拿 `score` 字段,缺省 0.0;
第二步把 `turn_num` 减 1 转 0-based idx;
第三步做边界 check...
```

读者的困惑:**为什么这样设计?这步在解决什么?这步走了之后会怎样?**——这种讲法把这些全留给读者自己猜。

**改写为"学习者递进"**(示范,完整版见 16 章 §4.3):

```markdown
**场景**:第三方 LLM 评完一个 turn,拿到 `score ∈ {-1, 0, +1}`。现在需要把这个分数落进三个独立的地方。

**为什么三个地方**:SkillClaw 把"score"和"skill 效果"分开存——
- turn record(session 完整证据,evolve server 拉过去做摘要时看到)
- SkillManager(决定 `effectiveness`,影响下次是否推送该 skill)
- pending dict(让 finalize 流程能拿到最终结果)

**怎么走**(六步,但**顺序不能换**):
1. 拿 score 字段
2. turn_num 减 1 转 0-based idx
3. 边界 check
4. 写 turn record
5. SkillManager 两边都回灌(注入组 + 读取组)
6. 挂到 pending dict
```

### "代码翻译"和"学习者递进"的判别

读你写完的段,问自己三个问题:
1. **第一句** 讲的是"这个问题在用户视角是什么",还是"这个函数名是什么"?
2. **每个分步** 是不是都回答了"为什么这步在这"+"这步的输出是什么"?
3. **段末** 有没有讲"走完之后状态是什么 / 下一步从哪接"?

如果 1/2/3 都做不到,就是"代码翻译"——重写。

### 适用范围

- **16/31/32/40 章(模块层核心章)的核心讲解段**——必须按"四段式"重写
- **13/14/20/30/33 章(模块层支撑章)**——核心讲解段按"四段式"写,但允许"## 1. 顶层 X 步"先讲 happy path 走线,再分"## X.1 异常路径"段
- **10/11/12/15/17/21/22 章(模块层操作章)**——以"操作步骤 + 边界条件"为主,允许简化的"四段式"(场景 1 句 + 流程 + 边界)
- **00/01/02/41 章(总览/端到端)**——已是"学习者递进"风格,不动

## 怎么排错

> **前提**:以下路径假设你已经读完 00-序章 + 01-全景 + 02-核心概念词典;没读完先回去读这三章,否则排错路径里引用的术语看不懂。
>
> **调试路径 ≠ 阅读路径**。阅读路径按"先上游后下游"理解系统(10 → 11 → 12 → 13 → …),调试路径按"出问题的最近因果点"切入,可能与依赖图反向——前者服务"系统理解",后者服务"快速定位"。

- **"我装好了但代理没起来"** → 10(CLI 启动)→ 11(配置)→ 12(代理)。
- **"我的 agent 拿不到 skill"** → 12 → 15(技能库)→ 17(看你接入的 agent 对应哪个适配器)。
- **"skill 共享没生效"** → 20(共享存储与同步)→ 11(配置里 `sharing.*` 段)。
- **"Evolve server 跑了一晚没产出"** → 30 → 31(Workflow)/ 32(Agent)→ 33。
- **"想给 SkillClaw 加一个新的 agent CLI"** → 17(适配器矩阵)→ 11(配置 `claw_type`)→ 10(setup 向导)。
- **"deployment 上服务怎么扩"** → 41(部署形态)→ 30 → 20。
- **"数据流对不上 / 部署切模式后出问题"** → 40(数据流总览)→ 41(部署形态)→ 对应模块层章节。

## 章节体例约定

- **章首三段**:默认先讲"这一章讲什么 / 它在系统哪个位置 / 它的设计目的"。总览层 3 章(00 / 01 / 02)无"它在系统哪个位置"段(它们本身就是全景);模块层 / 细节层 17 章中,**16 / 21 / 22 / 40 章**已按这三段写,**32 章**因"## 术语速查"代位了"## 这一章讲什么"段(已在术语速查精简后补回,见 32 章 §章首)。其余 12 章遵循此约定。
- **每段有分量的逻辑**:先讲"问题 → 思路 → 步骤"。
- **数据形状**:用类 JSON 块描述输入/输出对象,被注入/改写的字段会**加粗**。
- **默认值 / 阈值**:用"→"或"="给出具体数值,例如"默认 30_000 字符"或"超时 60 秒";有"双源"会标 `(config.py:37 + api_server.py:2607)`。
- **章末"## 待确认 / 已知限制"**:除 00 / 01 / 02 总览三章外,每章末会标 "## 待确认 / 已知限制" 段(总览层不适用,模块 / 细节层适用)。**早期版本叫"未达项"或"待核"**——本版本统一为"## 待确认 / 已知限制";允许各章在标题后加副标题(如"分 3 类: 设计限制 / 错误路径 / 待对照验证"或"遗留决策 5 条")说明本章节内容侧重。章末"## 待确认 / 已知限制"段后直接接"`→ 下一篇`"链接。
- **章末"下一篇"**:除最后一篇(41 章)外每章末尾都有一行 `→ **下一篇**:xxx` 链接到下一章。
- **代码贴片**:默认每个 `.md` 整文档"关键入口路径"≤3 处引用、每段贴码 ≤10 行;**密集章放宽到 ≤8 处引用 / ≤20 行**。"密集章"指 13 / 16 / 30 / 31 这种逐函数 / 逐 stage 拆解的章节(13 章协议互转、16 章 PRM 多数票、30 章 env 表、31 章 6 段流水线);其余 16 章按默认约束执行。其他一律以叙述+形状+字段名表达。
