# 01 · 全景与设计哲学

## 术语速查(读本章前 1 分钟过一遍)

> 详细定义见 02 章核心概念词典;这里只给最简释义,方便第一次读到时不卡住。

- **Skill** —— 一段"agent 在合适时机能调用"的领域知识,最小单位是 `SKILL.md` 文件(frontmatter + body)。
- **SKILL.md / Frontmatter** —— skill 的主入口文件。YAML frontmatter 含 `name` / `description` / 可选 `metadata`,body 是实际内容。
- **Claw** —— SkillClaw 对它所代理的本地 CLI agent 框架的统称(OpenClaw / Hermes / Claude Code / Codex / OpenCode / QwenPaw / IronClaw / PicoClaw / ZeroClaw / NanoClaw / NemoClaw / `none`)。`claw_type` 决定走哪个适配器。
- **Two Loops** —— 任务时 loop(代理服务器,实时)和演化时 loop(`evolve_server`,后台)两个独立循环。
- **Sharing Backend** —— 客户端的"通用对象存储"后端:`local` / `s3` / `oss` / `nacos`(nacos 仅承载 skill 资产,不实现 ObjectStore 接口)。
- **Skill Backend** —— `sharing.skill_backend` 单独覆盖项;允许"skill 在 Nacos,session 在 OSS"的混合部署。
- **Session / Turn** —— Session 是一次连续对话;Turn 是 session 里的"模型出回答"事件,只有 `raw_turn_kind == "final"` 的轮次才推进 user-visible turn 计数。
- **PRM (Process Reward Model)** —— 用第三方 LLM(任何 OpenAI-compatible `/v1/chat/completions` 端点)对单条 turn 打 +1/-1/0,跑 `prm_m` 票取**多数票**(平票返 0.0)。详见 16 章。
- **Effectiveness** —— `positive_count / inject_count`,初始 0.5;`record_feedback` 写回 `skill_stats.json`。
- **Manifest** —— 共享存储里的 `manifest.jsonl`(每行一条 skill 记录)。注意 agent 引擎工作区内部叫 `manifest.json`(`evolve_server/engines/agent_workspace.py`),名字不一样但都是同一份"当前 skill 集合"的视图。
- **Publish Mode** —— 演化服务的发布模式:`direct`(直接写共享)/ `validated`(先 queue validation job)/ `validated`-客户端验证(写 `validation_jobs/<job_id>.json` + `candidate_skills/<job_id>/SKILL.md`,等 4 阈值满足才 finalize);`nacos_publish_mode` 另算:`review` / `direct` / `draft`。
- **Skill Verifier** —— `EVOLVE_USE_SKILL_VERIFIER=0`(默认关)开启后,evolve server 给候选 skill 打分;**拒绝条件是 `score < min_score(默认 0.75)`**,不是 4 个 checks 任一 < 0.5。
- **Session Judge** —— `EVOLVE_USE_SESSION_JUDGE=1`(默认开)给整个 session 打 0~1 分,作为信号而非门限。
- **`_skills_referenced` / `__no_skill__`** —— aggregator 用来把 session 按"读过的 skill 名字"分桶;没有引用任何 skill 的 session 进 `__no_skill__`。
- **OpenClaw** —— 一类支持 SKILL.md 协议的 coding agent(AMAP-ML 自家);Evolve server 的"agent 引擎"会把 workspace 丢给一个 OpenClaw 子进程。`EVOLVE_AGENTS.md` 协议详见 32 章。
- **Aggregator** —— workflow engine 第 4 步,按 `_skills_referenced` 字段把 session 分桶,每桶聚合出 `(rollout_count, mean_score, stability)` 等指标;详见 31 章 §3.2。
- **Summarizer** —— workflow engine 第 2 步,把 session 的完整 `messages` + `tool_calls` 压成"两步保真轨迹"(turn-level 摘要 + 关键 tool_call 名/参数/结果)+ LLM 摘要;详见 31 章 §3.2。
- **Evolver** —— workflow engine 第 5 步,按 Aggregator 分桶后给每桶调 LLM,返回 `DecisionAction`(见下) + 新 SKILL.md;详见 31 章 §3.4。
- **DecisionAction** —— `evolve_server/core/constants.py` 定义的枚举,字面值: `"improve_skill"` / `"optimize_description"` / `"create_skill"` / `"skip"`(默认)。**字符串字面值,不是属性名**;详见 31 章 §3.4。
- **两步保真轨迹** —— Summarizer 的产物形态:每个 turn 保留 `(turn_num, role, tool_call_name, tool_args 摘要, tool_result 摘要, 关键 user / assistant 文本)` 的压缩序列 + LLM 生成的会话级 `_summary`;详见 31 章 §3.2。
- **Polling cycle** —— 客户端 `SkillClawAPIServer` 的 `skill_reload_poller` 后台 task,每 `sharing.skill_reload_interval_seconds`(默认 30s)拉一次最新 manifest。Skill Reload Mode 详见 02 章 §24 / 20 章 §24。

## 设计目的

### 真正的痛点

每个用过 Hermes、OpenClaw、Claude Code、Codex 的人都经历过一个老问题:**"我的 skill 库慢慢就乱了"**(论文 arXiv:2604.08377)。

具体表现：
- 重复 skill：今天写的 `debug-systematically` 和上个月写的 `debug-bugs-step-by-step` 本质是同一件事，但谁也认不出谁。
- 过期 skill：上季度的 API 文档里写的端点都变了，skill 还在要求 agent 调老端点。
- 半成品 skill：写了一次的实验性 skill 没人删，堆在那里给未来的 agent 噪音。
- 跨设备 / 跨用户 / 跨 agent 隔离：在公司写的 React 模式 home 学不到，home 的 ML 模式 work 学不到。

传统思路是"让用户自己整理 skill"——但人在 skill 数到几十条之后就放弃整理了。

### Two Loops 范式

SkillClaw 的核心回答是**两个循环**（Two Loops，README 把它画成了 SVG `assets/two_loops.svg`）：

1. **任务时 loop（task-time loop）**——你不需要改的、你 agent 已经在做的事。
   - 用户 → 选 agent（Hermes / Claude Code / Codex / OpenClaw / …）→ agent 调 LLM。
   - SkillClaw 透明地"夹"在 agent 和 LLM 之间：一个 OpenAI 兼容的本地代理服务器。
   - 代理把**当前任务的 skill 目录**以 `<available_skills>` 的形式注入到 system prompt；模型像平常一样工作，只是在需要某个 skill 时多走一步 `read` 操作读 SKILL.md。
   - 同时，代理把整段对话的"工具调用 / 工具结果 / 哪个 skill 被读过"记到本地 record 文件。

2. **演化时 loop（post-task evolution loop）**——你不需要主动开的、SkillClaw 在后台做的事。
   - 一个独立的 `evolve_server` 进程，**周期地**或**被 HTTP 触发**地：去共享存储拉 session → 调 LLM 做摘要 / 评分 / 演化 → 把新生成的或改进的 skill 写回共享存储。
   - 写回的 skill 携带了来源信息（哪些 session 触发了这次演化），下次所有客户端的代理会通过 `skillclaw skills pull`（或自动 reload）把新版拉回去。

**这两个 loop 都不可见地工作**：用户只感觉到"我的 agent 越来越懂我在干什么了"。

### 设计原则

从代码里能反推出来几条 SkillClaw 强守的设计原则：

1. **对 agent 零侵入**。所有接入方式都是"把 agent 的 LLM endpoint 改到 `http://127.0.0.1:30000/v1`"——不改 agent 的代码、不改 agent 的 prompt。这是它能同时支持 12 种 CLI agent 的根因。
2. **存得下"真会话"，存得下"中间演化"**。共享存储布局既放了"完成态的 skill"（`skills/<name>/SKILL.md`），也放了"演化中的候选"（`candidate_skills/<job_id>/`）、"等待验证的任务"（`validation_jobs/`）、"失败回滚所需的 manifest.jsonl + evolve_skill_registry.json"。
3. **同一种 skill 格式，三种 agent 框架都用**。SKILL.md 的 frontmatter + body 是 OpenClaw、Pi coding agent、Hermes、AgentSkills 协议通用的事实标准。SkillClaw 不发明新格式。
4. **LLM 是组件，不是黑盒**。Evolve server 的工作流被显式拆成 Summarize / Judge / Aggregate / Evolve / Verifier / Upload 几个 stage，每个 stage 都有独立的 system prompt。`--engine workflow` 是固定流水线，`--engine agent` 是把同一个总结后的数据丢进 OpenClaw 让它自己读、改、写。
5. **保守优于激进**。Skill verifier 默认关闭（`EVOLVE_USE_SKILL_VERIFIER=0`），Nacos publish_mode 默认 `review`（不是 `direct`），client validation 默认 `validation.enabled=false`。要主动开才生效。

两条线只在"共享存储"这一个层面接头。这是 SkillClaw 部署的**核心契约**：客户端和服务端**只通过对象存储通信**，因此它们可以：
- 跑在同一台机器（个人自用）
- 跑在同一台机器，共享存储用本地目录（Path A 的"closed loop"）
- 跑在不同机器，共享存储走 OSS / S3 / Nacos（团队模式）
- 客户端可以同时被多个 evolve server 监控（但只有一个权威）
- 同一台 evolve server 可以服务任意多个客户端

## 端到端一条"session"的命运

把视角切到"一次完整生命周期",你就能在脑子里跑通整个项目。**注:第 4 步里 `~/.hermes/skills/` 是 Hermes 约定的本地 skill 目录;Claude Code / Codex / OpenClaw 等各有自己的路径,SkillClaw 自己使用的本地目录由 `skills.dir` / `claw_type` 共同决定,详见 17 章**。LLM 调用的 `read` 工具是 agent 框架自带的本地文件读取工具,SkillClaw 不注入、只观测其调用结果。

1. 上午 9:00,Alice 在公司用 Hermes 调起一个新对话。
2. Hermes 把请求发给 `http://127.0.0.1:30000/v1/chat/completions`(这是 SkillClaw 改写的)。
3. SkillClawAPIServer 拿到请求,注入 skill 目录里的所有 `SKILL.md` 描述,转发给上游 LLM。
4. 模型回了一段带 `tool_calls` 的内容,其中一个 `tool_call` 是 `read` 了 `coding-review-checklist` 这个 skill 的 SKILL.md。
5. SkillClaw 解析这段 tool_call,记下"这次 turn 读到了哪个 skill",连同完整对话写进 `conversations.jsonl`;同时异步触发 PRM 打分(PRM 用**多数票**,`prm_m=3` 票,平票返 0.0;score ∈ {-1, 0, +1})。
6. 用户提示"end of session"(或 idle 180s)→ SkillClaw 关闭这个 session(只有 `raw_turn_kind == "final"` 的轮次才推进 user-visible turn 计数;其他轮次只是"模型思考过"),把 `conversations.jsonl` 整段上传到 `{group_id}/sessions/{session_id}.json`。
7. 同时,`evolve_server` 在 10 分钟一次的 cycle(`evolve_interval=600s`)里发现这个新 session。
8. Summarizer 把这个 session 压成"两步保真轨迹"(每个 turn 保留 tool_call 名 + 关键参数 + 工具结果)+ LLM 摘要。
9. Session Judge(可选)给整个 session 打 0~1 的 `overall_score`,4 个加权维度:`task_completion 0.55` / `response_quality 0.30` / `efficiency 0.05` / `tool_usage 0.10`——**作为信号而非门限**。
10. Aggregator 按 `_skills_referenced` 把这个 session 归到 `coding-review-checklist` 这一组(也可能没有,归到 `__no_skill__`);**多个客户端同时改同一个 skill 时走 conflict detection**(详见 31 章)。
11. Evolver 把这一组 + 当前 SKILL.md + 库里其他 skill 名 → LLM,LLM 决策**字面值**为 `DecisionAction.IMPROVE`(`"improve_skill"`) / `OPTIMIZE_DESC`(`"optimize_description"`) / `CREATE`(`"create_skill"`) / `SKIP`(`"skip"`)。
12. 如果选 `"improve_skill"`,生成的新 SKILL.md → **Skill Verifier(可选)**,score ≥ `min_score=0.75` 才上传 → 写回 `{group_id}/skills/coding-review-checklist/SKILL.md` + 更新 `manifest.jsonl`(每行一条 bundle_v1 记录)。
13. SkillClawAPIServer 在 poll loop(默认 30s,可改 `sharing.skill_reload_mode` 为 `callback` / `off`)里发现 manifest 有新条目 → 拉新 skill → 重载本地 `SkillManager`。
14. Alice 下午在公司问一个相关问题,模型收到的 system prompt 里就已经有"updated checklist"了。

**这 14 步就是 SkillClaw 的本质**。后面所有章节都是这 14 步的"放大 + 拐角 + 备选路径"。

> **共享存储布局各路径职责**:
> - `skills/<name>/SKILL.md` —— 客户端能直接读的最终 skill 资产(client `pull` 时拉这个);
> - `manifest.jsonl` —— 每行一条 skill 记录(`name` / `skill_id` / `version` / `sha256` / `tree_sha256` / `format: "bundle_v1"` / `files: [...]` / `uploaded_by` / `uploaded_at`);用于客户端发现新版本、agent 引擎读取当前 skill 集合;
> - `sessions/<session_id>.json` —— 完整 session(包含 messages + tool_calls + injected_skills + 摘要 + judge 分);
> - `validation_jobs/<job_id>.json` —— 验证任务(只在 `publish_mode=validated` 模式写入);
> - `candidate_skills/<job_id>/SKILL.md` —— 等待客户端验证的候选 skill;
> - `validation_results/<job_id>/<user_alias>.json` —— 多个客户端各自的验证结果;
> - `evolve_skill_registry.json` —— `name → {skill_id, version, content_sha, history: [...]}`,支持回滚。

## 失败 / 边界场景速查

> 14 步只画了 happy path。这里把"系统实际会怎么兜底"按场景列;**每个场景是"我读这本源码书时,不能漏掉的隐含行为"**。

- **PRM 异步失败 / 第三方 LLM 不可达** —— 这次 turn 的 PRM task 静默失败,`record/prm_scores.jsonl` 不写这行;`skill_stats.json` 的 `effectiveness` 不会因这次失败改变(只统计成功返回的 PRM)。Agent 回答已经返回给用户,SkillClaw 不重写。
- **共享存储 S3/OSS 不可达** —— session snapshot 上传失败时,记录会留在本地 `~/.skillclaw/records/`(进程生命周期内),下个 `idle` cycle 重试;`SkillHub.push_skills` 失败时 `--no-filter` 也救不了,直接报 ClickException。
- **evolve_server 周期任务跑挂(进程死 / OOM)** —— 没有内置 watchdog,只有外部 systemd / launchd 兜底。重启后下一个 cycle 重新 drain。
- **polling 30s 间隙内 manifest 改了多个版本** —— 客户端一次拉取会按 `version` 升序处理所有新行,不会丢版本(除非网络中断)。
- **多客户端同时改同一个 skill** —— aggregator 端有 conflict detection(Nacos 走"按版本合并"分支,详见 31 章)。
- **session idle 180s 关 session,刚好在 LLM 流式返回中** —— `_close_session` 只关簿记,不动当前 stream;流返回照常完成,但不会触发下一次 user_turn 推进。
- **Daemon 进程被 OOM kill 但 PID 文件残留** —— `os.kill(pid, 0)` 在 PID 是僵尸时仍返回成功(见 10 章 8 节"待核"),下个 `start --daemon` 会被 `_ensure_daemon_not_running` 误判为在跑;生产建议用 systemd / launchd 兜底。
- **配置缺失** —— 字段未填时 `to_skillclaw_config` 用 dataclass 默认;`api_server.py:2607` / `3237` / `skill_manager.py:186` 还有一层调用点兜底(双源默认)。
