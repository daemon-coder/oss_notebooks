# 02 · 核心概念词典

> 写在前：这一章是**共同语言地基**。后面任何章节的"项目特有术语"第一次出现都会回到这里（"见〈核心概念〉→ XX"），不再展开。读者可以先把这一章当成术语表，需要时跳回来查。

---

## 1. Skill（技能）

SkillClaw 的"资产"是**一段可被 agent 加载的提示 / 知识 / 模板**。最小单位是一个 `SKILL.md` 文件，**通常还伴随一组辅助文件**（references / scripts / assets / history）。

- 在用户视角，一个 skill 是一段被 agent 在合适时机读取的领域知识。
- 在代码视角,一个 skill 是一个 `dict`(**这是 `SkillManager.get_all_skills()` 归一化后的形态;SKILL.md 源文件里 `category` 写在 `metadata.skillclaw.category`,归一化时被拍平到顶层 `category`**):
  ```python
  {
    "id": "<sha256(name)[:12]>",
    "name": "debug-systematically",
    "description": "Use when diagnosing a bug. ... NOT for: simple typo fixes.",
    "category": "coding",  # 默认 "general"——归一化后从 metadata.skillclaw.category 拍平过来
    "content": "<markdown body, 不含 frontmatter>",
    "file_path": "/absolute/path/to/SKILL.md",
    "metadata": { "skillclaw": { "category": "coding" }, ... },  # 可选,源 SKILL.md 里的嵌套形态
    "_extra_frontmatter": { "homepage": "...", ... }            # 可选,frontmatter 里 SkillClaw 不认识的字段透传过来
  }
  ```
- 在磁盘视角，一个 skill 是一个目录：
  ```
  my-skill/
    SKILL.md            # 必有
    references/...      # 可选
    scripts/...         # 可选
    assets/...          # 可选
    history/v<N>*.md    # 可选（agent engine 在 no-fresh 模式积累）
  ```

注意 "skill" 和 "Skill" 在不同上下文里的拼写差异——`Skill` 通常指 Python 类（`SkillManager`、`SkillHub`）；`skill` 指数据 / 文件级别的概念。

## 2. SKILL.md / Frontmatter / Body

**SKILL.md** 是 skill 的"主入口文件"，内容由两部分组成：
- **YAML frontmatter**(用 `---` 包起来):name / description / metadata(可选)/ category(可选,**SKILL.md 源里 `category` 写进 `metadata.skillclaw.category`,不写在顶层**——见上面 §1 归一化)
- **Markdown body**：实际的领域知识 / 提示 / 模板

最小可工作的 SKILL.md 长这样：

```markdown
---
name: debug-systematically
description: "Use when diagnosing a bug. Gather evidence before forming hypotheses. NOT for: simple typo fixes."
---

# Debug Systematically

1. Reproduce the bug.
2. ...
```

校验规则（`SkillManager._parse_skill_md`）：
- 文件不存在 → 跳过
- 不以 `---` 开头或找不到 `\n---` 收尾 → 跳过
- 解析 frontmatter 后 `name` / `description` 任何一个为空 → 跳过
- 否则 name 通过正则 `^[a-z][a-z0-9-]{1,63}$` 校验

**类别解析优先级**：`metadata.skillclaw.category` > 顶层 `category` > `"general"`。

## 3. Skill Bundle（多文件 skill 包）

一个 skill 不一定只有一个 SKILL.md——它可能还带 `references/`（参考文档）、`scripts/`（可执行脚本）、`assets/`（模板/图片）等。

**bundle** 是这个目录的"内容 + 指纹"表示：
- `bundle = {rel_path: bytes}`，比如 `{"SKILL.md": b"...", "references/api.md": b"..."}`
- `tree_sha256(bundle)` 把所有文件按 (path, sha256, size) 排序拼成 SHA-256，是 bundle 的"内容指纹"
- `bundle_file_records(bundle)` 输出 manifest 的 `files` 数组：`[{"path": "SKILL.md", "sha256": "...", "size": 1234}, ...]`

SKILL.md 是 bundle 的"entrypoint"。`bundle_v1` 是当前的 manifest 格式（`evolve_skill_registry.json`、`manifest.jsonl`、bundle record 都用这个 schema）。

被忽略的路径（`skill_bundle.is_ignored_bundle_rel_path`）：`.DS_Store`、`.git/`、`__pycache__/`、`.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`、`*.pyc` / `*.pyo`。

## 4. AgentSkill / OpenClaw 兼容

**AgentSkills 协议**（也称 OpenClaw skill 协议）是 SkillClaw 选用的事实标准。一段 SKILL.md 必须能被 OpenClaw / Pi coding agent 直接读懂，SkillClaw 才"放心"作为本地 skill 库的格式。

关键约束（直接影响 SkillClaw 实现）：
- `name` 必须是 kebab-case（小写字母+数字+短横线）
- `description` 是**触发描述**（不是摘要）——它告诉模型"什么时候用、不什么时候用"
- `metadata.openclaw.emoji` / `metadata.skillclaw.category` 这类嵌套结构会被保留
- `disable-model-invocation: true`（顶层 frontmatter 字段）会被 `SkillManager.get_all_skills()` 过滤掉

## 5. Claw（CLI agent 适配对象）

"Claw" 是 SkillClaw 对**任何被它代理的本地 CLI agent 框架**的统称。支持 12 种 claw type：
- `openclaw`、`hermes`、`codex`、`claude`、`opencode`、`qwenpaw`、`ironclaw`、`picoclaw`、`zeroclaw`、`nanoclaw`、`nemoclaw`
- `none`：不自动配置（仅手动把 agent 指向 `127.0.0.1:30000`）

每个 claw 都有一个 `claw_adapter._configure_<name>(cfg)` 函数。`configure_claw(cfg)` 是一个 dispatcher，按 `cfg.claw_type` 选适配器执行。

## 6. Claw Type

`cfg.claw_type` 字段，决定：
1. `SkillClawLauncher` 启动时调哪个 adapter
2. `ConfigStore.resolve_skills_dir` 选哪个本地 skills 目录（`~/.hermes/skills` / `~/.codex/skills` / `~/.claude/skills` / `~/.config/opencode/skills` / `~/.skillclaw/skills`）
3. `ConfigStore.default_llm_api_mode_for_claw` 选哪个 upstream 模式（`codex` 默认 `responses`，其它默认 `chat`）
4. `doctor <claw>` / `restore <claw>` 命令的目标

**`configure_openclaw: false`** 在配置里被回退为 `claw_type=none`（保持向后兼容）。

## 7. Two Loops（任务时 loop + 演化时 loop）

见 [01 · 全景与设计哲学](01-全景与设计哲学.md)。任务时 loop = `SkillClawAPIServer` + `SkillManager` 在用户和 LLM 之间做"透明中间人"；演化时 loop = `evolve_server` 在后台把 session 炼成 skill。

## 8. Session（会话）

Session 是 SkillClaw 视角的"一次连续对话"。一个 session 拥有：
- `session_id`：从 OpenClaw 来的是 `X-Session-Id` header；从 Hermes 来的是 `x-claude-code-session-id`（或请求 body 里的 `session_id`）；从 TUI 类 agent（QwenPaw / IronClaw / 通用 OpenAI 兼容客户端）来的是启发式生成（`tui-<model>-<8hex>`）
- `turn_count` / `user_turn_count`：内部计数器
- 若干 `turn_record`（见 Turn）
- `turn_type`：`main`（主对话）或 `side`（子任务）。Side turn 不会被记入主 session 流程
- `session_done`：显式 `X-Session-Done: true` 或 `body.session_done: true` 才触发 `_close_session`
- 关闭触发条件(任一满足即触发 `_close_session`):
  1. 显式 `session_done`:`X-Session-Done: true` header 或 body 字段;触发后写 record + 上传 snapshot。
  2. **180s 全局无活动**(`session_idle_close_seconds`,默认 180;所有 session 适用)—— 内部 idle sweeper 每 30s 扫一次,满足就关。
  3. **TUI 边界**(仅 TUI 类 agent,启发式识别为 `tui-<model>-<8hex>` 形式 session_id):"最近一窗消息数 ≤ 上一窗消息数" **AND** 距上一请求 ≥ 300s。两条 AND 判定。
  4. **进程关闭**:`atexit` / SIGTERM 钩子调 `_close_session`(走记录 + 上传);SIGKILL / OOM 杀进程时 record 只写到上次 flush 点为止,**不**补。

**session 不是 stream**——SkillClaw 不维护一个 long-lived 的 WebSocket / SSE session 上下文；它把所有信息塞进本地内存（`_session_turns`、`_pending_turn_data` 等） + 持久化 record 文件 + 共享存储。

## 9. Turn（轮次）

Turn 是 session 里的一次"模型出回答"事件。每个 turn 在 SkillClaw 内部是这样一个 dict（**与 §1 的 Skill dict 完全不同**——Turn 是事件，Skill 是资产）：

```python
{
  "session_id": str,                 # 来自 X-Session-Id / x-claude-code-session-id
  "turn_num": int,                   # 1-based, session 内单调递增
  "user_turn_num": int,              # 只在 user 边界推进
  "turn_type": "main" | "side",      # 来自 X-Turn-Type header 或 body 字段
  "raw_turn_kind": "user" | "side_user" | "tool" | "side_tool" | "self_check" | "final",
                                    # SkillClaw 内部综合判定,详见 §23
  "messages": [...],                 # 完整 OpenAI / Responses / Anthropic 消息链
  "tool_calls": [...],               # 如果是 tool turn
  "tool_observations": [...],        # tool 返回
  "tool_errors": [...],              # tool 异常
  "injected_skills": [name, ...],    # build_injection_prompt 实际塞进去的
  "read_skills": [name, ...],        # 后续 read_skill 工具读到的
  "modified_skills": [name, ...],    # 后续 edit_skill 工具改过的
  "reasoning_content": str | None,   # 来自 extended thinking
  "prm_score": float | None,         # PRM 完成后回灌(见 §10)
}
```

**持久化**:`conversations.jsonl` 每行只写 `messages` / `tool_calls` / `injected_skills` / `prm_score` 四个字段(其它字段只在内存,见 §25)。`_classify_raw_turn_kind` 判断"这是不是一个 user 边界"——只有 user 边界会推进 `user_turn_num`、触发 `_maybe_upload_session_snapshot`。

## 10. PRM（Process Reward Model）

PRM 是 SkillClaw 用**第三方 LLM**（任何 OpenAI-compatible `/v1/chat/completions` 端点）给模型回答打的"过程分"。

打分规则（见 `_build_prm_judge_prompt`）：
- `+1`（有用）/ `-1`（无帮助）/ `0`（模糊）
- 输出格式：以 `Score: 1` / `Score: -1` / `Score: 0` 结尾（兼容 `\\boxed{N}` 旧格式）
- 跑 `prm_m` 票（默认 3 票）取多数票；平票返回 0.0

返回 `{"score": float, "votes": [...], "eval_text": str}`，score ∈ {-1.0, 0.0, 1.0}。

PRM 的消费者：
- `SkillManager.record_feedback` → 写入 `skill_stats.json`（更新 effectiveness）
- `record/prm_scores.jsonl` 行追加
- 不修改 LLM 的回答（SkillClaw 是**外部代理**而不是"重写器"）

## 11. Effectiveness（技能有效度）

`SkillManager._stats[name].effectiveness`：`positive_count / inject_count`，初始 `0.5`（未观察 = 中性）。

数值范围 [0, 1]。被两类事件影响：
- `record_injection(skill_names)`：每次 skill 被注入到 prompt，`inject_count += 1`
- `record_feedback(skill_names, score)`：PRM 完成后回灌，score > 0 → `positive_count += 1`，score < 0 → `negative_count += 1`，score == 0 → `neutral_count += 1`

`effectiveness` 用于：
- 推送门：默认 `min_effectiveness >= 0.3` + `min_injections >= 5` 才会被 `skillclaw skills push` 上传
- 排序：embedding 模式里 `_weighted_score = similarity * (0.3 + 0.7 * eff)`，高 effectiveness 的 skill 在相似度相近时优先

`skill_stats.json` 每 10 次 mutation flush 一次到磁盘。

## 12. Sharing Backend（共享存储后端）

`sharing.backend`：客户端的"通用对象存储"后端。可选值：
- `local`：本地目录
- `s3`：AWS S3 / S3 兼容（MinIO / R2 / B2）
- `oss`：Alibaba Cloud OSS
- `nacos`：Nacos 存 skill 资产（仅 skill 资产进 Nacos）

`sharing.skill_backend`（可选，覆盖项）：如果设了，skill 资产走这个后端而不是 `sharing.backend`。其它 session / validation 数据继续走 `sharing.backend` / `sharing.session_backend`。

`SkillHub.from_config(config)` 是入口：如果 `skill_backend=nacos` 走 `NacosSkillHub`，否则走通用 `SkillHub`。

## 13. Skill Backend

指"skill 资产专门走哪个后端"，独立于 session / validation 走的后端。这套拆分允许：
- 全部用 OSS：skill + session + validation 都去同一个 bucket
- 混合 Nacos + OSS：skill 在 Nacos（带版本 / 审核 / 标签生命周期），session 在 OSS
- 全部 local：单机自用

## 14. Group ID / User Alias

`sharing.group_id`：共享命名空间。同一 group 内的所有客户端共享同一组 skill、session、validation 资源。默认 `"default"`。

`sharing.user_alias`：客户端在 session 上传时被记为作者。默认从 `$USER` 环境变量读。推送 skill 时 `manifest.jsonl` 会带 `uploaded_by: <user_alias>`。

`auto_pull_on_start`：启动时自动从共享存储拉最新 skill。默认 `false`。

## 15. Publish Mode（演化服务的发布模式）

`EVOLVE_PUBLISH_MODE` / `evolve_server.config.publish_mode`：
- `direct`（默认）：evolve server 跑完 `EvolveServer._upload_skill` 后，SKILL.md 直接写进共享存储
- `validated`：evolve server 把候选 skill 写进 `validation_jobs/<job_id>.json` + `candidate_skills/<job_id>/SKILL.md`；等客户端验证（`ValidationWorker`）积累足够结果后，最终才把 SKILL.md 写进正式 `skills/<name>/` 路径

`validated` 模式的判定门(`validation_*` 配置,均默认 1):
- `validation_required_results`:累计 result 数 ≥ 这个值(默认 1)
- `validation_required_approvals`:accepted 数 ≥ 这个值(默认 1)
- `validation_min_mean_score`:mean score ≥ 这个值(默认 0.75)
- `validation_max_rejections`:rejected 数 ≥ 这个值就 reject(默认 1)

**前置守卫**:`_finalize_validation_jobs` 仅在 `publish_mode == "validated"` 时被调用;否则直接 return,不下任何判定。

**判定规则(对每个 job 独立执行,4 条互斥)**,按下列优先级:
- **1. 硬性拒绝**:`rejected_count >= validation_max_rejections`(默认 1)→ finalize 为 **rejected**,立即终止该 job。
- **2. 通过**:`accepted_count >= validation_required_approvals`(默认 1) **AND** `mean_score >= validation_min_mean_score`(默认 0.75)→ finalize 为 **accepted**,候选 skill 写进 `skills/<name>/`。
- **3. 暂缓**:`results_count >= validation_required_results`(默认 1) 但 accept 条件未满足 → finalize 暂缓,等下次 cycle 再判;暂缓 job 长期不通过会被 `validation_max_pending_cycles`(默认 10)兜底:超过则自动 finalize 为 rejected 并清空 candidate。
- **4. 继续积累**:`results_count < validation_required_results` → 不动,继续积累。

注:`validation_min_mean_score=0.75` 与 Skill Verifier 的 `EVOLVE_SKILL_VERIFIER_MIN_SCORE=0.75` 是**两个独立的阈值**——前者是 client 端验证阶段的通过线,后者是 server 端生成阶段的"值得上传"线;不要混。

## 16. Skill Verifier（候选闸门）

`EVOLVE_USE_SKILL_VERIFIER=0`（默认）= 关闭。打开后，evolve server 在 candidate 生成后、上传前**再调一次 LLM**，给候选 skill 打一个 0~1 分（`EVOLVE_SKILL_VERIFIER_MIN_SCORE=0.75`）。低于阈值就 reject，不上传。

打分的 4 个子维度：
- `grounded_in_evidence`
- `preserves_existing_value`
- `specificity_and_reusability`
- `safe_to_publish`

## 17. Session Judge（session 级评分）

`EVOLVE_USE_SESSION_JUDGE=1`（默认开）= 开启。evolve server 在 summarizer 之后给每个 session 打 0~1 分，4 个加权维度（`task_completion 0.55`、`response_quality 0.30`、`efficiency 0.05`、`tool_usage 0.10`），加权得 `overall_score`。这个分数会进入 summary，被 evolve 的 LLM prompt 看到。**不**作为门限，只作为信号。

如果 session 已经有更可靠的"benchmark score"（含 `aggregate` 字段如 `rollout_count` / `mean_score` / `stability`），judge 会跳过该 session。

## 18. Engine（演化引擎）

`EVOLVE_ENGINE` / `evolve_server.config.engine`：
- `workflow`（默认）：固定 6 阶段流水线（drain / summarize / judge / aggregate / evolve|create / upload）
- `agent`：把整个 `workspace/` 目录丢给一个 OpenClaw 子进程，让 LLM 读 SKILL.md 改 SKILL.md

两种引擎共用 `EvolveEngineMixin`（存储 / 命名 / history 持久化），但对 session 的处理方式不同。

## 19. Object Store / 共享存储

四种 adapter 都实现同一接口（`iter_objects` / `get_object` / `put_object` / `delete_object`）：
- `LocalObjectStore`：本地目录
- `S3ObjectStore`（boto3）
- `OSSObjectStore`（oss2）
- `NacosSkillClient`（仅 `SkillHub` 用，不实现 `ObjectStore` 接口）

`build_object_store(backend, ...)` 是工厂函数（`object_store.py`）。`normalize_backend` 把 `filesystem` / `fs` / `s3-compatible` / `minio` / `r2` / `b2` 这些 alias 归一到 `local` / `s3`。

## 20. Skill Bundle Protocol（bundle_v1）

共享存储里 skill 的"序列化协议"：
- `skills/<name>/SKILL.md`（必有）
- `skills/<name>/files/<rel_path>`（可选，多文件 bundle）
- `skills/<name>/versions/v<N>/SKILL.md` + `.../versions/v<N>/files/...`（历史版本）
- `skills/<name>/versions/v<N>/bundle.json`（这一版本的 manifest 记录）
- `manifest.jsonl`（每行一条 skill 记录，含 `name` / `skill_id` / `version` / `sha256` / `tree_sha256` / `format: "bundle_v1"` / `entrypoint: "SKILL.md"` / `files: [...]` / `uploaded_by` / `uploaded_at` / `description` / `category`）
- `evolve_skill_registry.json`（`name → {skill_id, version, content_sha, history: [...]}`）

## 21. Dashboard / SQLite Projection

`skillclaw dashboard sync` 把本地 skill 库 + 共享 skill 库 + record 文件 + validation_jobs 投射到 `~/.skillclaw/dashboard.db`（SQLite，WAL 模式）。`skillclaw dashboard serve` 暴露一个 FastAPI（端口 3788）+ 静态 HTML/JS 前端。

Dashboard 永远**只读**——它不写回任何东西，只是把"快照"读出来。

## 22. Idle State Provider（验证器空闲判定）

`ValidationWorker.idle_provider` 实现 `IdleStateProvider` 协议：
- `active_session_count()`：当前还在进行中的 session 数
- `last_request_age_seconds()`：上一次有请求距今的秒数
- `is_idle_for_validation(idle_after_seconds)`：是否满足"没活跃 session + last_request_age ≥ N"

`SkillClawAPIServer` 实现了这 3 个方法（`active_session_count` / `last_request_age_seconds` / `is_idle_for_validation`）。`SkillClawLauncher` 把 server 注入 `ValidationWorker` 的 `idle_provider`。

## 23. Main turn vs Side turn

`X-Turn-Type` header（或 body `turn_type`）决定：
- `main`（默认）：注入 skill / 记 record / 触发 PRM / 计入 session 簿记
- `side`：不注入 skill（避免被 agent 的子任务污染本地库）、不记主 record，但仍转发 LLM

子任务（side）通常来自 OpenClaw 内部的小工具调用，比如"先帮我搜一下这段代码"——这些不应该被记成"用户使用了哪些 skill"。

## 24. Skill Reload Mode

`sharing.skill_reload_mode`：
- `poll`（默认）：client 端 SkillClawAPIServer 每 `sharing_skill_reload_interval_seconds`（默认 30s）拉一次最新 skill
- `callback`：client 注册 `POST /internal/reload-skills` HTTP 端点；evolve server 上传完后**主动** POST 通知（要配 `EVOLVE_PROXY_RELOAD_URL`）
- `off`：不主动 reload；只能等下次手动 `skillclaw skills pull`

`callback` 模式的链路：evolve server 看到 `uploaded_skills > 0` → `EvolveServer._notify_proxy_reload` → 3 次重试 → 调 `POST {proxy_reload_url}/internal/reload-skills`（带 `Bearer {proxy_reload_api_key}`）。

## 25. Conversation Record / PRM Record

`config.record_enabled=True`（默认）时，SkillClawAPIServer 在 `record_dir/`（默认 `records/`）下：
- `conversations.jsonl`：每行一个 turn 记录（持久化字段:`messages` / `tool_calls` / `injected_skills` / `prm_score`——其它 turn 字段如 `read_skills` / `modified_skills` / `reasoning_content` 只在内存,见 §9）
- `prm_scores.jsonl`：每行一个 PRM 结果（session_id, turn, score, votes）

启动时这两个文件会被**清空**（`with open(self._record_file, "w"): pass`）——所以 record 是"这一进程生命周期内"的，不是跨重启累积的。

## 26. 重要"反概念"（避免混淆）

> (与 [01 章 §1.5](01-全景与设计哲学.md#15-它不是什么反概念) 同源;01 章作为读者第一道心理防线,本节作为术语表的位置。)

- **SkillClaw 不是 RAG**。它不做向量检索召回 + 喂上下文片段。它把**整段 skill 描述**塞进 system prompt，让模型自己挑——再按需 `read` 具体 SKILL.md。
- **SkillClaw 不是训练框架**。它不动模型权重。它只增删改本地和共享存储里的 SKILL.md。
- **SkillClaw 不是 LLM agent 框架**。它不调度工具、不维护 agent 状态机；它只是 agent ↔ LLM 之间的"中间人"。
- **SkillClaw 不是 prompt 工程工具**。它不写"更好"的 system prompt；它写"可被 LLM 在对的时候调用的、写在 SKILL.md 里的领域知识"。
- **EvolveServer 不是 worker queue**。它一次只跑一个 cycle（`run_periodic`）；新 session 进来只能等下一个周期。
