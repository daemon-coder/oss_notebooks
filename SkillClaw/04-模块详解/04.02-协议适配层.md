# 04.2 协议适配层 `protocols/`

> 把三种 LLM 协议(OpenAI chat / OpenAI Responses / Anthropic Messages)互相翻译,统一到一个内部表示。

## 设计动机

Agent 端会用三种主流 LLM 协议之一跟 SkillClaw 对话。每种协议的 body shape、role 字段、tool_call 表达都不一样。SkillClaw 想:

- **不**改 LLM 上游——可以保留任何 OpenAI 兼容的 LLM;
- **支持**所有三种 Agent 端协议;
- **统一**内部处理(skill 注入、session 累积)用一份代码。

最简单做法:选一种协议作为"内部规范"(代码里选的是 OpenAI chat-completions),把其他协议**进**来时转成它,**出**去时也只暴露这种规范的"等效形式"。

## 核心概念

| 概念 | 定义 | 引用 |
|---|---|---|
| **3 种 LLM 协议** | (1) OpenAI `/v1/chat/completions` (2) OpenAI `/v1/responses` (3) Anthropic `/v1/messages` —— Agent 用其中之一跟 SkillClaw 对话 | 全章 |
| **内部规范 = OpenAI chat-completions** | SkillClaw 内部**统一**用 OpenAI chat 协议作为"中间表示";其他两种协议"进来时"转成它,"出去时"也只暴露它的等效形式 | `api_server.py:_anthropic_to_openai_body` |
| `protocols/anthropic_messages.py` | Anthropic ↔ OpenAI body 转译(完整版) | 文件全文 |
| `protocols/openai_responses.py` | OpenAI Responses ↔ OpenAI chat 转译 | 文件全文 |
| `protocols/common.py` | 共用工具(46 字节,极小,预留位置) | 全文 |
| `_anthropic_to_openai_body` | api_server 内的快速版转译(早期实现,完整版在 `protocols/anthropic_messages.py`) | `api_server.py:1094` |
| `_PROTOCOL_ANTHROPIC_MESSAGES` | 协议标识常量 | `api_server.py:54` |

## 实现要点

### A. Anthropic Messages → OpenAI chat-completions

`api_server.py:1094` 的 `_anthropic_to_openai_body` 是简化版,完整版在 `protocols/anthropic_messages.py`。两版做的事相同:

**Anthropic body 关键差异 → OpenAI body 等效字段**:

```
Anthropic                          OpenAI
────────────────────────────────────────────────────────
system: "..." 或 [{type:"text"}]   messages[0] = {role:"system", content:"..."}
messages: [{role, content,         messages: [{role, content, 
            tool_use, tool_use_id}]            tool_calls:[{...}]}]
tools: [{name, description,        tools: [{type:"function", function:
         input_schema}]                       {name, description, parameters}}]
tool_choice: {type, name}          tool_choice: "auto" | "none" | 
                                                {type:"function", function:{name}}
max_tokens: 整数                    max_tokens: 整数
stop_reason: "end_turn" | "tool_use" finish_reason: "stop" | "tool_calls"
usage.input_tokens/output_tokens    usage.prompt_tokens/completion_tokens
content_block.type = "tool_use"     message.tool_calls[0].function.name
content_block.input = {...}          message.tool_calls[0].function.arguments
content_block.id = "toolu_..."       message.tool_calls[0].id = "call_..."
content_block.type = "tool_result"  separate message: role:"tool",
  + tool_use_id + content              content + tool_call_id
```

**注意事项**:
- Anthropic 的 `system` 字段是 top-level,不是 `messages[0]`;要提取出来再插。
- Anthropic 的 tool_use 嵌在 assistant content blocks 里,要拆出独立的 `tool_calls` 数组。
- Anthropic 多模态用 `content: [{type: "image", source: {...}}]`,OpenAI 同样支持但 source shape 不同(anthropic 用 base64 + media_type,openai 用 image_url 字符串)。
- 一些 OpenAI 高级特性(`parallel_tool_calls`、`logprobs`、`metadata` 等)在 Anthropic 端无对应,转译时直接丢弃。

### B. OpenAI Responses → OpenAI chat-completions

`protocols/openai_responses.py` 处理 OpenAI 的新协议(`/v1/responses`)。

**Responses 协议关键差异**:

```
Responses API                    chat-completions API
──────────────────────────────────────────────────────
input: "..." 或 [{role, content,   messages: [{role, content, ...}]
                ...}]               (结构几乎一样)
instructions: "..."               → 合到 messages[0] system
previous_response_id: "..."        → 拉取该 id 的历史 messages
tools: [{type, name, parameters}]  → 同(只是 function 包装)
include: ["reasoning.encrypted_..."] → 透传(chat 不支持时丢弃)
truncation: "auto"                → 不支持,直接传 max_output_tokens
reasoning: {effort, summary}      → 不支持,忽略
text: {format: {type: "json_schema", ...}} → response_format
```

**状态化 vs 无状态**:
- chat-completions 每次请求带完整 messages,无状态
- responses 是**有状态**的:服务端记 `response_id`,后续可以靠 `previous_response_id` 拉历史

SkillClaw 对此的处理是:**代理在内部把 responses 转成 chat 的 messages 列表**,把"状态化"特性"扁平化"为完整 messages。这牺牲了 responses 的"服务端记忆"能力(本来可以省 token),换来跟其他协议一致的处理路径。

### C. 反向转译(出协议)

`_assemble_streaming_chat_completion`(`api_server.py:714`)把 OpenAI chat 流式响应**重打包**成三种协议各自的 streaming shape:
- OpenAI: 原样
- Anthropic: 转 `message_start` / `content_block_start` / `content_block_delta` / `message_delta` / `message_stop` 事件
- Responses: 转 `response.created` / `response.output_item.added` / `response.content_part.added` / `response.output_text.delta` / `response.done` 事件

### D. 共享工具

`protocols/common.py`(46 字节)目前**几乎是空的**——只是预留位置。真正共享的工具(如 `_data_url_bytes`、`_image_dimensions_from_bytes`、`_image_token_estimate_*`)在 `api_server.py` 内。

## 常见误区

1. **"Anthropic body 真的转给 Anthropic 上游"** —— **通常不**。SkillClaw 的默认 `llm_api_base` 是 OpenAI 兼容 URL。Anthropic body 被转成 OpenAI body 之后,转给 OpenAI 兼容的上游。
2. **"Responses 协议走的是 OpenAI 上游"** —— 看 `llm_api_mode`(`config.py:90`)。`chat` 模式把 responses 拍平到 chat;`responses` 模式则保留原 body 直发。
3. **"SkillClaw 支持的所有 LLM 都自动支持所有三种协议"** —— 不。Agent 端用什么协议是 Agent 的事,SkillClaw 会在代理这一层"假装什么协议都懂",但最终发出去的是 OpenAI chat 格式。
4. **"`include` / `reasoning` / `truncation` 这些 Responses 高级字段被保留"** —— 不,转译时丢弃或简化(见上)。
5. **"Anthropic image / PDF 多模态"** —— 部分支持,见 `_image_token_estimate_*`(`api_server.py:1115-1240`)。PDF、audio 等暂未处理。
