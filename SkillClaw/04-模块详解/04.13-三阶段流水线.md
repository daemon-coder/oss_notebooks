# 04.13 三阶段流水线 `evolve_server/pipeline/`

> 5 个模块,实现 "session → skill" 的纯函数式步骤:**summarize → aggregate → evolve/create/merge**。可独立测试、可替换、可跳过。

## 设计动机

`pipeline/` 是 evolve server 的"业务核心"。它跟 `engines/` 的关系是:

- `engines/` 负责"何时跑、跑几次、跟谁通讯(HTTP / 共享存储)"
- `pipeline/` 负责"具体怎么把 session 变成 skill"

所以 `pipeline/` 的代码**应该是纯函数 + asyncio 协程**(无 HTTP、无文件 IO 副作用),便于单测。`engines/` 包一层 orchestration + 副作用。

## 核心概念

| 概念 | 定义 | 引用 |
|---|---|---|
| **`_summary`** | session 的 LLM 生成摘要:因果链、洞察(因果分析) | `summarizer.py` |
| **`_trajectory`** | session 的程序化生成摘要:完整 tool_call / result 步骤(无信息损失) | `summarizer.py:114` |
| **`_skills_referenced`** | session 引用过的 skill 名集合(从 `_summary` 解析出来) | `summarizer.py:_extract_session_metadata` |
| **`_avg_prm`** | session 内 turn 的 PRM 平均分 | `summarizer.py` |
| **`_has_tool_errors`** | session 是否发生过 tool 调用错误 | `summarizer.py` |
| `summarizer.py` | session → {`_summary`, `_trajectory`, `_skills_referenced`, ...} | 全文 |
| `aggregation.py` | 多个 session → 按 skill 分组(纯函数) | 全文 |
| `execution.py` | 现有 skill + sessions → (improve / create / merge / skip) 决策 | 全文 |
| `session_judge.py` | 给没有 benchmark 分的 session 打 overall_score(可选) | 全文 |
| `skill_verifier.py` | 候选 skill 写入前的二次验证(LLM 打 5 个分) | 全文 |
| `DecisionAction` | 4 个 action 常量: `improve_skill` / `optimize_description` / `create_skill` / `skip` | `core/constants.py` |
| `NO_SKILL_KEY` | aggregation 中"无 skill session"占位 key(`"__no_skill__"`) | `core/constants.py` |
| `_build_session_evidence` | 构造给 LLM 看的"evidence 字符串"(默认 `max_sessions=30`) | `execution.py:302` |
| `set_summarizer_debug_dir` | 摘要阶段 debug 落盘路径 | `summarizer.py:408` |
| `set_evolve_debug_dir` | 进化阶段 debug 落盘路径 | `execution.py:255` |

## 实现要点

### A. `summarizer.py` —— 程序化 + LLM 双轨

每个 session 生成两个东西:

#### `_trajectory`:程序化构造,无信息损失

```python
def build_session_trajectory(session) -> str:
    turns = session.get("turns", [])
    first_prompt = turns[0]["user_content"] if turns else ""
    
    if any(turn for turn in turns if turn.get("reasoning_content")):
        return _build_rollout_trajectory(turns, first_prompt)
    return _build_flat_trajectory(turns, first_prompt)
```

`_build_flat_trajectory`:

```
<USER_TASK>
[user] 写一个 K8s 客户端
</USER_TASK>

<STEP 1>
  [assistant] (text) 好的,我来...
    tool: read(args={"file": "k8s_api.md"})
      → ✓
  [user role=tool] "K8s API spec..." (truncated to 400 chars)
</STEP 1>

<STEP 2>
  [assistant] (text) 根据文档,我用 python kubernetes client
    tool: shell(args={"command": "pip install kubernetes"})
      → ✓ cmd=pip install kubernetes | Successfully installed
</STEP 2>
...
```

设计:**所有 tool_call 名字 + args(截断 400 字符)+ tool_result(截断 400 字符)+ tool_error(如果有)**。这种"程序化轨迹"比"让 LLM 总结"更可靠——所有原始信息都保留。

#### `_summary`:LLM 总结,提炼因果链

```python
async def summarize_sessions_parallel(llm, sessions):
    tasks = [summarize_session(llm, s) for s in sessions]
    return await asyncio.gather(*tasks)

async def summarize_session(llm, session):
    trajectory = build_session_trajectory(session)
    prompt = _build_summarizer_prompt(trajectory)    # 系统+用户
    summary = await llm.chat([system, user])
    session["_summary"] = summary
    session["_trajectory"] = trajectory
    # 提取元数据
    _extract_session_metadata(session, summary)
    return summary
```

`_extract_session_metadata` 解析 LLM 输出的 JSON,提取:
- `_skills_referenced` (set of skill names)
- `_avg_prm` (float)
- `_has_tool_errors` (bool)

#### `summarize_sessions_parallel` 的并发

每个 session 一次 LLM 调用,**全部并行**(`asyncio.gather`)。20 个 session 一次 run 触发 20 个并发 LLM 调用,可能撞 rate limit——`evolve_batch_size` 默认 20 是经验值。

### B. `aggregation.py` —— 简单分组,无 LLM

```python
def aggregate_sessions_by_skill(sessions):
    groups = defaultdict(list)
    for session in sessions:
        skills = session.get("_skills_referenced") or set()
        if not skills:
            groups[NO_SKILL_KEY].append(session)
        else:
            for skill_name in skills:
                groups[skill_name].append(session)
    return dict(groups)
```

**关键设计**:
- 一个 session **引用多个 skill** → 同时进多个组
- 一个 session **没引用任何 skill** → 进 `NO_SKILL_KEY` 组
- "无 skill session 占比高"通常意味着"用户没用 SkillClaw 注入 skill",这部分会触发 `create_skill` 决策

### C. `execution.py` —— LLM 决策核心

三个主要 LLM 调用:

1. `evolve_skill_from_sessions(llm, skill_name, existing_md, sessions)`:
   - 现有 skill + 多个 session → LLM 决策(4 个 action)
   - System prompt: `_EVOLVE_FROM_SESSIONS_SYSTEM`(200+ 行,**保守编辑**核心规则)

2. `create_skill_from_sessions(llm, sessions)`:
   - 多个无 skill session → LLM 决策(可能 0 个 / 1 个 / 多个新 skill)
   - System prompt: `_CREATE_FROM_SESSIONS_SYSTEM`

3. `execute_merge(llm, existing_skill, incoming_skill)`:
   - 现有 + 新版同名 skill → LLM 合并
   - System prompt: `_MERGE_SKILL_SYSTEM`

#### 决策枚举

```python
class DecisionAction:
    IMPROVE_SKILL = "improve_skill"             # 改 body
    OPTIMIZE_DESCRIPTION = "optimize_description" # 只改 description
    CREATE_SKILL = "create_skill"               # 创建新 skill
    SKIP = "skip"                                # 不动
```

`action == "create_skill"` 表示"当前 skill 主题不适合吸收,需要新 skill"——这是为了避免"主 skill 被膨胀成万能 skill"。

`set_evolve_debug_dir(path)` 把每次 LLM 调用的 system + user + raw 落到 `path/<timestamp>/`,便于排查。

### D. `session_judge.py` —— 当 session 没有 PRM 分时,LLM 兜底

```python
async def judge_session(llm, session):
    if _should_skip_judging(session):
        return session
    
    payload = _build_judge_payload(session)
    # 构造 system + user
    raw = await llm.chat([system, user])
    scores = _parse_scores(raw)   # 多个维度
    _apply_judge_scores(session, scores)

async def judge_sessions_parallel(llm, sessions):
    tasks = [judge_session(llm, s) for s in sessions]
    await asyncio.gather(*tasks)
```

`_should_skip_judging`:
- `use_session_judge=False` → 跳过
- 已有 benchmark overall_score → 跳过
- 已有 aggregate mean_score → 跳过
- 有 turn-level 旧分 → 跳过

`_build_judge_payload` 提取 session 的关键内容(任务、output 摘要、工具调用统计、错误模式),让 LLM 在多个维度上打分(任务完成度、效率、健壮性等)。

### E. `skill_verifier.py` —— 候选 skill 写入前验证

```python
async def verify_skill_candidate(llm, candidate_skill, sessions):
    """给候选 skill 5 个分:
    - grounded_in_evidence
    - preserves_existing_value
    - specificity_and_reusability
    - safe_to_publish
    - overall
    """
    evidence = _build_session_evidence(sessions)
    prompt = _build_verifier_prompt(candidate_skill, evidence)
    raw = await llm.chat([system, user])
    checks = _parse_checks(raw)
    score = _compute_score(raw_score, checks)
    
    if score is not None and score >= threshold:
        return {"enabled": True, "accepted": True, "score": score, "checks": checks, ...}
    return {"enabled": True, "accepted": False, "score": score, "checks": checks, ...}
```

**跟 PRM 区别**:PRM 打"用户回复对指令的质量";这里打"候选 skill 写得对不对、好不好、值不值得 publish"。

### F. `_build_session_evidence` —— 决定 LLM 看什么

这是 pipeline 中"信息压缩"的统一入口:

```python
def _build_session_evidence(sessions, max_sessions=30) -> str:
    """把多个 session 拼成 LLM prompt 里的 evidence 块。"""
    out = []
    for i, session in enumerate(sessions[:max_sessions]):
        out.append(f"\n## Session {i+1}")
        out.append(f"session_id: {session.get('session_id')}")
        out.append(f"summary: {session.get('_summary', '')[:1200]}")
        out.append(f"skills_referenced: {sorted(session.get('_skills_referenced', []))}")
        if session.get('_judge_scores'):
            out.append(f"judge_overall: {session['_judge_scores'].get('overall_score')}")
        if session.get('_avg_prm') is not None:
            out.append(f"avg_prm: {session['_avg_prm']}")
    return "\n".join(out)
```

**关键**:只取**摘要 + 关键元数据**,不传完整 tool_calls 原文(否则 prompt 过长)。需要细节时,LLM 看不到的"raw tool_calls"由 `_build_full_evidence`(可选用)单独提供。

## 常见误区

1. **"pipeline 是单步调用"** —— **不**,各模块独立,可以在 `engines/` 自由组合。比如只跑 summarize + judge 不跑 evolve。
2. **"LLM 决定一定被采纳"** —— 不。`_parse_evolve_result` 返回 None 时,evolve 会"静默 skip",不报错。
3. **"evidence 越多越好"** —— **不**。`_build_session_evidence` 默认 `max_sessions=30`,太多反而稀释 LLM 注意力。`max_sessions=30` 是经验值,基于**三重约束**的折中:(a) 单个 LLM call 的 context window 上限(把 ~30 个 session 的 `_summary` + 元数据塞进 prompt 不爆);(b) LLM 注意力衰减(超过 ~30 个证据块,LLM 倾向于只看头尾而忽略中间);(c) 单次 `run_once` 的总 token 成本(30 个 session × 摘要 ≈ 几百到几千 token 提示,在可接受范围)。生产环境如果发现某些 skill 长期 "证据不够"被 `skip`,可以上调 `max_sessions`(在 `pipeline/execution.py:302` 改 `max_sessions` 默认值,或在 `engines/workflow.py` 的 `_evolve_skill_group` 调用处显式传更大值)。
4. **"create_skill 出来就一定 new"** —— **不**。`_parse_create_result` 返回空 list 也合法,LLM 决定"不创建"是合理输出。
5. **"skill_verifier 跟 publish_mode=validated 是同一件事"** —— **不是**。skill_verifier 是**单次 LLM 自评**(可选,use_skill_verifier 控制);validated 是**多 client 端 replay 评估**(必须 >=1 client 同意才 publish)。两者可同时开。
6. **"judge_session 一定会调 LLM"** —— **不**。`_should_skip_judging` 在多个条件下 skip,见上 D 节。
7. **"`_EVOLVE_FROM_SESSIONS_SYSTEM` 里的"保守"是真有效"** —— **是的**,这是 SkillClaw 团队基于经验总结的"如何避免 LLM 把好 skill 改坏"的具体规则。详见 05.02 设计决策。
