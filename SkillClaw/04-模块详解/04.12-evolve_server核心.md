# 04.12 Evolve Server 核心 `evolve_server/core/`

> `core/` 是 evolve server 的"基础设施层"——配置、LLM 客户端、Skill ID 注册表、共享常量、纯函数工具。

## 设计动机

`evolve_server/engines/` 和 `pipeline/` 是业务逻辑,但都需要:

- 调 LLM(异步,OpenAI 兼容协议)
- 维护每个 skill 的稳定 ID + 版本号 + 内容 hash
- 解析 / 构造 SKILL.md
- 配置管理(支持 env / CLI / 复用 client config)

`core/` 集中这些,避免在 engines/pipeline 里重复实现。

## 实现要点


`__post_init__` 做归一化:
- `engine` 强制小写
- `publish_mode` 强制 ∈ {direct, validated},否则 → direct
- `nacos_publish_mode` 强制 ∈ {draft, review, direct},否则 → review
- `skill_reload_mode` 强制 ∈ {off, poll, callback},否则 → poll
- `validation_min_mean_score` 强制 ∈ [0, 1]
- `engine=agent` 时,如果没设 `llm_model`,默认 `gpt-5.4`

### B. 三个工厂路径

```
EvolveServerConfig()  ← 默认

```

`from_skillclaw_config` 关键:把 client 的 `sharing_*` 映射到 server 的 `storage_*`,把 `llm_api_key` / `prm_api_key` 兜底,处理 `sharing.skill_backend=nacos` 时 storage 不接管 skill 资产的情况。

设计:**输入/输出都是 string**,不暴露 token usage / streaming。这是给上游 pipeline 用的"高层 LLM 调用"。

`api_type`:
- `openai-completions` —— 走 OpenAI SDK async
- `anthropic-messages` —— 走 httpx 直发 /v1/messages(见 `engines/agent.py:_AnthropicMessagesLLMClient`)
- `openai-responses` / `google-generative-ai` / `ollama` —— 各种适配

`_normalize_temperature`:不同模型对 `temperature=0` 的支持不一致(Ollama 不接受 0,有的 OpenAI 兼容端点也不接受),所以归一化到 `max(0.01, requested)`。

#### temperature 策略

SkillClaw 内部**至少有三档不同的 temperature 取值**,分别服务 Replay 评估、Evolve 流水线、PRM judge 三个场景。看似"不统一",实则是各场景设计意图的显式编码。本节作为这三档的**集中索引**,各档的详细 rationale 仍在各自所在章节(04.10 / 04.09 / 04.12 本节 §C)。

| 取值 | 用途 | 章节定位 | 关键设计理由 |
|---|---|---|---|
| `0.1` | Replay 评估(`ValidationWorker._run_replay_branch`) | [04.10 §A. ValidationWorker 构造](./04.10-后台验证.md#a-validationworker-构造) | **稳定性优先**。Replay 用同一段历史 user instruction 替换 candidate skill 后再跑 LLM,核心目的是"candidate vs baseline PRM 分对比"——温度越低采样越稳定,两侧噪声越小,判分越公平 |
| `0.4`(默认) | Evolve 流水线通用 LLM 调用(`evolve_server/engines/*` + `pipeline/*`)+ AsyncLLMClient 默认参数 | 本节 §C(AsyncLLMClient `__init__`) | **平衡探索**。Evolve 要让 LLM 在"skill 文档怎么改"这种多解优化空间里探索足够多的可能性;太低会过早收敛到同一种优化路径,太高会脱离"该 skill 主题"。0.4 是"既能看到不同方向、又不至于完全跑题"的折中点 |
| `prm_temperature=0.6`(默认) | PRM judge 多次投票(默认 `prm_m=3`) | [04.09 PRMScorer 概念表](./04.09-prm评分.md#核心概念) | **投票分歧**。PRM 走 majority vote:同 prompt 跑 M 次,统计 ±1/0 的多数。温度需要"略高"才能让多次采样之间**有意愿地给不同分**——否则全票同分(尤其全 0),majority 退化成 single-shot,投票机制失效 |

**为什么不是 0**(完全确定性)或 1(最大探索):

- **`temperature=0`** —— 不同模型对 0 的支持不一致(Ollama / 部分 OpenAI 兼容端点直接拒绝);且即便支持也意味着"完全按概率最大的 token 走",长链路里一旦陷入局部最优就出不来。`_normalize_temperature(t)` 因此把 0 归一化成 `0.01` —— 这是一个"**近似确定性但不写死 0**"的工程妥协,见本节 §C 末尾。
- **`temperature=1`** —— 多样性过大,evolve 流水线会让 LLM 写出"对所有 skill 类型都适用"的空洞优化建议(对单个 skill 的针对性弱);PRM 投票也会变成"几乎随机",反而让 majority vote 失效。

**调参时的反作用**:

- 把 `0.1` 调高(Replay)→ candidate vs baseline 的 PRM 对比噪声变大,validation publish 门控容易抖。
- 把 `0.4` 调低(Evolve)→ evolve 流水线过早收敛到"一种优化路径",对 skill 集合的多样性提升变小。
- 把 `0.6` 调低(PRM)→ 多次投票全票同分,majority vote 退化成 single-shot,反馈信号变弱。

**交叉引用**:

- `0.1` 的内联 rationale(stability vs exploration 进一步展开)见 [04.10 §C. Replay 实现](./04.10-后台验证.md#c-replay-实现)。
- `prm_temperature=0.6` 的设计意图(投票为何需要略高温度)见 [04.09 PRM 评分](./04.09-prm评分.md)。
- `0.4` 是本节 AsyncLLMClient 的默认参数;`_normalize_temperature` 把 0 归一化为 `0.01` 的兼容性设计见本节 §C 末尾。

### D. SkillIDRegistry

```python
class SkillIDRegistry:
    def __init__(self):
        self._state: dict[str, dict] = {}    # name → {skill_id, version, content_sha, ...}

    def get_or_create(self, name) -> str:
        """Stable skill_id: 首次见返回新 sha256(name)[:12], 否则复用"""
        ...

    def record_update(self, name, content_sha, *, action, bundle_record=None) -> int:
        """记录一次更新,返回新版本号(v1, v2, ...)"""
        entry = self._state.setdefault(name, {...})
        entry["version"] += 1
        entry["content_sha"] = content_sha
        entry["last_action"] = action
        ...
        return entry["version"]

    def load_from_oss(self, bucket, prefix):
        """启动时从 OSS 拉回 state,保证跨进程版本号一致"""
        ...

    def snapshot(self) -> dict:
        return {name: dict(v) for name, v in self._state.items()}
```

设计要点:
- **stable skill_id** = sha256(name)[:12]—— 名字定了 ID 就定了,内容变 ID 不变
- **版本号单调递增** —— 每次 `_upload_skill` +1
- **持久化在 OSS** —— 跨进程重启,版本号不丢

### E. build_skill_md / parse_skill_content

```python
def build_skill_md(skill: dict) -> str:
    """dict → SKILL.md 字符串(YAML frontmatter + body)"""
    name = skill["name"]
    description = skill["description"]
    category = skill.get("category", "general")
    content = skill["content"]
    metadata = skill.get("metadata", {})
    extra = skill.get("_extra_frontmatter", {})
    
    parts = [f"---\nname: {name}\ndescription: {description}\ncategory: {category}"]
    if metadata:
        parts.append(f"metadata: {yaml.safe_dump(metadata, ...)}")
    if extra:
        parts.append(yaml.safe_dump(extra, ...))
    parts.append("---")
    parts.append("")
    parts.append(content)
    return "\n".join(parts)
```

`parse_skill_content` 反向操作,但**不完全是 build 的逆**——前者只解析 frontmatter,后者保留所有未识别字段。

## 常见误区

1. **"EvolveServerConfig 字段跟 SkillClawConfig 重复"** —— **有重叠**,但演化方向不同。Evolve 的字段更聚焦"如何跑一次 run_once",client 的字段聚焦"如何接 agent 请求"。`from_skillclaw_config` 做映射,见 5.2 的样例。
2. **"AsyncLLMClient 是 OpenAI SDK 的 wrapper"** —— 大部分情况是,但 `api_type=anthropic-messages` 时它**绕过** OpenAI SDK,直发 httpx。两者接口相同。
3. **"SkillIDRegistry 必须落 OSS"** —— **不一定**。可以纯内存,但**重启就丢**。`load_from_oss` 是给"跨进程稳定"用的,evolve server 重启 / 多实例时必用。
4. **"build_skill_md 出来的 SKILL.md 可以被本地 SkillManager 直接读"** —— **可以**,因为格式是 AgentSkills / OpenClaw 兼容。
5. **"constants.py 里的常量是 magic string 集合"** —— 是,但**比直接散落各处的字符串好维护**。
6. **"NO_SKILL_KEY 出现在 manifest 里"** —— **不会**,aggregation 内部用,不会写进 manifest。manifest 永远只列"实际 skill 名"。
