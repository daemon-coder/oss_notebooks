# 04.1 API 代理服务 `api_server.py`

> SkillClaw client 的入口。3438 行,所有 LLM 请求 / 响应的"必经之路"。

## 设计动机

`api_server.py` 同时承担 **4 个职责**:

1. **协议入口**:OpenAI `/v1/chat/completions`、OpenAI `/v1/responses`、Anthropic `/v1/messages` 三套协议。
2. **状态机**:在每个请求的生命周期里维护"session → turns 累积"的状态。
3. **后台任务**:session 录制、PRM 评分、shared skill 周期 pull、validation worker 调度。
4. **生命周期**:FastAPI `lifespan` 启停 + uvicorn 配置。

这 4 个职责**全部塞在一个文件**里,没有任何抽象层(没有 `class ProxyService`、没有依赖注入),只有顶层的 `SkillClawAPIServer` 一个大类和若干顶层 helper。

> 这种"集中式单体"是有意为之:它让一个新人能"通读 3000 行就懂整个代理",而不是在 12 个文件之间跳来跳去。

## 核心概念

| 概念 | 定义 | 关键行号 |
|---|---|---|
| `SkillClawAPIServer` | 顶层类,**单文件单类**架构,包揽协议入口 + session 状态机 + 后台任务 + 生命周期 4 个职责 | 类的位置约在 `api_server.py:1380` 附近 |

| `_user_turn_counts` | 内存 session → user_turn_num 计数(用于触发周期上传) | 类属性 |
| `_SESSION_IDLE_CLOSE_SECONDS` | session 空闲超时 180s | `:79` |
| `_SESSION_SWEEP_INTERVAL_SECONDS` | sweeper 间隔 15s | `:80` |
| `_SHUTDOWN_DRAIN_TIMEOUT_SECONDS` | 关闭时最多等 15s | `:81` |

### B. 内部"子服务器"模式

代码在内部用 `asyncio.create_task` 起了几个常驻协程:

| 任务 | 启动点 | 作用 |
|---|---|---|
| `_start_session_idle_sweeper` | `lifespan` 启动 | 每 15s 扫一次,把空闲超 180s 的 session 关闭 |
| `_start_skill_reload_polling` | `lifespan` 启动 | 每 N 秒调一次 `SkillManager.refresh_if_changed`,也按 `sharing_skill_reload_mode` 主动 `pull` |
| 后台 PRM 评分 | 在 `_post_request_hooks` 中 fire-and-forget | 调 LLM 评分当前 turn |
| 后台 session 上传 | 在 `_maybe_upload_session_snapshot` 中 | 每 N 个 user_turn 上传一次 |
| 后台 evolve trigger | 在 `_upload_session_snapshot_and_trigger` 中 | 上传后调 evolve server |
| 后台 validation worker | 单独线程/任务 | 见 04.10 |
| 后台 skill pull | `pull_skills` 周期任务 | 见 04.04 |

### C. 请求处理骨架(三协议共享)

```
async def _handle_chat_like(request_body, headers, protocol, stream):
    # 1. metadata 提取
    session_id = _resolve_session_id(headers, body, tui_fallback)
    session_done = _resolve_session_done(headers, body)
    turn_type = _resolve_turn_type(headers, body, default="main")
    
    # 2. 协议规范化(Anthropic → OpenAI body)
    if protocol == "anthropic_messages":
        request_body = _anthropic_to_openai_body(request_body)
        # 提取 image / tool calls 特定处理
        ...
    
    # 3. session 累积:把 prior_turns 拼到 messages 前面
    prior_turns = self._session_turns.get(session_id, [])
    request_body["messages"] = prior_turns + request_body["messages"]
    
    # 4. skill 注入(仅 main turn)
    if turn_type == "main" and self.config.use_skills:
        candidates = self.skill_manager.retrieve(
            _extract_last_user_instruction(request_body["messages"]),
            top_k=self.config.skill_top_k,
        )
        request_body["messages"] = _inject_skills(request_body["messages"], candidates)
        self.skill_manager.record_injection([s["name"] for s in candidates])
    
    # 5. 转发 upstream
    response = await upstream_chat(request_body, stream=stream)
    
    # 6. 后置钩子(异步)
    self._safe_create_task(self._post_request_hooks(
        session_id, turn_type, prior_turns, request_body, response, ...
    ))
    
    return response
```

### D. 工具调用规范化

Agent 在不同协议 / 不同模型下的 tool_call 形态差异巨大。`api_server.py` 在 200-560 行集中处理:

- **OpenAI 标准 tool_calls 字段** —— 原样转发。
- **Kimi `<|tool_call_begin|>` 文本标记** —— 正则提取,转 OpenAI 格式(`_KIMI_TOOL_CALL_RE`)。
- **Qwen `<tool_call>` 文本标记** —— 类似处理(`_QWEN_TOOL_CALL_RE`)。
- **Anthropic `tool_use` 块** —— `_anthropic_to_openai_body` 转译。
- **tool_call 名字飘移** —— `call_kimi_0` 这种 handle 不当 function name,`_normalize_tool_name` 修复。
- **思考标签** —— `<think>...</think>` 块剥掉,避免污染 main content(`_THINK_RE`)。

### E. Session 边界检测的三条路径

```
1. 显式:body.session_done=True 或 header X-Session-Done: true
   ↓
   _resolve_session_done() → True

2. 隐式:idle 超时
   ↓
   _start_session_idle_sweeper() 周期性扫:
   for session_id in self._session_turns:
       if (now - last_activity) > _SESSION_IDLE_CLOSE_SECONDS:
           close_session(session_id)

3. 隐式:TUI 模式(代理猜测)
   ↓
   _resolve_tui_session(): 无 session_id 时,基于 IP/port 推断
   (不推断 session_done;见 api_server.py:1604 注释)
```

### F. PRM 评分后置钩子

```
async def _post_request_hooks(self, session_id, turn_type, ...):
    # 1. 累积 turn 到内存
    turn = build_turn_record(...)
    self._session_turns[session_id].append(turn)
    
    # 2. 写 conversations.jsonl
    with open(self._record_file, "a") as f:
        f.write(json.dumps(turn, ensure_ascii=False) + "\n")
    
    # 3. 异步 PRM 评分
    if turn_type == "main" and _is_user_turn_boundary(turn_kind):
        self._safe_create_task(self._prm_score_turn(session_id, turn))
    
    # 4. session_done 处理
    if session_done:
        self._safe_create_task(self._finalize_session(session_id))
```

`_finalize_session` 会:
- 把这个 session 标记成"可上传"
- 如果 `sharing_session_upload_interval=0` 则 session 关闭时也立即上传
- 触发 `trigger_evolve`(如果配了)

### G. 启动 / 停止生命周期

```
# lifespan
async def lifespan(app):
    # 启动
    self._ready_event.set()
    self._start_session_idle_sweeper()
    self._start_skill_reload_polling()
    self._start_validation_worker()  # if validation.enabled
    
    yield
    
    # 关闭
    self._ready_event.clear()
    await self._shutdown_cleanup()
```

`_shutdown_cleanup` 会:
- 关闭所有 validation worker
- 把内存中的 session 全部 finalize
- 关闭 asyncio 任务
- 给 `_SHUTDOWN_DRAIN_TIMEOUT_SECONDS`(15s)超时

### H. 内部 IPC 端点

`POST /internal/reload-skills` 是给"evolve server 完成后"或"手动 `skill claw skills pull`"触发的:
- 检查 `authorization` header(如果 `proxy_api_key` 配置了)
- 调 `_pull_skills_from_cloud`
- 触发 `SkillManager.refresh_if_changed`

`evolve_server/engines/workflow.py:_notify_proxy_reload` 走的就是这个端点。

## 常见误区

1. **"打开 api_server.py 会看到清晰的 class"** —— **是**,但内部绝大多数方法是 `_private_method`,且 class 内部用了大量 `self.X` 直接访问内部状态。这是**单文件单类**架构,不是分层。
2. **"SkillClaw 启动后立刻生效"** —— 部分。`auto_pull_on_start=true` 才在启动时拉云端 skill;默认是 False,要等 `sharing_skill_reload_mode=poll` 的 polling 周期。
3. **"所有 turn 都会调 LLM"** —— **错**。Tool result 中转 turn、`turn_type=side` 的 turn、工具调用过程中的中间 turn,都不会被转发,只是被记录。
4. **"Streaming 和 non-streaming 走两套代码"** —— 是的,见 `_assemble_streaming_chat_completion`(`:714`)。但核心流程(skill 注入、session 累积)是两套都共享的。
5. **"proxy_api_key 是给 LLM 上游认证用的"** —— **错**。它是给 `/internal/reload-skills` 这种"内部端点"做 auth 的,跟 upstream LLM 的 API key(`llm_api_key` / `prm_api_key`)无关。
6. **"所有 /v1/messages 请求都走 Anthropic 上游"** —— 错。SkillClaw 内部把 Anthropic body 转成 OpenAI body,然后通过 `llm_api_base` 转发,通常是 OpenAI 兼容的 LLM。如果用户想走真正的 Anthropic 上游,需要在协议适配层做反向转译(`_anthropic_to_openai_body` 的逆操作,见 04.02)。
7. **"session 关闭 = 上传"** —— 见 03.02。
