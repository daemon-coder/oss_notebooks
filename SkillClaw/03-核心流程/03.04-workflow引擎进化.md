# 03.4 Workflow 引擎的 session → skill 进化

> Evolve Server 的默认引擎。`run_once()` 一次跑完所有步骤,可按 **3 阶段**(Summarize / Aggregate / Execute)或 **8 步**(Drain → Summarize → Judge → Aggregate → Per-group evolve → Conflict+merge → Validation publish → Persist)两种颗粒度理解。

## 设计动机

`evolve_server` 的核心命题:**一批真实会话(session)怎么凝练成一份可复用的 skill 文档?**

Skills 框架不能训练模型,但它可以把"经验"固化成"提示词级别的文档",让未来的 agent 直接读到。凝练过程需要:

1. **可审计** —— 每次输出都能在 debug dump 里看到,便于排查"为什么这次没产生 skill"。
2. **可降级** —— 任何一步 LLM 调用失败,不能阻塞整个 pipeline。
3. **幂等** —— 同样的 session 集合,两次跑应该产出相同或近似相同的 skill。
4. **保守** —— "不动" 是默认值,只在 evidence 强烈支持时才编辑。

Workflow 引擎通过"显式的 3 阶段流水线"满足这些:每阶段都是独立的 LLM 调用 + 独立 prompt,失败/异常都能定位到具体阶段。

## 核心概念

| 概念 | 定义 | 引用 |
|---|---|---|
| **Engine 类型** | `workflow` / `agent`,CLI 切换:`--engine workflow` | `evolve_server/__main__.py` |

## 实现流程(pseudo-code)

`run_once()`(`engines/workflow.py:894`)实现可以**用两个不同颗粒度**理解:

- **3 阶段**(高层抽象,从 LLM 调用形态看):
  1. **Summarize** —— 给每个 session 跑一次 LLM,提炼 `_summary` / `_trajectory` / `_skills_referenced`。
  2. **Aggregate** —— 程序化分组,无 LLM 调用。
  3. **Execute** —— 现有 skill 演进(`improve_skill` / `optimize_description` / `create_skill` / `skip`) + 冲突检测 + merge + 上传。
  - 可选辅助:`SessionJudge` 落在 Summarize 后、Execute 前;`SkillVerifier` 落在 Execute 内部。

- **8 步**(底层 pseudo-code,从代码结构看):Drain → Summarize → Judge → Aggregate → Per-group evolve → Conflict+merge → Validation publish → Persist。

下面按 8 步的顺序列 pseudo-code,关键步骤(2 摘要 / 4 聚合 / 5 演进)对应的 3 阶段会标在注释里。

```python
async def run_once(self):
    summary = empty_summary()
    
    # ──────── 步骤 1:Drain sessions(读共享存储里未处理的 session) ────────
    session_keys = list_session_keys(self._bucket, self._prefix)   # sessions/**/*.json
    for key in session_keys:
        session = read_json_object(self._bucket, key)
        if not session:
            continue
        if session["session_id"] in self._processed_log:   # _processed_log 是去重表
            continue                                       # 已处理过的 session 跳过(避免重复进化)
        sessions.append(session)
    
    if not sessions:
        return summary
    
    # ──────── 步骤 2:Summarize(LLM 摘要,3 阶段中的第 1 阶段) ────────
    # 每个 session 提炼出:
    #   _trajectory:  步进式 tool_call / result(程序化生成,无信息损失,直接保留原始 tool 调用)
    #   _summary:     LLM 生成的因果链分析、洞察
    #   _skills_referenced: 本 session 引用的 skill 名集合(从 _summary 解析出来)
    #   _avg_prm:     session 内 turn 的 PRM 平均分
    #   _has_tool_errors: 是否发生过 tool 调用错误
    await summarize_sessions_parallel(self._llm, sessions)   # 每个 session 一次 LLM 调用,asyncio.gather 并发
    
    # ──────── 步骤 3:Session judge(可选辅助) ────────
    # 给没有 benchmark 分的 session 打 overall_score(LLM judge)
    judge_summary = await self._run_session_judge(sessions)   # use_session_judge=False 时此步为 no-op
    
    # ──────── 步骤 4:Aggregate by skill(纯程序化分组,3 阶段中的第 2 阶段) ────────
    # 一个 session 引用 skill X → 进 X 的组
    # 引用 X + Y → 同时进 X 和 Y(同一 session 可进多组)
    # 没引用任何 → 进 NO_SKILL_KEY 组(占位 key,见 04.13 常量)
    groups = aggregate_sessions_by_skill(sessions)
    # groups = {
    #   "python-debug": [session_a, session_b],
    #   "k8s-deploy":   [session_c],
    #   NO_SKILL_KEY:   [session_d, session_e, ...],   # 准备触发 create_skill
    # }
    
    # ──────── 步骤 5:Per-group evolution(LLM 决策,3 阶段中的第 3 阶段) ────────
    skill_records = []
    
    # 5a. 现有 skill 的演进(improve_skill / optimize_description / skip)
    for skill_name, skill_sessions in groups.items():
        if skill_name == NO_SKILL_KEY:
            continue
        existing = self._fetch_skill(skill_name)         # 拉远端当前 SKILL.md 文本
        if existing:
            record = await self._evolve_skill_group(
                skill_name, existing, skill_sessions
            )
            skill_records.append(record)
    
    # 5b. 无 skill session → 尝试 create_skill(从 _CREATE_FROM_SESSIONS_SYSTEM prompt 决策)
    if NO_SKILL_KEY in groups:
        created = await self._handle_no_skill_sessions(groups[NO_SKILL_KEY])
        skill_records.extend(created)   # LLM 可能决定不创建,此时 created=[]
    
    # ──────── 步骤 6:Conflict detection + merge(同 skill 名合并) ────────
    for record in skill_records:
        await self._resolve_and_upload(record["skill"], record["action_type"])
        # 同名 skill 已存在 → 走 _MERGE_SKILL_SYSTEM prompt 合并
    
    # ──────── 步骤 7:Validation publish(仅在 publish_mode=validated 时跑) ────────
    # 把候选 skill 写为 validation/jobs/<job_id>.json,等 client 端 validation worker 接单
    if self.config.publish_mode == "validated":
        await self._finalize_validation_jobs()
    
    # ──────── 步骤 8:Persist processed log + history(去重 + 审计) ────────
    for session in sessions:
        self._processed_log.add(session["session_id"])   # 加去重表,下次同 session_id 跳过
    save_processed_log(self._processed_log, self.config.processed_log_path)
    save_history(skill_records, self.config.history_path)   # 审计日志,evolve_history.jsonl
    
    return summary
```

### 5a. 现有 skill 演进(核心 LLM 调用)

```
async def _evolve_skill_group(self, skill_name, existing_md, sessions):
    # 构造 evidence 字符串(把 sessions 拼成 LLM prompt 里的 evidence 块,默认 max_sessions=30)
    evidence = _build_session_evidence(sessions, max_sessions=30)
    
    # 调 LLM(详见 pipeline/execution.py:_EVOLVE_FROM_SESSIONS_SYSTEM——200+ 行 system prompt)
    prompt = _build_evolve_user_prompt(skill_name, existing_md, evidence)
    raw = await self._llm.chat([system, user], response_format={"type": "json_object"})
    
    # 解析(严格 JSON 校验,见 pipeline/execution.py:_parse_evolve_result)
    result = _parse_evolve_result(raw, skill_name)
    # result["action"] ∈ {"improve_skill", "optimize_description", "create_skill", "skip"}
    # result["skill"] = {...}  if action != "skip"
    # 解析失败返回 None → evolve 静默 skip,不报错
    
    return {
        "skill": result.get("skill") or {"name": skill_name, "content": existing_md},
        "action_type": result["action"],
        "rationale": result.get("rationale", ""),
    }
```

`_EVOLVE_FROM_SESSIONS_SYSTEM` 这个 system prompt 极其长且重要(200+ 行),核心策略是:

- **保守编辑**:`improve_skill` 时优先"小改",不要"重写"
- **保留 API 细节**:不要把 skill 里的"endpoint / port / payload format"删掉换成"读 utils.py"
- **不增加与失败无关的 best practice**
- **冲突时跳过比乱改好**

这是 SkillClaw 对"经验变成 skill"这件事的**核心世界观**,见 05 章的设计决策。

### 5b. 无 skill session 创建(从 _CREATE_FROM_SESSIONS_SYSTEM 决策)

```
async def _handle_no_skill_sessions(self, no_skill_sessions):
    # 把多个无 skill session 聚合成一个 LLM 调用,产出可能的新 skill
    # _CREATE_FROM_SESSIONS_SYSTEM 的 prompt 强调:
    #   - 必须与现有 skill 名字不同
    #   - 描述必须包含 "Use when" 和 "NOT for"
    #   - 内容要"压缩环境信息",不是泛泛 best practice
    
    raw = await self._llm.chat([system, user], response_format={"type": "json_object"})
    candidates = _parse_create_result(raw)   # 可能是空 list(LLM 决定不创建)
    
    return candidates   # 每个 candidate 是一个新 skill dict
```

### 5c. 冲突检测 + 合并(走 _MERGE_SKILL_SYSTEM prompt)

```
async def _resolve_and_upload(self, skill, action_type):
    name = skill["name"]
    
    # 1. 检冲突:远端是否已有同名 skill(同 tree_sha 视为相同,跳过;不同才视为冲突)
    if self._detect_conflict(name, skill):
        # 2. 拉远端已有版本
        existing_md = self._fetch_skill(name)
        existing_skill = parse_skill_content(name, existing_md)
        
        # 3. LLM 合并(走 _MERGE_SKILL_SYSTEM system prompt)
        merged = await execute_merge(self._llm, existing_skill, skill)
        # merged.name == name;merged.content = 合并后 body
        
        # 4. 上传合并版
        return self._upload_skill(merged, "merge")
    
    else:
        # 没冲突,直接上传
        return self._upload_skill(skill, action_type)
```

合并 system prompt `_MERGE_SKILL_SYSTEM` 在 `pipeline/execution.py:25`。

### 5d. 上传 + 版本化(写远端 + 更新 manifest)

```
def _upload_skill(self, skill, action):
    name = skill["name"]
    skill_id = self._id_registry.get_or_create(name)            # 稳定 skill_id = sha256(name)[:12]
    md_content = build_skill_md(skill)                          # dict → SKILL.md 字符串(frontmatter + body)
    content_sha = sha256(md_content)
    tree_sha = bundle_tree_sha256({"SKILL.md": md_content})     # bundle 整体 hash(用于增量同步)
    
    # 写两份:
    # 1) 最新版 skills/{name}/SKILL.md(给 client pull 拉)
    self._bucket.put_object(f"{prefix}skills/{name}/SKILL.md", md_content)
    
    # 2) 版本化 bundle: skill_versions/{name}/v<N>/record.json + SKILL.md(永久历史,client 默认不拉)
    version = self._id_registry.record_update(name, content_sha, action=action)   # version 单调 +1
    save_version_bundle(self._bucket, prefix, name, version, {"SKILL.md": md_content})
    
    # 3) 更新 manifest(所有 skill 的元数据清单)
    manifest = self._load_remote_manifest()
    manifest[name] = {
        "name": name, "skill_id": skill_id, "version": version,
        "sha256": content_sha, "tree_sha256": tree_sha,
        "format": "bundle_v1", "entrypoint": "SKILL.md",
        "files": [{"path": "SKILL.md", "sha256": content_sha, "size": len}],
        "uploaded_by": "evolve_server",
        "uploaded_at": "...",
        "description": skill["description"],
        "category": skill["category"],
    }
    save_manifest(self._bucket, prefix, manifest)   # 整 manifest 覆盖写(不是 append-only)
    
    return "uploaded"
```

`SkillIDRegistry.record_update` 是单调递增的版本号,每次上传 +1,从 registry 的 jsonl / OSS 状态里读出当前最大版本。

## 常见误区

1. **"session 跑完就会被消费"** —— 不一定。`_processed_log` 持久化(默认 `evolve_processed.json`),重启服务后不会重复处理同一个 session_id。`processed_log_path` 字段可改。
2. **"没引用 skill 的 session 一定会产生新 skill"** —— **不一定**。`_CREATE_FROM_SESSIONS_SYSTEM` 明确告诉 LLM:"如果 session 之间没有共同模式,产出空 list"。LLM 通常遵循。
3. **"create_skill 出来的 skill 名一定不会撞"** —— **不保证**。LLM 偶尔会"幻觉"出与现有 skill 同名的名字。`_resolve_and_upload` 会在上传前 `_detect_conflict`,撞了走 merge。但 merge 后名字相同的 LLM 决策应该已经规避,这是"双保险"。
4. **"evolve 出来就是终态"** —— 不。`SkillIDRegistry.record_update` 永远 +1,**所有历史版本都保留**在 `skill_versions/<name>/v<N>/`。`pull` 默认只拉 latest(但远端清单里能看到所有 version)。
5. **"session_judge 总是运行"** —— 否。`use_session_judge=False` 时跳过;另外已有 benchmark 分的 session 也会被 `_should_skip_judging` 跳过(`pipeline/session_judge.py:185`)。
6. **"publish_mode=validated 默认"** —— **不**。默认是 `direct`,即跑完就上云。`validated` 模式要把候选 skill 写到 `validation/jobs/<job_id>.json`,等 client 端 `validation_worker` 跑完 replay,达到阈值才 publish,见 [03.06](./03.06-后台验证.md)。
7. **"skill_verifier 是 PRM"** —— 错。`pipeline/skill_verifier.py` 是**对候选 skill 文档本身**打 5 个分(grounded_in_evidence / preserves_existing_value / specificity_and_reusability / safe_to_publish / overall),跟 `prm_scorer.py` 的 turn-level 评分不是一回事。
