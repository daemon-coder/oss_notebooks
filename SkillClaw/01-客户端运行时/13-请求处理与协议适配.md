# 13 · 请求处理与协议适配

## 这一章讲什么

这一章讲"一个请求进到 FastAPI 后到 FastAPI 返回前，每一步做了什么"——覆盖三个端点（OpenAI Chat / OpenAI Responses / Anthropic Messages）、system prompt 压缩、skill 注入、context 截断、LLM 转发、响应整形、record 写盘、PRM 触发。

## 它在整个系统的哪个位置

`SkillClawAPIServer` 的核心方法。`api_server.py` 的 ~1400 行大部分在这一章会展开。

> **几个本章要用到的术语速览**：
> - **`claw_type`**:本机跑的 CLI agent 类型,值见 [17 · 适配器矩阵](17-适配器矩阵.md)(本章用到的有 `openclaw` / `codex` / `nanoclaw` / `claude_code` / 通用 OpenAI 客户端等;1.1.d / 1.2.a 等多处按它分支)。
> - **`turn_type`**:见 1.1.b(`main` / `side`)。
> - **`raw_turn_kind`**:SkillClaw 内部对单条 turn 的分类标签,见 1.2.f。
> - **`_served_model`**:SkillClaw 对客户端**声明**的模型名(用于响应回填 `response.model`);与 `config.llm_model_id`(实际转发给上游的模型名)可不同。

## 设计目的

让 SkillClaw 在协议层对**任何 agent** 都透明——agent 用什么协议（OpenAI Chat / Responses / Anthropic）、上游 LLM 用什么协议（OpenAI / Anthropic / Bedrock / OpenRouter）、中间的所有翻译都在 `_handle_request` + `protocols/` 包里完成。

---

## 1. `/v1/chat/completions` 完整数据流

**场景**:一条 `/v1/chat/completions` 请求从 Hermes 进来——SkillClaw 拦截,做技能注入,转给上游 LLM,解析响应,记录会话,触发 PRM 评分。整条流水线是 SkillClawAPIServer 的核心。

**为什么需要拦截**:SkillClaw 的核心价值是"让 agent 知道有哪些 skill 可用 + 评分反馈"——这两个能力**必须**在 agent 调 LLM 时插入。`/v1/chat/completions` 是 OpenAI 标准端点,所有 agent 都调——拦截这一个端点就覆盖 12 种 CLI agent。

**整体流程图**:

```
HTTP POST /v1/chat/completions (来自 Hermes / Claude Code / Codex / OpenClaw)
  │
  ├─ 1. 入口: chat_completions(request, ...)
  │     ├─ _mark_request_activity()  # 触摸 session,触发 idle sweeper 重置
  │     ├─ _check_auth(authorization)  # Bearer token 校验
  │     └─ request.json()  # 解析 body
  │
  ├─ 2. session 解析: _resolve_turn_type + _resolve_session_id
  │     ├─ 拿 X-Session-Id header (TUI 客户端可能不发)
  │     ├─ _resolve_tui_session (TUI 模式自动分 session)
  │     └─ turn_type 判定: main / tool_result / thinking
  │
  ├─ 3. _handle_request(openai_body, session_id, turn_type, session_done)
  │     ├─ 协议标记 (走 anthropic_messages 路径)
  │     ├─ touch session (_session_last_active[sid] = now)
  │     ├─ system prompt 压缩 (OpenClaw 客户端)
  │     ├─ skill 注入 (main turn, 拼 <available_skills> 到 system 末尾)
  │     ├─ context 截断 (max_context_tokens 贪心丢老 message)
  │     ├─ 转发 LLM + 解析 tool_calls / read_skills / modified_skills
  │     ├─ 写 turn_record
  │     ├─ _maybe_finalize_ready_turns (上一轮 PRM 完的 finalize)
  │     └─ session_done? → _close_session
  │
  └─ 4. 返 response (JSONResponse 或 StreamingResponse)
```

详细 9 步见 [40 章 §2.2](../04-端到端/40-数据流总览.md)。本节讲 13 章特有的细节。

### 1.1 入口:`chat_completions(request, authorization, x_session_id, x_turn_type, x_session_done)`

```python
# 伪代码骨架(见 api_server.py:chat_completions):
async def chat_completions(request, ...):
    owner = request.app.state.owner
    owner._mark_request_activity()
    await owner._check_auth(authorization)
    body = await request.json()
    # ... session_id 解析、turn_type、_handle_request
    result = await owner._handle_request(openai_body, session_id, turn_type, session_done)
    return JSONResponse(content=result["response"])  # 或 StreamingResponse
```

#### 1.1.a `_rewrite_new_session_bootstrap_prompt`

OpenClaw 在开新 session 时会发一段以 `"A new chat session just started."` 开头的 user message；某些 provider(Azure)的 content filter 会对这种"开关 session"语义敏感,所以 SkillClaw **改写 user message 的 content 字段**——把 stock 文本替换为"**Greet the user briefly in 1-3 sentences and ask what they want to do.**"(去除触发字符串前缀,**避免与同前缀内容形成循环**;行为保持但措辞避开 content filter)。改写时 `rewritten += 1` 用于日志统计;**实际是修改**,不是只统计计数;每次请求**只改一次**——替换后的内容**不再以 trigger 开头**,下次请求按新形态再判定(不会无限循环)。

#### 1.1.b `_resolve_turn_type`

```python
_VALID_TURN_TYPES = {"main", "side"}
def _resolve_turn_type(header, body, *, default="main"):
    if default not in _VALID_TURN_TYPES: default = "main"
    candidate = header if header is not None else body
    raw = str(candidate or "").strip().lower()
    if not raw: return default
    if raw in _VALID_TURN_TYPES: return raw
    logger.warning("[SessionDetect] invalid turn_type=%r; fallback=%s", raw, default)
    return default
```

"客户端带了 `turn_type=bogus`" → 警告 + 走 main。绝不"无声"归零。

#### 1.1.c `_resolve_session_done`

把 `X-Session-Done` header 和 body 里的 `session_done` 合并成 bool（truthy / falsy）。**不**从"新 session bootstrap"启发式推断——必须显式。

#### 1.1.d `_resolve_tui_session`（关键）

详见 [14 · Session 与 Turn 簿记](14-Session与Turn簿记.md)。对 QwenPaw / IronClaw / 通用 OpenAI 客户端（不发 X-Session-Id 的）做"消息数下降 / 300s 不活动 → 视为新 session"启发式。

#### 1.2.a System prompt 压缩（仅 OpenClaw）

```python
if self._compress_system_prompt:        # 仅 claw_type == "openclaw"(自动判定,见章首术语速查)
```

`run_llm`（`utils.py`）按 `llm_provider` 选 OpenAI / Bedrock 客户端——所以**这次压缩调用**是 SkillClaw 内部唯一"主动"调 LLM 的地方（其它都是转发 agent 的请求）。

#### 1.2.c Context 截断


#### 1.2.d 转发 LLM(`_forward_to_llm`)

```python
async def _forward_to_llm(self, body):
    if self.config.llm_provider == "bedrock":
        return await self._forward_to_llm_bedrock(body)
    return await self._forward_to_llm_openai(body)
```

`_forward_to_llm_openai`(`api_server.py:2872+`)用 `httpx.AsyncClient`,POST 到 `{llm_api_base}/chat/completions`,带 `Authorization: Bearer {llm_api_key}`。**关键行为**:

- **超时**:`_llm_request_timeout_seconds()` 读 `SKILLCLAW_LLM_REQUEST_TIMEOUT_S` 环境变量(默认 120s),`httpx.AsyncClient(timeout=...)` 应用。
- **body 预处理**:移除 Tinker-specific 字段(`logprobs` / `top_logprobs` / `stream_options`);`body["model"]` 覆盖为 `self.config.llm_model_id`;`stream` 强制为 `False`(agent 的 stream 由 SkillClaw 在外层用 `StreamingResponse` 重新模拟)。
- **OpenRouter 扩展**:当 `llm_provider == "openrouter"` 时——
  - 注入 header `X-Title` = `openrouter.app_name`(如果有)、`HTTP-Referer` = `openrouter.app_url`(如果有)
  - `openrouter.route != "fallback"` 时,body 加 `provider: {sort: <route>}`(`price` / `throughput` / `latency` 三个值之一)
  - `openrouter.fallback_models` 解析为逗号分隔,body 加 `models: [<主model>] + <fallback list>`
  - `openrouter.data_policy == "deny"` 时,body `provider.data_collection = "deny"`
- **重试策略**:`max_retries = 6`。**特殊 400 兜底**(不算"重试 6 次",而是"识别 4 类错误后改 body 再试"):
  1. body 文本含 `"'temperature' is not supported"` → `pop("temperature")` 后 `continue`(同一 attempt 重试)
  2. body 文本含 `"Stream must be set to true"` → 改用 SSE stream(`stream=True`)+ `_collect_sse_chat_events` 拼装响应;stream 失败抛 HTTPException 502
  3. 其它可重试错误 → `wait = min(2**attempt + random.uniform(0, 1), 30)` 后 `continue`(指数 backoff + jitter,封顶 30s)
  4. 6 次后仍失败 → 抛 HTTPException(向上抛错给 FastAPI 层)

`_forward_to_llm_bedrock` 走 `BedrockChatClient` 的 Converse API(不走 OpenAI 协议)。

### 1.3 流式响应

`body.stream == true` 时，SkillClaw 走**先非流式转发、再 mock SSE** 的方案（`owner._stream_response`）：

```python
async def _stream_response(self, result):
    payload = result["response"]
    # chunk 1: delta = {role: assistant, content: ..., tool_calls: ...}
    yield f"data: {json.dumps(first, ensure_ascii=False)}\n\n"
    # chunk 2: delta = {} + finish_reason
    yield f"data: {json.dumps(final, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"
```

**这是兼容 OpenAI 客户端库的一种折衷**——agent 仍然按 SSE 协议读，只是 SkillClaw 把上游非流式响应"切"成两段发。**不**走"逐 token 流式"，因为 `_forward_to_llm` 用 `stream=False`。

## 2. `/v1/responses` 数据流

> Codex 客户端默认走这个端点。它有 `previous_response_id` 状态保留 / `tools: [{type: "custom"}]` / `store: true` 等 OpenAI Chat 没有的能力。

### 2.1 两种实现模式

```python
if owner._responses_native_enabled():   # llm_api_mode == "responses"
    # 原生模式：直接转发到上游 /v1/responses
    ...
else:
    # 翻译模式：body 转 OpenAI Chat → 转发 → 响应转回 Responses 格式
    openai_body = _responses_to_openai_body(body, owner._served_model)
    openai_body["_skillclaw_protocol"] = _PROTOCOL_RESPONSES_COMPAT
    ...
```

`_responses_native_enabled` 是 `config.llm_api_mode == "responses"`——codex 默认（`default_llm_api_mode_for_claw("codex") == "responses"`），其它 agent 默认 `"chat"`。

### 2.2 翻译模式

**场景**:Codex 默认走"翻译模式"——上游 LLM 是 OpenAI Chat 协议(`/v1/chat/completions`),但 Codex 发的是 Responses 协议(`/v1/responses`)。SkillClaw 需要在中间"翻译"——body 翻译 + 响应翻译。

**`responses_to_openai_body`(`protocols/openai_responses.py`)做的事**:

| 字段 | 翻译 |
|---|---|
| `body.input: [item]` | 转 `messages: [{role, content}]` |
| `body.tools: [{type: "function", ...}]` | **保留**(OpenAI Chat 也有 tools,字段名相同) |
| `body.previous_response_id` | **不转**——SkillClaw 自己的 `_responses_store[response_id]` 内存里查(避免暴露 OpenAI 状态机) |
| `body.instructions` | 合并到 `messages[0].content`(OpenAI Chat 用 system message) |

**`_merge_previous_response_messages`**:把"之前那一轮"的 messages merge 进当前 body——去重用 `_message_identity` 哈希(避免同一条 message 重复 send)。这是"多轮对话"的基础——Codex 用 `previous_response_id` 引用前一轮,SkillClaw 在 `_responses_store` 找到前一轮的完整 messages 后合并到当前 body。

**响应翻译**:`_openai_chat_to_responses_payload` 把 `choices[0].message` 翻回 Responses 格式——含 `output: [{type: "message", content: [...]}, {type: "function_call", ...}]`。`output` + `messages` 一起存到 `_responses_store[response_id]`,给下一轮 `previous_response_id` 引用。

**关键边界**:

- **`previous_response_id` 不在 `_responses_store`**:Codex 发了一个不认识的 id,SkillClaw 走"找不回前一轮" 分支(只发当前 body)
- **`tools` 里有 Responses-only 字段**(`type: "custom"` 等):原样发到 OpenAI Chat,OpenAI Chat 会忽略(不识别)
- **响应 `output` 包含 function_call**:SkillClaw 把它转成 OpenAI Chat `tool_calls` 形式,Codex 收到时还原

**为什么是 2 段翻译(请求 + 响应)**:

- 请求翻译:OpenAI Chat 协议不识别 `input` / `previous_response_id`,必须转成 `messages` 形式
- 响应翻译:Codex 不识别 OpenAI Chat 的 `choices[0].message.tool_calls`,必须转成 Responses 协议 `output: [{type: "function_call", ...}]`
- 中间走 OpenAI Chat 协议,两端是 Responses 协议

### 2.3 原生模式

`_prepare_responses_forward` 构造 `POST {llm_api_base}/responses`，body 原样转发（除了 `_NON_STANDARD_BODY_KEYS`），加 `Authorization: Bearer {llm_api_key}`。**不做任何翻译**——`tools: [{type: "custom", ...}]` 这种 Responses-only 字段原样过去。

`_forward_to_llm_responses` 走 `_prepare_responses_forward` 后用 `httpx.AsyncClient` 发请求。

`record_responses_turn` 拿 `record_body`（未翻译的原始 Responses body）+ `response_payload`（原始 Responses 响应）写 record。

### 2.4 `/v1/responses/{id}` 的 GET / DELETE

### 3.1 `_anthropic_to_openai_body`

**场景**:Claude Code / Anthropic SDK 客户端发的是 Anthropic Messages 协议(`/v1/messages`)。SkillClaw 在中间把 Anthropic 形态转成 OpenAI Chat 形态——这样**所有 LLM 客户端**都能用,不需要给每个 provider 写一套。

**Anthropic → OpenAI Chat 字段映射**(`protocols/anthropic_messages.py`):

| Anthropic 字段 | OpenAI Chat 字段 | 翻译说明 |
|---|---|---|
| `messages: [{role, content}]` | `messages: [{role, content}]` | **同结构,只改字段名细节** |
| `system: "..."` (顶层 string) | `messages[0].role="system", content="..."` | Anthropic 把 system 放顶层,OpenAI Chat 放 messages[0] |
| `content: [{type: "text"}, {type: "image"}]` | `content: [{type: "text"}, {type: "image_url"}]` | image 字段名 `image` → `image_url` |
| `tools: [{name, description, input_schema}]` | `tools: [{type: "function", function: {name, description, parameters}}]` | 工具定义字段嵌套一层 `function` |
| `max_tokens: N` (必填) | `max_tokens: N` | **Anthropic 必填**,OpenAI Chat 可选 |
| `stop_reason: "end_turn"` (响应) | `finish_reason: "stop"` | 响应字段名不同 |
| `usage: {input_tokens, output_tokens}` | `usage: {prompt_tokens, completion_tokens}` | 响应 usage 字段名不同 |
| `content[0].text` | `choices[0].message.content` | 响应内容字段名不同 |
| `tool_use: {id, name, input}` | `tool_calls: [{id, type, function: {name, arguments}}]` | 工具调用响应字段名不同 |
| `system: "..."` 或 `system: [{type: "text", text: "..."}]` | `messages: [{role: "system", content: "..."}]`（最前面插一条） |
| `messages: [{role: "user", content: "..."}]` | 同 |
| `messages: [{role: "assistant", content: [{type: "text", ...}, {type: "tool_use", id, name, input}]}]` | `messages: [{role: "assistant", content: "<text>", tool_calls: [{id, type: "function", function: {name, arguments: json.dumps(input)}}]}]` |
| `messages: [{role: "user", content: [{type: "tool_result", tool_use_id, content}]}]` | `messages: [{role: "tool", tool_call_id, content}]` |
| `tools: [{name, description, input_schema}]` | `tools: [{type: "function", function: {name, description, parameters: input_schema}}]` |
| `tool_choice: {type: "tool", name: "X"}` | `tool_choice: {type: "function", function: {name: "X"}}` |
| `max_tokens: N` | `max_tokens: N` |
| `temperature` / `top_p` / `stop_sequences` | 同（`stop_sequences` → `stop`） |

工具 name 用 `_CLAUDE_TOOL_NAME_ALIASES` 归一（小写、snake_case、kebab-case 各种形式 → 标准 PascalCase 名，例如 `read` / `read_file` / `file_read` → `Read`）。**这条规则只在 `x-claude-code-session-id` 存在时激活**（即 Claude Code 客户端路径）。

图片块（`type: "image"`）用 `_image_block_to_openai_part` 转成 OpenAI 的 `{"type": "image_url", "image_url": {"url": "data:..."}}`。

**反向归一（关键）**：OpenAI 风格 tool input 字段名在 Claude Code 收到响应后会被 `_sanitize_tool_use_input` 翻译回 Anthropic 期望的 schema——`Bash`: `cmd` → `command`；`Edit`/`Read`/`Write`/`MultiEdit`: `path`/`file` → `file_path`；`Glob`/`Grep`/`LS`: `file_path`/`file` → `path`；`NotebookEdit`/`NotebookRead`: 各种 path 变体 → `notebook_path`；`Edit`: `oldString`/`newString`/`replaceAll` → `old_string`/`new_string`/`replace_all`；`MultiEdit` 的 `edits[]` 子项也做同样归一；`Read`: `pages == ""` 会被 pop。**这是让 Claude Code 客户端收到响应后能正确处理 tool_use 的关键**。

**server tools 过滤**：Anthropic 的 `web_search*` / `server_tool_use` / `web_search_tool_result` 类工具在 chat 上游**被跳过不翻译**——chat 协议无法执行 server tools,只有 native Anthropic 路径才支持(注:本章范围内 `/v1/messages` 都走翻译路径,不存在 native 路径)。

### 3.2 `_openai_to_anthropic_response`

反向翻译：把 OpenAI Chat 响应（`{choices: [{message: {content, tool_calls}}]}`）转 Anthropic 形态：

```json
{
  "id": "msg_...",
  "type": "message",
  "role": "assistant",
  "model": "...",
  "content": [
    {"type": "text", "text": "..."},
    {"type": "tool_use", "id": "toolu_...", "name": "Read", "input": {...}}
  ],
  "stop_reason": "end_turn" | "max_tokens" | "tool_use" | "stop_sequence",
  "usage": {"input_tokens": N, "output_tokens": M}
}
```

`stop_reason` 映射：OpenAI `stop` → `end_turn`；`length` → `max_tokens`；`tool_calls` → `tool_use`；`content_filter` → `stop_sequence`。

`_anthropic_usage_from_openai_usage` 把 OpenAI 的 `prompt_tokens` / `completion_tokens` 转 Anthropic 的 `input_tokens` / `output_tokens`。

### 3.3 `stream_from_openai_result`

流式（`stream=True`）路径。SkillClaw 把非流式 OpenAI 响应按 Anthropic SSE 事件格式发出去（`message_start` / `content_block_start` / `content_block_delta` / `content_block_stop` / `message_delta` / `message_stop`）。

## 4. `/v1/messages/count_tokens`

```python
@app.post("/v1/messages/count_tokens")
async def anthropic_count_tokens(request, authorization=None, x_api_key=None):
    owner = request.app.state.owner
    owner._mark_request_activity()
    auth_header = authorization or (f"Bearer {x_api_key}" if x_api_key else None)
    await owner._check_auth(auth_header)
    raw_body = await request.json()
    openai_body = _anthropic_to_openai_body(raw_body)
    input_tokens = _estimate_openai_body_input_tokens(openai_body)
    return JSONResponse(content={"input_tokens": input_tokens})
```

**纯本地估算**——**不**调上游 LLM。

`_estimate_openai_body_input_tokens` 用字符级近似（`len(text) / 4` 或对图片的固定估算），不是真正的 token 化。NanoClaw / Claude Code 通常只在 UI 显示进度时调这个——精度不重要。

## 5. token 估算（`_estimate_openai_body_input_tokens`）

`api_server.py` 的 `1222-1310` 行实现了一个**无依赖的 token 估算器**（不调 tiktoken）：

| 内容类型 | 估算方式 |
|---|---|
| 文本字符串 | `(len(text) + 3) // 4`(向上取整的字符数/4,约 4 字符/token) |
| 文本列表(OpenAI-style) | 拼接 `text` 部分 |
| 工具定义(`tools` 数组) | name + description 字符估算 |
| 图像 | `_image_token_estimate_from_part`:**`max(1600, (width * height + 749) // 750)`**——下限 1600(`_IMAGE_TOKEN_ESTIMATE` 常量);按 (像素数 + 749) // 750 估算 |
| `content: "..."` string | `(len + 3) // 4` |

`_token_estimate_text(content)` 是核心 helper,对 string / list / dict 递归估算。

`_image_token_estimate_from_url(url)`(`api_server.py:1183+`)**实际公式与 fallback 顺序**:

1. `_data_url_bytes(url)` 尝试把 data URL 的 base64 部分解出来;
2. 解不出来 → 返回 `_IMAGE_TOKEN_ESTIMATE = 1600`(URL 是 HTTP URL 或非 base64,无法读宽高);
3. 解出来但 `_image_dimensions_from_bytes` 失败(不是 PNG / JPEG / **WEBP** / GIF 头或宽高 ≤ 0)→ 返回 1600;
4. 解出来且有宽高 → **`max(1600, (width * height + 749) // 750)`**。

> **不是 OpenAI 的"按 512×512 tile 算 85 token" 公式**。SkillClaw 用的是**线性近似** `(像素总数 + 749) // 750`,与 OpenAI 官方不一样——这是一个**有意的精度/速度权衡**;按 750 像素/token 算约等于 1 token = 28×28 patch,但**绝对值不要和 OpenAI 文档对照**。

**为什么不调 tiktoken**：SkillClaw 的 `dependencies` 里有 `tiktoken`（pyproject），但实际 token 估算用了"4 字符/token"近似 + 图片专用公式——**这是一个有意的精度/速度权衡**。`_truncate_messages` 是热路径（每个请求都跑），用 tiktoken 会拖慢 RTT。**[待实测]**这个近似在中文 / 多字节字符上是否够准（中文实际约 1.5 字符/token，估算偏高，可能导致 context 截断过于激进）。

## 6. tool_call 抽取（`_extract_tool_calls_from_text`）

一些上游（Kimi / Qwen 旧版）会**把 tool_call 写在文本里**而不是用结构化字段。SkillClaw 在文本里用正则抓：

```python
_KIMI_TOOL_CALL_RE = re.compile(

    r"<\|tool_call_argument_begin\|>\s*(\{.*?\})\s*"

)
_QWEN_TOOL_CALL_RE = re.compile(r"<\uff08tool_call\uff09>\s*(.*?)\s*</\uff08tool_call\uff09>", re.DOTALL)
_TOOL_HANDLE_RE = re.compile(r"^call_(?:kimi|xml)_\d+$")
```

`_TOOL_ARGS_MAX_CHARS = 4000`：单个 tool call 的 arguments 字符上限。`_TOOL_RESULT_CONTENT_MAX_CHARS = 4000`：tool result content 上限（用于 PRM / record）。

`_prepare_native_responses_body_inplace(body, turn_type=...)`(`api_server.py:2596+`)在 Responses body 里注入 `<available_skills>`。**注入位置**:`body["instructions"]` ——不是塞进第一条 `input` item 的 `content`,而是**追加到 `body["instructions"]`**(responses 协议的"系统提示"位置,等价于 Chat 的 system message):

- 若 `turn_type != "main"`(side turn)或 `skill_manager` 缺失 → 直接 return,不做注入

## 8. 待确认 / 已知限制

> 下面是边界未实测或设计取舍的事项,部署方按需决定是否验证 / 调整。

- **system prompt 压缩的 cache 路径**:`{record_dir}/system_prompt_cache_{claw_type}_{llm_provider}.json`——**进程重启会丢**(record_dir 在 `__init__` 重新清空时也会受影响,但 `os.makedirs` 不会清文件)。**待实测**这是有意的"重启重新压"还是疏忽。
- **`_truncate_messages` 的边界**:丢了老 message 后 `last_request` 重新计算 token,**保证** ≤ max_prompt 但**不保证** + system 的总和。**待实测**这条逻辑在极端 case(system 本身超长)下行为。
- **`/v1/responses` 翻译模式丢 `previous_response_id` 链**:`previous_response_id` 在原生模式直接转发 OK,但翻译模式会从 SkillClaw 内存 store 查;如果进程重启 store 没了,会 404。**待实测**这个 404 是否给了足够清楚的错误信息。
- **PRM 触发和 skill 注入在同 turn**:skill 在 main turn 注入 → 触发 PRM 时 evaluate 的 response_text 已经包含 `<available_skills>` 在 context 里——但 PRM 看的是 response + instruction(用户那条),**不**看 system。**待实测**这是否符合 PRM 的初衷(评估"回答有没有用"),还是"评估时应该看到完整 system"。
- **Anthropic 工具 name 归一的前提**:`_anthropic_to_openai_body` 不归一 tool name——归一发生在 `_anthropic_request_tool_names` 之后、传给 `_openai_to_anthropic_response` 之前。**待实测**这个流程是否在所有响应路径都覆盖(特别是 tool_call 列表里只有部分有 name 的情况)。
