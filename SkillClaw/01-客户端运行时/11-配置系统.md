# 11 · 配置系统与字段归一化

## 这一章讲什么

这一章回答"SkillClaw 的所有可配字段到底在哪儿、被谁写、被谁读、被谁归一到一个内部 dataclass"。读完之后你应该能在不查 README 的情况下，手写一个 `~/.skillclaw/config.yaml`。

## 它在整个系统的哪个位置

配置是**所有上层模块的底座**。`SkillClawLauncher` / `SkillClawAPIServer` / `SkillManager` / `PRMScorer` / `claw_adapter` / `SkillHub` / `ValidationWorker` / `DashboardService` 全部从 `ConfigStore.to_skillclaw_config()` 拿到同一个 `SkillClawConfig` dataclass 再做事。

## 设计目的

两件事：
1. **让用户只填他关心的字段**——YAML 里大量字段都有默认值，写一个最小配置文件就能跑。
2. **让代码只面对一个** `SkillClawConfig` **类型**——所有"如果用户没填就回退到 LLM 配置"这种归一化都集中在 `ConfigStore.to_skillclaw_config()` 一次性做完，运行时不重算。

## 3. `ConfigStore` 的工作模式

`ConfigStore` 持有路径 `self.config_file: Path`（默认 `~/.skillclaw/config.yaml`）。

| 方法 | 行为 |
|---|---|
| `exists() -> bool` | 路径是否在 |
| `load() -> dict` | 读 YAML。**任何**异常（YAML 解析失败、OSError）都返回**纯默认** dict。返回的 dict 经过 `_deep_merge(_DEFAULTS, data)`，所以**用户没写的字段**也会带默认值。 |
| `save(data: dict)` | 写 YAML，`allow_unicode=True`（中文 key 不被转义） |
| `get(dotpath) -> Any` | 按 `"a.b.c"` 切路径读值 |
| `set(dotpath, value) -> None` | 按 dotpath 写值。`value` 走 `_coerce`：字符串 `true`/`false` → bool；纯数字 → int / float；其它原样 |
| `to_skillclaw_config() -> SkillClawConfig` | 读 + 归一化，构造 `SkillClawConfig` |
| `describe() -> str` | 给人看的多行字符串，含 claw_type / llm / proxy / skills / prm / sharing / evolve / validation / dashboard 全部段 |

### 3.1 `_coerce` 自动类型推断

```python
def _coerce(value):
    if not isinstance(value, str): return value
    if value.lower() == "true":  return True
    if value.lower() == "false": return False
    try:  return int(value)
    except ValueError: pass
    try:  return float(value)
    except ValueError: pass
    return value
```

意味着 `skillclaw config sharing.enabled true`（CLI 传字符串）会被存成 bool，`skillclaw config proxy.port 30001` 会被存成 int。`skillclaw config sharing.auto_pull_on_start True` 同样正确。

### 3.2 `_deep_merge`

```python
def _deep_merge(base, override):
    result = dict(base)
    for k, v in override.items():
        if k in result and isinstance(result[k], dict) and isinstance(v, dict):
            result[k] = _deep_merge(result[k], v)
        else:
            result[k] = v
    return result
```

这是一个**保留默认值的浅覆盖**：用户给 `sharing: {enabled: true}`，最终 dict 会带 `sharing: {enabled: true, backend: "", endpoint: "", ...}`。这对"老用户加新字段不破配置"很重要。

### 3.3 几个特殊归一化函数

- **`_infer_sharing_backend(sharing)`**:
  ```
  1. sharing.backend 显式设了 → 用它
  2. sharing.local_root 显式设了 → "local"
  3. sharing.endpoint / bucket / access_key_id / secret_access_key / region / session_token 任一非空 → "s3"
  4. 其它 → ""
  ```
  这套规则是**兼容老配置**——老 SkillClaw 版本没设 `backend` 字段时，**只要有 bucket / endpoint / key 就默认当 S3 用**。
  > **⚠ Nacos 用户的 footgun**:Nacos 后端的配置**不**在规则 3 的判定项里(`nacos_server` / `nacos_namespace_id` / `nacos_label` 等是 Nacos 专用字段)。如果只填 `sharing.nacos_server: xxxx` 而**忘了显式填 `sharing.backend: nacos`**,系统会被规则 3 误判为 s3,后面去连一个不存在的 S3 endpoint 直接报错。**结论:Nacos 用户必须显式写 `backend: nacos`**。

- **`resolve_skills_dir(skills_dir, claw_type=...)`**：
  - 如果用户没填 `skills.dir` → 按 `claw_type` 选默认目录（hermes → `~/.hermes/skills`，codex → `~/.codex/skills`，claude → `~/.claude/skills`，opencode → `~/.config/opencode/skills`，其它 → `~/.skillclaw/skills`）
  - 如果用户填了 `skills.dir = ~/.skillclaw/skills`（**且 claw_type 是 hermes/codex/claude/opencode**），会被**自动改写**为该 claw 的 native 目录——这是为了让"在 Hermes 下跑 SkillClaw 时不要污染 `~/.skillclaw/skills`"
  - 其它情况保持用户填的值

- **`default_llm_api_mode_for_claw(claw_type)`**：`codex` → `"responses"`，其它 → `"chat"`。`codex` 默认走 Responses API 是因为 Codex 的客户端已经按 Responses 协议工作。

- **`_default_served_model_name(llm_model_id)`**：
  - 留空 → `"skillclaw-model"`
  - GPT-5 系（`gpt-5...`）→ 也回退到 `"skillclaw-model"`（避免触发 Hermes 内部对 gpt-5 的 Responses 模式适配）
  - 其它 → 用 `llm_model_id` 本身

  **这是一段很容易被忽略的细节**——它解释了"为什么我配了 `model_id: gpt-5.2` 但代理报出来的却是 `skillclaw-model`"。

- **`_normalize_validation_mode(value)`**：**强制写回 `"replay"`**，忽略传入值。当前 SkillClaw 不支持其它 validation 模式。

- **`_normalize_choice(value, allowed, default)`**：把字符串归到 `allowed` 集合里，否则用 `default`。被 nacos_publish_mode / skill_reload_mode 用。

- **`_normalize_non_negative_int(value, default)`**：`max(0, int(value or 0))`。`session_upload_interval` 配 -5 会被归一为 0（关闭）。

- **`_normalize_reload_interval(value)`**：最低 5s。配 0 会被改成 5；配 1000 保持 1000。

## 4. ConfigStore 的写入路径

`ConfigStore` 的写入只有两个真实来源：
- `setup`（`SetupWizard.run`）——构造完整 dict 后 `cs.save(data)`
- `config KEY VALUE`（`ConfigStore.set`）——单字段 dotpath 写

被 `set` 改的字段再 `load()` 时会**经过 `_deep_merge(_DEFAULTS, data)`**——所以老字段不会丢。

`ConfigStore.set` 的实现有个**细节**：用 `data.setdefault(k, {})` 一路创建嵌套 dict 容器，**覆盖**叶子值。这意味着 `config proxy.port 30001` 不会清掉 `proxy.host` 或 `proxy.api_key`。

## 5. `SkillClawConfig` 的内部一致性

`SkillClawConfig` 是 `@dataclass`，**没有 `__post_init__` 校验**。所有校验在 `to_skillclaw_config` 完成。这意味着：
- 直接 `SkillClawConfig(llm_api_mode="bogus")` 是合法的——但 api_server 用 `getattr` 加 `or` 兜底
- `_normalize_*` 只在归一化路径触发
- `nacos_publish_mode` / `skill_reload_mode` 这种"枚举"字段没在 `SkillClawConfig` 自身做校验——它们被 NacosSkillHub / api_server 显式归一

## 6. evolve_server 共享的字段

`evolve_server/core/config.py` 的 `EvolveServerConfig` 是**独立**的 dataclass，但通过 `EvolveServerConfig.from_skillclaw_config(skillclaw_config)` 把 `SkillClawConfig` 的相关字段映射过来。

映射时一个**关键差异**：`nacos` 后端的 `storage_endpoint` 会被**清空**——因为 skill 资产走 Nacos，session 不能也走 Nacos。`from_skillclaw_config` 会在 `sharing.backend == "nacos" && not sharing_session_backend` 时把 `storage_endpoint = ""` 强制归零。

详见 [30 · Evolve 服务端与引擎选择](03-Evolve服务/30-Evolve服务端与引擎选择.md)。

## 7. 配置文件如何与"环境变量"共存

`evolve_server/.env`（用 `python-dotenv` 自动加载）和 shell 环境变量是**给服务端**的——`os.environ.get(...)` 在 `EvolveServerConfig.from_env()` 里读。客户端这边**不**读 `.env`——只读 `~/.skillclaw/config.yaml`。

唯一一个客户端读的环境变量是：
- `SKILLCLAW_DAEMON_READY_TIMEOUT_S`（CLI 启动 daemon 时等 `/healthz` 的超时，默认 15s）
- `SKILLCLAW_LLM_REQUEST_TIMEOUT_S`（api_server 的 LLM 请求超时，默认 120s）
- `USER`（fallback `sharing.user_alias`）
- `SKILLCLAW_RUNTIME_KIND` / `SKILLCLAW_RUNTIME_LOG_PATH`（daemon 内部用，告诉子进程"你是 daemon 模式"+"日志写这里"）

## 8. 待确认 / 已知限制

- **YAML 写入的中文 / Unicode**：`yaml.dump(allow_unicode=True, default_flow_style=False)` 不会转义中文。但如果 `setup` 输出了某些特殊字符（如冒号在 description 里），`parse_skill_md` 那一层会再次校验——配置层**不**做内容校验。
- **数值边界没在 `SkillClawConfig.__init__` 校验**：`proxy_port=999999` 是合法的，但 uvicorn 会拒绝。SkillClaw 把这类边界检查让给了底层组件。
- **`config show` 打印顺序**：`describe()` 按固定顺序打（claw → llm → proxy → skills → prm → sharing → evolve → validation → dashboard），但 Nacos 段会**插队**在 sharing 段里——这让"看 Nacos 配置"更直观，也让自动化解析变难。**待确认**未来要不要把 Nacos 拆成独立段。
- **配置版本迁移**：当前 `ConfigStore.load()` 用 `_deep_merge` 兼容老字段，但**没有"配置 schema 版本号"**。如果某天字段语义变化（比如 `prm.m` → `prm.prm_m`），用户的老配置会被默默忽略——**待确认**是否需要 `skillclaw config migrate` 子命令。
