# 40 · 数据流总览

## 这一章讲什么

这一章把前 9 章的所有细节**串成 1 条线**——一个 session 从 Hermes 进来、到 evolve server 把它炼成 skill、再被下次同步拉回本地、最终被下一个 user 看到。这条线让你能"从头到尾看一次 SkillClaw"。

## 它在整个系统的哪个位置

细节层（整本书到这一章收尾，只有 40 和 41 两章；上面是模块层 15 章 10–32，再上面是总览层 3 章 00–02）。

## 1. 时间线总览

**图例**：`→` 同子系统内步骤 / `⮕` 写入共享存储 / `↓` 跨子系统边界

```
[用户] ─► [agent] ─► [SkillClawAPIServer] ─► [upstream LLM]
                   │                         │
                   │ 1. POST /v1/chat/completions (X-Session-Id, X-Turn-Type)   [client]
                   │ 2. 注入 skills (XML)                                       [client]
                   │ 3. 转发 LLM ───────────────────────────────────────────►
                   │ 4. ◄── response + tool_calls                              [client]
                   │ 5. 提取 read/modified skills                              [client]
                   │ 6. 写 conversations.jsonl                                 [client]
                   │ 7. 触发 PRM task (async)                                  [client]
                   │
                   │ (turn 2 进来)
                   │ 8. fire 之前 turn 的 PRM 完成                             [client]
                   │ 9. close_session() → upload session.json                  [client]
                   │ 10. pull skills (skip modified)                           [client]
                   ↓
            [shared storage: {group_id}/]
                   │ pull_skills() 定时 reload (默认 30s,可在 `sharing.skill_reload_interval_seconds` 改,下限 5s)
                   ↓
              [evolve_server] (每 `evolve_interval` 秒,默认 600s,env `EVOLVE_INTERVAL`)
                  ──── client/server 边界 ────
                  [ES] 1. Drain sessions/
                  [ES] 2. Summarize (LLM #1: 每个 session)
                  [ES] 3. Judge (LLM #2: 每个 session, optional)
                  [ES] 4. Aggregate (按 _skills_referenced)
                  [ES] 5. Evolve (LLM #3: improve/create/skip, 每个 group)
                  [ES] 6. Verifier (LLM #4: optional, 默认关)
                  [ES] 7. Conflict check (sha256) → if conflict: Merge (LLM #5)
                  [ES] 8. Upload SKILL.md + version bundle + manifest
                  [ES] 9. Delete processed sessions
                  [ES] 10. Notify proxy reload (callback 模式)

> **注意**:客户端 10 步 (client 侧,标 1–10) 和 evolve_server 10 步 (server 侧,标 `[ES] 1–10`) **不一一对位**——字符集物理上已经分开（阿拉伯数字 vs 字母前缀），但即便如此，**逻辑上仍不要按编号对位理解**：客户端先 close_session 写入 `sessions/`,evolve server 之后下一次 cycle 才 drain 读取。同一份"step 5"在不同子系统里走的是不同事件。读时序时请按"客户端先 → server 后"的串行顺序理解,不要按编号对位。
```

## 2. 第一段：客户端代理（详见 12-14 章）

### 2.1 入口

```
[Hermes / OpenClaw / Claude Code / Codex / QwenPaw / ...]
  ↓ 改 base_url 到 http://127.0.0.1:30000/v1（17 章 claw_adapter 做的）
POST http://127.0.0.1:30000/v1/chat/completions
  Headers:
    X-Session-Id: <session_id>
    X-Turn-Type: main
    Authorization: Bearer <config.proxy_api_key>   # 若 config.proxy_api_key 非空则要求,空则不校验
  Body: {messages: [...], model: "skillclaw-model", tools: [...], ...}
```

> `X-Session-Id` 中时间戳的 `:` 换成 `-`（如 `hermes-2026-07-22T10-30-15`）是 Hermes 命名约定——避免 header value 解析问题;其他客户端可不遵循此格式,daemon 当不透明字符串。

`SkillClawAPIServer.chat_completions`：
1. `_mark_request_activity`（idle 探测器用）
2. `_check_auth`（`/internal/reload-skills` 强制 / chat-completions 不强制）
3. 读 body JSON
4. `_rewrite_new_session_bootstrap_prompt`（处理 OpenClaw 的 "A new chat session just started" 提示）
5. 解析 `session_id` / `turn_type` / `session_done`（header 优先 / body 兜底）
6. 调 `_handle_request(body, session_id, turn_type, session_done)`（详见 13 章）

### 2.2 `_handle_request` 内部

**场景**:SkillClawAPIServer 拿到一条 HTTP 请求(`/v1/chat/completions` / `/v1/responses` / `/v1/messages`)——这是 SkillClaw 拦截 agent 调 LLM 的"主入口"。每个 turn 进来都走这条 9 步流水线。

**为什么是 9 步而不是 1-2 步**:SkillClaw 的核心职责都在这 9 步里——

- 协议互转(让 12 种 agent 都能用)
- Session 簿记(把 stateless HTTP 串成 session)
- Skill 注入(让模型知道有哪些 skill 可用)
- Context 截断(防止超出上游 LLM 的 context window)
- Turn 记录(为 PRM / evolve 提供完整证据)

这 9 步**是必须串行**的——下一步依赖上一步的输出。

**整体流程图**:

```
_handle_request(request)
  │
  ├─ 1. 协议标记 (走 anthropic_messages 路径时设 _PROTOCOL_ANTHROPIC_MESSAGES)
  │
  ├─ 2. Touch session (更新 _session_last_active[session_id] = now)
  │      # 给 idle sweeper 判断:距上次活动 ≥ 180s → close
  │
  ├─ 3. System prompt 压缩 (对 OpenClaw 客户端, 因为它 prompt 模板大)
  │
  ├─ 4. Skill 注入 (对 main turn, 调 _inject_skills 拼 <available_skills> 到 system 末尾)
  │
  ├─ 5. Context 截断 (按 max_context_tokens 贪心丢老 message)
  │
  ├─ 6. 转发上游 LLM (POST 给 cfg.upstream_url, 解析 tool_calls / read_skills / modified_skills)
  │
  ├─ 7. 写 turn_record (append 到 _session_turns[session_id] + _pending_records)
  │
  ├─ 8. Finalize ready turns (调 _maybe_finalize_ready_turns)
  │      # 上一轮 PRM task 已 done 的 turn 走 finalize
  │
  └─ 9. Session done? (是) → _close_session(session_id)

return response
```

**9 步的"为什么这么排"**:

| # | 步 | 依赖上一步什么 | 这一步产生什么 | 为什么在这 |
|---|---|---|---|---|
| 1 | 协议标记 | request.headers (X-Protocol) | `self._protocol` 标志 | 影响第 6 步的请求构造 |
| 2 | Touch session | X-Session-Id header | `_session_last_active[sid] = now` | 第 8 步 finalize 可能触发 close |
| 3 | System prompt 压缩 | 上游 LLM context 限制 | 压缩后的 system prompt | OpenClaw prompt 模板默认很大 |
| 4 | Skill 注入 | SkillManager 加载的 skill 集 | system prompt 末尾加 `<available_skills>` | 模型需要知道有哪些 skill 可用 |
| 5 | Context 截断 | max_context_tokens 配置 | 截断后的 messages list | 防止超出 LLM context window |
| 6 | 转发 LLM | 截断后的 messages | 完整 LLM response + 解析出的 tool_calls | SkillClaw 的核心转发 |
| 7 | 写 turn_record | LLM response + injected + read skills | turn_record: dict(给 PRM / evolve 用) | 这一 turn 的完整证据 |
| 8 | Finalize ready turns | `_prm_tasks` 中已 done 的 task | 调 `_finalize_turn_feedback` 写 prm_scores.jsonl | 让异步 PRM 结果尽快落盘 |
| 9 | Session done? | X-Session-Done header 或 _pending_records 空 | `_close_session(sid)` | session 生命周期收尾 |

**为什么第 3 步只对 OpenClaw 客户端**:`_PROTOCOL_ANTHROPIC_MESSAGES` 是 OpenClaw 协议特有的——其它 agent (Hermes / Claude Code / Codex) 不需要压缩。这是 SkillClaw 对 OpenClaw 的"特殊照顾"。

**为什么第 4 步只对 main turn**:`raw_turn_kind` 有 `main` / `tool_result` / `thinking` 等——只有 `main` (用户可见的 turn) 才需要注入 skills。`tool_result` 是给 LLM 喂 tool 调用的返回,不需要再注入。

**为什么第 5 步在第 4 步之后**:Skill 注入会**增加** system prompt 长度(每个 skill 描述 ~200 tokens,几十个 skill 就是几 K tokens)——必须先注入,再截断,不能反过来。

**为什么第 8 步在第 7 步之后**:第 7 步写 turn_record 是"准备数据",第 8 步是"finalize 上一轮"——这两步是不同 turn 的 finalize 时机错开:

- Turn N 进来时,`turn_type=main, turn_num=N` —— **上一轮** turn N-1 的 PRM 还在异步跑(还没 done)
- 第 7 步写本轮 turn_record,但 `_maybe_finalize_ready_turns` 会去查 turn N-1 的 PRM task
- 如果 turn N-1 的 PRM 已 done → finalize 它;否则跳过

这就是为什么 PRM 是**异步的**——每个 turn 进来都触发上一轮 PRM,本轮不等 PRM 完。

**为什么第 9 步可能不触发**:只有 `X-Session-Done: true` header 显式触发,或者 idle sweeper 后台检测到 180s 无活动时调 `_close_session`。正常每个 turn 进来都走 1-8 步,不进第 9 步。

**关键边界**:

- **OpenClaw 客户端** (`X-Client: OpenClaw`):第 3 步做 prompt 压缩,其它 agent 跳过
- **Anthropic Messages 协议** (`X-Protocol: anthropic-messages`):第 1 步设标志,第 6 步走 Anthropic 格式,response 也按 Anthropic 格式返
- **Max context 超限**:第 5 步贪心丢老 message(从最早 user message 开始丢,保留 system + 最近 2-3 轮对话)
- **LLM 调用失败**:第 6 步抛错,响应返 502 给 agent——但已写进 `_pending_records` 的 turn(如果有)会被下次 sweep 清理
- **Session 不存在** (`X-Session-Id` 是新的):第 2 步创建新 entry,后续步骤按新 session 处理
- **Session 正在 close** (`session_id in _closing_sessions`):第 8 步 `_maybe_finalize_ready_turns` 会跳过(避免在关闭过程中再触发新 task)

**走完之后**:

- 内存里多了一条 turn_record(等 PRM 异步评完 finalize)
- `conversations.jsonl` 本地累加一行(session 关闭时整段上传)
- 如果是 session 末尾:session 关闭,上传 `sessions/<sid>.json` 到共享存储
- Agent 收到 LLM response(包含 tool_calls / read_skills),继续它的循环
- SkillClawAPIServer 准备好接下一条请求

### 2.3 Turn 2 进来时:PRM 触发

**场景**:Alice 发出第 2 条 user message——SkillClaw 需要**评估上一轮**(turn 1) 的回答对 turn 2 有没有用。这就是 PRM 的"延后一格"语义:**评上一个回答对下一个问题的价值**。

**完整流程链**:

```
1. POST /v1/chat/completions
   X-Session-Id: abc
   body.messages = [user1, assistant1, user2, ...]
   │
2. → _handle_request(turn_type=main, turn_num=2)
   │
3. → 注入 skills(2nd turn,SkillManager 拉一次新 manifest)
   │
4. → 转发 LLM 拿 response2
   │
5. → _buffer_record 触发 _fire_prm_scoring
   # 触发条件:next_state=turn2 的 user message 存在
   │
6. → 创建 PRM task(prm_m=3 票多数票)
   task.add_done_callback(_on_prm_done)
   │
7. → 写 turn_record = {
       turn_num: 2,
       prm_score: None,  # 初始为 None,PRM 完才写
       injected_skills: [...],
       read_skills: [...],
       response_text: response2,
   }
   │
8. → _maybe_finalize_ready_turns(session_id)
   # 看到 turn 1 的 PRM 还在跑(down callback 未触发)
   # 跳过本轮 finalize → return
```

**为什么是"延后一格"**:

PRM 的语义是"评**上一个回答对下一个问题有没有用**"——turn N 还没进来时评 turn N-1 没意义(没"下一个问题")。`next_state=turn2` 的存在意味着"还有下一条 user message",所以**为 turn 1 触发 PRM 合法**。

**PRM 任务的关键参数**:

| 参数 | 值 | 含义 |
|---|---|---|
| `prm_m` | 3(默认) | 多数票数——3 票中多数决 |
| 聚合方式 | `_majority_vote` | **不**是中位/均值;`prm_m=3` 时多数票 = 0/-1/+1 平票返 0.0 |
| 最终 score | `float` ∈ {-1.0, 0.0, +1.0} | 多数票返 int,转 float 写进 turn record |
| callback | `_on_prm_done` | task done 时触发,落 score + 触发 finalize |

**`turn_record` 初始字段**(PRM 还没完):

```python
turn_record = {
    "turn_num": 2,
    "user_turn_num": 2,  # user-visible turn 计数
    "raw_turn_kind": "main",  # user turn 边界的 turn
    "prm_score": None,  # PRM 没完留 None
    "injected_skills": [...],  # 2nd turn 注入的 skill
    "read_skills": [...],  # 模型实际 read 的 skill
    "response_text": response2,
    "tool_calls": [...],  # 模型返回的 tool_calls
    "timestamp": iso_now(),
}
```

**`_maybe_finalize_ready_turns` 为什么"跳过本轮 finalize"**:

- turn 1 的 PRM task 还没 done(`_on_prm_done` 还没触发)
- 即使本轮 finalize 也只能处理"已 PRM 完的 turn"——turn 1 不在 ready 状态
- turn 1 的 PRM done 后,turn 3 进来时再调 `_maybe_finalize_ready_turns`,那时 turn 1 已 ready,能 finalize

**关键边界**:

- **`prm_scorer=None`**(`use_prm=False`):`_fire_prm_scoring` 守卫早返,**不**创建 task
- **LLM 调失败** (异步 task 抛异常):`_on_prm_done` 钩子 catch,turn_record 的 `prm_score` 留 None
- **session 正在 close**:`_fire_prm_scoring` 走 `_on_prm_done_record_only` 路径(不触发 finalize)
- **turn 1 PRM 还在跑时 turn 3 进来**:turn 2 的 PRM 触发,turn 1 finalize 等 turn 3 进 `_maybe_finalize_ready_turns` 时检查

**PRM 单次评分的精确说法**:

| 字段 | 值 | 来源 |
|---|---|---|
| 单次评分 | `int` ∈ {+1, 0, -1} | `prm_scorer._parse_prm_score` 只解析 `Score: 1` / `Score: -1` / `Score: 0` |
| 多数票 | `int` | `_majority_vote`(`prm_scorer.py:99`)取投票最多的 int |
| 平票或全 None | `0.0` | `_majority_vote` 返 0.0 |
| **最终 score** | `float` | `_majority_vote` 返 `float(top[0])`,**∈ {-1.0, 0.0, +1.0}** |
| **不是 4 维评分** | — | 4 维(`task_completion` / `response_quality` / `efficiency` / `tool_usage`)是 **Session Judge** 的维度,**不是 PRM** |

`record_feedback(injected, score)` 的 `score` 就是这个 float 多数票值。

**走完之后**:

- turn_record 写进 `_session_turns[sid]`(内存 dict)
- PRM 异步 task 跑(0.5-2s 完成)
- turn 3 进来时,`_maybe_finalize_ready_turns` 检查 turn 1 / 2 的 PRM 状态,ready 的 finalize
- 整个 session 关闭时(`_close_session`),turn 1 / 2 / 3 全部 finalize + 上传

**PRM 单次评分的精确说法（与多数票规则）**:
- **单次评分 = 1 个分数 ∈ {+1, 0, -1}**(`prm_scorer._parse_prm_score` 只解析 `Score: 1` / `Score: -1` / `Score: 0`),**不是**"4 维度评分"(task_completion / response_quality / efficiency / tool_usage 是 Session Judge 的维度,不是 PRM 的);
- **`prm_m=3` 默认 3 票多数票**,平票或全 None → `0.0`(`_majority_vote` 在 `prm_scorer.py:99`),不是中位/均值;
- `_majority_vote` 返 `float`(投票值 `int` → `float(top[0])`),所以**最终 score ∈ {-1.0, 0.0, +1.0}**——这是 `record_feedback` 和 session.json 里 `prm_score` 字段的实际取值集合。
- `record_feedback(injected, score)` 的 `score` 就是这个 float 多数票值;§2.5 session.json 示例里若出现 `0.85` 之类小数,**不是 PRM 多数票结果**——那是别的来源(详见 [16 章](16-PRM与反馈.md) 关于 session judge / aggregator 的连续分),重写时勿混淆。

### 2.3.1 `_apply_prm_result` 同时回写到 injected + read

`_on_prm_done` → `_apply_prm_result(session_id, turn_num, prm_result)`(`api_server.py:2244+`)**对同一 turn 的 PRM 分数会调两次 `record_feedback`**:第一次拿 `injected = turns[idx].get("injected_skills", [])`,如果非空且 `self.skill_manager` 存在就 `self.skill_manager.record_feedback(injected, score)`;第二次拿 `read = turns[idx].get("read_skills", [])`,如果非空,从 list of dict 里抽 `r["skill_name"]`(`isinstance(r, dict) and r.get("skill_name")` 双判),得 `read_names` 非空就再 `self.skill_manager.record_feedback(read_names, score)`。

**这是有意行为**——"注入了"和"读了"是两类独立事件,被分别记分才能正确推 effectiveness。**同 skill 同时出现在两个 list 时**会被记两次(同 score),这是当前实现的语义;是否 dedup 是开放设计选择:dedup → 单一 score;不 dedup → 同 skill 收到两倍 feedback 但 score 一致。

### 2.4 Turn 3 / 4 / 5 / ... / N：PRM 累积

每个 turn 进来都触发上一轮的 PRM。`_prm_tasks[session_id][turn_num]` 跟踪。

### 2.5 `X-Session-Done: true` 或 idle 超时 → `_close_session`

标题完整配置项说明:**`session_idle_close_seconds`(默认 180s, ≤ 0 关闭 idle sweeper)**,idle sweeper 每 15s 扫一次,距上次活动 ≥ 180s 触发 close;或 `X-Session-Done: true` header 显式触发。

**`_close_session(sid)` 走 7 步**:

**场景**:session 要关了(显式 `X-Session-Done: true` header / idle 超时 180s / 进程关闭)——SkillClaw 需要把这个 session 的"完整状态"落盘 + 上传,这样 evolve server 才能拿到完整证据做摘要。

**为什么是 7 步**:

- 步骤 1-3:把"异步 PRM"赶紧收尾(避免 session 关了 PRM 还在跑浪费)
- 步骤 4-5:把"还没 finalize 的 turn"落进 SkillManager + `prm_scores.jsonl`
- 步骤 6:把整个 session 上传到共享存储 + 顺便拉最新 skill(因为 session 关闭后 agent 可能马上要下一个)
- 步骤 7:清理内存状态(为下次同 session_id 复用准备)

**整体流程图**:

```
_close_session(sid)
  │
  ├─ 1. Flush pending record
  │      _flush_pending_record(sid, None)  # 把最后一行写入 conversations.jsonl
  │      # next_state=None 表示"这是 session 最后一条,不再触发新 PRM,只 flush 当前 record"
  │
  ├─ 2. 为 pending turn 启动 PRM (finalize-skip 路径)
  │      # 只对还没 finalize 的 turn 启动;score 可能为 None
  │      # 用 _on_prm_done_record_only 而非 _on_prm_done(避免在关闭过程中再触发新 task)
  │
  ├─ 3. Drain PRM tasks (最多 shutdown_drain_timeout_seconds=15s)
  │      # 等所有 PRM task done(同步等,15s 超时)
  │
  ├─ 4. _finalize_turn_feedback
  │      # 调 SkillManager.record_feedback + 写 prm_scores.jsonl
  │
  ├─ 5. SkillManager._save_stats() 强制刷盘
  │      # 把内存里的 effectiveness 统计写到 ~/.skillclaw/skill_stats.json
  │
  ├─ 6. _upload_session_data + _pull_skills_from_cloud
  │      # 6a. 上传 sessions/<sid>.json 到共享存储(给 evolve server)
  │      # 6b. 顺便拉一次最新 skill(因为 session 关了,可能马上要新 skill)
  │
  └─ 7. 清 7 个 session_id 状态表
       # _session_turns / _prm_tasks / _pending_turn_data / _closing_sessions
       # / _user_turn_counts / _session_last_active / _session_idle_close_deadlines
```

**7 步的"为什么这么排"**:

| # | 步 | 依赖上一步 | 产出 | 为什么在这 |
|---|---|---|---|---|
| 1 | Flush pending record | 内存里 `_pending_records[sid]` 的最后一行 | `conversations.jsonl` 完整一段 | session 关闭前必先写完最后一行 |
| 2 | 启动 PRM (finalize-skip) | `_prm_tasks[sid]` 中还没 done 的 | 一组 `_on_prm_done_record_only` callback 注册 | 关闭时也要给 pending turn 一次评分机会 |
| 3 | Drain PRM | Step 2 启动的所有 task | 所有 PRM task done(15s 超时) | 不能让 session 关了 PRM 还在跑(浪费 + 数据丢) |
| 4 | Finalize feedback | Step 3 done 的 PRM | `prm_scores.jsonl` 加 N 行 + SkillManager 已收分 | 把异步 PRM 结果真正落盘 |
| 5 | `_save_stats` | SkillManager 内存 | `~/.skillclaw/skill_stats.json` 刷盘 | 强制把 effectiveness 写盘,避免进程异常退出丢数据 |
| 6 | 上传 + 拉新 skill | session 完整 record | 共享存储 `sessions/<sid>.json` 写好;本地 skill 集更新 | session 完整证据交付;同时预热下次拉新 |
| 7 | 清状态表 | — | 内存里 7 个 dict 不再有 `sid` 这条 | 为下次同 `sid` 复用准备(idle 后 agent 可能复用) |

**为什么第 1 步用 `next_state=None`**:`_flush_pending_record(sid, next_state)` 的 `next_state` 参数表示"flush 后是否还有 user turn 进来"——`None` 表示"这是最后一条",flush 后**不再触发新 PRM**,只 flush 当前 record。

**为什么第 2 步用 `_on_prm_done_record_only` 而非 `_on_prm_done`**:两个 callback 区别是"是否调 `_maybe_finalize_ready_turns`"——session 关闭时**不应**再触发新 finalize 流程(避免在关闭过程中又调出新 task,导致 race condition)。

**为什么第 3 步有 15s 超时**:进程关闭时不能无限等——`shutdown_drain_timeout_seconds` 给一个上限,超时后即便 PRM 没完也强制 finalize(用 `None` 兜底)。

**为什么第 5 步强制刷盘**:`_save_stats()` 默认 lazy flush(等 `_save_stats_deadline` 到才写盘)——session 关闭是显式时机,强制刷保证 `skill_stats.json` 不会因为进程异常退出丢数据。

**为什么第 6 步要"拉新 skill"**:session 关闭时,客户端 daemon 可能要立即开下一个 session——如果先 `_upload_session_data` 不 `_pull_skills_from_cloud`,下一个 session 进来时 SkillManager 还是旧 skill 集,evolve server 上一轮 cycle 刚出炉的新 skill 没被本地看到。

**为什么第 7 步要清 7 个状态表**:这 7 个 dict 内存里都是 `Dict[session_id, ...]`——不清理会一直占内存,且下次同 `sid` 进来会拿到脏数据(例如 `_user_turn_counts[sid]` 旧值)。

**关键边界**:

- **idle 超时触发 close**:跟显式 close 走相同 7 步——但**不**等 PRM 完(因为 idle sweeper 是后台 task,不能卡住 event loop),会更快 finalize
- **进程被 SIGTERM 关**:走 `lifespan` 的 shutdown hook,直接进 `_close_session_all` 批量 close 全部 session
- **`shutdown_drain_timeout_seconds=0`**:禁用 drain,直接进 step 4(可能丢 PRM task)
- **上传失败** (Step 6):`conversations.jsonl` 留在本地,下次 idle cycle 重试(`reupload_pending_sessions`)
- **多个 session 同时 close**:每个 session 独立跑这 7 步,但**共享** SkillManager / `_save_stats`(可能并发 flush,SkillManager 内部有锁)

**走完之后**:

- 共享存储 `sessions/<sid>.json` 写好(给 evolve server 下一轮 cycle 拉)
- 本地 `conversations.jsonl` 累加完一段
- `prm_scores.jsonl` 累加完本 session 的所有 turn 分
- `~/.skillclaw/skill_stats.json` 刷盘(本 session 的所有 effectiveness 收尾)
- 内存 7 个 dict 清掉 `sid` 记录
- 客户端 daemon 准备好开下一个 session

**session.json 内容**(注意 `prm_score` 是多数票 float,值域 `{-1.0, 0.0, +1.0}`):顶层字段 5 个——`session_id` / `timestamp` (ISO) / `user_alias` / `num_turns` / `turns` 列表;每条 turn 含 `turn_num` / `user_turn_num` / `raw_turn_kind` / `prompt_text` / `response_text` / `tool_calls` / `read_skills` (list of `{skill_name, path}`) / `modified_skills` / `tool_results` / `tool_errors` / `injected_skills` (list of skill name) / `prm_score` (多数票 float)。

**`prm_score` 在 turn_record 里**——evolve server 后续 summarizer 拿到的 session 里能看到这个分（**作为信号**;PRM 失败 / drain 超时的 turn 该字段为 `null`,evolve server summarizer 看到 `null` 不报错但按"无信号"处理,详见 §10)。

## 3. 中段：共享存储（详见 20 章）

### 3.1 并行的三个时序：poller / record / evolve

三件事频率**各自独立**、并不"同时"——以下是它们的节奏:

- **client-side reload poller**（每 30s,jitter 10% + 失败 backoff 上限 60s,`sharing.skill_reload_interval_seconds` 配,下限 5s）：从 storage 拉 manifest → diff → pull 新 skill → `SkillManager.reload()`
- **client-side record**（每次 `_close_session`）：upload session.json 到 `sessions/<sid>.json`;无独立周期,与 close 事件同频
- **evolve server 周期**（每 600s,env `EVOLVE_INTERVAL` 配）：drain sessions → ...

## 4. 第三段：Evolve Server（详见 30-32 章）

### 4.1 `EvolveServer.run_once`(workflow 引擎,6 步流水线)

workflow 引擎的 6 步流水线:**Stage 1 · Drain** ——`list_session_keys` 列 sessions + `read_json_object` 逐个读 JSON;**Stage 2 · Summarize** ——LLM #1 给每个 session 并行做摘要,加上程序元数据 `_trajectory` / `_skills_referenced`;**Stage 3 · Session Judge** ——LLM #2 给每个 session 打分(optional,默认启用),结果写到 `_judge_scores`;**Stage 4 · Aggregate** ——按 skill name 聚合 sessions,落不到任何 skill 的进 `__no_skill__` group;**Stage 5 · Evolve + Create** ——LLM #3 给每个 group 决策 improve / optimize_desc / skip(`no_skill` group 走 create);**Stage 6 · Upload** ——verifier(LLM #4, optional)→ conflict detect(sha256)→ 冲突时 merge(LLM #5, optional)→ `_upload_skill` 落盘。

### 4.2 Evolve LLM 看到的 prompt(`evolve_skill_from_sessions`)

**完整 prompt 模板结构** = system (固定字符串) + user (三段: `## Current skill` / `## Session evidence (N sessions)` / `## Existing skill names in the library`;N 由 sessions 数决定)。LLM 自由发挥的部分是 `## Session evidence` 内每个 session 的 `**Analysis**` 摘要;`## Current skill` / `## Existing skill names in the library` / system 都是**程序拼好**给 LLM 看的。

system 段固定写:"You are a skill editor for SkillClaw. Given the current skill '<skill_name>' and N sessions that reference it, decide: improve / optimize_description / skip. Return JSON {action, skill, rationale}."。user 段是 3 段拼起来——`## Current skill` 段给当前 SKILL.md 的 Name / Description / Category / Content(markdown 块);`## Session evidence (N sessions)` 段列 N 个 session,每个 session 一段 `### Session <id> {avg_prm, has_tool_errors, skills: [...]}` + `**Trajectory**`(step-by-step 文本) + `**Analysis**`(LLM 自由发挥的判断);`## Existing skill names in the library` 段给当前 skill 库的名称列表。

> "skill editor" 是 SkillClaw 给 Evolve 阶段 LLM 起的**角色名**(区别于客户端的 user/agent 角色)——INDEX [02 章](02-核心概念词典.md) 已定义。

LLM 返回 3 字段字典:`action`(DecisionAction 字面值,字符串不是属性名,详见 `evolve_server/core/constants.py:35-41`)+ `skill`(4 字段:`name` / `description` / `category` / `content`,LLM 必填)+ `rationale`(字符串,LLM 解释为什么这样改)。例:某次 evolve LLM 决定 `action="improve_skill"`,`skill.name="debug-systematically"`,`description` 加了 "Now includes explicit verification step" 提示,`content` 加了"Verify root cause before fixing"步骤,`rationale` 写"Session abc missed verification step; adding it explicitly. Other steps stay the same to preserve behavior."。

**`skill` 字段表——LLM 必填 4 字段 + server 追加 6 字段**:

| 字段 | 谁填 | 类型 | 格式 / 计算方式 |
|------|------|------|------------------|
| `name` | LLM 必填 | str | kebab-case `^[a-z][a-z0-9-]{1,63}$`;CREATE 路径走 `_sanitise_name`,IMPROVE 路径被 `_materialize_skill` 强制 overwrite 为 `current_skill['name']`(LLM 想 rename 也会被覆盖) |
| `description` | LLM 必填 | str | 单段文本;OPTIMIZE_DESC 只改它,body 继承老的 |
| `category` | LLM 必填 | str | 自由文本;manifest 写时若 LLM 没给 → 默认 `"general"` |
| `content` | LLM 必填 | str | markdown body;`build_skill_md(skill)` 拼成完整 SKILL.md |
| `version` | server 追加 | int | 1-based,`SkillIDRegistry.record_update` 自增;LLM 不算、不写 |
| `sha256` | server 追加 | str | `sha256(content.encode("utf-8")).hexdigest()`;LLM 算不出 |
| `tree_sha256` | server 追加 | str | `sha256(按 (path, sha, size) 排序拼,中间 \0 + 末尾 \n)`,见 `bundle_tree_sha256`(`skillclaw/skill_bundle.py:103`) |
| `files` | server 追加 | list | `bundle_file_records` 扫 bundle 目录生成;每文件 `{path, sha256, size}`;LLM 不返回 files,server 在 `save_version_bundle` 里由 bundle 目录直接打包 |
| `format` | server 追加 | str | 固定字面值 `"bundle_v1"`;LLM 不写 |
| `skill_id` | server 追加 | str | `sha256(name.encode()).hexdigest()[:12]`(12-hex);`SkillIDRegistry.get_or_create` 派生 |

> LLM 必填字段集只有 4 个(`name` / `description` / `category` / `content`);其余 6 字段(`version` / `sha256` / `tree_sha256` / `files` / `format` / `skill_id`)由 evolve server 在 LLM 返回后**追加**——LLM 不算、不写。重写 `_parse_evolve_result` / `_resolve_and_upload` 时,LLM 不会返回后 6 字段,server 必须在 `_upload_skill` 之前补齐。

**`DecisionAction` 4 个值**(`core/constants.py:35-41`):
- `CREATE = "create_skill"`(从 no-skill bucket 造新 skill)
- `IMPROVE = "improve_skill"`(老 skill 改写)
- `OPTIMIZE_DESC = "optimize_description"`(只改 description,body 继承)
- `SKIP = "skip"`(LLM 决定不动)

**4 决策的建议准则(prompt 实际不强制、LLM 自由发挥,以下为参考骨架,prompt 里通常不显式列)**:
- `sessions < 3` → SKIP(数据不够,不值得演进)
- `所有 session PRM < 0.3`(注意:PRM 值域是 {-1.0, 0.0, +1.0},0.3 实际是 `avg_prm <= 0.0` 即负信号占多数)→ OPTIMIZE_DESC(description 问题大,body 还能用)
- 目标 skill 已存在且 `session evidence` 显示 description 能改进 → IMPROVE
- 目标 skill 不存在(no-skill bucket) → CREATE
- 4 决策以外的字符串 / `action` 字段缺失 → **默认 SKIP**(`execution.py:447`)

> **默认是 SKIP**:`_parse_evolve_result`(`execution.py:447`)的 action 默认值是 `DecisionAction.SKIP`——LLM 不返回 action 字段时,默认**跳过**该 skill。读者按"IMPROVE 是默认"实现,会跟代码不一致。
>
> **CREATE 路径的兜底降级**:`_parse_evolve_result`(`execution.py:456-465`)——LLM 偶发返回 `create_skill` 但 `name == skill_name`(等于改名没改)时,会被**静默改写**为 `IMPROVE`,避免同名 create 改写历史。
>
> **`_materialize_skill` 强制 name 行为**:`workflow.py:760-764` 在 `_materialize_skill` 里:**`action_type == DecisionAction.IMPROVE` 时强制 overwrite skill name 为 `current_skill['name']`**——LLM 想 rename 也会被覆盖;`CREATE` 路径才走 `_sanitise_name`。

### 4.3 Upload

**场景**:evolve server 把 LLM 决定的新 SKILL.md 写到共享存储——这是"团队级共享"的入口,写完后其它客户端 30s 内 poll 到,拉新 skill。

**三种后端**:

| 后端 | manifest 写 | registry 写 | version 来源 |
|---|---|---|---|
| **OSS / S3 / Local**(默认) | 写 `manifest.jsonl` | 写 `evolve_skill_registry.json` | `SkillIDRegistry.record_update` 自增 |
| **Nacos** | **不**写 manifest | **不**写 registry | Nacos 服务端分配 |
| **Local only** | 仅本地文件 | 仅本地 | registry 自增 |

本节以 **OSS 路径为主线**(最常用);Nacos 走 `nacos_skill_client.upload_skill_zip` + `submit()` + `publish()`(见 20 章 Nacos 适配器)。

**`_resolve_and_upload` 全 9 步**(OSS 路径,以一个有冲突的 cycle 为例):

```python
async def _resolve_and_upload(self, skill, action_type):
    # 段 1:名字规范化
    skill["name"] = self._sanitise_name(skill["name"])
    # 规范名字("debug-systematically")不变;LLM 怪字符("my-skill v2")被清洗

    # 段 2:可选 verifier
    if self.config.use_skill_verifier:
        verdict = await self._run_skill_verifier(...)
        if not verdict.get("accepted"):
            return {"action": "verification_rejected", ...}

    # 段 3:publish_mode=direct 跳过 validation
    if self.config.publish_mode == "validated":
        return await self._queue_validation_job(skill, action_type, ...)

    # 段 4:_resolve_and_upload(冲突检测 + 合并 + 上传)
    # 4a. _detect_conflict 判冲突
    has_conflict = self._detect_conflict(skill, current_skill)
    # 4b. 没冲突直接 _upload_skill
    if not has_conflict:
        upload_status = await self._upload_skill(skill, action_type)
    # 4c. 有冲突 execute_merge 调 LLM 合并
    else:
        merged = await execute_merge(self._llm, current_skill, skill)
        upload_status = await self._upload_skill(merged, "merge")

    # 段 5:返回上传状态
    return self._upload_status_to_action(action_type, upload_status)
```

**`_upload_skill` 6 个子步**(OSS 路径):

```python
async def _upload_skill(self, skill, action_type):
    # 子步 1:算 object_key
    object_key = f"{self._prefix}skills/{skill['name']}/SKILL.md"

    # 子步 2:put_object 写 SKILL.md
    skill_md = build_skill_md(skill)
    await self._call_storage(put_object, self._bucket, object_key, skill_md)

    # 子步 3:SkillIDRegistry.record_update(name, sha, action, bundle_record)
    # 4 参均必填;action 集合 {create, improve, optimize_description, merge}
    version = self._id_registry.record_update(skill["name"], content_sha, action_type, bundle_record)

    # 子步 4:save_version_bundle 写 v<N>/ 目录
    # v 是字面前缀,version=8 是 1-based int
    # v8/SKILL.md + v8/files/<rel_path> + v8/record.json
    await self._save_version_bundle(skill["name"], version, ...)

    # 子步 5:manifest[name] = {..., version=8, ...} 写新条目
    manifest = await self._load_remote_skills()
    manifest[skill["name"]] = {
        "name": skill["name"],
        "skill_id": ...,
        "version": version,
        "sha256": content_sha,
        "tree_sha256": tree_sha,
        ...
    }

    # 子步 6:save_manifest(...) 覆盖整文件
    await self._save_manifest(self._bucket, self._prefix, manifest)
```

**`_upload_skill` 之后 4 步**(Stage 8 finalize):

```python
# 段 6:registry save_to_oss(把内存 dict 持久化到 <bucket>/<group_id>/evolve_skill_registry.json)
await self._id_registry.save_to_oss(self._bucket, self._prefix)

# 段 7:delete_session_keys(N sessions)
await self._call_storage(delete_object, self._bucket, ...)

# 段 8:_append_history(summary) 写 evolve_history.jsonl
await self._append_history(summary)

# 段 9:uploaded_skills > 0 触发 _notify_proxy_reload
if uploaded_count > 0:
    await self._notify_proxy_reload(summary)
```

**`_notify_proxy_reload` 细节**:

| 字段 | 值 |
|---|---|
| URL | `config.evolve_proxy_reload_url`(默认 `http://127.0.0.1:30000/internal/reload-skills`) |
| Authorization | `Bearer <config.proxy_reload_api_key>`(**与**客户端 `proxy_api_key` **不同**) |
| 方法 | POST |
| 重试 | 3 次 attempt 0/1/2,线性 backoff `1.0 * (attempt + 1)`(间隔 1s/2s/3s) |
| 单次 timeout | 5s |

**关键边界**:

- **`_detect_conflict` True**:走 execute_merge LLM 合并;**merge 失败 fallback 用 incoming**
- **`save_manifest` 失败**:抛错,这一 change 标记失败,Step 9 跳下一个 change
- **`_notify_proxy_reload` 3 次失败**:记 logger.warning,不抛错(下一轮 polling 自然会发现)
- **Nacos 路径**:`_upload_skill` 整段被 `nacos_skill_client.upload_skill_zip` 替代——`manifest.jsonl` / `evolve_skill_registry.json` 都不写
- **并发 agent 引擎 + workflow 引擎**:同时跑同一 skill,`_detect_conflict` 不会 catch 这个 race condition——`save_manifest` 覆盖语义可能丢变更(见 31 章 §4.2 / 32 章 §4.2)
- **`proxy_reload_api_key` 配错**:reload POST 401,客户端 30s 后 polling 自然发现新 manifest(轮询兜底)

**走完之后**:

- 共享存储 `skills/<name>/SKILL.md` 写好 + `versions/v<N>/` 历史目录写好
- `manifest.jsonl` 全量重写
- `evolve_skill_registry.json` 持久化
- `_notify_proxy_reload` 触发客户端拉新 skill(callback 模式);polling 模式 30s 后发现
- `evolve_history.jsonl` 多一行 cycle 记录

### 4.4 替代：Agent Engine

**引擎选型**——通过 `evolve.engine = "workflow" | "agent"` 配置项切换(env `EVOLVE_ENGINE` 或 CLI `--engine`,默认 `"workflow"`);**没有**"两种都跑"的中间态,evolve server 启动时一次性选定。

- **workflow 引擎**(默认)适合:大批量 session 批处理 / 成本敏感 / 不需要 OpenClaw 进程级隔离的场景
- **agent 引擎**适合:需要 OpenClaw 进程级隔离 / 多步调试 / 跨轮记忆(`--no-fresh`)/ 让 LLM 自由写多个 skill 的场景

`AgentEvolveServer.run_once`:
1. Drain N sessions(按 `list_session_keys` 实际数量)
2. Summarize(用同一个 summarizer pipeline)
3. Workspace reset (`--fresh`) 或保留
4. Fetch all skills bundles → 写 workspace/skills/
5. 写 sessions/ + manifest.json + EVOLVE_AGENTS.md + 4 个 bootstrap
6. Snapshot tree_sha
7. 启 OpenClaw 子进程(session_id 跨轮记忆)
8. OpenClaw 读 sessions/、读 EVOLVE_AGENTS.md、写 skills/<name>/SKILL.md
9. Snapshot after
10. collect_changes: diff → 2 changes (create + improve)
11. 上传 N 个 skill
12. Cleanup

**关键差异**:workflow 引擎是**"evolve server 调 LLM"**,agent 引擎是**"evolve server 启 OpenClaw 进程,OpenClaw 调 LLM"**。

## 5. 第四段：Client Reload

### 5.1 Callback 模式

evolve server 的 `_notify_proxy_reload` POST `/internal/reload-skills` 走"3 次重试 + 1s/2s 间隔"两步:第一步构造 `url = config.evolve_proxy_reload_url`(默认 `http://127.0.0.1:30000/internal/reload-skills`)+ `Authorization: Bearer <config.proxy_reload_api_key>`(这把是 evolve server → 客户端 reload 端点专用,**与**客户端 `proxy_api_key` **不同**);第二步 `resp = await client.post(url, headers={"Authorization": f"Bearer {api_key}"})`。

`SkillClawAPIServer.reload_skills` 走"鉴权 + pull + 报数"3 步:第一步 `await self._check_auth(authorization)` 校验 token;第二步 `await self._pull_skills_from_cloud()` 拉新 skill;第三步 `skill_count = len(self.skill_manager.get_all_skills())` 拿当前 skill 数,返 `{"ok": True, "skills": skill_count}`。

`_pull_skills_from_cloud(skip_names=...)` 走"起 hub + 调 pull + 决定是否 reload"3 步:第一步 `hub = SkillHub.from_config(self.config)`;第二步 `pull_result = hub.pull_skills(self.config.skills_dir, skip_names=skip_names)`,pull_result 含 `downloaded` / `skipped` / `failed` / `deleted` 4 个数;第三步 `if self.skill_manager and (downloaded > 0 or deleted > 0 or restored_from_backup): self.skill_manager.reload()`。

`SkillHub.pull_skills` mirror=True(默认)→ 把 manifest 镜像到本地 + 删 extras + 失败回滚。

### 5.2 Poll 模式(默认)

`_skill_reload_poll_loop` 每 `sharing.skill_reload_interval_seconds`(默认 30s,下限 5s)跑一次(带 10% jitter + 失败 backoff 上限 60s),走"while True 循环"框架:循环体第一步(非首次时)`await asyncio.sleep(interval + jitter + backoff)`;第二步 `try: await self._pull_skills_from_cloud() except: consecutive_failures += 1`,成功时 `consecutive_failures = 0`(让 backoff 归零)。

**30s 默认延迟** = 新 skill 拉取最多滞后 30s(默认配置下);pull 成功后,**`skill_manager.refresh_if_changed()` 在下一个 main turn 入口**被 `_inject_skills` 调到,比对 `self._skill_fingerprint` 与当前,变化即重建 prompt(详见 §6.1)。

## 6. 第五段：用户看到更新

### 6.1 下一次 main turn

下一次 main turn 走"用户 → Hermes → 代理 → LLM → 完成"4 段:用户说"我又要 debug 一个 bug"→ Hermes 发 `POST /v1/chat/completions` → SkillClawAPIServer 内部走 6 步——(1) `skill_manager.refresh_if_changed()`(由 §5.2 poll loop 在 pull 成功后设 `_skill_fingerprint`,此处比对变化);(2) `skill_manager.build_injection_prompt(max_chars=30_000)`(`max_chars=30_000` 在 Chat Completions 路径硬编码,**非** config);(3) `<available_skills>` 里 `debug-systematically` 的 description 已经是 "Now includes explicit verification step";(4) `record_injection(["debug-systematically", ...])`;(5) 转发 LLM,LLM 看到新 description 决定 `read` SKILL.md;(6) SKILL.md 的 content 也已更新(多了"Verify root cause before fixing"),走完。

**端到端延迟**:
- session_done → session upload:~立即
- evolve server 周期:~600s(`EVOLVE_INTERVAL` 默认)
- evolve server 处理:~5-30s(5-10 个 LLM 调用)
- 拉回本地:30s(poll)或 <1s(callback)
- **总延迟**:5-15 分钟(默认配置)

> 数字基于 DeepSeek / Qwen3 中等 session (5-15 turn) 经验值,**非 SLA**——不同 LLM / session 规模差异大。

## 7. 数据流关键时序图

> 本节时序图为**示意**,时长均为"由用户行为 / 配置项决定",非系统固定时序。

```
T+0s:  user turn 1 (POST /v1/chat/completions)
       → record 1 buffered
       → PRM task 1 created (waiting for turn 2)
T+Xs:  user turn 2 (由用户决定,几秒~几小时都有可能)
       → record 2 buffered
       → PRM task 1 done (score ∈ {-1.0, 0.0, +1.0} 多数票)
       → record 1 finalized: prm_score=1.0, SkillManager.record_feedback
T+Ys:  user turn 5 + X-Session-Done: true (由用户决定)
       → _close_session (session_idle_close_seconds 配或显式 done)
       → upload session.json
       → pull skills (manifest unchanged)
T+`evolve_interval`(默认 600s): evolve server 下一次 cycle
       → drain 1 session (the one we just uploaded)
       → summarize (LLM ~3s)
       → aggregate
       → evolve "debug-systematically" (LLM ~5s, "improve_skill")
       → upload (sha256 changed, conflict path; merge with LLM ~5s; upload merged)
       → manifest["debug-systematically"].version = 8
       → notify proxy reload
T+`evolve_interval`+~5s: SkillClawAPIServer reload
       → pull_skills("debug-systematically" sha mismatch → download new SKILL.md)
       → skill_manager.reload()
       → _skill_fingerprint 变化
T+`evolve_interval`+~6s (or next main turn): user turn 6
       → skill_manager.refresh_if_changed() detects change
       → <available_skills> now has updated description
       → LLM reads new SKILL.md
```

## 8. 关键对象 ID 与命名约定

## 10. PRM 反馈回路(端到端视角)

5 条遗留决策以**两列对比**呈现——左列是当前实现行为;右列是"部署方按需决定"。

| # | 当前实现行为 | 部署方按需决定 |
|---|------------------------|----------------------------|
| 1 | **session.json 没有去重**:同 session_id 二次 upload(`_close_session` 一次 + `dashboard.export_local_sessions` 一次)会**完全覆盖**——内容相同所以无害。 | 是否在 dashboard export 时加 `if existing == content: skip` 去重保护。 |
| 2 | **Evolve server 不读 conversations.jsonl**:它只读共享存储的 `sessions/<sid>.json`。PRM 失败 / turn 还没 finalize 的 session 不会被 evolve(`_close_session` 之前 PRM 强制 drain `shutdown_drain_timeout_seconds`,默认 15s)。 | drain 15s 超时后,PRM 失败的 turn 上传时 `prm_score=null`——是否给这类 turn 显式 `_prm_failed: true` 标志位。 |
| 3 | **Manifest 写覆盖不原子**:`save_manifest` 全量读后全量写——并发 push 会丢一方的变更(无 ETag 保护)。 | 是否加 ETag 保护 / 是否改用 append-only 写入 / 是否加写入锁。 |
| 4 | **`prm_score` 在 `turn_record` 里但 upload 后是 `null`(如果 PRM fail)**:evolve server 的 summarizer 不会额外说明——按"无信号"处理,不报负信号。 | 是否在 session.json 顶层加 `_prm_failed_count` 聚合字段,让 summarizer 看到"本 session 整体弱信号"。 |
| 5 | **Evolve server 周期内 concurrency = 1**:多个 cycle 不能并行(用 `self._running` 标志位)——长 cycle 会阻塞下一次。 | 是否加 cycle 队列 / 是否允许多 cycle 并行(配 cycle_id 防冲突) / 是否对长 cycle 加超时报警。 |
