## 1.5 核心概念(第一次读请先扫这里)

下面这些术语在 4.2 数据流图和后续章节会反复出现。**首次出现时**会有括号定义或同节提示;这里给一个**总览表**,方便回头查。

| 术语 | 一句话定义 | 详细章节 |
|---|---|---|
| **Client Proxy** | 本机代理,SkillClaw 暴露在 `127.0.0.1:<port>` 的 FastAPI 服务,Agent 把 LLM 请求发到这里 | 04.01 |
| **Evolve Server** | 独立进程,周期读 session、调 LLM、生成 skill、写回共享存储 | 04.12-04.14 |
| **Skill** | 一份可复用的能力文档,= `skills/<name>/SKILL.md` + 可选 `scripts/ references/ assets/` | 04.03 |
| **SKILL.md** | skill 的文本文件:YAML frontmatter(必含 `name` + `description`)+ Markdown body | 04.03 |
| **Session** | 一次用户对话,从第一个用户消息到 `session_done=true` 的完整轨迹 | 03.02 |
| **Turn** | 一对 user + assistant(可能含 tool_calls) | 03.01 |
| **PRM(Process Reward Model)** | 在 SkillClaw 里**弱化**为"turn-level 回复质量评分",LLM judge 打 {-1, 0, 1} | 04.09 |
| **_summary / _trajectory** | session 的两种摘要:前者 LLM 生成的因果分析,后者程序化生成的完整 tool_call 步骤 | 03.04 / 04.13 |
| **_skills_referenced** | session 引用过的 skill 名集合(从 LLM 摘要里 extract 出来) | 03.04 / 04.13 |
| **Bundle** | 一个 skill 的所有文件 dict,`{rel_path: bytes}`(包括 SKILL.md + scripts/ 等) | 04.04 |
| **Manifest** | 共享存储里的 `{group_id}/manifest.jsonl`,所有 skill 的元数据清单(每行一条 skill 记录) | 04.04 |
| **Tree SHA** | `bundle_tree_sha256(bundle)`——对 sorted paths + contents 整体算的 sha256,增量同步的"指纹" | 04.04 |
| **Generation** | `SkillManager.generation` 自增计数器,文件变化时 +1,标记 skill 库版本 | 04.03 |
| **Effectiveness** | `positive_count / inject_count`,PRM 反馈聚合,默认 0.5(从未被评过) | 04.03 |
| **Sharing** | 跨用户/设备的 skill 共享机制,通过对象存储(OSS/S3/local/Nacos) | 03.03 / 04.04 |
| **Group ID / User alias** | `sharing.group_id` = 共享命名空间;`sharing.user_alias` = 上传者 tag,隔离不同用户的 session | 04.07 |
| **Workflow engine** | Evolve Server 默认引擎,3 阶段(Summarize / Aggregate / Execute)LLM 流水线 | 03.04 |
| **Agent engine** | Evolve Server opt-in 引擎,启动 OpenClaw 子进程用工具编辑 skill | 03.05 |
| **Agent 框架(Claw)** | LLM Agent 客户端框架(本图顶层 ASCII 里列出的 `OpenClaw` / `Hermes` / `Codex` / `Claude Code` / `QwenPaw` 等),`claw_adapter.py` 通过改写它们的 `base_url` 配置把 LLM 请求劫持到 SkillClaw 代理,**不**修改 Agent 代码本身 | 04.06 |

> **Agent 框架总览**:上述 5 个是 SkillClaw 顶层 ASCII 图中点名的代表性 Agent 框架,其中 `Hermes` / `Codex` / `Claude Code` 是当前主流的 LLM Agent 客户端,`OpenClaw` / `QwenPaw` 是 SkillClaw 适配的 opt-in 框架。SkillClaw 通过改写它们的 `base_url` 配置来劫持 LLM 请求,无需修改 Agent 代码本身;完整 12 种框架的协议面差异与各 Agent 详细接入方式见 [04.06](./04-模块详解/04.06-代理适配层.md)。

> **计数说明**:本节"模块"按"`skillclaw/<file>.py` 顶层职责"切分,所以 Client 端 11 个(client/)= 04 章的 04.01-04.11,Server 端 3 个(04.12-04.14)= 共 14 个总模块。02 章用 11 是 client 视角,04-INDEX 用 14 是总视角——粒度不同,数字都对。Server 端的 `storage/` 子包没有独立 04.x 章节,内容在 [04.04 (Skill 共享中心)](./04-模块详解/04.04-skill共享中心.md) 的 "service 端 `storage/oss_helpers.py`" 段落和 04.12 / 04.13 / 04.14 的"关键文件"表中按需出现。

## 三、跨进程边界:共享存储

`SkillHub` 和 `evolve_server.storage.oss_helpers` 都围绕同一个对象存储抽象(`object_store.build_object_store`):

```
{group_id}/
├── manifest.jsonl                    # 当前所有 skill 的元数据
├── skills/
│   └── <name>/
│       ├── SKILL.md                  # 最新版本
│       └── files/                    # 可选:scripts/ / references/ / assets/
├── skill_versions/
│   └── <name>/
│       └── v<N>/
│           ├── record.json
│           └── SKILL.md
├── sessions/
│   └── <user_alias>/
│       └── <session_id>.json
├── validation/
│   ├── jobs/<job_id>.json            # 候选 skill + replay cases
│   └── results/<user_alias>/<job_id>.json
├── evolve_history.jsonl              # 服务端本地,与本机数据分离
└── evolve_processed.json             # 服务端本地
```

> **注**:Nacos Skill Registry 后端**不**走这套 prefix 树;它有自己的 zip / version / label 协议,见 [04.05](./04-模块详解/04.05-nacos适配.md)。

## 四、控制流 vs 数据流

### 4.1 控制流(谁调用谁)

```
┌─ 用户 ─────────────────┐
│  shell: skillclaw ...  │
└──────┬─────────────────┘
       │
       ▼
┌─ CLI (Click) ──────────┐
│  cli.py:main           │  ← 单进程 / 守护进程分流
└──┬──────────┬──────────┘
   │ start    │ other commands
   ▼          ▼
┌─ launcher  ┌─ 各子命令
│  fork 子   │  (skills/validation/dashboard/...)
│  进程      │
└──┬─────────┘
   │
   ▼
┌─ uvicorn ─────────────┐
│  FastAPI app          │
│  api_server.py:1533+  │  ← 用户请求入口
└──┬─────────┬──────────┘
   │         │
   │         │ 后台 tasks
   │         ▼
   │    ┌─ asyncio.create_task ─┐
   │    │ session recorder      │  ← 落 records/ 和 shared sessions/
   │    │ PRM scorer (async)    │  ← 调 LLM 评分
   │    │ validation worker     │  ← 空闲时拉 job,replay 评估
   │    │ shared skill puller   │  ← 定时 poll bucket
   │    └───────────────────────┘
   │
   ▼
┌─ upstream LLM ─────────────────────────────────┐
│  via OpenAI client / Anthropic SDK / Bedrock   │
└────────────────────────────────────────────────┘
```

Evolve Server 的控制流是单进程 asyncio 循环:

```
┌─ main() (evolve_server/__main__.py) ──────┐
│  parse args → EvolveServerConfig          │
└──┬──────────────────────────────────┬────┘
   │ --once/--mock                │ --port / 周期
   ▼                              ▼
┌─ run_once() ──────────┐  ┌─ run_periodic() ─────┐
│  5 步流水线(见 03.04) │  │  while True:         │
│  串行 + 部分并发       │  │    await run_once()  │
│                       │  │    sleep(interval)   │
└───────────────────────┘  └──────────────────────┘
```

### 4.2 数据流(skill 怎么"流")

> 标号 ①-⑲ 是端到端的 19 个数据流动作。下文每个标签**自带说明**——首次出现的术语(PRM、_summary、_trajectory、_skills_referenced、generation、tree SHA、manifest、bundle 等)在 ⑨-⑲ 范围内首次出现时,本节内带括号定义或链接到核心概念表。

```
用户对话(用户 + LLM Agent 的一次交互回合)
   │
   │  ① API request(Agent 发的 OpenAI 或 Anthropic 协议请求)
   ▼
[Client Proxy(SkillClaw 本地代理,skillclaw/)]
   │  ② 选 skill:SkillManager.retrieve 按"任务描述"检索 top-K 相关的 skill 文档
   │  ③ 把选中的 skill 注入到 system prompt(把 SKILL.md 拼成 <available_skills> 块)
   │  ④ 把"带 skill 上下文"的 messages 转给 upstream LLM(真正的远端模型)
   │  ⑤ 收到 upstream LLM 的 response
   │  ⑥ 落 session:把这一 turn 追加到 records/<session_id>.json(本地落盘)
   │  ⑦ 后台:PRM 评分(Process Reward Model——LLM judge 给"回复是否有用"打 {-1,0,1})→ 更新 skill effectiveness
   │  ⑧ 周期性:SkillHub.push 把累积的 session 推到 shared sessions/<user>/<session_id>.json
   ▼
[Shared Storage(共享对象存储,local / OSS / S3 / Nacos 任选)]
   │
   │  ⑨ EvolveServer 周期 drain sessions(读取所有未处理的 session JSON)
   ▼
[Evolve Server(evolve_server/,周期跑 run_once)]
   │  ⑩ Summarize 阶段(LLM):提炼出 _summary(LLM 生成的因果分析)+ _trajectory(程序化生成,完整 tool_call 步骤)
   │  ⑪ Aggregate 阶段(程序化,无 LLM):按 _skills_referenced(本 session 引用的 skill 名集合)把 session 分到不同 skill 组
   │  ⑫ SessionJudge(可选):给没有 benchmark 分的 session 打 overall_score
   │  ⑬ Execute 阶段 LLM 决策:对每个 skill 组,LLM 决定 improve_skill / optimize_description / create_skill / skip
   │  ⑭ Conflict detection + Merge:如果同名 skill 已存在,LLM 合并现有版 + 新版
   │  ⑮ Upload:把最终 SKILL.md 写到 shared skills/<name>/SKILL.md
   │  ⑯ Save manifest(所有 skill 的元数据清单 jsonl)+ version bundle(每个版本的完整快照)
   ▼
[Shared Storage]
   │
   │  ⑰ Client 启动时 / 定时 poll → 调 SkillHub.pull_skills 拉远端所有 skill
   ▼
[Client Proxy]
   │  ⑱ SkillHub 拉远端:先 backup 本地,再 mirror 远端,失败时 restore
   │  ⑲ SkillManager.refresh_if_changed:对比 fingerprint(文件路径+mtime+size 元组),变了就 reload 并 generation += 1
   ▼
下一次对话 ①(generation 标记当前 skill 库的版本,新一轮对话会注入最新版的 skill)
```

## 五、关键设计选择(摘要)

- **两个进程 + 共享存储** vs **单进程** —— 见 [05.01](./05-关键设计决策.md#51-为什么是双进程-为什么是共享存储) 。

- **workflow 引擎默认,agent 引擎可选** —— 见 [05.03](./05-关键设计决策.md#53-为什么-workflow-是默认引擎) 。
- **SKILL.md 作为单一文件格式** vs **多文件** —— 见 [05.04](./05-关键设计决策.md#54-为什么-skill-就是-skillmd) 。
- **PRM 评分用 majority vote** —— 见 [05.05](./05-关键设计决策.md#55-为什么-prm-用多投票-majority-vote) 。
- **Nacos 作为可选后端** —— 见 [05.06](./05-关键设计决策.md#56-为什么-nacos-是可选后端不是默认) 。

## 六、阅读建议(本图怎么用)

- 看到 "session" 概念时,先想"一段对话"——一次用户发起到 `session_done=true` 的完整轨迹。
- 看到 "skill" 概念时,先想"`skills/<name>/SKILL.md`"——一个目录一个 skill。
- 看到 "Agent 框架"时,想"OpenAI / Anthropic 协议的 client 端"——它本身和 SkillClaw 没耦合,SkillClaw 通过改写它的 config 来劫持流量。
