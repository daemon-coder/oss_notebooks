# 关键设计决策

> 这一章回答"为什么这样写而不是另一种"。每个决策都基于源码 + 注释 + commit history 的反推,不在 README 营销段落里。

## 5.1 为什么是双进程 + 共享存储?

**决策**:Client 进程(`skillclaw`)和 Evolve Server 进程(`evolve_server`)是两个独立 Python 进程,通过**共享对象存储**通讯,**不**走 RPC / 消息队列 / 共享内存。

**反方方案**:
- 方案 A:单进程,所有逻辑在一个 daemon 里。问题:LLM 调用慢(分钟级),会阻塞代理;进程重启影响所有用户的 session 上传。
- 方案 B:RPC(client → server)。问题:部署时需要端口、鉴权、TLS、心跳——一个本地小工具用不上。
- 方案 C:消息队列(Kafka / Redis)。问题:多一个依赖,不适合"一个 docker 跑起来就完事"的工具定位。

**正方选择 + 后果**:
- ✅ 部署简单:evolve server 可以跑在另一台机器甚至另一个云,只要能访问 bucket 就行。
- ✅ 进程隔离:evolve server 跑 LLM 失败 / OOM / 卡死,不影响 client 代理的实时请求处理。
- ✅ 自然解耦:client 不知道 server 跑几次、是否在跑;server 不知道 client 有几个。
- ⚠️ **最终一致性**:session 上传 → server drain → 写新 skill → client pull 有一个**异步**链路,不是强一致。这要求所有读操作都是"乐观"——读不到就用本地的旧 skill。
- ⚠️ **没有 RPC**,所以 client 触发 evolve server 走的是"POST /trigger" HTTP,但这是**可选的**(周期轮询也能跑)。

**关键代码**:
- Client 端触发:`api_server.py:3116` `_trigger_evolve` (走 `evolve_server_url`)
- Server 端入口:`engines/workflow.py:1028` `create_http_app`(`/trigger` 端点定义在 `:1034`–`:1035`;只有 `--port` 才启 HTTP)
- 周期 vs 触发:`evolve_server/__main__.py:main`(`--once` 一次 / 默认周期 / `--port` 周期+HTTP 三选一)

## 5.2 为什么是 session 级别聚合,不是 turn 级别?

**决策**:`aggregate_sessions_by_skill` 把"整个 session"塞进它引用的 skill 的组,而不是按 turn 拆。

**反方方案**:
- Turn 级别:每个 turn 单独打"贡献了哪个 skill"。
- Token 级别:每个 token / 句子标注 skill 来源。

**正方选择**:
- ✅ session 是**有意义的单元**——一次用户发起到 session_done 的完整对话;LLM 看到的是一个完整上下文。
- ✅ turn 级别会让"用户在中间改了方向"或"在多 skill 之间切换"的复杂情况难以处理。
- ✅ 标注成本低(只在 session 末尾记 `_skills_referenced: set`)。
- ⚠️ 但 **session 级别意味着 effectiveness 是聚合信号**——如果一个 session 注入了 skill A 和 B,PRM 评 -1,你不知道是 A 还是 B 的问题。这是"反馈稀疏性"代价。

**关键代码**:
- 聚合:`pipeline/aggregation.py:16` `aggregate_sessions_by_skill`
- session 边界:`api_server.py:202` `_resolve_session_done`
- session 累积:`api_server.py` 内 `_session_turns` 内存结构

## 5.3 为什么 workflow 是默认引擎?

**决策**:`--engine workflow` 是 `evolve_server` 的默认引擎,`--engine agent` 是 opt-in。

**反方方案**:agent 引擎让 LLM 自己用工具编辑 skill,更"通用"。

**正方选择**:
- ✅ **可控性**:workflow 是结构化流水线(摘要→聚合→进化),每步可观测、可调试;agent 引擎是黑盒。
- ✅ **成本**:agent 引擎每 session 跑一次 OpenClaw 子进程,可能 1-5 分钟,几十次 LLM 调用;workflow 是 3-5 次 LLM 调用,秒级。
- ✅ **可降级**:workflow 任一步失败可以"跳过"继续;agent 失败就整个 fail。
- ✅ **审计**:workflow 的 `set_evolve_debug_dir` 把每次 LLM 调用的 system/user/raw 都落盘,排查方便;agent 的诊断靠 workspace + 子进程日志。
- ⚠️ agent 引擎**也有它的场景**:跨多 session 引用 / 需要 grep 已有 skill / 需要反复试错的复杂情形。

**关键代码**:
- 派发:`evolve_server/__main__.py:_build_server`
- workflow 主类:`engines/workflow.py:52`
- agent 主类:`engines/agent.py:133`
- 默认 engine:`evolve_server/core/config.py:engine` 默认 `"workflow"`

## 5.4 为什么 skill 就是 SKILL.md?

**决策**:一个 skill = 一个 `SKILL.md` 文件(YAML frontmatter + Markdown body)+ 可选 `scripts/` `references/` `assets/`。

**反方方案**:
- JSON / YAML 内联(单文件)
- 多文件结构但不用 Markdown(自家格式)
- 数据库表(每行一个 skill,字段化)

**正方选择**:
- ✅ **生态兼容**:`SKILL.md` 格式跟 OpenClaw、Pi coding-agent、AgentSkills 都兼容;SkillClaw 不是孤岛。
- ✅ **人可读**:维护者可以 `cat` 一个 skill 看,直接 `vim` 编辑,git diff 友好。
- ✅ **LLM 可读**:Markdown 是 LLM 训练数据中最多最熟的格式,不需要额外 schema 解释。
- ✅ **bundle 化**:`scripts/` `references/` `assets/` 打包后是同质化的"文件",可以走通用的 `bundle_tree_sha256` 增量同步。
- ⚠️ 不擅长"skill 之间有复杂关系图"——目前 skill 之间只通过 Markdown 内的相对路径引用,没有中心化关系数据库。

**关键代码**:
- 解析:`skill_manager.py:53` `_parse_skill_md`
- 构造:`evolve_server/core/utils.py:103` `build_skill_md`
- bundle 序列化:`skill_bundle.py`

## 5.5 为什么 PRM 用多投票 majority vote?

**决策**:`PRMScorer` 调 LLM judge `prm_m`(默认 3)次,取 majority vote 作为最终分。

**反方方案**:
- 单次 judge(便宜但不稳)
- 加 chain-of-thought(贵但解释性好)
- 训练专用 PRM 模型(项目定位用不上)

**正方选择**:
- ✅ **稳定性**:`±1` 的判断比"软分数"更稳,majority vote 抵御单次 LLM 偶发偏差。
- ✅ **可降级**:某次 vote 失败(`None`)不阻塞聚合。
- ✅ **成本可控**:`prm_m=3` 比 `prm_m=5` 便宜很多,效果差距不大。
- ✅ **可解释**:返回 `votes=[1, -1, 1]` → score=1,直接看到分歧。
- ⚠️ 仍然**是 LLM judge**,本身可能偏置(比如偏向"我(LLM)生成的回复")。SkillClaw 不解决 judge 偏置,只把"分歧暴露"。

**关键代码**:
- 投票聚合:`prm_scorer.py:120` `_majority_vote`
- 异步并行:`prm_scorer.py:155` `evaluate` (`asyncio.gather` 跑 prm_m 次)
- 解析主格式:`prm_scorer.py:98` `_parse_prm_score`(`Score: N` 优先,`\boxed{N}` 兜底)

## 5.7 为什么 "保守编辑" 是 LLM prompt 的核心?

**决策**:`_EVOLVE_FROM_SESSIONS_SYSTEM`(200+ 行)明确告诉 LLM:

- 改 skill 时**只改 evidence 明确指出**的地方
- **保留**所有 API 细节(endpoint / port / payload format)
- **不**加"与失败无关的 best practice"
- **不**删除"已经有但 agent 没用到"的信息
- 不确定时,**skip > 乱改**

**反方方案**:让 LLM 自由编辑(简单 prompt)。

**正方选择**:
- ✅ **可逆性差**:skill 是给所有用户用的(团队共享),改坏了影响所有人;保守编辑"宁愿不改也别改坏"。
- ✅ **agent 失败 ≠ skill 失败**:`_EVOLVE_FROM_SESSIONS_SYSTEM` 明确区分 "skill problem / agent problem / environment problem",避免把 agent 不会用 skill 当成 skill 写得差。
- ✅ **删错的代价 > 改漏的代价**:少改 / 漏改可以下次改;删错了就丢了。
- ⚠️ 保守也意味着**反应慢**——某个 skill 真的"过时"了,可能需要多次 session 累积 evidence 才会被改。

**关键代码**:
- evolve system prompt:`evolve_server/pipeline/execution.py` 顶部(200+ 行)
- merge system prompt:`evolve_server/pipeline/execution.py` 顶部 `_MERGE_SKILL_SYSTEM`
- create system prompt:`evolve_server/pipeline/execution.py` 顶部 `_CREATE_FROM_SESSIONS_SYSTEM`

### 附:`_EVOLVE_FROM_SESSIONS_SYSTEM` 关键 prompt 节选

下面是 SkillClaw "保守编辑" 世界观的具体措辞(从 `pipeline/execution.py:58-192` 节选,已略去重复段落):

**1) 4 个 action 的开场白**(让 LLM 知道"做什么决定"):

> Analyze the session evidence alongside the current skill content, then decide the best course of action:
>
> 1. **improve_skill** - The skill content needs targeted edits based on the session evidence (for example missing guidance, outdated information, or unclear instructions). Produce the updated skill.
> 2. **optimize_description** - The skill body content is fine, but its description causes it to be matched to wrong tasks. Rewrite ONLY the description for more precise triggering. Do NOT change the body content.
> 3. **create_skill** - The session evidence reveals a recurring pattern, capability gap, or reusable strategy that does NOT belong in the current skill. A brand-new, separate skill is needed. The current skill remains unchanged.
> 4. **skip** - The skill is working well enough, or the evidence is too weak or ambiguous to justify changes. No action needed.

**2) Editing principles(编辑原则)**——核心"保守"在这里:

> - Treat the CURRENT skill as the source of truth, not as a rough draft to be rewritten.
> - Read the original skill first, then the session evidence.
> - Default to targeted edits, not rewrites.
> - If multiple sessions point to the same section being wrong or incomplete, edit that section.
> - Preserve the original structure, heading order, terminology, and effective guidance, especially parts supported by successful sessions.
> - Only rewrite an entire section if the evidence shows that section is materially wrong.
> - If the skill contains concrete API details (endpoints, ports, payload schemas, tool names) that are factually correct, KEEP them even if the agent did not use them well. These details are the skill's core value.

**3) Hard constraints(硬约束)**——明确禁止的"反模式":

> - Do NOT casually change task API contracts, ports, endpoints, output paths, payload formats, or required filenames. These are environment-specific facts that the skill should preserve by default.
> - Do NOT remove core capabilities, API references, command patterns, or tool-usage examples unrelated to the observed failures.
> - Do NOT turn the skill into a different skill with a different purpose.
> - Do NOT rewrite the whole skill from scratch.
> - Do NOT impose a new template, new mandatory section structure, or a different writing style unless the evidence requires it.
> - Do NOT add generic best-practice guidance (for example rate-limit handling, retry logic, state management, or caching) that the agent should handle on its own.

**4) Distinguishing skill problems from agent problems(关键判断)**——这条是 SkillClaw "编辑哲学" 的灵魂:

> Not every failure is a skill deficiency. Before editing, consider whether the failure was caused by:
> - **The skill** (wrong, missing, or misleading guidance) → edit the skill.
> - **The agent** (subagent misuse, unnecessary restarts, context overflow, or not reading the skill properly) → these are agent-level issues; do NOT bloat the skill with agent-runtime advice.
> - **The environment** (mock API instability, network flakiness, docker quirks) → add a brief note if repeated.
>
> Critical anti-pattern to avoid: if the skill ALREADY contains correct environment information (API endpoints, ports, payload formats, tool names) and the agent failed because it did NOT use that information, that is an AGENT problem, not a skill problem. Do NOT delete the correct API information from the skill and replace it with instructions like "go read utils.py" or "inspect the mock service code". The whole point of the skill is to save the agent from having to discover those details.
>
> When in doubt, prefer **skip** over a speculative edit.

**5) Output format**——明确"4 个 action 对应的 JSON shape",LLM 严格按这个返回,客户端 `pipeline/execution.py:_parse_evolve_result` 严格校验:

- `improve_skill` → `{action, rationale, skill: {name, description, content, category, edit_summary}}`
- `optimize_description` → `{action, rationale, skill: {name, description}}`
- `create_skill` → `{action, rationale, skill: {name, description, content}}`(name **必须**不等于 `{skill_name}` 也不在已有列表里)
- `skip` → `{action, rationale}`

> 完整 200+ 行 prompt 见 `evolve_server/pipeline/execution.py:58-192`。`_CREATE_FROM_SESSIONS_SYSTEM` 在 `:193-` 起,`_MERGE_SKILL_SYSTEM` 在 `:25-` 起,都遵循同样的"保守 + JSON out" 风格。

## 5.8 为什么 "client idle 才跑 validation"?

**决策**:`ValidationWorker` 必须等 client idle(`is_idle_for_validation`)才接单;`force=True` 可跳过。

**反方方案**:随时跑 validation(简单)。

**正方选择**:
- ✅ **不抢用户资源**:validation 跑 LLM + 写共享存储,跟用户对话抢资源,会让对话卡顿。
- ✅ **优先级合理**:用户的活 > 团队的活。
- ⚠️ "idle" 判定是启发式(`last_request_age > N` + 无 active session),不是严格保证。

**关键代码**:
- Idle 协议:`validation_worker.py:25-29` `IdleStateProvider`
- 实现:`api_server.py` 中 `is_idle_for_validation` 等方法
- 默认 idle 时间:`config.py:validation_idle_after_seconds=300`(5 分钟)

## 5.9 为什么 session 关闭 ≠ 上传?

**决策**:
- session 关闭 = "停止累积,标记 inactive"(清理内存)
- session 上传 = "把累积的 turns 写到共享存储"(`sharing_session_upload_interval` 控制节奏)

**反方方案**:session 关闭立刻上传。

**正方选择**:
- ✅ **去抖动**:用户可能 1 秒内"误触"多次 session_done,立刻上传会重复写。
- ✅ **批量友好**:每个 user_turn 都写一次太频繁,周期 N 个 user_turn 写一次。
- ✅ **可恢复**:`sharing_session_upload_interval=0` 时不自动上传(关 sharing 时也不上传),session 关闭只清内存。
- ⚠️ **session 关闭事件触发不了上传**——这点是反直觉的,需要文档明确说。

**关键代码**:
- 关闭路径:`api_server.py` `_finalize_session`
- 周期上传:`api_server.py:3106` `_maybe_upload_session_snapshot`
- 配置:`config.py:sharing_session_upload_interval`

## 5.10 为什么用 `dataclass` 而不是 `pydantic`?

**决策**:`SkillClawConfig` 和 `EvolveServerConfig` 都是 `@dataclass`,不用 pydantic。

**反方方案**:pydantic 提供自动校验、JSON schema、IDE 提示。

**正方选择**:
- ✅ **轻量**:不引入 pydantic 依赖(`pyproject.toml` 没有)。
- ✅ **显式**:`__post_init__` 写归一化逻辑,行为可读;pydantic 的 `validator` 装饰器在大型配置上不直观。
- ✅ **跟 pyyaml 直接对接**:`yaml.safe_load` → dict,再 `dataclass(**dict)` 即可;pydantic 需要 `.parse_obj`。
- ⚠️ **没有自动校验**——`_normalize_*` 静态方法手动做(在 `__post_init__` 里调)。

**关键代码**:
- 客户端 config:`skillclaw/config.py`(整文件)
- 服务端 config:`evolve_server/core/config.py:60`
- 归一化:`evolve_server/core/config.py:115` `__post_init__`

## 5.12 为什么 SkillClaw 不训练模型权重?

**决策**:skill 进化是"写文档",不是"调模型参数"。

**反方方案**:用 LoRA / fine-tuning 让模型"内化"skill。

**正方选择**:
- ✅ **可读可审**:skill 文档是"人 + LLM 都能读"的形式,改错了能查。
- ✅ **可逆**:删一个 skill 比"撤销 fine-tune"容易得多。
- ✅ **跨模型**:skill 文档对任何 LLM 都生效;fine-tune 绑死一个 base model。
- ✅ **无训练成本**:不需 GPU、不需训练数据。
- ⚠️ skill 文档**依赖**于 LLM 能"读懂"它。如果 LLM 上下文窗口太短 / 注意力分散,skill 注入可能没用。

## 5.13 为什么 PRM 是 turn-level,不是 session-level?

**决策**:`PRMScorer` 给"单 turn 回复"打分,不是"整段 session"。

**反方方案**:session 结束才打一个综合分。

**正方选择**:
- ✅ **粒度细**:"这次用了 skill A,PRM 给 -1;下次同 skill 又给 +1"——可以学到 skill 级别的效果。
- ✅ **实时反馈**:`SkillManager.effectiveness` 是 running average,新数据立刻影响下次排序。
- ⚠️ **稀疏性**:每个 turn 都要 1 次 LLM judge(prm_m=3 次),开销大。
- ⚠️ **judge 可能误判**:单 turn 的"是否有用"是个粗糙指标,可能跟 skill 本身无关(取决于用户问的、agent 状态等)。

## 5.14 为什么 session_id 是 Agent 显式传,不是推断的?

**决策**:`session_id` 从 body 或 header 读,Agent 没传时(`_resolve_tui_session`)按 IP / port 启发式推断。

**反方方案**:server 端自动识别"同一 IP 短时间内 = 同一 session"。

**正方选择**:
- ✅ **显式优先**:`session_id` 是用户/Agent 的意图,启发式只是兜底。
- ✅ **跨 IP 友好**:用户切换网络(家里 WiFi → 咖啡厅)时,session 不会"误断"。
- ⚠️ Agent 必须**配合**传 session_id 才能正确聚合。

## 5.15 为什么 `claude` 走 `ANTHROPIC_BASE_URL`,不是 base_url 替换?

**决策**:`_configure_claude` 改 `~/.claude/settings.json` 的 `env.ANTHROPIC_BASE_URL`。

**反方方案**:跟 OpenAI-based Agent 一样 patch provider 配置。

**正方选择**:
- ✅ **尊重 Agent 原生配置**:Claude Code 的"上游 URL"是 env 变量,不是 provider 字段;改 env 是 Claude Code 设计的方式。
- ✅ **不需要新增 provider 条目**:只是改 base URL,其他配置不动。

## 5.16 为什么 dashboard 默认是 `127.0.0.1`,不是 `0.0.0.0`?

**决策**:`config.dashboard_host = "127.0.0.1"`。

**反方方案**:默认 `0.0.0.0`,允许远程访问。

**正方选择**:
- ✅ **安全默认**:dashboard 读本地 session 内容(可能含敏感信息),不该默认开放。
- ✅ **本机优先**:SkillClaw 定位是"本机工具",dashboard 是"本机看"。
- ⚠️ 想远程看,改 `dashboard_host: "0.0.0.0"` + 配 firewall。

## 5.17 为什么 `_call_storage` 用 `run_in_executor`?

**决策**:evolve server 调同步 storage(boto3 / oss2 / Nacos)时,扔到线程池跑,避免阻塞 asyncio 事件循环。

**反方方案**:`boto3` / `oss2` / `Nacos` 都换成 async SDK,或在 asyncio 循环里直接调。

**正方选择**:
- ✅ **不改依赖**:boto3 / oss2 都有官方同步 SDK,但异步版不成熟 / 缺功能。
- ✅ **简单**:`run_in_executor(None, sync_fn, ...)` 一行包装。
- ⚠️ **线程开销**:每次 LLM 之间穿插 storage I/O 会创建/回收线程(默认 ThreadPoolExecutor 池)。`evolve_batch_size=20` 一次 20 个 session 就是 20 个并发 storage 调用。
- ⚠️ **无 cancellation**:sync SDK 不响应 `asyncio.CancelledError`,evolve server 关闭时线程可能不优雅退出。

## 5.18 为什么 "1 个 skill = 1 个文件夹" 而不是 "1 个 skill = 1 个 .md"?

**决策**:每个 skill 是 `<skills_dir>/<name>/SKILL.md`,不是 `<skills_dir>/<name>.md`。

**反方方案**:平铺,每个 skill 单独 .md 文件。

**正方选择**:
- ✅ **天然 bundle**:`scripts/` `references/` `assets/` 是同级目录。
- ✅ **git 友好**:`git add scripts/`,而不是 `.md` 内嵌代码。
- ✅ **OpenClaw 兼容**:OpenClaw 期望 `<skill>/SKILL.md` 结构,SkillClaw 跟随。
- ⚠️ **文件数多**:50 个 skill = 50 个 `SKILL.md` + 50 个目录(在 `ls` 时不好看)。

## 5.19 一些"看起来能做但没做"的项

- **没有 skill version 控制(客户端)**:client 拉到的总是 `latest` 远端版本;要回滚得手动从 `skill_versions/<name>/v<N>/` 拷。
- **没有 skill 之间的依赖图**:skill A 不能"依赖" skill B;只能 Markdown 内的"see also"。
- **没有 user-level override**:用户的本地修改(没 push)会被 pull 覆盖;没有 .gitignore 风格的文件级保留。
- **没有 rate limiting 内部机制**:依赖上游 LLM 的 rate limit;自己**不**做 RPM throttle。
- **没有 SSO / RBAC**:任何能访问 bucket 的人都能读/写 skill;权限走 bucket ACL(OSS / S3 / Nacos 自带)。
- **没有 audit log**:除了 `evolve_history.jsonl` 的 evolve 决策日志,skill 修改、validation 决策没有独立 audit 表。

## 5.20 决策之外的"非决策"

有些事不是 SkillClaw "选择不做",而是"目前没做"——文档要区分:

- **多语言**:目前 skill 文档默认英文(LLM 输出),但 SkillClaw 不阻止你写中文 skill。
- **图像 / 视频 skill**:bundle 支持 `assets/`,但 `SkillManager.retrieve` 只用 name+description+content 文本做 embedding,**不**看图像内容。
- **Skill hot-swap 持久化**:`refresh_if_changed` 改了 generation,但正在处理的请求用的是旧 generation;没有 transactional swap。

## 5.21 总结:SkillClaw 的"哲学"

如果让我用 3 句话总结 SkillClaw 的工程哲学:

1. **保守优于激进**——LLM 改 skill 时倾向"不动 / 小改",skill 验证倾向"等多人同意才 publish",session 上传倾向"周期批量不立即"。
2. **可逆优于最优**——backup + rollback、processed_log + skip-on-rerun、config 默认 + explicit override,都比"找一个最聪明的方案"重要。
3. **可观测优于可解释**——`set_evolve_debug_dir` 落每次 LLM 调用、PRM votes 全打 log、PRM 输出也存——宁可"数据多",不要"黑盒"。
