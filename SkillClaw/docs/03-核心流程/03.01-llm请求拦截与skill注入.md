# 03.1 LLM 请求拦截与 skill 注入

> 这是 SkillClaw 的"心脏"流程。Agent 的每一次 LLM 调用都要经过这条路径。

## 设计动机

LLM Agent 的核心是"调用 LLM → 拿回复 → 决定下一步"。SkillClaw 想要在**不修改 Agent 代码**的前提下,在 LLM 调用这一步注入额外上下文(相关的 skill 文档)。最简单的办法是:**让 Agent 把 LLM 请求发到本地代理,代理在转发给真实 LLM 之前,把 skill 拼到 system prompt 里**。

为此,SkillClaw 要解决三件事:

1. **协议兼容**:Agent 用的可能是 OpenAI `/v1/chat/completions`、Anthropic `/v1/messages`、OpenAI `/v1/responses` 之一。代理要会所有三种,响应体也要对得上。
2. **skill 检索**:用户输入"用 Python 写一个 K8s 客户端",代理要从几百个 skill 里挑出 top-K 相关的塞进 system prompt。
3. **透明转发**:除了"加了 skill 文本"之外,代理必须把所有其他字段原封不动转给上游 LLM(温度、tool、stream、tools schema 等),否则 Agent 跑起来行为不一致。

## 核心概念

| 概念 | 定义 | 关键引用 |
|---|---|---|
| **代理端口** | `proxy.port`,默认 `30000` | `config.py:79` |
| **暴露的模型名** | `served_model_name`,默认 `skillclaw-model` —— Agent 把 LLM 请求的 model 字段改成这个值,SkillClaw 看到才接 | `config.py:81` |
| **本地 skill 库** | `skills_dir`,默认 `~/.skillclaw/skills`,每个 skill 一个 `SKILL.md` | `config.py:54` |

| **技能效果分(effectiveness)** | `effectiveness = positive_count / inject_count`,默认 0.5(从未被评过) | `skill_manager.py:230` |
| **Turn** | 一对 user + assistant 消息(可能含 tool_calls / tool_results) | 全章 |
| **Session 边界** | 请求里 `session_done: true` 标志着会话结束(也走 idle 超时) | `api_server.py:202` `_resolve_session_done` |

| **Streaming 注入** | 流式响应也支持 skill 注入:先发 "header chunks" 含 skill 块,再发 "body chunks" | `api_server.py:714` `_assemble_streaming_chat_completion` |

## 实现流程(pseudo-code)

```
# api_server.py: POST /v1/chat/completions
def handle_chat_completions(body, headers):
    # 1. 规范化 + 字段提取
    body = _normalize_messages_for_template(body.messages)
    protocol = detect_protocol(body)              # "chat" | "responses" | "anthropic_messages"
    session_id, session_done, turn_type = extract_session_meta(body, headers)
    
    # 2. session 累积:把历史 turn 拼到 messages 头部
    prior_turns = session_store.get(session_id) or []
    messages = prior_turns + body.messages
    
    # 3. skill 检索(只在 main turn)
    if turn_type == "main" and config.use_skills:
        task = _extract_last_user_instruction(messages)
        candidates = skill_manager.retrieve(task, top_k=config.skill_top_k)
        skill_block = _format_skills_for_injection(candidates)
        system_prompt = merge_system(messages, skill_block)
        skill_names_recorded = [s["name"] for s in candidates]
    else:
        skill_names_recorded = []
    
    # 4. 转发 upstream(可能 streaming)
    response = upstream.chat(messages, model=config.llm_model_id, stream=body.stream)
    
    # 5. 后置钩子(async fire-and-forget)
    asyncio.create_task(_post_request_hooks(
        session_id, turn_type, body, response, skill_names_recorded
    ))
    
    # 6. 返回 response(保持原协议 shape)
    return response
```

`_post_request_hooks` 是关键的后台行为,见 [03.02](./03.02-会话录制与归档.md)。

### skill 注入到 system prompt 的具体位置

注入发生在"把 messages 发给上游 LLM 之前"一步,有三种典型策略(代码里挑的是"合并到 system"):

```
原 messages:
[
  {"role": "system", "content": "You are Hermes..."},
  {"role": "user",   "content": "用 Python 写 K8s 客户端"},
  ...
]

注入后(伪码):
[
  {"role": "system", "content": "You are Hermes...\n\n<available_skills>\n  <skill>\n    <name>python-k8s-client</name>\n    <description>Use when... NOT for: simple scripts.</description>\n    <body>...</body>\n  </skill>\n  ...\n</available_skills>"},
  ...
]
```

具体拼接函数见 `skill_manager.format_skills_block`(类内方法)+ `api_server.py` 在请求处理中的拼装点(以 `_format_*` 为关键字搜索)。

## 常见误区

1. **"skill 是直接当 system prompt 用的"** —— 错。SkillClaw 拼到一个独立的 `<available_skills>` 块里,放在原有 system 之后,让 LLM "看到但不强制使用"。`use_skills: false` 可以完全关闭这个能力(`config.py:53`)。
2. **"每个 turn 都重新检索"** —— 是的,但 `SkillManager.refresh_if_changed` 会在文件变化时**只**重做 IO,embedding 缓存(若启用)命中时不重算。
3. **"streaming 时不能注入"** —— 可以。代码分两块:非流式直接拼;流式先发送"header chunks"再发送"body chunks",skill 块是 header 的一部分。`api_server.py:714` 的 `_assemble_streaming_chat_completion` 可见实现。
4. **"`session_id` 必须是客户端生成"** —— 不是。它是 SkillClaw 用来聚合"一段连续对话"的内部 key。Agent 没传时,代理会用启发式(同一 IP 短时间内复用 last session_id,见 `_SESSION_IDLE_CLOSE_SECONDS` 常量)推断,见 `_SESSION_IDLE_CLOSE_SECONDS = 180` 和 `_SESSION_SWEEP_INTERVAL_SECONDS = 15`(`api_server.py:79-80`)。
5. **"turn_type 必须是 main"** —— 不是。`turn_type: "side"` 的请求**不会**触发 skill 检索和 PRM 评分,主要用于过滤掉 Claude Code 内部的 `generate_session_title` 这类辅助调用。判定函数在 `_looks_like_session_title_response`(`api_server.py:215`)。
6. **"skill 注入会污染 tool_calls"** —— 不会。`_assistant_message_has_tool_calls` 严格区分"文本里嵌的工具调用"和"真正 tool_calls 字段",后者原样转发(`api_server.py:516`)。
