# 项目概述

> **关于 arXiv:2604.08377**:该论文([https://arxiv.org/abs/2604.08377](https://arxiv.org/abs/2604.08377))讨论 LLM agent 之间的 skill 迁移与共享问题(同类系统的学术背景)。本文档**不**展开论文方法论,**只**覆盖 SkillClaw 的工程实现;想了解学术背景请直接读论文。SkillClaw 团队把论文作为"问题意识"参考,不声称实现遵循其方法。

## 一句话定位

> SkillClaw = LLM Agent 的 **OpenAI/Anthropic 协议代理** + **会话录制层** + **skill 进化器**。
> 它让一个 Agent 在真实使用中产生"技能",并让技能在多用户、多设备、多 Agent 之间**集体共享 + 持续进化**。

## 典型使用场景

### 场景 A:个人单用户

只有 client,自己用 Hermes / Codex / Claude Code 跟模型对话。SkillClaw 在本地抓取所有 LLM 请求,自动注入相关的 skill,等会话结束把整段 session 落盘。**不部署 evolve server** 也能用——只是 skill 不会"自动进化",只会从你手动 pull 进来的 skill 里检索。

### 场景 B:个人 + 自动进化

个人本机既跑 client 也跑 evolve server(配 `interval=300` 之类的),共享存储用 `local`(指一个本机目录)。每个 5 分钟,evolve server 读本地 session,产出新 skill 写回本地,client 下次启动就会拉到。

### 场景 C:团队共享

N 个用户都装 client,共享一个 OSS bucket。运维侧只跑一个 evolve server。所有用户的 session 都会进同一个 bucket 的 `sessions/<user_alias>/...` 命名空间;evolve server 统一消费,产出的 skill 写到 `skills/<name>/SKILL.md`;每个用户 client 启动时自动 `pull` 拉新 skill,本地落盘到 `~/.skillclaw/skills/<name>/`。

## 关键不变量(读完一遍代码后提炼的设计承诺)

1. **协议层不改变用户视角**。Agent 配置好 base_url 指向 SkillClaw 之后,**不**应该感知到 SkillClaw 的存在——所有 OpenAI / Anthropic 的请求/响应体保持原样(可能多了一些非标字段如 `session_id`,但 transport 兼容)。
2. **共享存储是唯一跨进程边界**。Client 和 Evolve Server 之间没有 RPC、没有共享内存、没有消息队列,只通过"读 key / 写 key"交互。
3. **skill 文档是 SKILL.md 文本**。YAML frontmatter(必须含 `name` + `description`)+ Markdown body。这是和 OpenClaw / Pi coding-agent / AgentSkills 共享的格式,不发明新格式。
4. **session 数据是 JSON Lines**。每条 session 一个 JSON 对象,落 `records/` 目录或共享存储的 `sessions/<user>/<session_id>.json`。
5. **LLM 调用的最终 prompt 都是 JSON in / JSON out**。所有 evolve 决策都收敛到结构化 JSON,客户端代码严格 parse,失败时走降级路径(`pipeline/execution.py:423` 的 `_parse_evolve_result`)。

## 核心不做什么

- **不做** Agent 训练 / 微调。所有 skill 进化都是 prompt 驱动的"文档编辑",不更新模型权重。
- **不做** Skill 之间的复杂图结构。每个 skill 是独立文件夹,引用靠 Markdown 内的相对路径,没有中心化的关系数据库。
- **不做** 强一致的事务。`SkillHub.pull` 用"先 backup,再 mirror,再 restore on failure"做软一致性,没有两阶段提交。
- **不做** 实时推理路径上的强校验。所有 skill 注入决策在请求处理时发生,不做额外的一致性检查——内容错误由 PRM 评分 + 下次 evolve 修正。
