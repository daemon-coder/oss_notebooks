# 33 · 共享层与存储适配

## 这一章讲什么

evolve server 怎么读 / 写共享存储、3 种 ObjectStore 后端（local / S3 / OSS）+ 1 个独立的 skill-only Nacos 路径怎么选型、bundle v1 协议的字段定义与算法、`--mock` 模式是什么。

读完这一章，读者能：

- 说出 3 种 ObjectStore 后端的选型表（什么场景用哪个），并知道 Nacos 为何单列
- 画出 `oss_helpers` → `object_store` → SDK 三层调用链 + Nacos 旁路
- 解释 `--mock` 模式与 `backend=local` 的区别（哪条路径走 `LocalBucket`、哪条走 `LocalObjectStore`）
- 写出 bundle v1 协议的 6 个字段值、谁写谁读、什么时候算 `tree_sha256`
- 解释 Nacos-only 模式下"skill 走 Nacos、session 走 OSS"的写盘行为

## 它在整个系统的哪个位置

3 个源文件 + 1 个客户端旁路、**2 条调用链**（ObjectStore 主链 + Nacos 旁路）：

```
evolve_server (workflow.py / agent.py)
  ├── 主链 (ObjectStore 抽象)
  │   → engines/common.py:_build_bucket        (按 mock / Nacos / 普通分流,见 §5)
  │   → evolve_server/storage/oss_helpers.py    (16 个业务包装函数,见 §4)
  │       → skillclaw/object_store.py           (ObjectStore 接口 + 工厂,见 §2)
  │           → boto3 (S3) / oss2 (OSS) / LocalObjectStore (本地)
  │   → evolve_server/storage/mock_bucket.py    (mock 模式的 LocalBucket,见 §3.1)
  └── 旁路 (Nacos skill-only, 绕过 ObjectStore)
      → NacosSkillClient (skillclaw/nacos_skill_hub.py)
          → Nacos HTTP REST API (/v3/admin/ai/skills/...)
```

文件清单 + 行数：`evolve_server/storage/oss_helpers.py`（263 行）+ `evolve_server/storage/mock_bucket.py`（104 行）+ `evolve_server/engines/common.py`（112 行 + EvolveEngineMixin._build_bucket）+ 客户端 `skillclaw/object_store.py`（255 行）+ 旁路 `skillclaw/nacos_skill_hub.py`（NacosSkillClient + NacosSkillHub）。

**为什么分主链 + 旁路**：Nacos 走 HTTP REST（label-based 路由 + namespace 隔离 + 版本历史），不是 OSS 兼容的对象存储协议——强行抽象成 ObjectStore 会丢失 Nacos 的 label-based query、版本历史等特性，且 Nacos 的"key"长度 / value 大小限制（KB-MB 级）跟 OSS / S3 的 GB 级不在一个量纲。所以 Nacos 单独走 `NacosSkillClient` + `NacosSkillHub`，详见 [20 · 共享存储与同步 §8](../02-客户端共享层/20-共享存储与同步.md)。

## 设计目的

让 evolve server **沿用**客户端的对象存储抽象（同一份 `ObjectStore` 接口）——evolve server 读同一份对象存储是为了和客户端 view 一致，避免本地 / 远端视图分裂；并给"只跑在本地"的开发 / 测试场景提供 `LocalBucket` / `LocalObjectStore` 替代品。Nacos 不实现 `ObjectStore` 接口，它**单独**走 `NacosSkillClient` + `NacosSkillHub`，原因见上一段。

## §1 · 高层抽象：3 种 ObjectStore + 1 个 Nacos 旁路

evolve server 在存储上只有"3 + 1"种选择：3 种走 `ObjectStore` 接口（local / S3 / OSS），1 种走 Nacos 旁路（skill 资产专用，绕过 `ObjectStore`）。

| 后端 | 触发条件（用户视角） | evolve server 怎么用 | 客户端怎么用 | 适用 |
|---|---|---|---|---|
| `local`（mock 模式） | `evolve-server --mock [--mock-root <dir>]` | `LocalBucket(mock_root)`（`mock_bucket.py`） | （无） | 单机自用 / 调试（`LocalBucket` 比 `LocalObjectStore` 早存在、行为更直接，且 mock 模式不依赖 cfg / 不打网络） |
| `local`（`backend=local`） | `sharing.backend=local` + `sharing.local_root=...` | `LocalObjectStore(local_root)`（`object_store.py`） | `LocalObjectStore`（`SkillHub.object_storage_from_config` 内部 `from skillclaw.object_store import build_object_store`） | 团队开发 / 集成测试（走完整对象存储接口） |
| `s3` | `sharing.backend=s3`（或 `minio` / `r2` / `b2` / `s3-compatible`，自动归一到 `s3`，见 §2.1） | `S3ObjectStore(endpoint, bucket, ...)` | 同 | AWS S3 / MinIO / R2 / B2 |
| `oss` | `sharing.backend=oss` | `OSSObjectStore(endpoint, bucket, ...)` | 同 | Alibaba Cloud OSS |
| `nacos`（旁路） | `sharing.skill_backend=nacos`（同时仍需 `sharing.backend=oss` 等为 session / validation 走） | **不**走 `ObjectStore`——走 `NacosSkillClient` | `NacosSkillHub` | 团队用 Nacos 做 skill registry / 审核流 |

**两条 `local` 路径的边界**：

- `--mock` 走 `LocalBucket`（`evolve_server/storage/mock_bucket.py`）：完全不校验 `sharing.*` 配置、不读 cfg、不打网络、纯本地文件。给"evolve-server 第一次启动、没跑过 setup"的开发者用。
- `backend=local` 走 `LocalObjectStore`（`skillclaw/object_store.py`）：走完整 `ObjectStore` 接口，给"想跑完整 `ObjectStore` 抽象的集成测试"用。

两条路径**不能并存**——`_build_bucket` 看到 `mock=True` 直接返回 `LocalBucket` 而不走 `build_object_store`，详见 §5.1。

**`local` 路径的两个实现接口几乎一致**：都实现 `get_object` / `put_object` / `delete_object`；差异：`LocalBucket` **不**实现 `iter_objects`，list 时走 `LocalObjectIterator(LocalBucket, prefix)`（`os.walk` 走整树）；`LocalObjectStore` 自己实现 `iter_objects`（`Path.rglob`）。这是 mock 模式的历史设计（见 §3.3），不是技术债——`os.walk` 走整树能发现 `rglob` 在边界 case 漏掉的文件，但代价是性能差。

`MockBucket = LocalBucket`（向后兼容别名）、`MockObjectIterator = LocalObjectIterator`（向后兼容别名）。

## §2 · ObjectStore 三种后端实现

`ObjectStore` 接口（`skillclaw/object_store.py`）有 4 个方法：`get_object(key)` / `put_object(key, data)` / `delete_object(key)` / `iter_objects(prefix="")`。`data` 支持 `bytes` / `str`（utf-8 编码）/ `io.IOBase`（helper `_read_bytes` 统一）。`iter_objects` 按字典序 yield `ObjectInfo(key)`，不过滤文件后缀（要 `.json`-only 过滤由调用方负责，见 §4.1 `list_session_keys`）。

### §2.1 `build_object_store` 工厂

`object_store.py` 的 `build_object_store(*, backend, endpoint="", bucket="", access_key_id="", secret_access_key="", region="", session_token="", local_root="")` 是入口。

**关键规则**：

- 字符串先 `str(backend or "").strip().lower().replace("_", "-")` 再查表（大小写不敏感，下划线 / 连字符等价）
- `local` 必须有 `local_root`（否则 `ValueError("Local storage backend requires local_root.")`）
- `s3` 必须有 `bucket`（否则 `ValueError("S3 storage backend requires a bucket.")`）
- `oss` 必须有 `endpoint` + `bucket`（否则 `ValueError("OSS storage backend requires endpoint and bucket.")`）
- 用户没传 `backend` 时：先看 `local_root` 是否有值（→ `local`）→ 否则看 `endpoint` 是否含 `aliyuncs.com`（→ `oss`，否则 → `s3`）；都不匹配 → `ValueError("Unsupported storage backend: '<原始值>'.")`

**`normalize_backend` 别名映射表**（优先级：别名匹配 → 显式值 → local_root 启发 → endpoint 域名启发）：

| 用户输入（已 `lower()` + `replace("_","-")`） | 解析后 `resolved` | 必要参数 | 备注 |
|---|---|---|---|
| `"filesystem"` / `"fs"` | `"local"` | `local_root` | 别名 |
| `"local"` | `"local"` | `local_root` | 显式 |
| `"s3-compatible"` / `"minio"` / `"r2"` / `"b2"` | `"s3"` | `bucket` | 4 个别名都归一到 `s3`（MinIO 自托管、Cloudflare R2、Backblaze B2 走 S3 兼容协议） |
| `"s3"` | `"s3"` | `bucket` | 显式 |
| `"oss"` | `"oss"` | `endpoint` + `bucket` | 显式 |
| `""` + `local_root` 非空 | `"local"` | `local_root` | local_root 启发 |
| `""` + endpoint 含 `aliyuncs.com` | `"oss"` | `endpoint` + `bucket` | 域名启发 |
| `""` + endpoint 不含 `aliyuncs.com`（或空）+ bucket 非空 | `"s3"` | `bucket` | 默认 s3 |
| `""` + 任何参数都空 | `""` → `ValueError` | — | 无任何参数 |
| 其他（`"abc"` / `None`） | 原样回传 `resolved` | — | 进入 `if resolved == "local" / "s3" / "oss"` 都不命中 → `ValueError` |

### §2.2 `S3ObjectStore`

`object_store.py` 的 `S3ObjectStore`（`boto3` 后端，支持 AWS S3 + MinIO + R2 + B2）：

- **构造**：用 `boto3.session.Session(...空串 → 跳过)` 包装，空字段不传（让 boto3 走默认 credential chain），`session.client("s3", endpoint_url=endpoint or None, region_name=region or None)`。
- **`iter_objects`**：用 `paginator.paginate(Bucket=..., Prefix=...)` 拉所有 page（S3 `list_objects_v2` 一次最多 1000 个 key）→ `ObjectInfo(key)` yield 出去。paginator 内置指数退避 3 次 retry，永久错误（`AccessDenied` 等）**冒泡到调用方**（`oss_helpers.list_session_keys` 不 try/except 包裹 → evolve-server loop 模式会**整轮 raise 退出**，不等同于"持续重试"）。
- **`get_object` / `put_object` / `delete_object`**：单行 boto3 包装（`get_object` 返回的 `Body` 自带 `.read()`，与 `LocalBucket.get_object` 形状一致）。

**支持 MinIO / R2 / B2**：在 `sharing.backend` 字段写 `minio` / `r2` / `b2` / `s3-compatible` 之一，`normalize_backend` 都归一到 `s3`（见 §2.1 别名表），`endpoint` / `endpoint_url` 指向对应非 AWS endpoint。

### §2.3 `OSSObjectStore`

`object_store.py` 的 `OSSObjectStore`（`oss2` 后端，Alibaba Cloud OSS）：

- **构造**：`oss2.Auth(access_key_id, secret_access_key)` + `oss2.Bucket(auth, endpoint, bucket)`。`region` / `session_token` 参数**接受但忽略**（`del region, session_token`）——OSS 用 endpoint 区分 region，不支持 STS session token 直接传。
- **`iter_objects`**：用 `oss2.ObjectIterator(self._bucket, prefix=prefix)`。`oss2.ObjectIterator` 默认 `delimiter='/'` 但**仍递归**列所有 nested keys（不限制深度）——所以 `prefix='a/b/'` 实际列 `a/b/`、`a/b/c/`、`a/b/c/d/...` 全部。要列直接子项需显式设 `delimiter='/'` + 用 `list_objects` 接口的 `CommonPrefixes` 字段；本章 `oss_helpers` 用的是递归模式。
- **`get_object` / `put_object` / `delete_object`**：直接 `oss2.Bucket` 方法。`get_object` 返回的 `Object` 自带 `.read()`。

`OSSObjectStore` 自己实现了 `iter_objects`，所以 `oss_helpers.list_session_keys` 的 `hasattr(bucket, "iter_objects")` 命中，**不会走** `oss2.ObjectIterator` fallback 分支。fallback 存在的意义是：历史代码可能直接传 `oss2.Bucket` 对象（不经过 `OSSObjectStore` 包装），那走 fallback。

### §2.4 `LocalObjectStore`（`backend=local` 路径）

详见 §3.2（按"用途路径"而非"文件"组织——`LocalObjectStore` 是 `backend=local` 走的实现）。

## §3 · mock 与本地实现：两条 local 路径

`local` 在 evolve server 里有**两条**完全不同的实现路径：`--mock` 模式用的 `LocalBucket`（早于 `ObjectStore` 接口）+ `backend=local` 用的 `LocalObjectStore`（`ObjectStore` 接口标准实现）。两者**不是**别名，API 也不完全一致。

### §3.1 `--mock` 模式用的 `LocalBucket`

`evolve_server/storage/mock_bucket.py` 的 `LocalBucket`（`MockBucket = LocalBucket` 向后兼容别名）：

| 维度 | `LocalBucket` |
|---|---|
| 默认 root | `evolve_server/storage/mock/`（仓库内 directory，会被 git 跟踪，生产别用默认） |
| override | `LocalBucket(root=...)` 或 `--mock-root /path/to/dir` |
| `get_object(key)` 返回 | `_LocalObject(data, key)`（`data` 是 `bytes`，有 `.read() -> bytes` 和 `.key: str` 字段；**没有** `.size` / `.last_modified` / `.etag`） |
| `get_object` 异常 | `FileNotFoundError("LocalBucket: key not found: <key>")` |
| `put_object(key, data)` | `str` 用 utf-8 编码（**写死**，不能换编码） |
| `iter_objects(prefix)` | **没**实现——list 时由 `oss_helpers` 的 `hasattr` 兜底走 `LocalObjectIterator(LocalBucket, prefix)`（`os.walk` 走整树） |
| 路径分隔符 | `os.walk` 拿到的是 `os.sep`，内部 `.replace(os.sep, "/")` 统一成 `/` |

`LocalObjectIterator`（`os.walk` 走整树、sorted by filename、过滤 `prefix` 字符串前缀）：

```
class LocalObjectIterator:
    def __iter__(self):
        for dirpath, _dirs, filenames in os.walk(root):
            for fn in sorted(filenames):
                full = os.path.join(dirpath, fn)
                rel = os.path.relpath(full, root).replace(os.sep, "/")
                if rel.startswith(self._prefix):
                    yield _LocalObjectInfo(rel)
```

**为什么 `LocalBucket` 不实现 `iter_objects`**：mock 模式不追求 list 性能，且 `os.walk` 走整树能发现 `rglob` 在某些边界 case 漏掉的文件——这是历史设计取舍，不是技术债。但代价是 mock 模式下大目录 list 慢（**待核**是否要改用 `pathlib.Path.rglob`）。

### §3.2 `backend=local` 用的 `LocalObjectStore`

`skillclaw/object_store.py` 的 `LocalObjectStore`（`ObjectStore` 接口标准实现）：

| 维度 | `LocalObjectStore` |
|---|---|
| root | `LocalObjectStore(root=...)` 必须显式传（`build_object_store` 工厂要求） |
| `get_object(key)` 返回 | `_BytesObject(data, key)`（同样 `data` 是 `bytes`，有 `.read() -> bytes` 和 `.key: str`） |
| `get_object` 异常 | `FileNotFoundError("LocalObjectStore: key not found: <key>")` |
| `put_object(key, data)` | `_read_bytes` helper 统一处理 `bytes` / `str`（utf-8 编码） / `IOBase` |
| `iter_objects(prefix)` | **自己实现**——`Path.rglob("*")` 走所有子目录、过滤 `prefix` 字符串前缀（**不是路径段**）、`sorted(keys)` 后 yield `ObjectInfo(key)` |
| 路径分隔符 | `path.relative_to(root).as_posix()` 统一成 `/` |

**`_BytesObject` 和 §3.1 的 `_LocalObject` 不是同一个类**：前者是 `skillclaw/object_store.py` 私有、后者是 `evolve_server/storage/mock_bucket.py` 私有；命名风格不同因不同文件独立演进。两者**shape 一致**（`data: bytes` + `.read() -> bytes` + `.key: str`），可互换使用。

**`iter_objects` 的 `prefix` 是字符串前缀**（不是路径段）：`prefix='default/sessions/'` 也会列到 `default/sessions-archive/` 下的文件——这是已知限制，调用方需保证 prefix 末位带 `/` 来切分。**待核**是否要改用 `pathlib.PurePosixPath.parts` 段级匹配。

`iter_objects` 行为：

```
def iter_objects(self, prefix=""):
    root = Path(self._root)
    if not root.exists(): return iter(())
    keys = []
    for path in root.rglob("*"):
        if not path.is_file(): continue
        rel = path.relative_to(root).as_posix()
        if rel.startswith(prefix):
            keys.append(rel)
    return iter(ObjectInfo(key) for key in sorted(keys))
```

### §3.3 两条 `local` 路径的差异表

| 维度 | `LocalBucket`（mock） | `LocalObjectStore`（backend=local） |
|---|---|---|
| 触发条件 | `evolve-server --mock` | `sharing.backend=local` + `sharing.local_root=...` |
| 默认 root | `evolve_server/storage/mock/`（仓库内） | 无默认（必须传） |
| 配置文件依赖 | 无（不读 cfg） | 必须跑过 `skillclaw setup` 写 cfg |
| `iter_objects` | 走 `LocalObjectIterator`（`os.walk`） | 自己实现（`Path.rglob`） |
| 异常类 | `FileNotFoundError` | `FileNotFoundError` |
| 路径分隔符 | 内部 `.replace(os.sep, "/")` | `.as_posix()` |
| 文件对象类 | `_LocalObject` | `_BytesObject` |
| 在 evolve-server 哪里用 | `_build_bucket(mock=True)` | `_build_bucket(mock=False)` → `build_object_store("local")` |
| 在客户端哪里用 | （无） | `SkillHub.object_storage_from_config` 内部 `from skillclaw.object_store import build_object_store` 后 `build_object_store("local", local_root=...)` |

### §3.4 `is_not_found_error` 跨后端归一

`object_store.py` 的 `is_not_found_error(exc)` 帮 `oss_helpers` 的读函数把 4 个后端的"找不到"异常归一为 `True`：

```
def is_not_found_error(exc):
    if isinstance(exc, FileNotFoundError): return True
    name = type(exc).__name__
    return "NoSuchKey" in name or "NotFound" in name or "NoSuchBucket" in name
```

- 命中：`FileNotFoundError`（`LocalObjectStore` / `LocalBucket`）/`botocore.exceptions.ClientError`（S3，name 含 `NoSuchKey`）/`oss2.exceptions.NoSuchKey`（OSS）/`oss2.exceptions.NoSuchBucket`（OSS）
- **不**命中：自定义异常类（name 不含 `NoSuchKey` / `NotFound` / `NoSuchBucket`）——**已知限制**：`is_not_found_error` 字符串匹配对自定义异常类不严谨，生产里换成 `botocore.exceptions.ClientError` + `oss2.exceptions.NoSuchKey` isinstance 检查。

`oss_helpers` 的"找不到"行为**统一**：捕获 `Exception` 后 `logger.warning` 并返回 `None`（`read_json_object` / `fetch_skill_content` / `fetch_skill_bundle_text` / `load_manifest` / `load_version_bundle_record`），或返回空 dict（`load_manifest`）/ 空 bundle（`fetch_skill_bundle` / `fetch_version_bundle`）。

## §4 · oss_helpers 写路径核心 API

`evolve_server/storage/oss_helpers.py` 16 个函数按"职责"分 4 组：**Manifest / Session / Skill / Skill Bundle 写 / Key 路径计算**。**所有读操作不抛"找不到"类异常、返回 None 或空；所有写操作覆盖式、不原子、写失败向上抛**（manifest 写为整文件覆盖，非行级 append；bundle 写为先 file、再 bundle.json、最后清 stale files，详见 §4.5）。完整 16 行函数签名表见章末附录 A。

### §4.1 Manifest / Session 类

| 函数 | 输入 | 输出 | 失败模式 |
|---|---|---|---|
| `load_manifest(bucket, prefix)` | bucket + `prefix` | `{name: {"format": "bundle_v1", "version": int, "tree_sha256": str, "uploaded_at": str, "uploaded_by": str, "files": [...]}}`（找不到 / 解析失败 → `{}`） | 找不到 key → `{}`；json 解析失败 → 该行 skip |
| `save_manifest(bucket, prefix, manifest)` | bucket + `prefix` + `{name: record}` dict | 整文件覆盖写 `manifest.jsonl`（非行级 append） | 写失败向上抛（不原子） |
| `list_session_keys(bucket, prefix)` | bucket + `prefix` | `[key, ...]`（**只**含 `{prefix}sessions/*.json`，**过滤**非 `.json` 后缀——防御式过滤 sessions 下的元数据混入） | 三种 iterator dispatch（见 §3.4 + §2.2/§2.3）；iterator 内部异常向上抛 |
| `list_object_keys(bucket, prefix)` | bucket + `prefix` | `[key, ...]`（**全部** key，**不过滤**文件后缀） | 同上 |
| `read_json_object(bucket, key)` | bucket + `key` | `dict | None` | 找不到 / json 解析失败 → `None`（`logger.warning`） |
| `delete_session_keys(bucket, keys)` | bucket + `[key, ...]` | 成功删除数（int） | 逐个 try/except，单条失败不中断，最后 `logger.info` 报成功 / 总数 |

**`list_session_keys` 的三段式 dispatch 顺序**（防御式 duck typing，**实际不应**出现 hybrid bucket）：

```
def list_session_keys(bucket, prefix):
    if hasattr(bucket, "iter_objects"):
        iterator = bucket.iter_objects(prefix=f"{prefix}sessions/")  # 新抽象
    elif isinstance(bucket, LocalBucket):
        iterator = LocalObjectIterator(bucket, prefix=f"{prefix}sessions/")  # 老 mock
    else:  # 兜底：原生 oss2.Bucket
        import oss2
        iterator = oss2.ObjectIterator(bucket, prefix=f"{prefix}sessions/")
    return [obj.key for obj in iterator if obj.key.endswith(".json")]
```

末行 `if obj.key.endswith(".json")` 是防御式过滤——目前 `sessions/` 下只放 `.json` record（无 `.jsonl` / `.tmp` / `.lock`），但 `endswith(".json")` 避免被 `sessions/manifest.json` 之类的元数据混入。`list_object_keys` **不**走这个 `.json` 过滤（清 stale files 时要看全部 key）。

### §4.2 Skill 类（读）

| 函数 | 输入 | 输出 | 失败模式 |
|---|---|---|---|
| `fetch_skill_content(bucket, prefix, skill_name)` | bucket + `prefix` + `name` | `str | None`（`{prefix}skills/{name}/SKILL.md` 的文本） | 找不到 → `None` |
| `fetch_skill_bundle(bucket, prefix, skill_name, record=None)` | bucket + `prefix` + `name` + 可选 `record`（manifest 记录） | `{rel_path: bytes}` | 没 record + `SKILL.md` 找不到 → `{}` |
| `fetch_skill_bundle_text(bucket, prefix, skill_name, record=None)` | 同上 | `str | None`（bundle 的 `SKILL.md` entrypoint 文本） | 找不到 → `None` |

`fetch_skill_bundle` 的 record 双形态：

- 新版（`record.files` 是非空 list）→ 按 `record.files[].path` 列表走：`SKILL.md` → `{prefix}skills/{name}/SKILL.md`；其它 → `{prefix}skills/{name}/files/{rel_path}`
- 老版（record 无 `files` 字段，或 list 为空）→ 回退到只读 `{prefix}skills/{name}/SKILL.md`（v0 单文件 bundle 协议兼容）

### §4.3 Skill Bundle 写

| 函数 | 输入 | 输出 | 失败模式 |
|---|---|---|---|
| `save_version_bundle(bucket, prefix, skill_name, version, bundle_files)` | bucket + `prefix` + `name` + `version: int`（≥ 1，容错：`max(1, int(version or 1))` 防止 `version=0` 冷启动异常）+ `{rel_path: bytes}` | `record dict`（含 `format / entrypoint / tree_sha256 / files`） | 单步写失败向上抛；stale file 删除单条 try/except 不中断 |
| `load_version_bundle_record(bucket, prefix, skill_name, version)` | bucket + `prefix` + `name` + `version: int` | `record dict | None`（`{prefix}skills/{name}/versions/v<N>/bundle.json`） | 找不到 / 解析失败 → `None` |
| `fetch_version_bundle(bucket, prefix, skill_name, version, record=None)` | bucket + `prefix` + `name` + `version: int` + 可选 `record` | `{rel_path: bytes}`（同 `fetch_skill_bundle`） | 找不到 → `{}` |

### §4.4 Key 路径计算

| 函数 | 输入 | 输出 | 备注 |
|---|---|---|---|
| `skill_version_prefix(prefix, skill_name, version)` | 3 参 | `"{prefix}skills/{name}/versions/v{max(1, int(version or 1))}/"` | `version=0` 归一为 1（冷启动容错）；末尾**不**带 `/` |
| `skill_version_bundle_key(prefix, skill_name, version, rel_path)` | 4 参 | `SKILL.md` → `.../versions/v<N>/SKILL.md`；其它 → `.../versions/v<N>/files/{path}` | `rel_path` 用 `/` 统一分隔符 |
| `skill_version_record_key(prefix, skill_name, version)` | 3 参 | `.../versions/v<N>/bundle.json` | manifest 记录 |
| `make_bucket(endpoint, bucket_name, key_id, key_secret)`（positional） | 4 参 | `OSSObjectStore(endpoint, bucket_name, key_id, key_secret)` | 兼容老 OSS SDK 的 positional 风格（其他函数都用 `(*, ...)` kwargs） |

### §4.5 `save_version_bundle` 写盘顺序与崩溃恢复

`save_version_bundle` 写盘有严格的**3 步顺序**，每步的崩溃恢复语义不同：

| 步 | 动作 | 崩溃后状态 | pull 端可见 |
|---|---|---|---|
| 1 | 遍历 sorted(bundle) → `put_object` 每个 file 到 `v<N>/SKILL.md` 或 `v<N>/files/<path>`，同时**收集** `keep_keys` | file 写了一半 | 看到 v<N> 半新半旧 files（无 bundle.json / 有旧 bundle.json）→ pull 走 record 旧版，文件可能 missing → 走 fallback |
| 2 | `list_object_keys(bucket, ...files/)` → 删 `keep_keys` 之外的（old bundle 有、new bundle 没有的 stale file） | 已写完 files、stale 没清完 | 新 files 都在 + 几个旧 stale 残留（无 bundle.json）→ pull 走旧 record，stale 不被读到 |
| 3 | `put_object(bundle.json, record json)` | 已写完 files + 清完 stale、bundle.json 没写 | 看到 v<N> 完整新 files 但 bundle.json 仍是旧版（或缺失）→ pull 走旧 record（指向 v<N> 但 files 是新的）→ **inconsistency**（**待核**：是否要给 bundle.json 加"显式 commit" 二阶段） |

**为什么不反过来**（先 bundle.json 再 file）：反过来崩溃后 pull 端看到新 bundle.json 指向的 file 还没写 → **`fetch_version_bundle` 走新版路径会 `bucket.get_object` 抛错**。当前顺序下，崩溃最坏看到"半新半旧 files + 旧 bundle.json"，pull 走旧 record 路径还能恢复（`fetch_version_bundle` 的 record 缺失会 fallback 到只读 SKILL.md，见 §4.2）。

**stale file 删除范围**（已知限制）：用 `list_object_keys(...prefix+files/)` 列 `v<N>/files/` 下**全部** key（包括非 `.json` 后缀）—— `list_object_keys` 不过滤后缀（与 `list_session_keys` 区别在这里）。但 prefix 是字符串前缀（`...v<N>/files/`），**不**是路径段匹配——如果存在 `v1/files-archive/xxx` 这种"前缀命中但不是 files 子目录"的 key，会被误判为 stale 删除。**已知限制**：stale 删除范围是"字面 prefix 命中"，调用方要保证 `v<N>/files/` 下没有前缀撞车。

**`save_version_bundle` 的步骤骨架**（伪代码）：

```
record = {"format": "bundle_v1", "entrypoint": "SKILL.md",
          "tree_sha256": bundle_tree_sha256(bundle),
          "files": bundle_file_records(bundle)}
keep_keys = set()
for rel_path, data in sorted(bundle.items()):
    key = skill_version_bundle_key(prefix, skill_name, version, rel_path)
    keep_keys.add(key)
    bucket.put_object(key, data)         # step 1
for key in list_object_keys(bucket, f"{skill_version_prefix(...)}files/"):
    if key not in keep_keys:
        bucket.delete_object(key)        # step 2
bucket.put_object(skill_version_record_key(...),
                 json.dumps(record).encode("utf-8"))  # step 3
```

### §5.1 `EvolveEngineMixin._build_bucket` 路由

`evolve_server/engines/common.py:EvolveEngineMixin._build_bucket(config, *, mock=False, mock_root=None)` 的**3 路分流**（`if mock` 在最前；接着是 Nacos 校验；最后是工厂）：

if mock:
    return LocalBucket(root=mock_root)        # 路径 1
if (config.skill_storage_backend == "nacos"
    and not config.storage_backend):
    raise ValueError(                         # 路径 2（提前 raise，错误信息更可读）
        "sharing.skill_backend=nacos stores skill assets only. "
        "Configure session storage with sharing.backend, sharing.session_backend, "
        "sharing.local_root, EVOLVE_STORAGE_*, or use --mock."

return build_object_store(...)                 # 路径 3

### §5.2 `_uses_local_storage` / `_call_storage`

`_uses_local_storage()` 决定 storage 调用是 sync（`LocalObjectStore` / `LocalBucket`）还是 `asyncio.to_thread` 跑 worker thread（S3 / OSS 不阻塞 event loop）：

```
def _uses_local_storage(self) -> bool:
    backend = str(self.config.storage_backend or "").strip().lower()
    if backend == "local" or self._mock:
        return True
    bucket_type = type(self._bucket).__name__.lower()
    return "local" in bucket_type and bool(self.config.local_root)
```

**`bucket_type` 匹配 `LocalBucket`**：`type(self._bucket).__name__.lower()` = `"localbucket"`，含 `"local"` + `local_root=mock_root`（**非空**）→ 走同步。S3 / OSS 不会命中（type name 不含 `"local"`）。

## §6 · Bundle v1 协议

`bundle_v1` 是**当前唯一已实现**的 manifest 格式版本号（设计上预留 v2 字段扩展位，详见 [20 · 共享存储与同步 §9 bundle 协议](../02-客户端共享层/20-共享存储与同步.md)）。所有走 OSS / S3 / Local 后端的 skill 版本记录都用这个格式；Nacos 路径走 zip 协议（见 [20 · 共享存储与同步 §8.2](../02-客户端共享层/20-共享存储与同步.md)），不写 `manifest.jsonl`。

### §6.1 字段表

`bundle_v1` 的 6 个字段（`format / entrypoint / tree_sha256 / files / name / version`）写在 `manifest.jsonl` 的每行 + `bundle.json` 里：

| 字段 | 类型 | 写者 | 读者 | 用途 |
|---|---|---|---|---|
| `format` | `"bundle_v1"` | `save_version_bundle` 写 | `fetch_version_bundle` / `coerce_skill_bundle` 读 | 协议版本（当前唯一已实现；预留 v2 扩展位） |
| `entrypoint` | `"SKILL.md"` | `save_version_bundle` 写 | `bundle_entrypoint_text` 读 | bundle 的入口文件名 |
| `tree_sha256` | hex string | `save_version_bundle` 调 `bundle_tree_sha256` 算 | `SkillHub.push_skills` / `pull_skills` / `AgentWorkspace.collect_changes` 比对 | bundle 指纹（见 §6.2） |
| `files` | `[{"path", "sha256", "size"}, ...]` | `save_version_bundle` 调 `bundle_file_records` 算 | `fetch_version_bundle` 校验 / manifest 展示 | 文件清单（`sorted(coerce_skill_bundle(bundle).items())` 按 `rel_path.as_posix()` 排序） |
| `name` | string | 由 manifest 调用方（`_upload_skill` / `put_skill_bundle`）传入 | 客户端 / agent 引擎读 | skill 标识 |
| `version` | int（≥ 1，`max(1, int(version or 1))` 容错） | 由 manifest 调用方传入（每次自增，冷启动取 `max(existing version) + 1`） | 客户端 / agent 引擎读 | 版本号（v<N> 子目录的 N） |
| `content_sha` | hex string（**与 `files[0].sha256` 等价**——`files` sorted 后 `SKILL.md` 必是第一个） | `save_version_bundle` 算（与 `files[0].sha256` 同一份） | `SkillIDRegistry` 比对（OSS / S3 / Local 路径下作为 skill_id 的 content 字段） | 单文件协议兼容（见 §6.3） |

### §6.2 `tree_sha256` 算法

输入：bundle 内每个 file 的 `(rel_path, sha256(content), byte_count)`，按 `rel_path.as_posix()` 排序（**路径段字典序**，跨平台一致）。

拼接格式（**`skillclaw/skill_bundle.py:bundle_tree_sha256`**）：

```
SHA-256(
  "{path1.as_posix()}\0{sha256(content1)}\0{size1}\n"
  "{path2.as_posix()}\0{sha256(content2)}\0{size2}\n"
  ...
)
```

每个 file 的 `sha256` 是**文件内容 hash**（`hashlib.sha256(data).hexdigest()`），不包 size（size 单独字段拼在后面）；`size` 是**字节数**（`len(data)`）。

**`tree_sha256` 的 3 个用途**：

1. `SkillHub.push_skills`：与 remote manifest 的 `tree_sha256` 比对，相同 → 跳过上传（**内容相同，省 I/O**）
2. `SkillHub.pull_skills`：与本地 `versions/v<N>/` 的 `tree_sha256` 比对，相同 → 跳过更新
3. `AgentWorkspace.collect_changes`：与 `snapshot_skills()` 算的**当前 workspace** `tree_sha256` 比对（详见 [32 · Agent 引擎详解 §2.3-2.4](../03-Evolve服务/32-Agent引擎详解.md)）——不同 → 触发新 version 写入。**`collect_changes` 自己算 `tree_sha256`，但**不**写 `bundle.json`**（只算 fingerprint，`bundle.json` 仍由 `save_version_bundle` 写）

### §6.3 `content_sha` 用途

`content_sha` = `sha256(SKILL.md content)`，与 `files[0].sha256` 等价（`files` 排序后 `SKILL.md` 必是第一个）。

**"Nacos 老协议"** 一词的澄清：Nacos Skill registry 在早期只把单个 `SKILL.md` 文本作为 skill 资产——label-based 路由到 `content_sha`（当时是 SKILL.md 的 sha256），用于客户端"按内容拉"。当前 Nacos 已升级为多文件 zip 协议（见 [20 · 共享存储与同步 §8.2](../02-客户端共享层/20-共享存储与同步.md)），但 `content_sha` 这个**单文件 sha256** 字段名仍被 `SkillIDRegistry` 沿用——`SkillIDRegistry` 用 `content_sha` 作为 skill_id 的 content 字段（详见 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md) 中 OSS / S3 / Local 路径的 `SkillIDRegistry` 段）。

当前实现里 `content_sha` 的实际用途：

- `evolve_skill_registry.json` 里每条 record 的 `content_sha` 字段（**Nacos 路径不写这个 registry**，仅 OSS / S3 / Local 路径用）
- `SkillIDRegistry` 比对"agent workspace 当前 SKILL.md 是不是已经是 remote 的版本"（避免无谓上传）
- **不是**给 Nacos 用的——Nacos 路径的 ID 路由走 Nacos 自己的 label / version

**待核**：`content_sha` 与 `files[0].sha256` 冗余存储是否要在未来去掉一者（去掉 `content_sha` 需要改 `SkillIDRegistry` 比对逻辑、去掉 `files[0].sha256` 是反规范）。

### §6.4 Nacos-only 模式下的 bundle 写行为（流程图）

```
[evolve server 启动]
  ↓
[_upload_skill(name, bundle_files, version)]
  ↓
  ├── skill_storage_backend == "nacos" ?
  │     ├── YES → 调 NacosSkillClient.upload_skill_zip
  │     │           (zip 打包 bundle_files → multipart POST /v3/admin/ai/skills/upload
  │     │            → submit() → publish() 改 latest label)
  │     │        → 写 Nacos（**不** 写 manifest.jsonl / **不** 写 bundle.json / **不** 写 v<N>/files/）
  │     │        → **不**调 save_version_bundle
  │     │
  │     └── NO → 调 save_version_bundle(bucket=OSSObjectStore, prefix, name, version, bundle_files)
  │                → 走 §4.5 三步写盘
  │                → 写 manifest.jsonl + bundle.json + v<N>/files/
  │
  └── 任何模式都写 SkillIDRegistry (本地文件, 不走 bucket)
```

**关键点**：

- Nacos 路径**不**写 `manifest.jsonl` / `bundle.json` / `versions/v<N>/`——Nacos 内部用 zip + label 管理版本
- Nacos 路径**也不**写 `evolve_skill_registry.json`——这个 registry 对 Nacos 后端透明（详见 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md)）
- `save_version_bundle` 在 Nacos-only 模式下**不会**被调用（`_upload_skill` 直接走 Nacos 路径）
- session / validation 数据仍走 `OSSObjectStore`（在 `_bucket` 上）

## §7 · 已知限制 / 待核

按 `agent.md` 规则拆两类：`[已知限制]` = 当前行为已知 + 限制是设计取舍；`[待核]` = 真不知道 / 需 openbook 对照或部署环境验证。

### §7.1 已知限制（3 条）

- **[已知限制] `list_object_keys` 与 `list_session_keys` 过滤行为不一致**：`list_object_keys` 返回**全部** key（不过滤后缀），`list_session_keys` 走 `endswith(".json")` 过滤（防御 sessions 下的元数据混入）。`save_version_bundle` 的 stale file 删除用 `list_object_keys`（需要看到所有 key 才能正确清 stale），session 列表用 `list_session_keys`（只关心 session record）。两条函数的过滤行为是有意区分的。
- **[已知限制] `save_version_bundle` 的 stale file 删除范围是"字面 prefix 命中"**：`list_object_keys(bucket, f"{prefix+files/}")` 用字符串前缀匹配——如果存在 `v1/files-archive/xxx` 这种前缀撞车的 key，会被误判为 stale 删除。**当前 mitigation**：stale 删除前先 list → diff keep_keys → 只删 `keep_keys` 之外的；撞车 key 不会在 keep_keys 里（因为新 bundle 的 `rel_path` 不含 `-archive`），所以会被删。**修复路径**：把 prefix 改用 `pathlib.PurePosixPath.parts` 段级匹配（**待核**优先级）。
- **[已知限制] `is_not_found_error` 字符串匹配对自定义异常类不严谨**：`type(exc).__name__` 含 `NoSuchKey` / `NotFound` / `NoSuchBucket` 才算"找不到"——自定义 exception 类（不继承这三种）会漏判。**当前 mitigation**：生产里换成 `botocore.exceptions.ClientError` / `oss2.exceptions.NoSuchKey` isinstance 检查；`oss_helpers` 的"找不到"都用 `try: ... except Exception:` 兜底，**已知**会捕获"非找不到"异常并 `logger.warning`，调用方会拿到 `None` / `{}`。

### §7.2 待核（4 条）

- **[待核] `oss2.ObjectIterator` 递归到几层**：`oss2.ObjectIterator(bucket, prefix='a/b/')` 默认 `delimiter='/'` 但仍递归列所有 nested keys（不限制深度）。要列直接子项需显式设 `delimiter='/'` + 用 `list_objects` 接口的 `CommonPrefixes` 字段；本章 `oss_helpers` 用的是递归模式（要看到所有 nested file）。**当前行为 OK**（要列全部），但限制是"不限制深度 = 大 prefix 下 list 慢"。
- **[待核] `S3ObjectStore` 没分页错误处理**：`paginator.paginate` 自动指数退避 3 次重试，`AccessDenied` 等永久错误会冒泡——`oss_helpers.list_session_keys` 没 try/except 包裹，evolve-server loop 模式会**整轮 raise 退出**。**修复路径**（任一即可）：(a) `oss_helpers.list_session_keys` 加 try/except + `logger.error`；(b) evolve-server 引擎层加 storage retry decorator。**当前**是"严格 fail-fast"。
- **[待核] `OSSObjectStore` 忽略 `region` / `session_token`**：用户配 `region=us-east-1` 配 OSS 会**静默**忽略（`del region, session_token` 不报错）。**修复路径**：`__init__` 加 `if region: logger.warning("OSS ignores region=%r; OSS uses endpoint to select region.", region)`。当前**不**警告，依赖文档说清。
- **[待核] `LocalObjectStore.iter_objects` 用 `rglob` 字符串 prefix 匹配**：`prefix='default/sessions/'` 会列到 `default/sessions-archive/`。**修复路径**：改用 `pathlib.PurePosixPath(rel).parts[:len(prefix_parts)] == prefix_parts` 段级匹配（**待核**优先级 + 性能影响）。
