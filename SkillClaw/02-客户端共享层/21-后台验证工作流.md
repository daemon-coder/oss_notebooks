# 21 · 后台验证工作流

## 这一章讲什么

这一章回答"为什么 SkillClaw 有一个'先验证再发布'的环节、它怎么跑、用什么打分、谁能跑"。覆盖 `validation.enabled` / `validation.*` 字段、`ValidationWorker` 的 idle 检测、replay 打分、quota、`ValidationStore` 的 job/result/decision 三段状态、`publish_mode=validated` 时的完整生命周期。

## 它在整个系统的哪个位置

3 个角色协同完成 validation 流程:
- **客户端 daemon**：`SkillClawLauncher` 在 `validation_enabled=True` 时拉起 `ValidationWorker.run()` 作为后台 asyncio task，负责 idle 时拉取 open job、replay 推理、写入 result。
- **共享存储层**：`ValidationStore` 抽象读写 `{group_id}/validation_*` 路径的 job/result/decision 三个段（基于 `SkillHub.object_storage_from_config` 拿对象存储,走 local/OSS/S3,**不**走 Nacos）。
- **后台 Evolve server**：workflow engine 的 `EvolveServer` 在 `_queue_validation_job` 阶段把 candidate skill 写进 `validation_jobs/<job_id>.json` + `candidate_skills/<job_id>/SKILL.md`；在 `_finalize_validation_jobs` 阶段读 results、写 decision、把 SKILL.md 落到 `skills/<name>/`。

## 设计目的

给"先验证再发布"提供一个**可选的发布门**。当 SkillClaw 是多人共享时,一个用户编出来的 skill 不一定适合另一个人——`validated` 模式让服务端在写入正式 `skills/<name>/` 之前先**等 N 个客户端跑一遍**(在 idle 时,用本地 LLM replay 该 skill 当时依赖的 user task),按 mean score 决定接受 / 拒绝。

**这套机制完全是可选的**——`validation.enabled` 默认 `false`,`EVOLVE_PUBLISH_MODE` 默认 `direct`。开了才有效果。

**注意"可插拔"的精确含义**:`validation.mode` 配置项虽然存在,但 `ConfigStore._normalize_validation_mode(value)` 会**强制**写回 `"replay"`,其它值被忽略——当前 SkillClaw **只有 `replay` 一种 validation 模式**。所以**"可插拔"指的是开关本身**(`validation.enabled` / `EVOLVE_PUBLISH_MODE`),**不是指"可以选不同的 validation 模式"**。

> **关于 `submit_validation_review`**：这是预留的扩展点入口,目前**没有**运行时调用,只作为未来"人工 review 触发"或"自定义验证脚本调用"的接口占位（位于 `validation_worker.submit_validation_review(job_id, user_alias, decision, score)` 函数签名）。本文不展开其流程,见 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md) §4.4 的 `_finalize_validation_jobs` 实现。

## 1. 配置字段

### 1.1 客户端（`~/.skillclaw/config.yaml`）

```yaml
validation:
  enabled: true                 # 默认 false
  mode: replay                  # 实际强制为 "replay"，其它值被忽略
  idle_after_seconds: 300       # 默认 300
  poll_interval_seconds: 60     # 默认 60
  max_jobs_per_day: 5           # 默认 5
  max_concurrency: 1            # 默认 1
```

`ConfigStore._normalize_validation_mode(value)` **强制**写回 `"replay"`——**当前 SkillClaw 不支持其它模式**（注释里也写了"del value"）。

### 1.2 服务端（`evolve_server/.env`）

```bash
EVOLVE_PUBLISH_MODE=validated   # 默认 direct
EVOLVE_VALIDATION_REQUIRED_RESULTS=1
EVOLVE_VALIDATION_REQUIRED_APPROVALS=1
EVOLVE_VALIDATION_MIN_MEAN_SCORE=0.75
EVOLVE_VALIDATION_MAX_REJECTIONS=1
```

`__post_init__`(dataclass 标准的初始化后钩子,见 [30 · Evolve 服务端与引擎选择](../03-Evolve服务/30-Evolve服务端与引擎选择.md))把所有阈值归一化：
- `validation_required_results >= 1`
- `validation_required_approvals >= 1`
- `validation_min_mean_score` 截到 [0, 1]
- `validation_max_rejections >= 1`

## 2. `ValidationStore`：job/result/decision 三段状态

`skillclaw/validation_store.py` 把 validation 状态抽象成**三个 key 集合**：

```
{group_id}/validation_jobs/<job_id>.json       # server 写入
{group_id}/validation_results/<job_id>/<user_alias>.json  # 客户端写回
{group_id}/validation_decisions/<job_id>.json  # server finalize
{group_id}/candidate_skills/<job_id>/SKILL.md  # 候选 skill 落点
```

### 2.1 Job

`save_job(job)` 写 `{group_id}/validation_jobs/<job_id>.json`：

```json
{
  "job_id": "20260420143000-debug-systematically-ab12cd34",
  "status": "pending_validation",
  "created_at": "2026-04-20T14:30:00Z",
  "candidate_skill_name": "debug-systematically",
  "candidate_skill_id": "a1b2c3d4e5f6",
  "candidate_skill": {
    "name": "...",
    "description": "...",
    "category": "coding",
    "content": "..."
  },
  "current_skill": {...},                     # 可选，老版本
  "proposed_action": "improve_skill",
  "source": "skill_group",
  "rationale": "LLM 决定 improve...",
  "session_ids": ["..."],
  "session_evidence": [...],
  "replay_cases": [
    {
      "session_id": "...",
      "turn_num": 1,
      "instruction": "...",
      "baseline_response": "...",
      "candidate_response": "..."
    }
  ],
  "min_results": 1,
  "min_approvals": 1,
  "min_score": 0.75,
  "max_rejections": 1
}
```

**`replay_cases`** 是关键——server 已经把"原始 session 的 user instruction + baseline 回答 + candidate 回答"准备好，客户端只需要跑一次推理打 PRM 分。

`make_job_id(skill_name)` 生成 `YYYYMMDDHHMMSS-<slug>-<8hex>`。`list_jobs()` 按 `created_at` 升序列出所有 job。

### 2.2 Result

`save_result(job_id, user_alias, result)` 写 `{group_id}/validation_results/<job_id>/<user_alias>.json`：

```json
{
  "job_id": "...",
  "user_alias": "alice",
  "created_at": "...",
  "validator_mode": "replay",
  "decision": "accept" | "reject",
  "accepted": true | false,
  "score": 0.85,
  "threshold": 0.75,
  "reason": "Replay validation compared 1 case(s): candidate_mean=0.85, baseline_mean=0.50, threshold=0.75",
  "checks": {
    "grounded_in_evidence": 0.85,
    "preserves_existing_value": 0.85,
    "specificity_and_reusability": 0.85,
    "safe_to_publish": 0.85
  },
  "replay_summary": {
    "case_count": 1,
    "baseline_mean_score": 0.50,
    "candidate_mean_score": 0.85,
    "cases": [...]
  }
}
```

每个 user_alias 写一份（**一个用户只对同一个 job 写一次**——`list_open_jobs(user_alias=...)` 会跳过已有 result 的 job）。

### 2.3 Decision

`save_decision(job_id, decision)` 写 `{group_id}/validation_decisions/<job_id>.json`：

```json
{
  "job_id": "...",
  "status": "published" | "rejected" | "skipped",
  "published_action": "improve_skill",
  "result_count": 1,
  "accepted_count": 1,
  "rejected_count": 0,
  "mean_score": 0.85,
  "decided_at": "..."
}
```

`load_decision` 在 finalize 时被检查——`if load_decision: continue` 跳过已 finalize 的 job。

### 2.4 `list_open_jobs(user_alias="")`

只返回：
- 没有 `load_decision(job_id)` 的
- `user_alias` 传了的话，且该 user **没**已写 `save_result`

## 3. `ValidationWorker`：客户端 idle 验证

### 3.1 构造

```python
ValidationWorker(
    cfg,
    idle_provider=server,   # SkillClawAPIServer 实现了 IdleStateProvider 协议
)
```

内部组件：
- `self._store = ValidationStore.from_config(cfg)`：用 `SkillHub.object_storage_from_config` 拿对象存储（**不**用 Nacos）
- `self._client = AsyncLLMClient(...)`：本地 LLM 客户端（用 `cfg.llm_api_key` / `cfg.llm_api_base` / `cfg.llm_model_id`，默认 `gpt-4o`）
- `self._prm_scorer = PRMScorer(...)`：本地 PRM 客户端（用 `cfg.prm_*`，默认 `gpt-4o`）
- `self._user_alias = cfg.sharing_user_alias or os.environ.get("USER", "anonymous")`
- `self._stop_event = asyncio.Event()`
- `self._jobs_completed_today`：UTC 日期切换时重置的当日计数

### 3.2 Idle 判定

> **"5 个 gate" 这个说法在 §1/§3 之间略有混用**——实际校验条件是 **3 个核心 gate + 2 个循环控制点**。这里把**所有**"决定 run_once 是否跑 / 跑几个 / 跑哪些"的条件列清,避免读者误以为"5 个独立 gate"。

`run_once(*, force=False) -> dict` 走"3 个前置 gate + 2 个循环控制点"两步框架。

**前置 gate 阶段**(任一失败直接 return summary_empty):

```python
# 段 1:gate 1(enabled)——3 个开关全开
if not (validation_enabled and sharing_enabled and sharing_group_id):
    return summary_empty

# 段 2:gate 2(quota)——每日 quota 未用完
if not _quota_available():
    return summary_empty

# 段 3:gate 3(idle)——客户端 idle 或 force=True
if not (force or _is_idle_for_validation()):
    return summary_empty
```

**主循环阶段**(遍历 open jobs,每个 job 走"replay + save"):

```python
# 段 4:for job in self._store.list_open_jobs(user_alias=...):
for job in self._store.list_open_jobs(user_alias=...):
    # 段 4a:gate 4(quota 复用)——跑每个 job 前再 check
    if not self._quota_available():
        break

    # 段 4b:跑 replay 模式
    result = await self._validate_job(job)

    # 段 4c:存结果
    self._store.save_result(...)

    # 段 4d:gate 5(concurrency)——跑满 max_concurrency 提前 break
    if summary.validated_jobs >= max_concurrency:
        break
```

**3 个前置 gate + 2 个循环控制点**:

| 类型 | # | 条件 | 失败时行为 |
|---|---|---|---|
| 前置 gate | 1 | `validation_enabled and sharing_enabled and sharing_group_id`(三个开关全开) | 直接 return |
| 前置 gate | 2 | `_quota_available()`(每日 quota 未用完) | 直接 return |
| 3 | `force=True` 或 `idle_provider.is_idle_for_validation(idle_after_seconds)`(force 模式或 idle 满足) | 直接 return |

**循环控制点**(在主循环体内,控制迭代边界):

| # | 条件 | 触发时行为 |
|---|---|---|
| 4 | `_store.list_open_jobs(user_alias=...)` 自动跳过已写过 result 的 job | 跳过该 job(不是 break,继续下一个) |
| 5 | `validated_jobs >= max_concurrency`(默认 1) | break(主循环退出) |

### 3.3 Replay 验证（`_replay_validate_job`）

```python
# 伪代码骨架（见 validation_worker.py:ValidationWorker._replay_validate_job）:
async def _replay_validate_job(self, job) -> dict:
    # 1. 取前 3 个 replay_cases
    # 2. 各跑 baseline（current_skill）+ candidate（proposed_skill）两条分支
    # 3. candidate_mean / baseline_mean 比较
    # 4. accept 条件: candidate_mean >= min_score(默认 0.75) AND >= baseline_mean
    return {"validator_mode": "replay", "decision": ..., "score": candidate_mean, ...}
```

**`_run_replay_branch(case, skill, label)`**：
- 把 skill 包成"## Skill" system prompt（用 `_build_replay_skill_system`）
- 调本地 LLM 跑 `case.instruction`
- 用 PRM 评 response vs instruction
- 把 PRM score 归一到 [0, 1]（`_normalize_replay_score`）

**`_normalize_replay_score`** 把 PRM 的 -1/0/1 映射到 [0, 1]：
- `score <= -1.0` → `0.0`
- `score >= 1.0` → `1.0`
- `score == 0.0` → `0.5`
- 其它 → `(score + 1) / 2`

**判定门**：
- `candidate_mean >= threshold`（默认 0.75）
- `candidate_mean >= baseline_mean`（**不能比 baseline 差**——这个是软底线）

如果没 baseline（`current_skill` 为空），`baseline_mean = 0.0`，第二个条件就退化为 `candidate_mean >= 0.0`（永远满足）——等价于"只看 threshold"。

### 3.4 `run` 循环

`run(self)` 走"while not stop + 跑一次 + 等 N 秒或被停"3 步循环:第一步 `interval = max(5, validation_poll_interval_seconds)`(下限 5s,配 1s 也被强制改写);第二步 `while not self._stop_event.is_set():` 循环(没收到 stop 信号继续);第三步循环体——`try: await self.run_once() except: ...` 跑一次 cycle(失败不退出循环)+ `try: await asyncio.wait_for(self._stop_event.wait(), timeout=interval) except asyncio.TimeoutError: continue` 等 N 秒或被 stop,超时进下一轮。

**`asyncio.wait_for(stop_event, timeout=interval)`** 是一种"等 N 秒或被停"——超时（没人停）就 `continue` 跑下一轮 `run_once`。

**`interval` 最低 5s**（`max(5, ...)`）——比 session sweeper 的 15s 还密，因为 validation 是 IO 重（要调 LLM）。`validation.poll_interval_seconds` 配 1s 实际会被强制改写为 5s(下限);配 0/负数同样兜底到 5s。

## 4. 服务端 finalize 流程(`EvolveServer._finalize_validation_jobs`)

`evolve_server/engines/workflow.py` 的 `_finalize_validation_jobs` 在每个 cycle 末尾跑。**触发条件**:`self.config.publish_mode == "validated"`(`evolve_server/core/config.py:107` 默认 `"direct"`,`validated` 必须显式设)。其它模式下整个函数**直接 return**——`publish_mode` 是触发的**必要条件**。

**判定伪代码(简化版,完整实现见 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md) §4.4)**:

```python
# 触发条件:publish_mode == "validated" 才进入;否则整个函数直接 return
for job in self._validation_store.list_jobs():
    if self._validation_store.load_decision(job["job_id"]):  # 已 finalize → 跳过
        continue
    results = self._validation_store.list_results(job["job_id"])
    accepted = sum(1 for r in results if r.get("accepted"))
    rejected = sum(1 for r in results if not r.get("accepted"))
    mean_score = (sum(r["score"] for r in results if r.get("score") is not None)
                  / max(1, sum(1 for r in results if r.get("score") is not None)))

    # 判定 1:reject 优先(单 reject 即否)
    if rejected >= self.config.validation_max_rejections:
        self._validation_store.save_decision(job["job_id"], {"status": "validation_rejected", ...})
        continue

    # 判定 2:accept 条件(3 个 AND)
    if (len(results) >= self.config.validation_required_results
        and accepted >= self.config.validation_required_approvals
        and mean_score >= self.config.validation_min_mean_score):
        # 调 _resolve_and_upload(candidate_skill, proposed_action):
        #   - success:save_decision(status="published_after_validation")
        #   - merged 后 zip 不一致 / conflict 未解:save_decision(status="skipped")
        # 详见 31 章 §4.4 的 conflict detection / merge / Nacos upload 完整流程
        self._resolve_and_upload(candidate_skill, job["proposed_action"])
    # 判定 3:accept 条件未满足 → 不写 decision,等下次 cycle 再判

**4 种 decision 状态**:
- `pending_validation`(无 decision)→ 等 results
- `published_after_validation`(uploaded=True):uploaded 后写 `status: "published"`
- `skipped`(uploaded=False):`status: "skipped"`(conflict 解决路径里 merged 后 zip 不一致等)
- `validation_rejected`:max_rejections 触发;写 `status: "rejected"`

**判定优先级**:
- **reject 条件独立触发,优先级最高**——`rejected >= max_rejections` 就 `validation_rejected`,**不再判 accept 条件**。
- **accept 条件是 3 个 AND**(都满足才 publish):`result_count >= required_results` AND `accepted >= required_approvals` AND `mean_score >= min_mean_score`。
- 任一 accept 条件未满足 → 暂缓,等下次 cycle 再判(不写 decision)。

> **完整 server 端 finalize 实现**(含 conflict detection / merge / Nacos 上传)在 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md) §4.4;**4 阈值的具体配置**在 21 章 §1.2(已上)。

## 5. 端到端一次 validation 生命周期

```
[server] evolve cycle
  → workflow engine 跑完 summarize/judge/aggregate/evolve
  → _materialize_skill 生成 candidate
  → config.publish_mode == "validated"
  → _queue_validation_job(candidate, ...)
      → ValidationStore.save_job(job)
      → writes {group_id}/validation_jobs/<job_id>.json
      → writes {group_id}/candidate_skills/<job_id>/SKILL.md
      → returns action="queued_for_validation"

[client A] ValidationWorker.run
  → idle check pass + quota ok
  → ValidationStore.list_open_jobs(user_alias=alice)  # job 出现
  → _replay_validate_job(job)
  → ValidationStore.save_result(job_id, alice, result)  # alice 写 result

[client B] ValidationWorker.run
  → list_open_jobs 跳过 alice 已写的，bob 还能写
  → save_result(job_id, bob, result)

[server] 下一次 cycle _finalize_validation_jobs
  → list_results(job_id)  # 2 results
  → accepted=1, rejected=1, mean_score=...
  → 如果 publish_ready: _resolve_and_upload → 写 skills/<name>/SKILL.md
  → save_decision → job 完成
  → 如果 reject_ready: save_decision(`status: "validation_rejected"`)
  → 其它: 继续等
```

**注意**：服务端 finalize 在**下一次 evolve cycle 触发**（不是 job 创建后立即）——所以 validation 至少要等一个 `EVOLVE_INTERVAL`（默认 600s）才 finalize。

## 7. 待确认 / 已知限制

- **`replay_cases` 由谁填**？当前实现是 `EvolveServer._build_replay_cases(sessions)`——从 session 抽 instruction + response。**待确认**这个抽取的质量：早期 session 主要是 agent 的 tool calls，instruction 可能是 tool_call 之后的下一步操作——replay 模拟的是"原始 user 任务在 candidate skill 下能不能完成"。
- **`force=True` 跳过 idle** 但不跳过 quota——**待确认**这是否是设计（quota 是硬上限，idle 是软条件）。
- **server 端 finalize 是被动**（下次 cycle 才检查）——validation 完整周期 = `evolve_interval` + 实际推理时间。生产里建议 `EVOLVE_INTERVAL=60` 加快。
- **`_run_replay_branch` 跑的是 case 里的 instruction**——但 case 的 `baseline_response` 字段在 worker 里**没用到**（worker 用 `current_skill` 跑 baseline，case 里的字段是备选/审计用）。**待确认**是冗余设计还是 future use。
- **`is_idle_for_validation` 与 session_idle_close 的关系**：见 [14 · Session 与 Turn 簿记](14-Session与Turn簿记.md) §10。这两个值没耦合——容易误配（"validation 阈值 < session 关闭阈值" 会导致还没关 session 就开始 validation）。**待确认**要不要在 wizard 里加 warning。
- **Nacos 路径下 validation 仍可工作**——`ValidationStore` 用 `object_storage_from_config` 走 local/OSS/S3，**Nacos 只存 skill 资产**。但 job 里 `candidate_skill` 包含完整 SKILL.md 内容，server 端 finalize 时 `_resolve_and_upload` 会调 `_upload_skill` → Nacos 路径 `submit` + `_wait_nacos_publish`（30s 阻塞）。**待确认** Nacos publish 慢（人工 review）时 30s 超时是否合理。
