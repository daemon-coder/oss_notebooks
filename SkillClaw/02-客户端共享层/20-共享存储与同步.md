## 这一章讲什么

这一章回答"SkillClaw 怎么把本地 skill 库同步到云端、怎么从云端拉新 skill、怎么用 Nacos 替代对象存储"。覆盖三种对象存储后端(local / S3 / OSS)、`SkillHub` 的 push / pull / sync / list-remote 协议、Nacos 适配器、bundle 哈希协议、object store 抽象。

## 它在整个系统的哪个位置

`SkillClawLauncher` 启动时 `SkillHub.pull_skills`(如果 `sharing_auto_pull_on_start=True`);session 关闭时 `SkillHub.object_storage_from_config` 上传 session;`SkillClawAPIServer` reload poller 每 30s 拉一次;`skillclaw skills push/pull/sync` CLI 手动触发。

## 设计目的

让"团队共享"和"个人使用"在客户端用**同一份代码**。`SkillHub.from_config(cfg)` 是个工厂:按 `sharing.skill_backend` 路由到通用 `SkillHub` 或 Nacos 专用 `NacosSkillHub`——业务代码不关心。

## 1. 共享存储布局(key 命名约定)

**场景**:SkillClaw 的两条线(client + evolve_server)**只通过**这一个共享存储通信。理解 key 命名 = 理解 SkillClaw 怎么把"sessions / skills / validation / registry"组织在一个对象存储里。

**`{group_id}/` 是根前缀**。`group_id` 默认 `default`——团队模式改成 `acme` / `org-foo` 等。

**整体布局**(每个 key 路径的"写者 / 读者 / 用途"):

| Key 路径 | 写者 | 读者 | 用途 |
|---|---|---|---|
| `{group_id}/manifest.jsonl` | evolve_server | client daemon | skill 清单(每行一条 JSON record),client poll 这个找新版本 |
| `{group_id}/skills/<name>/SKILL.md` | evolve_server | client daemon | 客户端拉 skill 时直接读这个 |
| `{group_id}/skills/<name>/files/<rel_path>` | evolve_server | client daemon | 多文件 bundle 的辅助文件 |
| `{group_id}/skills/<name>/versions/v<N>/SKILL.md` | evolve_server | 回滚用 | 历史版本完整保留 |
| `{group_id}/skills/<name>/versions/v<N>/files/<rel_path>` | evolve_server | 回滚用 | 历史版本的辅助文件 |
| `{group_id}/skills/<name>/versions/v<N>/bundle.json` | evolve_server | 回滚用 | 该版本的 manifest 记录(供回滚时校验完整性) |
| `{group_id}/sessions/<session_id>.json` | client daemon | evolve_server | 完整 session(turns + PRM 分)——evolve server 拉这个做摘要 |
| `{group_id}/validation_jobs/<job_id>.json` | evolve_server | client validation worker | validated 模式下 server 写入,等其它客户端投票 |
| `{group_id}/validation_results/<job_id>/<user_alias>.json` | client validation worker | evolve_server | 多个客户端各自的验证结果 |
| `{group_id}/validation_decisions/<job_id>.json` | evolve_server | 运维 | server finalize 决策(accepted / rejected / skipped) |
| `{group_id}/candidate_skills/<job_id>/SKILL.md` | evolve_server | client validation worker | validated 模式下的候选 skill 落点(供 replay 验证) |
| `{group_id}/evolve_skill_registry.json` | evolve_server | evolve_server 启动 | `SkillIDRegistry` 持久化(`name → {skill_id, version, content_sha, history}`) |
| `{group_id}/processed_sessions.json` | evolve_server | evolve_server | 已处理 session 列表(避免下轮重复炼) |

**Nacos 路径不写这些**——Nacos 走 `nacos_skill_client` 自己的 label-based 状态机(详见 §8)。

```
{group_id}/
├── manifest.jsonl                       # skill 清单（每行一条 JSON record）
├── skills/<name>/
│   ├── SKILL.md                         # 必有
│   └── files/                           # 可选（多文件 bundle）
│       └── <rel_path>
├── skills/<name>/versions/v<N>/
│   ├── SKILL.md
│   ├── files/<rel_path>
│   └── bundle.json                      # 该版本的 manifest 记录
├── sessions/<session_id>.json           # 整段 session（含 turns + PRM 分）
├── validation_jobs/<job_id>.json        # validated 模式下 server 写入
├── validation_results/<job_id>/<user_alias>.json  # 客户端 validation 写回
├── validation_decisions/<job_id>.json   # server finalize
├── candidate_skills/<job_id>/SKILL.md   # validated 模式下的候选 skill 落点
├── evolve_skill_registry.json           # SkillIDRegistry 持久化
└── processed_sessions.json              # （evolve server 的）已处理 session 列表
```

`manifest.jsonl` 每行结构：

```json
{
  "name": "debug-systematically",
  "skill_id": "a1b2c3d4e5f6",
  "version": 3,
  "sha256": "...",
  "tree_sha256": "...",
  "format": "bundle_v1",
  "entrypoint": "SKILL.md",
  "files": [{"path": "SKILL.md", "sha256": "...", "size": 1234}, ...],
  "uploaded_by": "alice",
  "uploaded_at": "2026-04-20T14:30:00Z",
  "description": "Use when diagnosing a bug...",
  "category": "coding"
}
```

注意：manifest **不是演化状态机**，只是一个"上次演化后写出来的东西的快照"。`evolve_skill_registry.json`（`SkillIDRegistry`）才记真正的 ID/版本号历史。

## 2. 对象存储抽象

`object_store.py` 定义了三个具体后端 + 一个工厂：

| 类 | 后端 | 关键依赖 |
|---|---|---|
| `LocalObjectStore` | 本地目录 | 无 |
| `S3ObjectStore` | AWS S3 / S3 兼容（MinIO / R2 / B2） | `boto3` |
| `OSSObjectStore` | Alibaba Cloud OSS | `oss2` |

四个核心方法（统一签名）：
- `get_object(key) -> ObjectBody`（带 `.read()` 返回 bytes）
- `put_object(key, data)`（`data` 接受 bytes / str / IOBase）
- `delete_object(key)`
- `iter_objects(prefix) -> Iterator[ObjectInfo]`（`ObjectInfo` 有 `key` 字段）

### 2.1 `normalize_backend`

```python
def normalize_backend(backend, *, endpoint="", local_root=""):
    aliases = {"filesystem": "local", "fs": "local",
               "s3-compatible": "s3", "minio": "s3", "r2": "s3", "b2": "s3"}
    value = str(backend or "").strip().lower().replace("_", "-")
    if value in aliases: return aliases[value]
    if value: return value
    # 隐式推断: local_root 优先 / endpoint 含 aliyuncs.com → oss
    return "local" if local_root else ("oss" if "aliyuncs.com" in endpoint else "")
```

**自动猜测**：endpoint 含 `aliyuncs.com` → `oss`；否则 `s3`。

`build_object_store(backend, ...)` 是工厂：

```python
if resolved == "local": return LocalObjectStore(local_root)
if resolved == "s3":
    if not bucket: raise ValueError("S3 requires a bucket")
    return S3ObjectStore(endpoint, bucket, access_key_id, secret_access_key, region, session_token)
if resolved == "oss":
    if not endpoint or not bucket: raise ValueError("OSS requires endpoint and bucket")
    return OSSObjectStore(endpoint, bucket, access_key_id, secret_access_key)
raise ValueError(f"Unsupported storage backend: {backend!r}")
```

### 2.2 Nacos 不实现 `ObjectStore` 接口

`NacosSkillClient` 走 HTTP（`/v3/admin/ai/skills/...`）而不是 OSS 兼容协议——所以 Nacos **不**实现 `ObjectStore` 接口。`SkillHub.from_config` 在 `skill_backend=nacos` 时**专门**走 `NacosSkillHub`，不走 `SkillHub`。

**Object store 抽象的局限**：`NacosSkillClient` 不能用 `SkillHub.object_storage_from_config`——因为后者只看 local/S3/OSS。Nacos 路径需要显式 `NacosSkillHub`。

### 3.1 `from_config(config)` 工厂

```python
@classmethod
def from_config(cls, config):
    sharing_backend = str(getattr(config, "sharing_backend", "")).strip().lower()
    backend = str(getattr(config, "sharing_skill_backend", "")).strip().lower() or sharing_backend
    if backend == "nacos":
        from .nacos_skill_hub import NacosSkillHub
        return NacosSkillHub.from_config(config)
    ...

```

**关键**：当 `skill_backend="nacos"` 时**强制**走 `NacosSkillHub`；其它情况构造通用 `SkillHub`。

### 3.2 `object_storage_from_config(config)` 工厂

跟 `from_config` 平行，但只走**对象存储**（**不**走 Nacos）：

```python
sharing_backend = str(getattr(config, "sharing_backend", "")).strip().lower()
backend = str(getattr(config, "sharing_session_backend", "")).strip().lower()

    backend = sharing_backend

```

**这条规则**允许"skill 走 Nacos，session 走 local/OSS/S3"——`SkillClawAPIServer._upload_session_data` 用这个工厂。

## 4. `SkillHub.pull_skills(skills_dir, skip_names=None, mirror=True, include_names=None)`

**场景**:SkillClawAPIServer 在 idle 时或 `_close_session` 时调 `pull_skills(...)`——把"团队共享的 skill 集"从共享存储拉到本地 `~/.skillclaw/skills/`。

**`mirror=True`(默认)行为**:把共享存储的 skill 目录**完全镜像**到 `skills_dir`——

```python
def pull_skills(self, skills_dir, *, skip_names=None, mirror=True, include_names=None):
    # 段 1:从 manifest 读所有 skill
    targets = self._select_targets(self._load_manifest(), skip_names, include_names)
    backup_dir = self._make_backup_dir(skills_dir) if (mirror and not include_names) else None

    # 段 2:逐个拉 SKILL.md + files/,写到 skills_dir/<name>/
    failures = []
    for name in targets:
        try:
            bundle = self._download_skill_bundle(name)
            self._write_skill_to_dir(skills_dir / name, bundle)
        except Exception as e:
            failures.append((name, e))

    # 段 3:删 skills_dir/ 里**不在** manifest 的 skill(镜像 = 完全同步)
    if mirror and not include_names:
        for local_skill_dir in skills_dir.iterdir():
            if local_skill_dir.name not in targets:
                shutil.rmtree(local_skill_dir)

    # 段 4:任何失败 → 写一份 backup 到 ~/.skillclaw/skills/.backup-<timestamp>/,失败时回滚
    if failures and backup_dir:
        self._restore_from_backup(skills_dir, backup_dir)

    return {
        "downloaded": len(targets) - len(failures),
        "skipped": ...,
        "failed": len(failures),
        "failed_names": [n for n, _ in failures],
        "deleted": ...,
    }
```

**关键设计**:

- **`mirror=True`**:完全同步(共享是 source of truth)——本地多出来但 manifest 里没有的 skill 会被**删掉**
- **`include_names`**:白名单(只拉这几个)——`mirror` 自动为 False,跳过段 3。CLI `dashboard server` 的"拉指定 skill"模式用
- **`skip_names`**:黑名单(跳过这几个)——通常在 session 关闭时调,把本 session 内被模型改的 skill 跳过,避免覆盖
- **失败回滚**:整个段 2 拉取过程中如果某个 skill 失败,**回滚到 backup**(避免本地 skill 集半新半旧)
- **`_make_backup_dir`**:把现有 `skills_dir` 复制到 `~/.skillclaw/skills/.backup-YYYYMMDDHHMMSS-<8hex>/`
- **`_restore_from_backup`**:mirror 失败时整体回滚——保证本地 skill 库不被半路的状态搞坏
- **`skip_names` 的典型用法**:`_close_session` 末尾调 `pull_skills(skip_names=modified_skill_names)`——跳过本 session 内被模型改的 skill,避免覆盖

**关键边界**:

- **manifest 读失败** (OSS 不可达):`pull_skills` 抛异常,本地 skill 集不动
- **单个 skill 下载失败**:进 `failures` 列表,触发段 4 回滚
- **`include_names` 全不在 manifest**:targets=空,段 3 删全部本地 skill(危险操作)
- **`mirror=False`**:段 3 不删本地多余 skill,只增量拉新

**`restored_from_backup`**：pull 返回 dict 里的 `restored_from_backup` 字段让 caller 知道"我可能被你回滚了"。

### 4.1 `_load_manifest`

读 `manifest.jsonl`，每行解析成 dict，按 `name` 去重（**最后**出现的那行胜出——`save_manifest` 全量覆盖）。

### 4.2 `_select_targets`

按 `skip_names` / `include_names` 过滤：
- `include_names` 存在 → 只保留这些
- `skip_names` 存在 → 排除这些

**`session_done` 后的 `_pull_skills_from_cloud(skip_names=modified_skill_names)`** 跳过本 session 内被模型**修改**的 skill（避免覆盖用户刚改的本地版）。

## 5. `SkillHub.push_skills(skills_dir, skill_filter=None)`

**场景**:`skillclaw skills push` 命令手动调——把"本地的 skill 集"推到共享存储,让团队其它成员能用到。`evolve_server` 不会调(它走自己的 `_upload_skill` 路径)。

```python
def push_skills(self, skills_dir, *, skill_filter=None):
    # 段 1:读本地 bundles
    bundles = self._read_local_bundles(skills_dir)

    # 段 2:对每个 bundle 判定 + 上传
    uploaded, skipped, filtered = [], 0, 0
    manifest = self._load_manifest() or {}
    for name, bundle in bundles.items():
        # 段 2a:filter
        if not self._passes_filter(name, bundle, skill_filter):
            filtered += 1
            continue
        # 段 2b:去重(本地 sha == manifest sha 跳过)
        if manifest.get(name, {}).get("tree_sha256") == tree_sha(bundle):
            skipped += 1
            continue
        # 段 2c:上传
        self._upload_skill_bundle(name, bundle)
        uploaded.append(name)
        manifest[name] = self._make_manifest_record(name, bundle, sha)

    # 段 3:save_manifest 整文件覆盖
    if uploaded:
        self._save_manifest(manifest)

    return {"uploaded": uploaded, "skipped": skipped, "filtered": filtered, "total_local": len(bundles)}
```

**4 种结果**：
- `uploaded`：内容变了 + 过滤通过 → 上传新版本
- `skipped`：内容没变（`tree_sha256` 相同）→ 跳过
- `filtered`：被 `skill_filter` 过滤（effectiveness 不够）→ 不上传
- `submitted`：（仅 Nacos）`review` 模式上传后调 `submit()` 进入审核

**`skill_filter`** 由 CLI `skills push` 构造：

```python
skill_filter = {
    "stats": <skill_stats.json 内容>,
    "min_injections": cfg.sharing_push_min_injections,
    "min_effectiveness": cfg.sharing_push_min_effectiveness,
}
```

`_passes_filter(name, bundle, filter)` 检查 `inject_count >= min_injections && effectiveness >= min_effectiveness`。

## 6. `SkillHub.sync_skills(skills_dir)`

```python
def sync_skills(self, skills_dir):
    pull = self.pull_skills(skills_dir, mirror=True, include_names=None)
    push = self.push_skills(skills_dir, skill_filter=None)
    return {"pull": pull, "push": push}
```

`pull` 后 `push`——先**保证本地是 cloud 的镜像**，再**把本地新东西推上去**。`skill_filter=None` 表示 push 不过滤（`sync` 模式全量推）。

CLI `skillclaw skills sync` 走这条路径。

## 8. Nacos 适配器

### 8.1 `NacosSkillClient`

`nacos_skill_hub.py` 的 `NacosSkillClient` 是 Nacos Skill admin API 的薄包装：

| 端点 | 用途 |
|---|---|
| `POST /v1/auth/login` | 用户名密码登录拿 access token |
| `GET /v3/admin/ai/skills/list` | 列出所有 skill |
| `GET /v3/admin/ai/skills` | 查单个 skill（`?skillName=X`） |
| `GET /v3/admin/ai/skills/version/download` | 下载某个版本的 skill zip（admin） |
| `GET /v3/client/ai/skills` | 公开下载（按 `label` / `version`） |
| `POST /v3/admin/ai/skills/upload` | 上传 skill zip（multipart） |
| `POST /v3/admin/ai/skills/submit` | 提交审核 |
| `POST /v3/admin/ai/skills/publish` | 发布（更新 latest label） |

`_login()` 在 `username/password` 配了但没 `access_token` 时自动调一次。

### 8.2 Skill zip 协议

Nacos 把一个 skill 存成 zip，entry 是 `SKILL.md`（entrypoint）+ 其它 files。SkillClaw 用 `zipfile` 模块打包 / 解包：

- `_bundle_to_nacos_zip(skill_name, bundle_files) -> bytes`
- `_nacos_zip_to_bundle(zip_bytes) -> {rel_path: bytes}`

### 8.3 Skill 生命周期（nacos_publish_mode）

Nacos 区分三种 publish mode：

| mode | 流程 |
|---|---|
| `draft` | 上传即结束（不进审核流） |
| `review`（默认） | 上传 + `submit()` 触发审核；reviewer 通过 → `publish()` 改 `latest` label |
| `direct` | 上传 + `submit()` + 立刻 `publish()`（跳过人工 review） |

`nacos_skill_hub.NacosSkillHub.upload_skill` 实现这个状态机——读 remote record → 如果有 working version（未发布）→ 检查 zip 字节是否相同（`_bundle_matches_remote`）→ 不同就**用相同版本号覆盖**（避免无谓地建新版本）；否则 `_next_version(record, detail)` 算下一个 semver。

### 8.4 `_wait_nacos_publish`（server 端）

`evolve_server/engines/workflow._wait_nacos_publish(name, version, timeout=30.0)`：轮询 Nacos `get_skill` 看 `labels.latest == version`——`publish_mode=direct` 时调 `_nacos_skill_client.publish(name, version, update_latest_label=True)`，间隔 2s 轮询。

**这是同步阻塞**——workflow engine 上传后**等**到 Nacos 实际 publish 才继续。30s 超时。

### 8.5 Nacos 版本解析

`nacos_versions.py`：

- `_next_version(record, detail)`：从 `versions: [{version, status}, ...]` 找最大版本号 + 0.1.0 步进；`semver` / `v<major>` 两种格式都支持
- `_parse_semver(s) -> (major, minor, patch)`：解析 `1.2.3`
- `_parse_v_version(s) -> (major,)`：解析 `v1` / `V2`

`_nacos_working_version(record, detail)`：找"有但没 published"的版本——给 evolve server 用来"在 working version 上覆盖"。

`_nacos_published_version(record, detail, label="latest")`：找 `labels[label]` 对应的版本号——给 pull 用来"按 label 拉 latest"。

### 8.6 `NacosSkillHub`

```python
class NacosSkillHub:
    @classmethod
    def from_config(cls, config):
        return cls(server=..., namespace_id=..., access_token=..., username=..., password=..., label=..., group_id=..., user_alias=...)
```

- `pull_skills(skills_dir)`：**追加**语义——只拉 `labels[label]` 指向的 published skill zip → 解包到 `skills_dir/<name>/`，**不**删本地未在远端的 skill。**不**支持 `skip_names` / `include_names` 形参,需要过滤在调用方做。**不**实现 §4.2 的 `_pull_skills_from_cloud` 路径(Nacos 走自身 publish 状态机,不走"session 收尾跳过本 session 修改"逻辑)。
- `push_skills(skills_dir, skill_filter)`：本地 → zip → upload → submit（按 `nacos_publish_mode`）
- `list_remote()`：返回所有 skill 的 manifest 列表
- `publish_skill(name, version, update_latest_label=True)`：CLI `skills publish NAME VERSION` 显式 publish

> **与 §4 `SkillHub` 签名差异**:`NacosSkillHub.pull_skills(skills_dir)` 没有 `skip_names` / `include_names` / `mirror` 三个旋钮,语义是"追加拉取";`SkillHub.pull_skills` 默认是"镜像全量同步"。跨后端抽象时,调用方需注意这条语义差。

## 9. server 端协议:客户端视角的"我需要知道什么"

> **这一节是 server 端写共享存储的协议简述**——客户端**只读**这些文件,不写。完整实现见 [31 · Workflow 引擎详解](../03-Evolve服务/31-Workflow引擎详解.md) §5(manifest.jsonl + SkillIDRegistry)和 [33 · 共享层与存储适配](../03-Evolve服务/33-共享层与存储适配.md) §1-§3(oss_helpers.py + Nacos)。

| 文件 | 谁写 | 谁读 | 客户端关心什么 |
|---|---|---|---|
| `manifest.jsonl` | evolve server(`save_manifest`) | 客户端 pull 时读 | 每行一条 skill 记录;客户端**只读**,按 name 去重(后写覆盖前写) |
| `evolve_skill_registry.json` | evolve server(`SkillIDRegistry.record_update`) | 客户端**不直接读**;evolve server 内部用 | 客户端**不需要**知道这个文件存在——registry 的版本/历史对客户端透明 |
| `skills/<name>/versions/v<N>/bundle.json` | evolve server(`save_version_bundle`) | evolve server 内部 | 客户端**不读**这个——只读 `skills/<name>/SKILL.md` 当前生效版 |
| `processed_sessions.json` | evolve server(`record_processed_session`) | evolve server 内部 | 客户端**不读不写**——防重复 drain 的机制 |

> **重写 SkillClaw 客户端时,只需要知道 `manifest.jsonl` + `skills/<name>/SKILL.md` 两个文件**——其它都是 server 端的事。

## 11. bundle 协议(file 清单 / hash 协议)

> **客户端**用 `skill_bundle.py` 读 / 写 bundle(详见 [15 · 技能库与注入](../01-客户端运行时/15-技能库与注入.md) §9);**server 端**用 `evolve_server/storage/oss_helpers.py:save_version_bundle` / `fetch_version_bundle` 落盘 / 读取,见 [33 · 共享层与存储适配](../03-Evolve服务/33-共享层与存储适配.md) §1-§2。本章**不**重复展开。

**客户端必须知道的 bundle 协议约定**(`skill_bundle.py` 通用):
- `bundle = {rel_path: bytes}`,如 `{"SKILL.md": b"...", "references/api.md": b"..."}`
- `bundle_tree_sha256(bundle)`:把每个文件的 (path, sha256, size) 排序后拼 SHA-256,是 bundle 的"内容指纹"
- `bundle_file_records(bundle)`:输出 `files: [{"path": "...", "sha256": "...", "size": N}, ...]`
- 忽略路径:`.DS_Store` / `.git/` / `__pycache__/` / `.pytest_cache/` / `.mypy_cache/` / `.ruff_cache/` / `*.pyc` / `*.pyo`
- `bundle_v1` 是当前的 manifest 格式版本号——manifest.jsonl 的每条记录 `format: "bundle_v1"`

## 13. 待确认 / 已知限制

- **Nacos 不在 `object_storage_from_config` 路径里**：`NacosSkillClient` 不实现 `ObjectStore` 接口——所以"skill 走 Nacos，session 走 OSS"是支持的，但**session 也走 Nacos 是不行的**。**待确认**是否要给 Nacos 加最小 `ObjectStore` 适配。
- **bundle 协议的 `files` 数组没排序保证**：`bundle_file_records` 是 `sorted(coerce_skill_bundle(bundle).items())`——按 path 排序。但 `bundle_tree_sha256` 也按 sorted 排——**一致性** OK，**但** `manifest.jsonl` 的 `files` 字段如果是手工填的可能乱序。**待确认**要不要在 manifest load 时重排。
- **`pull_skills` 的 backup 性能**：`shutil.copytree` 在 N×M 大小的 skill 库上可能慢——N=100 skills, M=10KB/skill, 1000 skills 时单次 pull 要 copy 整个树。**待确认**是否该用 hardlink 而不是 copy。
- **`_select_targets` 不去重**：同名 skill 在 manifest 里出现多次时（理论不应有），后者覆盖前者——但**两次 pull 之间**如果 manifest 出现"幽灵"行，pull 会**创建**新文件然后 `delete_local_extras` 又**删掉**它。**待确认**该在 pull 入口去重。
- **Nacos `access_token` 过期**：当前 `_login()` 只在构造时跑一次。Nacos 默认 token TTL 几小时——**生产**会失效。**待确认**是否需要在每次 request 前检查 `expireTime` 并自动 re-login。
- **`SkillHub.push_skills` 的 race condition**：两个客户端同时 push 同一 skill → 后写覆盖前写；`manifest.jsonl` 不原子（**先** put 各 skill，**最后** save_manifest——race window）。**待确认**是否要用 lock 或 manifest 元数据 version + ETag。
