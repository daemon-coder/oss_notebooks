# DeepSeek Harness 消息排列与上下文注入机制

> 本文基于 deepseek-harness 源码分析（仓库路径：`/Users/daemoncoder/code/oss/deepseek-harness`），
> 回答三个问题：请求里的消息按什么顺序排列？三个注入（AGENTS.md / runtime context / Skill catalog）
> 是如何组织的、什么情况下注入？压缩前后消息序列如何变化？
> 配套文档：[上下文压缩](上下文压缩.md)。

## 1. 请求的整体结构：system 是字段，不是消息

每次调 LLM 接口的请求体由两部分组成（`packages/core/agent-loop/src/agent.ts` `buildRequest`）：

- **`system` 字段**：由 `systemPrompt.assemble()` 每次重新渲染（prompt sections + tool schemas），**不进消息数组、不进会话日志**，每次请求都是最新版，永远完整；
- **`messages` 数组**：`session.deriveMessages()` 的产物——会话事件日志中"surface 节点"的逐条投影，加上本轮 pre-step 注入的新消息。

以 DeepSeek wire 层为例（`packages/llm/llm-deepseek/src/serialize.ts`），**没有合并相邻 user 消息的逻辑**，
每个注入都是独立的一条 `user` 消息：

```
system: <系统提示词>
user: <用户问题>
user: <AGENTS.md 注入（<system-reminder>Instructions from: AGENTS.md…</system-reminder>）>
user: <Current runtime context. This snapshot supersedes…>
user: <system-reminder><available_skills>…</available_skills></system-reminder>
```

> 注：harness 内部每条消息还带 `source` 字段标记注入来源（`user` / `agent-instructions` / `skill-catalog` /
> `plugin:@deepseek-ai/dsh-system-prompt`），wire 层不会带上；tool-result 在 wire 层会从 user 消息里拆成 `role:'tool'`。
>
> **易混淆点**：注入文本里的 `<system-reminder>…</system-reminder>` 只是 **user 消息正文里的标签**，
> 用来提示"这是系统注入的提醒"，**不是** role=`system` 的消息——真正的 system 内容只在 `system` 字段里。

## 2. 一次请求的消息排列全景

```
[system]
[历史 surface 节点…（按日志顺序；也包含之前轮次的注入：问题、AGENTS、context、Skill、assistant、tool_result…）]
[本轮 segment:]
  [用户问题]              ← claimed（step 的锚点）
  [AGENTS.md]            ← agent-instructions 插入
  [runtime context]      ← driver 追加
  [Skill catalog]        ← tool-skill 追加（最末尾）
```

> 注意：注入**每轮都会在本轮 segment 里出现**，所以历史段里也躺着上一轮的旧注入（内容没变时新旧相同、
> 变了时新旧并存，旧的等压缩清理）。

## 3. 顺序是怎么产生的（waterfall 叠加）

`preStep`（`agent.ts:225-243`）先拿到基础决策，再让 `agent/pre-step` waterfall 的监听器依次加工：

1. **基础决策**：`{ messages: [...claimed, context] }`——用户问题在前，runtime context 紧跟其后（`agent.ts:238`）；
2. **agent-instructions 监听器**：把 AGENTS.md 注入**插到最后一个 claimed 消息之后**（`packages/context/agent-instructions/src/index.ts:343-346`，
   注释原话："Fold the context right after the claimed batch, so the direct prompt precedes it and the
   driver-appended runtime context follows it"）→ 得到 `[问题][AGENTS.md][context]`；
3. **tool-skill 监听器**：把 Skill catalog **追加到最末尾**（`packages/skill/tool-skill/src/index.ts:247-250`）→ 得到 `[问题][AGENTS.md][context][Skill]`。

最终顺序是"claimed 锚点 + 注入逐层垫后"的结构使然，并被测试钉死
（`packages/context/agent-instructions/tests/agent-instructions.spec.ts:1210-1223` 断言用户消息文本出现在 AGENTS.md 之前）。

> 说明：waterfall 监听器的 transform 是**逆注册序**执行的，但这里最终顺序与注册顺序无关——因为
> agent-instructions 的插入点（claimed 之后）和 tool-skill 的追加点（末尾）互不重叠，无论谁先 transform，
> 结果都是 `[问题][AGENTS.md][context][Skill]`。

## 4. 三个注入逐个详解

### 4.1 AGENTS.md（`agent-instructions` 插件）

- **注入条件**：工作区存在指令文件（默认候选 `AGENTS.md`、`CLAUDE.md`，另有用户全局 `~/.dsh/AGENTS.md` / `$DSH_HOME/AGENTS.md`）；
  还需要 `maxBytes > 0`（预算可配置、可关闭）和 `ctx.get('fs')` 可用。**没有文件就不注入**。
- **文件发现**：根目录 baseline 直接读；**嵌套目录的 AGENTS.md 依赖工具 touch 机制**——
  模型调用 `read`/`write`/`edit`（带 `file_path` 参数）后，`tools/result` 收集 touch，异步投影队列重新 compose
  （`index.ts:73-81`、`264-277`），pre-step 里的 `waitForProjections` 会等投影 settle 完再组装消息，
  保证"edit 完文件，下一个请求就带新规则"。
- **变更检测**：每个 pre-step 都 `compose()`（baseline 缺失/项目根变化时重读文件，平时做 touched paths 的增量 reconcile、查 inbox pending），内容没变（`sameContextPayload`）就不插入。
- **预算**：`maxBytes` 超限时截断/省略（渲染里带 `truncated …` / `omitted …` 标记）。

### 4.2 runtime context（`agent-loop` 的 `RuntimeContextProjection`）

- **内容来源**：`ctx.systemPrompt.context()` 注册的贡献者（默认有 `sandbox-policy` 的 `sandbox:policy`、approval 的模式等），按 `order` 拼接成一条快照
  （`Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n…`）。
- **注入条件**：快照文本与上次保留的不同才追加（`packages/core/agent-loop/src/runtime-context.ts:64-75`）；
  变空时追加 `Current runtime context: none. …` 清除标记；可被 `suppressRuntimeContext()` 整条抑制。
- **去重**：文本相同 → 不写（测试 `loop.spec.ts:384-386`：连续两轮只出现 1 条）。
- **压缩联动**：surface 替换事件命中自己保留的快照 → `retained = null` → 下一个 pre-step 重新投影（内容没变也会重发）。

### 4.3 Skill catalog（`tool-skill` 插件）

- **注入条件**（`packages/skill/tool-skill/src/index.ts:213-251`）：
  1. `skill` 工具对当前 agent **可见**（被 scope 限制/同名阴影替换则不可见，不注入）；
  2. 快照完整（`snapshot.complete`）；
  3. 存在**模型可调用**的技能（过滤 `isModelInvocable`，排除仅用户可调用/禁用模型调用的技能）；
  4. 首次且技能为空 → **不注入**（`!history.published && skills.length === 0` 直接返回）。
- **变更检测**：每个 pre-step 算快照 digest（技能名+描述），与历史发布比对；变了才发 `renderCatalogUpdate`
  （文案："This complete catalog replaces every earlier available-skills list"）；已发布过再变空 → 发"没有可用技能"的更新。
- 目录只含技能名称 + 截断后的描述（`catalogDescriptionMaxLength` 默认 500），不含正文。

### 4.4 注入触发时机汇总

| 时机 | 行为 |
|---|---|
| 首次请求（第一个 pre-step） | 三个机制**各自独立判定**是否注入（不一定"都"注入） |
| 之后每个 pre-step | 都做变更检测；**变了就在当前 step 尾部追加一条新版本**（旧版本留在历史里，不覆盖），没变就静默 |
| 同一轮内 | 工具 `edit` 文件 / 审批模式切换 / 技能集变化 → 下一个 step 的请求就带上更新 |
| 压缩后 | 即使内容没变也重新注入（可见的被 shadow 了，必须补齐） |
| resume 恢复 | 与磁盘保留版本不一致时按差异补更新 |

## 5. 为什么"问题在前、注入在尾"（缓存与模型体验）

这是对话中最关键的架构问题。直觉上"把静态的注入放前面、问题放最后"似乎缓存更好，但 harness 的设计恰恰相反，原因：

1. **注入是易变内容，不是静态内容**。尤其 runtime context 是"当前状态快照"，设计上就是要随状态频繁变化；
   AGENTS.md 会被工具修改、catalog 会随技能集变化。把易变内容放最前 = **一变就导致其后的全部内容缓存失效**；
   放尾部 = 变化只影响它之后的一小段尾部。
   这正对应代码文档引用的 Anthropic 公开缓存指导："places changing per-request context **after** the stable cached prefix"
   （见 `.agents/notes/implemented/feature/2026-07-30-current-sandbox-policy-context.md`）。

2. **"不变不写"的去重机制**使轮内注入成为稳定前缀：同一轮内 step1 → step2，
   `[问题][AGENTS][ctx][Skill]` 逐字节一致，天然命中缓存；只有真正变化才追加。

3. **跨轮缓存匹配的是"system + 完整历史"，与当前轮 segment 的内部顺序无关**。请求 = system + 完整历史 + 当前轮 segment。
   "把注入挪到 system 后"并不会多命中任何东西：注入没变时，它作为**上一轮的历史**照样位于匹配前缀里；
   真正的差异只在**注入变化时**——
   - 现状（注入在尾）：上一轮的注入在"历史段"里照常命中，本轮注入的变化只让尾部一小段未命中；
   - 你的方案（注入在头）：注入一变，请求的第一个 token 就与上一条请求不同，`[AGENTS][ctx][Skill][全部历史][问题]` 整段失效，只剩 system 命中。
   换句话说：放头部"赌注入不变"没有额外收益，却在注入变化（runtime context 的设计常态）时付出整段失效的代价。

4. **实测证据**：sandbox-policy 的 Agent Note 记录了权限切换场景的实测——
   每请求缓存读取 **14,848–15,872 tokens**、未缓存输入仅 **59–306 tokens**，
   证明"易变内容放尾部"下即使状态频繁变化，主体仍命中。

5. **模型体验**：问题紧跟 system（主指令在前），注入作为"提醒"垫后；而需要执行的素材
   （skill content 注入）按设计注释放在最后、离回答最近（`tool-skill/src/index.ts:163-176`）。

## 6. 如何判断一条消息是不是 surface 节点

三层判定（`packages/core/session/src/surface.ts`）：

1. **类型门槛**：只有 `user/message`、`assistant/message`、`tool/result` 三种事件类型能成为节点；
2. **标记门槛**：必须带 `surfaceOp`（`'append'` 或 `{op:'replace',start,end}`）——这三类事件不带标记会抛错，非这三类带标记也会抛错；
3. **权威判定**：`seq ∈ session.surface.nodes`——`nodes` 是当前按模型可见顺序排列的节点 seq 数组，
   `deriveMessages()` 就是逐节点投影出来的。被压缩 replace 遮蔽的旧节点不在数组里。

注意："是节点" ≠ "能派生出一条消息"（空内容的 `assistant/message` 是节点但投影为 null）；
`sourceEventSeqs` 不是判定条件而是 provenance 校验（replace 时必须引用全部被遮蔽节点）。

## 7. 存储与投影：历史是怎么存、怎么读的

- **内存真相源**：append-only 事件日志（`SessionEvent[]`，事件 append 时 deep-freeze，`seq = log.length` 连续契约）；
  surface 是它的增量投影（`SurfaceManager` 惰性 fold）。
- **磁盘**：write-behind 批量落盘（`PersistenceCoordinator`，按会话串行链 + 固定延迟窗口）：
  - **JSONL 后端**：`root/<项目key>/<encodeSegment(id)>/session.jsonl(.zstd)`，第一行是 `type:'session'` 头，之后每行一个事件记录（可选 zstd 压缩、可选 chunk 打包多事件一行）；
  - **SQLite 后端**：事件拆列存储 `(id, seq, type, time, data, sourceEventSeqs, surfaceOp, ignorable)`。
- **读取（进程内续接）**：Session 在内存，`deriveMessages()` 增量投影——`SurfaceManager` 惰性 fold 新事件到 `nodes`，
  缓存游标只投影新增节点；压缩 replace（`replaceGeneration` 变化）时整体重建缓存。
- **读取（重启恢复）**：`prepareCore` 从后端 `loadStored` 读出完整事件数组 → 校验格式/seq → 合成中断轮次的 `turn/end` →
  `sessions.prepare(id, {seed, meta})` 重建 Session（逐事件走同一套 surface 校验 + deep-freeze）→
  `requestHeader()`/`requestContext()` 通过 fold 缓存恢复上次的 system/tools（保证恢复后 system 字节不变、前缀缓存不失效）。

## 8. 压缩前后的消息序列对比

以"第一轮带工具调用、第二轮结束"为例（详见《上下文压缩》）：

```
压缩前请求的 messages：
  [user1][AGENTS1][ctx1][Skill1] [ai1(带tool_call)] [tool_result] [user2][AGENTS2][ctx2][Skill2] [ai2]
  \________________________________ 压缩范围（头部到保留尾前） ________________________________/ \_尾_/

压缩后下一次请求的 messages：
  [checkpoint 摘要] [user2][ai2] [新问题 user3] [重新注入的 AGENTS3] [重新注入的 ctx3] [重新注入的 Skill3]
```

要点：checkpoint 顶替被压范围（旧节点 shadowed，日志不删）；保留尾原样；三个注入**重新注入到新问题之后**
（不是 checkpoint 之后）；system 永远重新生成、从不参与压缩。

## 10. 一句话总结

**请求 = 重新生成的 system + 逐节点投影的历史消息 + 本轮"问题在前、注入垫后"的 segment；
三个注入各自独立判定、每个 pre-step 检测变更、变了才在尾部追加新版本（旧版本留历史等压缩清理）；
压缩把头部整体换成摘要，注入随后在新问题之后重来一遍——保证模型永远看到最新规则，且变化的影响被限制在请求尾部。**
