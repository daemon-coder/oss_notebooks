# DeepSeek Harness 插件机制详解（面向 Go 开发者）

> 目标读者：有 Go 和 agent 开发经验、但不熟悉 Node.js / TypeScript / Cordis 的开发者。
> 本文用 Go 的心智模型逐层解释 DeepSeek Harness 的插件机制，不依赖任何 TS 背景知识。
> 文末附有 "Fiber" 这个名字的词源解释。

## 0. 术语对照表（先把生词翻译成 Go 说法）

| Cordis/TS 里的词 | 用 Go 的说法就是 |
|---|---|
| **Context（上下文）** | 一个 `map[string]any`，存"名字 → 能力"，所有插件共享。类似 `context.Context` 里塞 value，但它是**依赖容器** |
| **Service（服务）** | 放进那个 map 里的一个值，通常是一个接口实现，比如 `ctx.shell` ≈ `ctx.Get("shell")` |
| **Plugin（插件）** | 一段启动代码：拿到 ctx，往里 `Provide` 服务、注册工具、订阅事件；可返回一个 cleanup |
| **Fiber** | 一个插件的**运行实例**：记住"这个插件注册了哪些 cleanup、当前什么状态"（词源见文末） |
| **effect** | "做一件可逆的事，把它产生的撤销函数记下来"。Go 里就是 setup 返回 `func()` |
| **inject（依赖）** | 声明"我这个插件要先有 `shell`、`subprocess` 才能启动"，框架按依赖排序自动加载 |
| **store** | 纯内部细节：一个插件"我已经拿到的依赖"的缓存 map。**可以暂时忽略这个词** |
| **event（事件）** | 一个发布/订阅总线；其中 `waterfall` 就是 Go 的 `http` middleware 链 |

## 1. 第一步：你在 Go 里写 agent harness，会怎么组织？

假设你要做一个 agent 运行环境，里面有：调 LLM 的、跑 bash 的、读写文件的、记录会话日志的。你最自然的写法大概是：

```go
type App struct {
    LLM     LLMClient
    Shell   ShellExecutor
    FS      FileSystem
    Tools   map[string]Tool
}

func main() {
    shell := NewLocalBash()       // 逐个 new 出来
    fs    := NewLocalFS()
    llm   := NewDeepSeek()

    app := &App{
        LLM:   llm,
        Shell: shell,
        FS:    fs,
        Tools: map[string]Tool{
            "bash": NewBashTool(shell, fs),   // 手动把依赖传进去
            "read": NewReadTool(fs),
        },
    }
    app.Run()
}
```

这没有任何问题，但有几个**会越来越痛的毛病**：

1. **换实现要改代码**：想从 `LocalBash` 换成"远程沙箱里的 bash"，你必须在 `main()` 里改 import 和 new，所有 `NewBashTool(shell, ...)` 的实参类型可能都得跟着动。
2. **依赖顺序是手写死的**：谁先谁后、`BashTool` 需要 `shell` 和 `fs` 这个事实，藏在 `main()` 里，没人能自动知道。
3. **没有"卸载"**：进程退了拉倒，但如果想**运行时热更新**（改配置换个 provider、卸载某个工具），你得自己写一堆清理逻辑，而且很容易漏。

Cordis 就是针对这三个痛点给的一套答案。它不引入任何魔法，只是换了个组织方式。

---

## 2. 第二步：核心转折 —— 用一个"共享服务表"替代"手动传依赖"

先看最小的一步。把"App 结构体里那些字段"换成一个 `map`：

```go
type Context struct {
    services map[string]any
}

func NewContext() *Context {
    return &Context{services: map[string]any{}}
}

// 注册一个能力，返回"撤销注册"的函数
func (c *Context) Provide(name string, svc any) func() {
    c.services[name] = svc
    return func() { delete(c.services, name) }
}

// 按名字取能力（等价于 TS 里的 ctx.shell）
func (c *Context) Get(name string) any {
    return c.services[name]
}
```

现在，**一个能力 = map 里一个带名字的值**。`ctx.shell` 这个写法，本质就是 `ctx.Get("shell")`。这就是 Cordis 里"Context 是服务的仓库"的全部含义——它和 Go 的 `context.WithValue` 思路很像，但用途是**依赖装配**，不是传取消信号。

> 一个类比：这就像你们公司内部的"服务发现"。A 团队要用 B 团队的接口，不去 `import` B 团队的具体代码，而是喊一句"我要 `shell` 这个服务"，注册中心把当前挂着的那个实现给它。

---

## 3. 第三步：插件 = 一段 setup 代码 + 一堆 cleanup

有了 map，接下来定义"插件"。Cordis 里插件本质上就是：

```go
type Plugin interface {
    // Apply 拿到 ctx，往里塞服务、注册工具、订阅事件……
    // 返回值 cleanup：当插件被卸载时执行（可以为 nil）
    Apply(ctx *Context) (cleanup func(), err error)
}
```

一个"本地 bash 提供者"插件长这样：

```go
type LocalBashProvider struct{}

func (LocalBashProvider) Apply(ctx *Context) (func(), error) {
    bash := &LocalBash{}                    // 自己 new 出实现
    return ctx.Provide("shell", bash), nil  // 挂到服务表，返回撤销函数
}
```

关键点：**`Provide` 返回的撤销函数，就是插件的 cleanup**。当插件卸载时，把这个名字从表里删掉，别人就再也取不到了。这就是"可逆"的来源。

---

## 4. 第四步：Fiber 和 effect —— 记住所有 cleanup，卸载时逆序执行

一个插件通常要注册**很多东西**：塞一个服务、订阅一个事件、挂一个工具……每一件都是"可逆"的，都该有一个对应的撤销动作。Cordis 用一个东西统一管理这些撤销动作，这个东西就叫 **Fiber**。

用 Go 写出来极其直白：

```go
type Fiber struct {
    ctx      *Context
    cleanups []func()   // 按注册顺序追加
    state    string     // pending / active / disposed
}

// effect：立刻执行 fn，它返回的 cleanup 被记录下来
func (f *Fiber) Effect(fn func() func()) {
    f.cleanups = append(f.cleanups, fn())
}

// 卸载：逆序执行所有 cleanup（后注册的先撤销）
func (f *Fiber) Unload() {
    for i := len(f.cleanups) - 1; i >= 0; i-- {
        f.cleanups[i]()
    }
    f.state = "disposed"
}
```

所以：

- **Fiber = 一个插件运行起来后，用来记账的那个结构体**。它记着"我这个插件注册了哪些可逆操作，现在是什么状态"。你不需要关心它内部多复杂，记住这句话就够了。
- **effect = "做一件可逆的事，同时把它产生的撤销函数交给我记账"**。Cordis 里 `ctx.on(...)`、`ctx.provide(...)`、`ctx.tools.register(...)` 内部全都是 effect。它们都会返回一个 disposer（撤销函数）。

为什么逆序？和 Go 的 `defer` 一样是 LIFO：先开的资源要后关。比如插件先 Provide 了服务 A，又基于 A 订阅了事件 B；卸载时要先撤销 B，再撤 A。

**这一步是整个机制最重要的思想**：因为"注册"这件事本身是可逆、可记账的，所以**卸载、热更新、作用域回收就都变成了"把 cleanups 逆序跑一遍"**，没有漏网之鱼。Go 里你靠 `defer` + 函数返回 `func()` 也能做到，Cordis 只是把它做成了每个插件的强制纪律。

## 5. 第五步：inject —— 声明依赖，框架自动排序加载

前面 `BashTool` 需要 `shell` 和 `fs`，Go 里是你手动在 `main()` 里传进去的。Cordis 改成**声明**：

```go
type BashToolPlugin struct{}

// 声明：我依赖这两个服务，它们都好了再启动我
func (BashToolPlugin) Inject() []string {
    return []string{"shell", "fs"}
}

func (BashToolPlugin) Apply(ctx *Context) (func(), error) {
    shell := ctx.Get("shell").(ShellExecutor)  // 保证能取到
    fs    := ctx.Get("fs").(FileSystem)
    // ...注册 bash 工具
    return nil, nil
}
```

框架（Registry）做的事：

```go
func (r *Registry) Load(def PluginDef) {
    for _, dep := range def.Inject() {
        if r.ctx.Get(dep) == nil {
            // 依赖还没齐，先挂起，等 dep 出现再加载
            r.pending = append(r.pending, def)
            return
        }
    }
    // 依赖齐了，Apply
    cleanup, _ := def.Apply(r.ctx)
    ...
}
```

好处：**加载顺序不用手写**。`shell` 提供者先 `Provide("shell")`，这时一直挂起的 `BashTool` 发现自己依赖齐了，自动被叫起来。你要加一个新工具、挪一个 provider，改的是声明，不是装配代码。

> Go 类比：这就像 `github.com/google/wire` 或 `fx` 做依赖注入，只不过 Cordis 是**运行时动态**的（可以热加载/卸载），而 wire 是编译期静态的。

## 6. 第六步：事件 + waterfall —— 就是 Go 的 http middleware

最后一个你可能不熟的词是"事件/waterfall"。先看**普通事件**，就是 pub/sub：

```go
ctx.On("tool_executed", func(name string, result any) {
    log.Printf("tool %s done", name)
})
```

而 `waterfall` 是特殊的一种，它是**可以插手的中间件链**。Go 程序员看这个签名一定秒懂：

```go
// Cordis 的 waterfall 监听器
type WaterfallListener func(args []any, next func() error) error
```

这和 `net/http` 的 middleware 一模一样：

```go
// Go 的 http middleware
func middleware(next http.Handler) http.Handler { ... }
```

规则也一样：**你可以决定调不调 `next`**。

- 调了 `next()` → 让后面的监听器（或默认行为）继续跑，你可以包一下结果再返回；
- 不调 `next()` 直接返回 → **截断/否决**，后面的不跑了。

这就是 dsh 里"策略插件能拦截甚至改写模型要看到的内容"的机制：比如 `agent/pre-step` 这个事件，策略插件可以改写要发给模型的消息，或者直接拒绝这一轮。普通的 `log.Printf` 式观察做不到"改写"，middleware 能。

## 7. 第七步：串起来 —— dsh 的 shell 到底怎么用这套东西

把上面所有概念用一遍，就是 dsh 里"换 shell 实现"的完整故事（三个角色）：

**角色一：定义接口**（dsh 里叫 Service Definition）

```go
// 只说"shell 这个能力长什么样"，不实现
type ShellExecutor interface {
    Run(spec ShellSpec) (ShellResult, error)
}
```

**角色二：给一个实现**（Provider），并注册成服务

```go
type LocalBashProvider struct{}
func (LocalBashProvider) Apply(ctx *Context) (func(), error) {
    return ctx.Provide("shell", &LocalBash{...}), nil
}
```

**角色三：使用它**（Consumer），比如 `bash` 工具

```go
type BashTool struct{}
func (BashTool) Inject() []string { return []string{"shell"} }
func (BashTool) Apply(ctx *Context) (func(), error) {
    shell := ctx.Get("shell").(ShellExecutor)   // 按名字取，不 import LocalBash
    return ctx.Provide("tool:bash", Tool{run: shell.Run}), nil
}
```

**注意角色三里最关键的一行**：`ctx.Get("shell")` 而不是 `import LocalBash`。所以哪天你想把 bash 换成"跑在远程沙箱里"，只需要再写一个 `SandboxBashProvider` 把它 `Provide("shell", ...)`，**`BashTool` 一行都不用改**。这就是 Cordis 所谓的"换 provider 不 fork 消费者"，也是 dsh 里 `packages/shell/` 目录下一堆包（`dsh-shell` 定义 / `dsh-bash-local` 实现 / `dsh-tool-bash` 使用）的意义。

## 8. 第八步：那整个 dsh 是怎么"组装"起来的？

最后一步你就能看懂架构文档了：一个运行中的 dsh，就是把**一堆这样的插件**（LLM 适配器、工具注册表、会话日志、agent loop……全都是插件）按一份配置列出来，框架读配置 → 逐个 `Load` → 按 `Inject` 依赖自动排序 → 每个变成一个 Fiber 记账。

配置（`cordis.yml`）大概就是一份"我要挂这些插件、每个配什么参数"的清单。所谓"热更新""改配置换 provider"，底层就是：把某个 Fiber 的 cleanups 逆序跑掉，再用新配置重新 Apply 一遍。你回头看第四步的 `Fiber.Unload()`，整件事的机制其实已经在你脑子里了。

---

## 9. 小结：你只需要记住 4 个点

1. **Context = 一个共享的 `map[string]any`**，能力按名字存取（`ctx.shell` = `ctx.Get("shell")`）。
2. **Plugin = 一段 setup 代码**，可以塞服务、注册工具、订阅事件。
3. **Fiber/effect = 记账机制**：每个可逆操作都返回撤销函数，卸载时逆序执行（Go 的 `defer` 思路）。
4. **inject + waterfall = 自动装配 + 可插手的中间件**（前者像 wire/fx，后者就是 http middleware）。

至于 `Proxy`、`declare module`、`symbol`、`epoch`、`store`，**都是 TypeScript/Node 的实现细节**，用来做静态类型、属性拦截、热更新记账的——理解这套思想完全不需要它们，可以全部忽略。

## 附 A："Fiber" 这个名字的含义

**代码里的事实**：在 Cordis 里，一个插件回调（callback）对应一个共享的 `Runtime` 记录，而这个 `Runtime` 上挂着一个 `fibers: DisposableList<Fiber>`，源码注释写着：

> Every live fiber of this plugin (one per `ctx.plugin()` call).

也就是说：**同一个插件可以被多次挂载到不同的 context，每一次挂载都产生一个独立的 Fiber**。同一个插件（一份代码），可以有多个"运行实例"（多个 fiber），各自有独立的生命周期、配置、effects，但它们共享同一个 `Runtime`。

**名字来源（最合理的解读）**：这个词来自数学里的 **fiber（纤维）**，出处是 **fiber bundle（纤维丛）** 这个概念。一个纤维丛由"总空间 + 底空间 + 投影映射"构成：底空间上每一个点，其"上方"的原像就叫做该点的**纤维（fiber）**。

对应到 Cordis 的结构里：

| 数学概念 | Cordis 里的对应 |
|---|---|
| 丛 / 总空间（bundle） | 插件本身（那份共享的 callback / Runtime） |
| 底空间上的一个点（base point） | 一个具体的 context（挂载位置） |
| 该点上方的纤维（fiber） | 这次挂载产生的那一份实例（Fiber） |

这个类比非常贴切：一个插件被"铺"到多个 context 上，就像一束纤维铺在底空间上；**同一根 bundle 在不同点上方，各有一根 fiber**。每根 fiber 是独立的（有自己的生命周期和配置），但又都属于同一个丛（共享同一个 callback）。这也解释了为什么类型叫 `Runtime.fibers`（复数）——一个 Runtime 下挂着一束 fiber。

**诚实说明**：本仓库的文档只描述了"fiber 是什么"（"一个已加载插件实例：它的生命周期状态、校验后的配置、以及注册过的 effects"），并没有明文记录这个命名的词源；"纤维丛"是基于代码结构（一 Runtime 多 fiber 的对应关系）最自然、也是社区通用的解读。

**另一个较弱的联想**：编程里 "fiber" 也指"纤程"（轻量级线程、协程，可挂起/恢复的执行单元，如 Ruby 的 Fiber、Windows Fiber）。它和 Cordis 的语义只有一层浅对应——fiber 有可挂起/恢复的生命周期（PENDING/ACTIVE/UNLOADING 之间切换）——但"一份插件实例 + 记账"这个核心含义明显更贴近"纤维丛"里的 fiber，而非"纤程"。
