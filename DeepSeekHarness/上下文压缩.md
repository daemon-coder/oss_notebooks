# DeepSeek Harness 上下文压缩（Compaction）机制

> 本文基于 deepseek-harness 源码分析（仓库路径：`/Users/daemoncoder/code/oss/deepseek-harness`），
> 主要涉及 `packages/compaction/compaction-basic/`、`packages/core/session/`、`packages/core/agent-loop/`。
> 配套文档：[消息排列与上下文注入](消息排列与上下文注入.md)。

## 1. 为什么需要压缩

LLM 上下文窗口有限。多轮对话 + 工具调用会让会话历史不断增长，到达窗口上限后请求会失败或质量下降。
DeepSeek Harness 的做法是：**把历史头部的一段"浓缩"成一条摘要（checkpoint），替换掉原始消息**，让模型继续对话。

核心设计点：

- 会话的**真相源是 append-only 事件日志**，压缩只影响"模型可见视图"（surface），**磁盘上的原始事件不会被删除**；
- 被压缩的内容仍可通过日志完整重建（"模型可见 ⟺ 日志可重建"不变量）；
- 压缩后，三个上下文注入（AGENTS.md / runtime context / Skill catalog）会在下一次请求前**重新注入**，保证模型看到的是最新规则。

## 2. 触发时机（两个）

| 触发 | 时机 | 条件 | 保留尾部 |
|---|---|---|---|
| **pressure（压力）** | 每个 `agent/pre-step`（即每次请求前） | `totalTokens >= thresholdRatio × contextWindow`（默认 `0.8`） | `retainRatio × contextWindow`（默认 `0.16`） |
| **context-overflow（溢出恢复）** | `agent/request-error` 且 provider 返回 `CONTEXT_WINDOW_EXCEEDED` | 无需阈值判断，直接压 | **0**（几乎全压） |

- pressure 触发的检查在 `agent/pre-step` 的监听器里（`packages/compaction/compaction-basic/src/index.ts:147-165`），压缩发生在请求组装之前；
- overflow 触发在 `agent/request-error` 监听器里（`index.ts:179-223`），压缩成功后返回 `{kind:'retry'}` 重试同一请求；
- 压缩前会先尝试模型无关的 `toolResultPruner`（裁剪巨大工具结果）；overflow 场景剪完直接压，pressure 场景剪完仍超阈值才做摘要压缩；
- **冷启动不触发**：pressure 需要 `routedTarget`（即已路由过一次请求、有 request header 记录 provider/model），首次请求前没有 header，`compactIfNeeded` 直接返回 `null` 不压缩；
- 相关配置（`packages/compaction/compaction-basic/src/config.ts`）：
  `thresholdRatio`(0.8)、`retainRatio`(0.16)、`retainTokens`、`summarizationProvider/Model`、`maxTokens`(8192)、`compactionRetries`(1)、`maxOverflowRetries`(1)、`modelPolicies`、`auto`(true)。

## 3. 压缩范围怎么选

`selectCompactableRange`（`packages/compaction/compaction-basic/src/region.ts:98-134`）三步：

1. **定价**：用 `ctx.tokenMeter` 对 surface 每个节点估算 token 数；
2. **保留尾部**：从最后一个节点往前累加 token，直到凑够 `retainTokens`，得到 `keepFromIdx`——这个索引之后的节点**原样保留**；
3. **平衡边界回退**：如果 `keepFromIdx` 处会**拆散一个 assistant 消息的 tool-call 与其 tool-result 对**（`toolPairingBalancedBefore`），就继续往前退到平衡边界。

最终压缩范围 = **`[第一个 surface 节点, 保留尾之前的节点]`**——注意是**从头开始**，所以首次用户问题、AGENTS.md、runtime context、Skill catalog 这些头部消息**全在压缩范围内**（除非被保留尾覆盖）。

```
压缩前 surface 节点（示意）：
  [user1][AGENTS][ctx][Skill][ai1(带tool_call)][tool_result][user2][ai2]
   \_____________________ 压缩范围 ____________________/ \_ 保留尾 _/
```

溢出触发时 `retainTokens=0`：保留尾只剩**最后一个节点**（若最后一个节点是不平衡的 assistant tool-call，则继续向前回退到平衡边界），其余几乎全压。

## 4. 压缩事务的执行流程

`compactSurfaceRegion`（`region.ts:152-254`）是一个带锁的事务：

```
1. validateSurfaceRegion   —— 校验 start/end 在 surface 上、边界平衡
2. compaction/start         —— 写入事件日志（事务锁，防止并发压缩）
3. prepareCompaction        —— 快照定价 + 构建摘要输入（含 token 数快照）
4. summarizeCompaction      —— 调 LLM 生成摘要；校验摘要比原文小，否则抛错
5. 稳定性校验                —— 总结期间 surface 若被改写则中止（whole-surface / selected-span）
6. commitCompactionBody     —— append checkpoint 消息：surfaceOp: {op:'replace', start, end}
7. compaction/end           —— 收尾（失败也写 end + error）
```

关键：`commitCompactionBody`（`region.ts:427-478`）追加一条 `user/message`（source 标记 `compact`），
其 `surfaceOp: { op: 'replace', start, end }` 使 surface 上 `[start, end]` 区间的节点被**遮蔽（shadowed）**，
checkpoint 自己的 seq 顶替其位置。之后 `deriveMessages()` 不再产出被遮蔽节点的消息。

> 旧节点仍留在 append-only 日志里（磁盘不删）；checkpoint 的 `sourceEventSeqs` 引用所有被遮蔽节点，
> 满足"模型可见内容可从日志重建"的 provenance 校验（`surface.ts:211-243`）。

## 5. 摘要调用复用会话的 KV 缓存（重要设计）

压缩要额外发一次 LLM 请求做总结。早期的实现里这次请求的前缀与会话不一致，导致**整个历史被算两次**。
现在的实现（`buildSummarizationInput`，`region.ts:498-514`）：

- 输入 = 会话自己的 `system` + `tools` + **压缩区域内按 surface 原顺序**的消息 + 追加的压缩指令；
- 这样总结请求的前缀与主会话最后一条请求**逐 token 一致**，能命中 provider 的 KV 缓存（prefix cache）。

参见设计笔记：`/Users/daemoncoder/code/oss/deepseek-harness/.agents/notes/implemented/bug-fix/2026-07-21-compaction-summary-prefix-cache-reuse.md`。

## 6. 压缩总结的原始提示词（COMPACTION_INSTRUCTION）

总结请求的完整构成（`packages/compaction/compaction-basic/src/summarizer.ts` `summarizeWithLlm`）：

- **输入**：重放的 `system`（会话自己的）+ `tools` + 压缩区域内按 surface 顺序的 messages；
- **压缩指令**：作为**最后一条 user 消息**追加（`summarizer.ts:31-66`），而不是独立的 summarizer system prompt——这样整个请求是最后一次主请求的"真前缀"，只有一条新消息，最大化 KV 缓存命中；
- **目标模型**：`summarizationProvider/Model` 配置 > 最近路由的请求 header > AgentOptions（`summarizer.ts:128-138`）；
- **输出约束**：只接受纯文本（含图片抛错、空输出抛错）；`maxTokens` 截断抛 `MAX_TOKENS`，绝不落一个不完整的检查点。

### 6.1 压缩指令原文（英文，逐字）

```text
You are now acting as a compaction engine for this AI coding assistant. Condense the conversation ABOVE into a structured checkpoint that lets another model resume the work with no loss of essential context.

Output EXACTLY the Markdown structure below: keep every section, in order. Use terse bullets, not prose paragraphs. Write "(none)" for an empty section — never drop a section.

## Primary Request and Intent
- [the user's original and evolving goals; quote verbatim where the exact wording matters]

## Key Technical Concepts
- [technologies, frameworks, patterns, and conventions in play]

## Files and Code
- [exact path: why it matters, key changes or snippets]

## Errors and Fixes
- [error: how it was resolved, plus any related user feedback]

## Pending Jobs
- [explicitly requested work not yet completed]

## Current Work
- [precisely what was in progress at this checkpoint]

## Next Step
- [the single next action, directly in line with the most recent request, or "(none)"]

## Critical Context
- [decisions and their rationale, constraints, user preferences, open questions, data needed to continue]

Rules:
- Write concise English engineering prose. Preserve exact file paths, commands, error strings, identifiers, numeric values, function signatures, and syntax fragments.
- Capture user feedback and explicit instructions faithfully, especially corrections.
- Do NOT mention this summarization request or that the context was compacted.
- Output only the checkpoint text: do not call any tool or take any other action.
- If the conversation already contains a <compacted-summary> block, it is a PRIOR checkpoint. Do not copy it forward verbatim: preserve still-true facts, drop stale ones, and merge newer information into a single consolidated summary under the same structure.
```

```text
严格按下面的 Markdown 结构输出：保留每一个小节，顺序不变。使用简短的要点，不要写成散文段落。空的小节写 "(none)"——绝不要删掉任何小节。

## 主要请求与意图

## 关键技术概念
- [涉及的技术、框架、模式与约定]

## 文件与代码
- [精确路径：为什么重要、关键改动或片段]

## 错误与修复
- [错误：如何解决的，以及相关的用户反馈]

## 待办事项
- [明确要求但尚未完成的工作]

## 当前工作
- [在此检查点时刻正在进行的确切内容]

## 下一步
- [唯一的下一个动作，直接对应当前最近的请求；没有则为 "(none)"]

## 关键上下文
- [决策及其理由、约束、用户偏好、未决问题、继续所需的数据]

规则：
- 用简洁的英文工程措辞书写。保留精确的文件路径、命令、错误字符串、标识符、数值、函数签名和语法片段。
- 忠实记录用户反馈和明确指示，尤其是更正类内容。
- 不要提及本次总结请求，也不要提及上下文曾被压缩。
- 只输出检查点文本：不要调用任何工具或采取任何其他动作。
- 如果对话中已包含 <compacted-summary> 块，那是之前的检查点。不要逐字照搬：保留仍然成立的事实，丢弃过时的内容，并将更新的信息合并为同一结构下的一份完整摘要。
```

### 6.3 落地的 checkpoint 帧（给"续接任务的模型"看）

总结完成后，`frameSummary`（`summarizer.ts:189-195`）把模型输出包装成落地的 checkpoint user 消息：

```
<compacted-summary>
…模型输出的结构化摘要（6.1 的结构）…
</compacted-summary>
```

消息开头固定是 `CHECKPOINT_PREAMBLE`（`summarizer.ts:69-70`）：

> **原文**：This is an automatically generated checkpoint condensing an earlier span of the conversation to free up context. Treat the captured context as established background and build on it without restating it. Continue the task directly from the messages that follow, without acknowledging this checkpoint.
>
> **译文**：这是一份自动生成的检查点，浓缩了对话中较早的一段以释放上下文。请将其中记录的内容视为既定背景，在此基础上继续而不复述。直接从接下来的消息继续任务，无需提及此检查点。

> 注意区分两个角色：**压缩指令**是给"总结模型"看的（要求结构化浓缩、保留关键细节）；**checkpoint 帧**是给"续接任务的模型"看的（把摘要当作既定背景，不要复述、不要提及压缩）。

## 7. 压缩后的下一次请求长什么样

压缩后 surface 变为 `[checkpoint][保留尾...]`。下一次请求（有新用户问题时）：

```
system（重新生成，永远完整）
[checkpoint 摘要]          ← 顶替被压缩的头部（注意：checkpoint 是一条 user 角色消息，
                             即使被压范围里混有 assistant/tool 消息）
[保留尾: user2][ai2]       ← 原样保留
[新用户问题 user3]
[重新注入的 AGENTS.md]      ← agent-instructions 重新 compose 并插入
[重新注入的 context]        ← RuntimeContextProjection 重新投影快照
[重新注入的 Skill]          ← tool-skill 重新发布目录
```

三个注入的重新注入细节（机制见《消息排列与上下文注入》）：

- **AGENTS.md**：`compose` 发现可见 baseline 已被 shadowed → 重新插入最新文件内容（测试：`packages/context/agent-instructions/tests/agent-instructions.spec.ts:1708-1749`）；
- **context**：`RuntimeContextProjection` 监听到替换事件命中自己保留的快照 → `retained = null` → 下一个 pre-step 重新投影（即使内容没变也会重发）（测试：`packages/core/agent-loop/tests/loop.spec.ts:413-446`）；
- **Skill**：`catalogHistory` 发现可见目录已不在 surface → 以 update 形式重发（`packages/skill/tool-skill/src/index.ts:361-377`）。

## 8. 压缩的多轮叠加

压缩是可重复的：下一轮压缩的范围从当前 surface 头部开始，**会连上一次的 checkpoint 一起再压**。
也就是说摘要会被"摘要的摘要"不断浓缩（模型不可见中间版本，只有最新 checkpoint 可见）。
仓库里有一个**未实现的提案**（recallable compaction）专门讨论这个问题——头部 checkpoint 每轮被重写，
请求前缀每次都整段缓存失效，且模型无法回读被遮蔽的内容：
`/Users/daemoncoder/code/oss/deepseek-harness/.agents/notes/proposed/feature/2026-07-06-recallable-compaction.md`

## 10. 一句话总结

**"头部整体换摘要 + 尾部保留 + 注入在下一次请求时按原插入规则重来"**——压缩只改模型可见视图，
日志原样保留；摘要调用复用会话前缀缓存；三个注入在压缩后重新注入以保证模型看到最新状态。
