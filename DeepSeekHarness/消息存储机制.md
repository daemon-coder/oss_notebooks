# DeepSeek Harness 消息存储机制

> 本文面向**完全没接触过 DeepSeek Harness（以及 Cordis 插件框架、事件溯源这类概念）的读者**。
> 回答几个问题：对话消息**存在哪**？**什么时候存**？**存了什么内容、存成什么格式**？
> 写盘到底是**同步还是异步**、会不会拖慢主流程？以及长期单会话下**读会不会越来越慢、怎么优化**。
>
> 文中每一个概念都会在用到之前先用大白话解释，不预设任何背景知识。
> 全文几乎不写代码，只按需给出落盘文件的真实行结构示意。
>
> 配套文档：[消息排列与上下文注入](消息排列与上下文注入.md)、[上下文压缩](上下文压缩.md)。
> 建议先读"消息排列"那份了解"surface / 事件日志"是什么，再读本文了解它到底是怎么被保存下来的。

## 1. 先分清两件事：对话消息 ≠ 文件

进入正题前，先划清一个容易混淆的边界。一个智能体在干活时，会产生**两类完全不同的东西**：

| 东西 | 是什么 | 例子 |
|---|---|---|
| **对话消息** | 对话本身的逐条记录 | 用户的话、AI 的回答、工具执行的结果、系统设定 |
| **文件** | 智能体用"写文件"能力落盘的内容 | 它帮你生成的一份报告、一段代码 |

这两类东西在 DeepSeek Harness 里的**保存方式完全不同**：

- **文件**是智能体主动"写"出来的，由**文件系统能力**（`packages/fs/`）负责，存到哪取决于你配的文件后端（本地磁盘、内存等）；
- **对话消息**则属于**会话（Session）**，由**会话持久化能力**（`packages/session/`）自动替它保存，智能体自己不用操心。

本文只讲**对话消息（会话）**这一件事。文件怎么存，是另一个话题。

## 2. 消息存在哪：内存里的"事件日志"，磁盘上的一个 JSONL 文件

### 2.1 关键概念：真相源是一条"事件日志"，不是"消息列表"

这是 DeepSeek Harness 与很多框架（包括 DeepAgents）最不一样的地方。它内部**不是**维护一份"消息列表"，而是维护一条**只追加、从不修改的事件日志（append-only event log）**：

```
[事件 0] [事件 1] [事件 2] [事件 3] ……
   ↑ 按顺序往后追加，seq（序号）就是它在队列里的位置，永不改写
```

每一件"发生了什么"都是一条**事件**：用户发了句话是一条事件、AI 回了条消息是一条事件、工具返回结果是一条事件、一轮对话开始/结束也是事件。**消息只是其中一类事件**（下文第 4 节细说）。

这条日志有几个铁律：

- **只追加、不覆盖、不删除**：新事件永远排在末尾，序号 `seq` 从 0 连续递增（`seq = 日志长度`）；
- **追加即冻结**：一条事件一旦进日志，就被深度冻结（deep-freeze），谁也不能再改它；
- **模型可见 ⟺ 日志可重建**：任何会出现在模型请求里的内容，都必须能从日志里还原出来。

> 配套文档《上下文压缩》会反复用到这一点：压缩（compaction）只会改"模型看到的视图"，**磁盘上的日志原样保留、绝不删**。

### 2.2 内存里：`Session` 对象就是这条日志

运行期间，会话真相源是一个内存里的 `Session` 对象（`packages/core/session/src/index.ts`）。它的核心就是那个 `SessionEvent[]` 数组。所有环节共享它：

- 模型通过 `deriveMessages()` 读它（投影成消息列表）；
- 工具结果、AI 回复通过 `append()` 往它末尾写事件；
- 持久化插件监听它的"新事件"通知，异步抄到磁盘。

> **一个重要澄清：不是"所有会话"都在内存。** `ctx.sessions` 只装**当前活跃（live）**的会话——即正挂在某个运行中 agent 上的会话。历史上攒下来、当前没在跑的会话，只躺在磁盘的 JSONL 里，不占内存。
>
> **那系统怎么决定把哪个 session 放进内存？不是"最近一次对话"，而是两个显式动作：**
> - **创建（create）**：你发一个新任务，agent 工厂当场建一个新 session → 进内存；
> - **恢复（resume）**：你**按 id 指定**"恢复第 42 号会话"（`resumeSessionId: 42`），系统就去磁盘**打开 42 号那个文件**读进内存 → 42 号进内存。
>
> 出内存也只有一条路：那个 agent **跑完**（它的 fiber 被卸载）→ 先 `flush` 落盘 → session 从内存移除。
>
> 所以内存里的 session 数 = **此刻同时在跑的 agent 数**（不是恒等于 1，也不是"最近一个"）：什么都没跑时是 0，开一次任务是 1 个主 session（可能再 fork 几个子 agent），服务并发接待时是多个。整个过程是**显式、确定**的——你 resume 谁，谁才从磁盘回到内存。
>
> 反过来，**一个长期活跃的会话**，它的内存日志会随事件数线性增长（append-only；压缩只遮蔽 surface、**不删内存日志**）。所以真正要留意的是"单个超长会话"，解决办法是第 8 节的结转新会话。

### 2.3 磁盘上：一个 JSONL 文件

要让消息"重启后还能接着聊"，必须加载**会话持久化后端**。DeepSeek Harness 官方内置的是 **JSONL 后端**（`packages/session/session-persistence-jsonl/`）。每个会话对应磁盘上的**一个 JSONL 文件**：

```
<根目录>/<项目目录key>/<编码后的会话id>/session.v2.jsonl        （不压缩时）
<根目录>/<项目目录key>/<编码后的会话id>/session.v2.jsonl.zstd   （默认，zstd 压缩）
```

- **`<根目录>`**：你在配置里指定的 `root`（必须显式指定，没有默认值）；
- **`<项目目录key>`**：按会话所在的工作目录（cwd）算出来的一个可读目录名（如 `/home/me/proj` → `--home-me-proj--`）；没有 cwd 就归到 `_no-cwd`；
- **`<编码后的会话id>`**：会话 id 做路径转义后作为一个子目录名（防止 `../` 越界和路径冲突）；
- **`session.v2.jsonl`**：文件名带**格式版本号**（当前是 v2，所以叫 `session.v2.jsonl`）。

> 这个文件**不是"数据库表"**，就是最朴素的**一行一行的 JSON 文本**（JSONL = JSON Lines）。第一行是"会话头"，后面每一行是一条事件。详细格式见第 5 节。

### 2.4 一句话小结

| 层次 | 是什么 | 谁负责 |
|---|---|---|
| 内存 | `Session` 的 append-only 事件日志（真相源） | `packages/core/session` |
| 磁盘 | 每会话一个 JSONL 文件（可 zstd 压缩） | `packages/session/session-persistence-jsonl` |

## 3. 什么时候存：append 进内存是同步的，落盘是"批量、异步、写后缓存"

这是最容易搞错的地方，单独拎出来讲。

### 3.1 先纠正一个直觉

很多人以为"每来一条消息就写一次盘"。**不是的。** 真实节奏分两层：

1. **进内存日志是同步的**：`session.append(type, data)` 一调用，事件立刻进内存日志、立刻对模型可见、立刻通知所有监听者。这一步**从不碰磁盘 I/O**，快。
2. **落盘是异步的 write-behind（写后缓存）**：持久化插件听到"有新事件"后，**不立刻写盘**，而是把它塞进一个缓冲队列，攒够一小批（或等一个很短的时间窗），再一次性写进文件。

### 3.2 一个具体的时间线

假设对话是：用户问一句 → AI 调两个工具 → 两个工具返回 → AI 总结。

真实发生的是：

| 时刻 | 内存里发生什么 | 磁盘上发生什么 |
|---|---|---|
| ① 用户发话 | `append('user/message', …)` 立刻进日志 | 先**只进缓冲**，不写盘 |
| ② AI 第一次回复 | `append('assistant/message', …)` 进日志 | 同上 |
| ③ 两个工具并行返回 | 两条 `tool/result` 事件进日志 | 同上 |
| ④ AI 总结 | `append('assistant/message', …)` 进日志 | 同上 |
| ⑤ 过了最多 200ms（或主动 flush） | —— | **缓冲里的这一批事件一次性追加写进文件** |

也就是说：**"存"的粒度不是"一条消息"，而是"事件进内存日志 + 后台批量刷盘"**。每次模型想一步、每个工具返回，都是往日志里追加一条/几条**事件**；而磁盘写入是**攒批**进行的。

### 3.3 那"什么时候真正写盘"？三个触发点

| 触发 | 时机 | 说明 |
|---|---|---|
| **批量定时器** | 缓冲里进了新事件后，最多等 **200ms**（`LIVE_WRITE_BATCH_MAX_DELAY_MS = 200`） | 到点就 drain（清空缓冲、写盘），这是常规路径 |
| **flush（持久化屏障）** | 你（或系统）主动要求"现在必须落盘" | `ctx.sessions.flush(session)` 或 handle 的 `flush()`——这是**唯一承诺"崩溃后也不丢"的操作** |
| **关闭 / 退出** | 会话销毁、进程退出、后端卸载时 | `close()` 会先把缓冲 drain 干净再释放锁，保证不丢 |

> **关键区别**：`append` 落盘是**尽力而为（best-effort）**的——事件已经进内存、已经能被本进程读到，但**只有 `flush` 才承诺它扛得住崩溃**。正常退出（close/teardown）会自动把没写盘的补上。

## 4. 存了什么内容

从**逻辑上**看，存的是**"截至此刻的完整事件历史"**——但**不是每次把全量重新抄一遍**（那样会越存越慢）。它是**纯追加**的：新事件永远只往文件末尾**追加几行**，前面的行一个字都不动。

### 4.1 每一条事件长什么样

一条事件（在日志里、也在文件里）由这些字段构成：

| 字段 | 含义 | 通俗解释 |
|---|---|---|
| `type` | 事件类型 | 这条事件"是什么"（如 `user/message`） |
| `seq` | 序号 | 在日志里的位置，从 0 连续递增，靠它对齐/定位 |
| `time` | 时间戳 | Unix 毫秒 |
| `data` | 载荷 | 事件的正文（消息内容、工具结果等），必须是"无损 JSON" |
| `surfaceOp`（可选） | 进 surface 的方式 | 只有三类"消息类事件"才有：`append`（追加）或 `{op:'replace',…}`（替换，压缩用） |
| `sourceEventSeqs`（可选） | 引用了哪些更早的事件 | 比如压缩的 checkpoint 会列出"我遮蔽了哪几条" |
| `ignorable`（可选） | 可安全忽略标记 | 为 `true` 表示"读者不认识这个类型时可以跳过，不影响重建" |

> 顺带一提 `ignorable` 的设计：**默认"缺省 = 必须认识"**。读到不认识的类型、又没有 `ignorable: true`，就**拒绝重建**而不是悄悄丢掉——宁可报错，也不静默恢复出一个残缺的会话。

### 4.2 只有三类事件能"成为消息"（surface 事件）

整条日志里有各种事件（一轮开始、重试、错误、路由信息……），但**只有三类会被投影成"模型能看到的消息"**（`packages/core/session/src/types.ts`）：

- `user/message`：用户/注入的消息；
- `assistant/message`：AI 的回复；
- `tool/result`：工具执行结果。

这三类**必须带 `surfaceOp`**，说明它怎么进入"模型可见的序列"（这个序列就叫 **surface**，详见第 7 节）。其它事件（`turn/start`、`request/header`、各种边界标记）是"只进日志、不进对话"的。

### 4.3 会话头：单独存，不进日志

除了事件日志，还有一个**会话头（SessionHeader）**，存的是这个会话的**身份与血缘**信息：

```
version（格式版本）、id（会话编号）、createdAt（创建时间）、cwd（工作目录）、
parentSession（父会话）、isSeeded（是否 fork 继承）、origin（是否子智能体）、
delegationDepth（委托深度）、agentPreset（预设）
```

关键点：**会话头是"存储层面的元数据"，刻意不放进事件日志**——因为日志是"可重放的对话状态"，头信息（比如当前格式版本）不属于对话本身。它在文件里占第一行。

## 5. 存储格式：一个 JSONL 文件的两部分

> 本节是全文核心。一个会话 = **一个 JSONL 文件**，里面是"一行头 + 一行行事件"。

### 5.1 一句话

> 存到磁盘里的**不是"一条条消息"，而是"一份份事件记录"**。消息只是其中三类事件（`user/message` / `assistant/message` / `tool/result`）。

### 5.2 文件的真实结构

以当前 v2、不压缩为例，文件长这样（示意，字段名真实、值省略）：

```
第一行（会话头）：
  {"type":"session","version":2,"id":"…","createdAt":1700000000000,
   "cwd":"/home/me/proj","isSeeded":false,"delegationDepth":0}

之后每行（一条事件）：
  {"type":"user/message","seq":0,"time":1700000000001,"data":{…},"surfaceOp":"append"}
  {"type":"assistant/message","seq":1,"time":1700000000002,"data":{…},"surfaceOp":"append"}
  {"type":"tool/result","seq":2,"time":1700000000003,"data":{…},"surfaceOp":"append"}
  ……
```

- **第一行**：`type` 固定是 `"session"`，其余是 4.3 节那些头字段。
- **之后每行**：一条完整事件（4.1 节那些字段），顺序即 `seq` 顺序。
- 压缩时（默认），整个文件是**校验过的 zstd 帧**，头和事件各自成帧，解码后就是上面这个纯文本。

> 两个落盘细节（对"看懂文件"有用）：
> - **fork 继承边界不在头里**：头行**没有**"继承了多少条"这个数字。fork 出来的子会话，会在事件体里放一条 `session/end-seed` 事件，`data` 为 `{inherited:true}`，它的 `seq` 就是"从父会话继承来的前缀长度"。
> - **`sourceEventSeqs` 会压区间**：事件里"引用了哪些更早事件"的编号列表，落盘时把连续递增的编号合并成 `[start,end]` 区间（例如 `[3,4,5,6]` 存成 `[3,6]`），省空间。

### 5.3 为什么文件名带版本号（`.v2`）

会话落盘格式是**会演进的**（字段会增删、语义会变）。为了"老文件永远能读"，格式用**版本号 + 相邻迁移**管理：

- 当前格式版本是 **v2**，文件名 `session.v2.jsonl`；
- 最老的是 v0，文件名 `session.jsonl`；
- 读到旧版本时，按"相邻迁移链"（v0 → v1 → v2）**逐步转换**，且**旧文件原样保留、生成新版本文件**，绝不原地覆盖；
- 读到**更高**版本（未来的文件）时，直接报"请升级 harness"，而不是瞎猜。

> 这个"相邻迁移、只增不改"的约定是仓库的铁律，与本文"只追加、不覆盖"的精神一脉相承。

### 5.4 一个易混淆点：SQLite 不是消息的"家"

仓库里确实有 SQLite（`packages/session-query/session-query-sqlite/`），但它**不是会话真相源，而是"全文搜索读模型"**——一个可以随时重建、删了也无所谓的**索引**，用来做"搜会话 / 搜历史消息"这类查询（FTS5 全文检索）。真正的消息正文只在 JSONL 里。别把两者搞混。

## 6. 写盘是同步还是异步：异步 write-behind，`flush` 是唯一屏障

这是关于"会不会拖慢"的核心问题。结论先说：**默认异步写盘，不阻塞主流程**。

### 6.1 默认：后台批量异步写

主循环调用 `append()` 时，事件**同步进内存日志**（这一步快，不碰磁盘），然后**立刻继续**。持久化插件在后台把事件攒批、最多 200ms 后一次性写盘。模型推理是秒级、一次磁盘写入是毫秒级，两者重叠，写盘延迟基本被"藏"起来。

### 6.2 两条"防出乱子"的保障

虽然是后台异步，但有两条保证，让你不会拿到"半成品"：

1. **每会话串行链 + 单写者**：同一个会话的所有写操作排成一条 promise 链，按顺序落盘、绝不乱序；并且每个会话**同一时刻只有一个写者**（进程内靠 writer 表、跨进程靠内核文件锁 `SessionWriteLease`），两个进程不会同时写同一份文件。

2. **退出兜底**：会话关闭、后端卸载、进程正常退出时，会**先把没写完的缓冲 drain 干净**再放手。所以正常退出后，数据一定已经落盘。

### 6.3 那"重不重"？

你的担心有道理，但实际开销没那么可怕，因为有三重减负：

1. **不是每条消息写盘，是攒批写**（见第 3 节，一次只追加几行）；
2. **写盘在后台，和模型调用并行**——真正耗时大头是模型推理（秒级），一次追加写是毫秒级，被"藏"起来；
3. **纯追加、不重写**——新事件只往文件末尾加几行，从不把整段历史重新打包一遍。

真正需要长期留意的是**两处累积**，而不是"每一步都在同步刷盘"：

- **历史本身会持续增长**：文件是纯追加的，长时间、多步骤的会话会越存越大（这是读变慢的根源，见第 8 节）；
- **压缩 + 写盘本身吃 CPU/磁盘**：zstd 压缩每一批、以及偶尔的全量解码，都需要算力；会话越大越明显。

## 7. 读的时候怎么拿回消息：surface 投影 + 增量缓存

> **先直接回答最常被问的问题：每一轮开启都要重读全量文件吗？——不用。**
> 要分清两种场景：
> - **进程内续聊（最常见）**：真相源是**内存里的日志**。每一轮只是往内存日志追加事件，`deriveMessages()` 从**内存**投影——**根本不读磁盘、不解压、不从头遍历**，只投影"这一轮新增的节点"（增量缓存）。
> - **进程重启后的 resume**：内存是空的，这时才**一次性**从磁盘读回全量事件（解压 zstd + 从头遍历 + 完整 surface 折叠），重建内存 Session；之后又回到"进程内续聊"的增量模式。
>
> 所以"解压全量文件 + 从头映射"是**启动/恢复时的一次性成本**，不是每一轮的开销。

第 2 节说过真相源是"事件日志"，但模型要的是"消息列表"。怎么从事件变回消息？这就是 **surface 投影**。

### 7.1 surface：日志的"模型可见视图"

日志里有各种事件，但只有带 `surfaceOp` 的三类消息事件会进入一个**有序序列**，叫 **surface**。它就是"模型看到的消息顺序"。`deriveMessages()` 做的事情就是：**按 surface 顺序，把每个节点投影成一条消息**。

- `surfaceOp: 'append'` → 追加到序列末尾；
- `surfaceOp: {op:'replace', start, end}` → 把 `[start, end]` 区间的节点**遮蔽（shadowed）**，换成自己（压缩的 checkpoint 就是这么进来的）。

被 replace 遮蔽的旧节点**仍在日志里**（磁盘不删），只是**不再出现在 surface** 上，于是模型看不到它们。

### 7.2 增量缓存：每次读只算"新增的节点"

`deriveMessages()` 是**缓存增量**的（`packages/core/session/src/index.ts`）：

- 每个 surface 节点**只在第一次被看到时投影一次**，之后复用；
- 一次调用的代价是 **O(新增节点数)**，而不是 O(全部历史)；
- 只有发生 replace（`replaceGeneration` 变化，即压缩）时，才**整体重建**缓存。

同样，`requestHeader()` / `requestContext()` 也是"折叠一次、按新事件增量"的缓存。所以**进程内续聊**时，读历史几乎不重复计算。

### 7.3 重启恢复（resume）怎么读

重启后内存是空的，得从文件读回来。`resume` 的流程（`packages/core/agent-loop/src/index.ts`）：

```
persistence.open(id, 'write')           —— 打开写句柄（独占写者）
  → handle.read(0)                       —— 读出完整事件数组（校验格式/seq 连续）
  → 合成中断轮次的收尾事件                 —— 上次崩在半路的一轮，补上 turn/end 等收尾
  → sessions.prepare(id, {seed, meta})   —— 用这些事件重建内存 Session（走同一套校验 + 冻结）
```

恢复后，`deriveMessages()` / `requestHeader()` 通过折叠缓存，能重建出**和崩溃前字节一致的** system / 历史（保证前缀缓存不失效）。

## 8. 长期单会话：读会越来越慢，怎么优化

前面（第 4、7 节）说过：历史是纯追加、总量线性增长。每次新回合都要把**全量事件历史**解码 + 投影回内存——这一步的代价和历史条数成正比。如果你的业务是"**同一个会话、长期不断新增对话**"，这个代价会随时间越来越明显。这一节讲怎么优化。

### 8.1 先看清：读的代价到底在哪

每次发一个新回合，读的过程是：

```
读日志（全量事件） ──► 逐条校验 + 解码 ──► surface 投影成消息 ──► （可选）压缩切掉旧部分
     ↑ 这一步和历史条数成正比，躲不掉
```

关键认知：**这一步跟"写盘异步与否"无关**。因为无论怎么存，读回来时都要把 N 条事件还原成内存对象。所以"优化读"的根本方向只有一个——**让 N 变小**（让存着的历史变短）。

### 8.2 方案一（最推荐）：定期"压缩"（compaction）

DeepSeek Harness 内置的**上下文压缩**（`packages/compaction/compaction-basic/`，详见《上下文压缩》）就是干这个的：把历史头部一整段**浓缩成一条摘要（checkpoint）**，用 replace 遮蔽掉原始节点。

- 日志里的原始事件**仍在磁盘上**（append-only，不删）；
- 但 surface（模型可见、每次请求要投影的）**变短了**，下次请求读的 N 就小了；
- 压缩是**可重复的**，多轮对话可以多轮压缩。

> 注意：压缩只缩"模型可见视图"，**不缩磁盘文件**。磁盘文件仍会越存越大，只是"每次请求要处理的历史"被压住了。

### 8.3 方案二：定期"结转"到新会话（磁盘文件真正变短）

如果连磁盘文件也要控制（比如长期跑的服务，磁盘日志无限膨胀），标准做法是**不要无限期让一个会话涨下去**，而是定期开新会话，把"摘要 + 最近几条"带过去：

```
旧会话（已积累很多轮）
      │ 触发结转
      ▼
1. 取出"摘要 + 最近若干条消息"
2. 新建一个会话，用它们作为初始消息（fork/seed）
3. 旧会话归档或删除
```

这样每个会话的事件数被**卡在一个上限**，读的代价不再随时间无限增长。DeepSeek Harness 的会话支持 fork/seed（`isSeeded` 头字段 + `session/end-seed` 事件标记继承前缀），本身就是为这种"带着前缀开新会话"设计的。

### 8.4 辅助手段一：投影缓存（进程内）

第 7 节说的 `deriveMessages()` 增量缓存，是"进程内续聊"的免重复计算保障。它不缩短历史，但保证**已经投影过的节点不会重算**。

### 8.5 辅助手段二：SQLite 全文搜索读模型（列表/搜索加速）

第 5.4 节提到的 `session-query-sqlite` 把会话和消息**索引进 SQLite FTS5**，专门加速"列出所有会话 / 全文搜历史"这类查询——它和"按会话读回完整历史"是两码事，互不干扰。它是可随时重建的派生物，删了不影响真相源。

### 8.6 几个"没用"的误区

| 你以为的优化 | 实际效果 |
|---|---|
| 换成异步写盘 | 只影响"写"的阻塞，不影响"读" |
| 只压缩、不结转 | 磁盘文件仍越存越大（日志纯追加），但每次请求要投影的历史变短了 |
| 只加 SQLite 索引 | 只加速列表/搜索，**不减**"按会话读回完整历史 + 投影"的代价 |
| 删除旧会话文件 | 能回收磁盘，但**别在依赖历史回放/恢复的场景下乱删**——真相源就是那份文件 |

## 9. 一句话总结

> 你每说一句话、AI 每想一步、工具每跑一步 → 往内存的 **append-only 事件日志**追加一条事件（同步、不碰磁盘）→ 持久化插件在后台把事件**攒批**（最多 200ms）**异步写盘**（`flush` 是唯一承诺崩溃不丢的屏障；正常退出会兜底 drain）。存的不是"消息列表"而是**完整事件历史**，磁盘上每会话**一个 JSONL 文件**：第一行会话头，之后一行一个事件，默认 zstd 压缩、带格式版本号。读的时候用 **surface 投影**把事件变成消息，靠**增量缓存**只算新增节点；长期单会话靠**压缩**（缩模型可见视图）+ **结转新会话**（缩磁盘文件）来控制读的开销。

## 10. 术语表

| 术语 | 通俗解释 |
|---|---|
| 事件日志（event log） | 会话的真相源：一条条"发生了什么"的记录，按 `seq` 只追加、从不改写 |
| 事件（event） | 日志里的一条记录（用户话 / AI 回复 / 工具结果 / 边界标记等） |
| seq | 事件的序号，等于它在日志里的位置，从 0 连续递增 |
| 会话头（SessionHeader） | 会话的身份/血缘元数据（id、版本、cwd、父会话等），单独存、不进日志 |
| surface | 日志的"模型可见视图"：只有带 `surfaceOp` 的消息类事件按顺序组成的序列 |
| surface 投影 | 把 surface 节点逐条变成"模型消息"的过程（`deriveMessages`） |
| surfaceOp | 消息类事件如何进 surface 的标记：`append`（追加）或 `replace`（替换/遮蔽） |
| 遮蔽（shadowed） | 被 replace 替换掉的旧节点：仍在日志里，但不再出现在 surface |
| JSONL | JSON Lines：一行一条 JSON 记录的文本文件格式 |
| write-behind（写后缓存） | 先写内存缓冲、后台再批量落盘的异步写策略 |
| flush | 持久化屏障：唯一承诺"崩溃后也不丢"的操作 |
| 写句柄（handle）/ 写租约（lease） | 每会话单写者：进程内靠 writer 表、跨进程靠内核文件锁保证不并发写 |
| 格式版本（SESSION_FORMAT_VERSION） | 会话落盘格式的版本号（当前 v2），用"相邻迁移"保证老文件可读 |
| 相邻迁移 | 读到旧格式时逐版本转换、旧文件保留、生成新版本文件的机制 |
| 压缩（compaction） | 把历史头部浓缩成摘要、遮蔽原始节点，缩"模型可见视图"（不删磁盘） |
| 结转 | 定期开新会话、把"摘要 + 最近消息"带过去，控制单个会话的事件数 |
| 全文搜索读模型 | 把会话/消息索引进 SQLite FTS5 的派生物，加速列表/搜索，不是真相源 |
