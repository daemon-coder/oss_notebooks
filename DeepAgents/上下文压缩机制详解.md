# DeepAgents 上下文压缩机制详解

> 本文面向**完全没接触过 DeepAgents（以及 LangChain / LangGraph 等框架）的读者**。
> 文中涉及的每一个概念（智能体、上下文窗口、消息、工具调用、状态、后端存储等）都会在用到之前先解释，不预设任何背景知识。
>
> 本文按**功能主题**组织：每个主题内部都是"**先讲设计思路（为什么）→ 紧跟着讲实现细节（怎么做）**"，
> 两者相邻，读实现细节时不需要回头找思路。整体顺序也是层层递进的：先讲"压缩的手段是什么"，
> 再讲"压缩哪部分、何时压缩、丢的东西怎么找回"，最后讲"压缩如何落地到系统状态、以及如何兜底"。

## 0. 阅读前提

你只需要对"调用大模型 API 构建应用"有一个最朴素的印象即可，例如知道：

- 你给大模型发一段文字（提示词），它回一段文字；
- 大模型一次能处理的文字量是**有限**的。

如果这两条你理解，本文的其余部分都能顺下来。

## 1. 背景：一个会"越聊越长"的问题

### 1.1 什么是"智能体"（Agent）

在 DeepAgents 里，一个"智能体"大致是这样工作的：你给它一个目标（比如"帮我统计这个仓库里的 TODO 并写报告"），它会**一轮一轮地和模型对话**：

1. 模型读到你之前发的内容，给出回复；
2. 回复里可能包含"我要调用某个工具"（读文件、写文件、执行命令）；
3. 程序执行这个工具，把工具结果追加回对话；
4. 模型再读全部内容，继续下一步……

关键点：**每一轮，模型都要把"到目前为止的整段对话"重新读一遍**，才能知道自己在干什么、下一步该做什么。

### 1.2 什么是"上下文窗口"（Context Window）

模型一次能读入的文字总量是有限的。这个上限通常以 **token**（可粗略理解为"半个到四分之三个汉字/英文单词"）衡量。比如某个模型"上下文窗口是 200k tokens"，就是一次调用最多塞 200k tokens。

我们把"某次调用实际发给模型的全部文字"叫**上下文**。

### 1.3 问题：对话无限增长，窗口有限

一个长任务可能产生几百上千条消息（用户消息、AI 回复、工具调用请求、工具结果……），全部累积在历史里。**对话越长，上下文越大，迟早撞上窗口上限**。一旦撞上，模型调用直接报错"输入超长"，任务就崩了。

这就引出本文主题——**上下文压缩（compaction / summarization）**：在上下文逼近上限时主动"瘦身"，把旧对话压缩成更短的形式，腾出空间让任务继续。

---

## 2. 压缩要解决的三个本质问题

压缩不是"把对话删短一点"那么简单，它要同时回答三个问题：

| 问题 | 朴素的错误做法 | 真正要满足的约束 |
|---|---|---|
| **A. 空间**：窗口会满，必须腾空间 | 直接砍掉最旧的消息 | 腾空间的同时，不能丢失"继续任务所必需"的信息 |
| **B. 信息**：旧对话里可能有以后还用得上的细节 | 摘要会丢细节 | 丢掉的细节要能"找得回来"（可恢复） |
| **C. 连续性**：模型要靠历史知道自己已做了什么、下一步做什么 | 只保留最近几句，丢了早期决策 | 摘要必须抓住"目标、已完成的事、产生的产物、下一步" |

## 3. 核心思想与整体架构

### 3.1 一句话与一张图

**一句话**：

> 当上下文快满时，把"较早的旧对话"交给模型做一次摘要，用这段摘要替换旧对话；被替换掉的原始旧对话**不丢弃，而是先写入文件系统**，摘要里带上文件路径，模型以后需要细节时可用"读文件"找回；**最近的对话**则原样保留。

```
压缩前（发给模型的全部消息）：
┌────────────────────────────────────────────────────────┐
│ [系统提示]  [用户消息] [AI消息] [工具结果] [AI消息] [工具结果] ... │
│  └────────────── 旧对话（可能几百条，越来越大）──────────────┘  │
└────────────────────────────────────────────────────────┘

压缩后：
┌────────────────────────────┬──────────────────────────────┐
│ [一段摘要消息]（带文件路径指针）│ [最近 N 条消息，原样保留]      │
│  "……完整历史已存到 xxx.md……" │  （最新对话，最相关，不压缩）   │
└────────────────────────────┴──────────────────────────────┘
              ▲                                ▲
        旧对话 → 摘要                    最近窗口 → 原样
              │
              └── 完整旧对话 → 先写入文件系统（可找回）
```

### 3.2 架构分层：三层拼图 + 两个工厂

压缩功能在代码里分三层，外加两个工厂函数：

```
┌─────────────────────────────────────────────────────────────┐
│ 层3: SummarizationToolMiddleware                            │  ← 提供 compact_conversation 工具（手动压缩）
├─────────────────────────────────────────────────────────────┤
│ 层2: _DeepAgentsSummarizationMiddleware                     │  ← DeepAgents 自动压缩中间件（对外叫 SummarizationMiddleware）
│      （在引擎外包装：后端外置 / 参数截断 / 溢出兜底 / 不改状态）│
├─────────────────────────────────────────────────────────────┤
│ 层1: LangChain 的 SummarizationMiddleware（内部叫 _lc_helper）│  ← 真正"引擎"：触发判定 / 切点计算 / 划分 / 摘要生成
└─────────────────────────────────────────────────────────────┘
```

- **层1（引擎）**：来自上游 LangChain，DeepAgents 构造时把它实例化存为 `_lc_helper`，负责四件核心事：是否触发、切到哪、怎么分、怎么生成摘要。
- **层2（包装）**：DeepAgents 自己的中间件，**不改写状态**，而是每次模型调用前改写"发给模型的请求"，把压缩事件记入私有字段 `_summarization_event`。
- **层3（工具）**：注册 `compact_conversation` 工具，让模型/人主动触发压缩，复用层2 的引擎。
- **两个工厂**：`create_summarization_middleware(model, backend)` 建层2；`create_summarization_tool_middleware(model, backend)` 一次建层2+层3。
- **默认装配**：入口 `create_deep_agent` 会**自动**为主智能体、通用子智能体、每个子智能体都插入压缩中间件——**开箱即用**。

下面第 4 节按功能主题逐一展开，每个主题内部"思路 → 细节"。

## 4. 功能主题：思路 + 细节

### 4.1 为什么要"摘要"而不是"截断"

**思路**：空间不够时，怎么处理旧消息？

- 方案 X：**直接丢弃**最旧的消息——简单零成本，但模型会"失忆"，早期决策（"我们决定用方案 B 而不是 A"）凭空消失，后续可能重复劳动。
- 方案 Y：**交给模型做一次摘要**，把旧对话浓缩成一段文字——保留"目标、关键决策、已产生的文件、下一步"这类高层信息，代价是多一次模型调用、且细节一定会丢。

DeepAgents 选 **Y**。对智能体来说"失忆"是致命的，花一次调用换"记得自己走到哪了"是划算的。为了让摘要不空洞，它把摘要做成**结构化**的。

**细节**（摘要怎么生成）：

1. **裁剪输入**：待摘要的旧消息先用 `trim_messages` 裁到 `trim_tokens_to_summarize`（默认 **4000 token**），参数 `strategy="last"`（留尾部）、`start_on="human"`（从人类消息开始）、`allow_partial=True`、`include_system=True`；裁剪异常时兜底只取**最后 15 条**。
2. **格式化**：用 `get_buffer_string` 转成纯文本（避免直接 `str()` 消息对象导致元数据膨胀 token）。
3. **填提示词**：用 `DEEPAGENTS_DEFAULT_SUMMARY_PROMPT`——它在上游默认摘要提示词基础上，往 `<messages>` 标记前**插入一段"媒体引用说明"**（告诉摘要模型遇到 `<image url=.../>` 引用要原样保留、别臆造视觉细节、需要时让后续模型 read_file 那个路径）。模板主体强制按四小节输出：
   - **SESSION INTENT**（本次目标）
   - **SUMMARY**（关键决策与结论，含被否决的方案及原因）
   - **ARTIFACTS**（创建/修改了哪些文件、改了些什么）
   - **NEXT STEPS**（接下来做什么）
4. **调用模型**：带 `metadata={"lc_source": "summarization"}`（便于追踪和后续识别）。
5. 空输入直接返回 `"No previous conversation history."`；模型调用异常则返回 `"Error generating summary: ..."`，**不抛异常**。

摘要生成后，把它包装成一条新的**人类消息**（`HumanMessage`），标记 `lc_source="summarization"`。有归档路径时是三段式：

```
You are in the middle of a conversation that has been summarized.

The full conversation history has been saved to {文件路径} should you need to refer back to it for details.

A condensed summary follows:

<summary>
{摘要文本}
</summary>
```

无路径（外置失败）则退化为简版：`Here is a summary of the conversation to date:\n\n{摘要}`。

### 4.2 滑动窗口 + 安全切点（压缩哪部分、切在哪）

**思路**：对话里**越近的消息越重要**——模型马上要做的下一步最依赖最近几条；很早以前的消息已被后续对话覆盖和推进，更适合被摘要。所以把对话切一刀：

- **旧前缀**（早的部分）→ 摘要；
- **最近窗口**（晚的部分）→ **原样保留**，一字不动。

保留多少可配置（`keep`）。默认：有模型窗口信息时保留**最近 10% 上下文**；否则保留**最近 6 条消息**兜底。

另一个必须处理的细节：一条 AI 消息会"发起"工具调用（如 `write_file`），紧接着有工具结果回来，这对"请求 + 结果"必须成对——若只留结果、把发起调用的 AI 消息摘要掉，模型会看到没有来由的结果。所以切点必须落在"安全"位置：**宁可多摘要一点，也不拆散请求/结果对**。这是"正确性 > 省空间的极致"的取舍。

**细节**（切点怎么算）：

1. **按 keep 预算找目标切点**：
   - `keep` 是 `tokens`/`fraction`：算出目标 token 数（如 `max_input_tokens × 0.10`），**二分查找**最小的下标，使 `messages[该下标:]`（后缀）token 数 ≤ 预算；
   - `keep` 是 `messages`：`切点 = 总条数 - keep值`。
2. **调到"安全"位置**（`_find_safe_cutoff_point`）：若切点落在 `ToolMessage`（工具结果）上，就**向前找**那条"发起这些工具调用的 AI 消息"（按 tool_call id 匹配），把切点**移到包含它**；找不到对应 AI 消息（边缘情况）才向后越过这串工具结果。
3. 二分查找用的是一个"不带 usage 缩放"的局部计数器（`_partial_token_counter`），保证切点计算稳定可复现（为什么刻意关掉缩放、以及"估算 vs 模型报告"的分工，见 4.3）。

默认 keep 值来自 `compute_summarization_defaults`：

| 场景 | 触发（trigger） | 保留（keep） | 参数截断 |
|---|---|---|---|
| 模型 profile 有 `max_input_tokens` | `("fraction", 0.85)`（85%） | `("fraction", 0.10)`（10%） | 开（85% / 10%） |
| 无 profile 信息 | `("tokens", 170000)` | `("messages", 6)` | 开（`("messages", 20)` / `("messages", 20)`） |

> 补充：上游 LangChain 引擎自己的默认 keep 是"保留 20 条消息"，DeepAgents 的工厂在能拿到窗口大小时改成"按比例 10%"，拿不到时用更保守的"6 条"。

### 4.3 何时触发压缩（阈值 + 报告用量）

**思路**：太早压缩——白花成本还丢信息；太晚——可能已撞上窗口上限。所以用一个**可配置的触发阈值**，支持三种粒度，任一满足即触发。除程序自己估算 token，还有一个更准的信号：**模型上次调用返回的"用量报告"**（真实 token 数）。这是"估算值 + 真实值"双保险。

**细节**（触发判定 `_should_summarize`）：

- `("messages", N)`：消息条数 ≥ N；
- `("tokens", N)`：估算 token ≥ N，**或**最近一条 AI 消息的 `usage_metadata.total_tokens`（模型报告的真实用量）≥ N；
- `("fraction", F)`：`max_input_tokens × F` 作阈值，同上两条判定。

"报告用量"这条路径有**防御**：要求这条 AI 消息确实来自当前模型（比对 `model_provider` 是否一致），避免串数据——用模型 A 的数字去触发模型 B 的压缩。

触发条件支持组合语义：**列表 = OR**（任一满足）；**字典 = AND**（同时满足）。如 `[("fraction", 0.8), ("messages", 100)]` 表示"到 80% 或到 100 条，先到先触发"。

**Token 计数：估算值 vs 模型报告值（两种来源，用途不同）**

压缩里其实有**两个 token 来源**，容易混淆，先分清：

1. **估算值**——程序自己按字符数折算（`chars_per_token` 默认 4.0，Claude 系 3.3），不依赖模型返回；
2. **模型报告值**——模型每次返回时，附带在 AI 消息 `usage_metadata.total_tokens` 上的真实用量。

**各自用在哪**（一句话：**"要不要压"用两者，"压到哪"只用估算**）：

| 环节 | 用的是 | 说明 |
|---|---|---|
| 触发判定（要不要压缩，本节） | 估算值 **或** 报告值 | 估算越阈值、或最后一条 AI 消息的报告值越阈值，二者满足其一即触发 |
| 二分查找切点（压到哪，4.2） | **纯估算值** | 刻意关掉 usage 缩放，用局部计数器 `_partial_token_counter` |
| 参数截断边界（4.4） | 纯估算值 | 同上，用局部计数器 |
| 溢出兜底裁剪（4.6） | 估算值 | 判断保留尾部的大工具结果是否够大 |

**估算值的两个已知问题**：

- **按模型只有两档**：内置调参只区分"Claude（3.3）"和"其他（4.0）"，没有 DeepSeek 等模型的专属折算值。
- **不区分中英文**：估算用 `len()` 按 Unicode 码点计数，1 个汉字 = 1 个英文字母 = 1 "字符"，再统一除以 `chars_per_token`。于是中文会被**严重低估**（1 个汉字常约等于 1 个 token，估算却只当 1/4 token）。

这个偏差本可由 `use_usage_metadata_scaling=True` 用真实值校正，但校正系数被夹在 `[1.0, 1.25]`，最多上浮 25%，**补不回中文那种几倍的缺口**。

**怎么自定义**：给中间件传 `token_counter` 参数即可（`SummarizationMiddleware` 与 `create_summarization_middleware` 都接受）。三种做法：改 `chars_per_token`；写一个"中文按 ~1 token/字、其余按 ~4 字符/token"的 CJK 加权计数器；或用模型官方 tokenizer 精确计数。注意：传了自定义计数器后，它会**同时**用于触发判定和二分查找（内置"触发带缩放、二分不带缩放"的分工会被跳过），所以你的计数器必须对任意切片都稳定、单调。

**其余计数细节**：

- 计数范围不止消息，还含系统提示和工具 schema（这两块也占窗口）。
- 用 `inspect.signature` 探测计数器是否接受 `tools=`：能收就传（工具定义占位 token 也计入），不能收就只数消息。
- **每轮只数一次**：工具 schema 转换很贵，"参数截断判定"和"摘要判定"共享同一次计数；只有截断实际发生才重新数一次。

### 4.4 分层瘦身：先截参数，再摘要

**思路**：很多情况下真正撑爆上下文的是少数几条"巨型消息"——`write_file` 塞了一整个文件、`edit_file` 塞了巨大补丁。为这些参数做一次完整摘要有点"杀鸡用牛刀"。所以先做一道**更便宜的预瘦身**：只对**旧消息**里这两个工具的**超大参数**做截断；截完 token 降回阈值以下就**根本不需要摘要**。

为什么只动旧消息、只动这两个工具：最近窗口是模型马上要用的不能截；只有 `write_file`/`edit_file` 的参数是"一次性塞大段代码/补丁"的重灾区。这是"**先用便宜手段，再用贵手段**"的分层防御。

**细节**（三道小步）：

1. **判定是否截**：`truncate_args_settings` 的 `trigger` 支持 messages / tokens / fraction 三种，与摘要触发同一套格式；没配则不截。
2. **定位截哪些**：按 keep 策略算出"老消息"边界，边界之前的才可能截，最近保留窗口不碰。
3. **执行截断**：只对旧消息里 AI 的 `write_file` / `edit_file` 工具调用参数动手——字符串值超过 `max_length`（默认 **2000 字符**）的，替换成 `前 20 个字符 + "...(argument truncated)"`。

截断有改动就重新数一次 token，再进入摘要判定。

### 4.5 可恢复性：外置到文件系统

**思路**：摘要一定会丢细节（某文件当时具体写了什么）。模型之后需要细节怎么办？答案是：在"用摘要替换旧对话"**之前**，先把完整旧对话**写入文件系统**存成归档，再在摘要消息里**嵌入文件路径**。为什么是文件——DeepAgents 的智能体本来就带一套文件工具，归档成文件天然能被模型用既有能力访问，不需要额外机制。

媒体是次生问题：图片是二进制塞不进文本归档。处理：把图片**解码后单独存成文件**（按内容指纹命名），归档里只留引用标签，摘要模型看到的也是引用而非原始字节。

**细节**（两类外置 + 文件长什么样）：

**(a) 历史归档：`conversation_history/{session_id}.md`**

1. **路径**：`{artifacts_root}/conversation_history/session_{uuid4hex}.md`。`session_id` 存在私有状态 `_summarization_session_id`，同一图调用内复用 → 同一次对话的多次压缩**追加到同一个文件**；子智能体各自独立互不串文件。
2. **过滤**：跳过上一次的摘要消息（`lc_source="summarization"`），避免链式压缩重复存储。
3. **渲染**：用 `get_buffer_string(..., format='xml')` 序列化成 XML。
4. **追加**：拼上 `## Summarized at {ISO时间}` 标题 append 到文件（先读旧内容再合并写入；读旧内容用"下载"而非"读文件"，因为后者返回带行号的内容、不适合拼接）。
5. **失败非致命**：写失败只记日志、发警告、返回"无路径"，摘要照做（退化为纯摘要）。

文件形态（追加式日志）：

```
## Summarized at 2025-06-01T12:00:00+00:00

<message type="system">你的角色……</message>
```

3. **去重**：按内容 `sha256` 取**前 16 位**命名，同内容只上传一份。
4. **上传**：写到 `{artifacts_root}/conversation_history/media/{指纹}.{后缀}`。
5. **重写**：把内联块换成带路径引用——图片/音频/视频映射成 `<image url="..."/>` 等类型引用，其他 MIME 退化成 `<file url="..."/>`；上传失败的替换成 `<image error="failed_to_offload" />` 占位。

**(c) 文件实际落哪**：SDK 层用虚拟路径（默认根 `/`），真实落盘由存储后端路由决定。以 dcode 为例：`conversation_history/` 有专用路由落到 `~/.deepagents/conversation_history/`（目录权限加固为仅本人可访问、跨会话保留）；沙箱/服务端模式下归档写在沙箱后端，本地无文件。

> 一个易混淆的伴生文件：FilesystemMiddleware 还有一条**独立的主动驱逐路径**（不属于压缩）——用户粘贴超大人类消息时，会把原文写到 `conversation_history/{uuid4}.md`（随机命名）、原消息标记 `lc_evicted_to` 并截断。所以该目录除 `session_*.md` 外还会出现 `{uuid4}.md`。

### 4.6 溢出兜底：失败也要优雅降级

**思路**：即便有阈值，仍可能出意外——提供方模型突然拒绝，抛"输入超长"错误（`ContextOverflowError`）。直接让任务崩溃吗？不。把它当作一次"被动触发压缩"的信号：先正常调用，失败后转入压缩流程重试。哲学是"**外部错误不该击穿系统，而应转化为一次自救**"。

**细节**：

1. 在"判断不用摘要"的路径上直接调用模型；若抛 `ContextOverflowError`，置 `overflow_triggered=True`，转入正常压缩流程。
2. 额外动作——**裁剪保留尾部的大工具结果**（`_clip_overflow_tail`）：
   - 检查"保留窗口"是否**以连续一串 `ToolMessage` 结尾**，且合计 token ≥ 阈值（阈值来自 keep 预算；keep 是消息数、拿不到 token 信息时默认 **5000**）；
   - 对每条超大结果：
     - 若是 `read_file` 的结果：**不写新文件**（原文件本就在后端），只把内容切到**前 4000 字符** + 提示"完整内容在 `{原路径}`，用 `read_file(file_path=..., offset=..., limit=...)` 分段读"；
     - 其他工具结果：全文写入 `/large_tool_results/{tool_call_id}`，原位替换成一条"桩消息"：

```
工具结果太大，这次调用的结果已保存到文件：/large_tool_results/call_42
请用 read_file 分段读取（例如 read_file(file_path=..., offset=0, limit=100)）。
下面是结果的头尾预览：
  1  <结果第一行>
  2  ...
  ... [省略 9000 行] ...
  9001 <结果最后一行>
```

   - 替换后的消息**带原来的 id**，通过 `Command` 更新写回状态（合并器按 id 覆盖原消息）。

> 说明：`large_tool_results/` 目录不专属于压缩——FilesystemMiddleware 还有一条"工具结果超过阈值就主动驱逐"的路径也写这里（甚至 `execute` 能把命令输出直接重定向进这个目录）。压缩只用到"溢出兜底"这一条。

### 4.7 存储与呈现分离：不改原始状态（最关键）

**思路**：压缩之后，对话历史到底变成什么样？**上游 LangChain 的默认做法**是直接在状态里删掉全部旧消息、塞入摘要 + 保留窗口——**原始历史真的没了**。

DeepAgents 的选择：**原始历史永远保留，一个字都不删**。做法是：

- 在"状态"里额外记一个**压缩事件**（摘要内容、切点位置、归档路径）；
- 每次发消息给模型时，**临时算出**模型该看的视图：`[摘要消息] + 原始历史[切点之后]`；
- 只改"发出去的东西"，不改"存着的东西"。

打个比方：**原始对话是一份完整台账，永远存档；发给模型的只是从台账里"投影"出来的一份精简视图**，压缩事件就是投影规则。

**为什么这样**：✅ 原始日志保留可回放/复盘/评测；✅ 自动压缩与手动压缩可共享同一份原始状态、通过同一套投影协作；✅ 链式压缩不重复摘要已摘要的东西。⚠️ 代价：状态持续变大，需额外字段和换算逻辑保证投影正确。这是"**存储与呈现解耦**"的设计——宁可多存不多删，宁可多算不丢信息。

**细节**：

- **压缩事件** `_summarization_event` 存三样：`summary_message`（摘要消息）、`cutoff_index`（切点在原始状态里的**绝对下标**）、`file_path`（归档路径，可能 `None`）。
- **投影** `_apply_event_to_messages`：没事件 → 视图 = 完整历史；有事件 → 视图 = `[summary_message] + 原始历史[cutoff_index:]`。模型每轮看到的永远是"摘要 + 切点之后的原始消息"。
- **绝对下标换算**：视图里的"切点"和原始状态里的"切点"不是同一个数（视图第 0 位是摘要消息）。若之前已有事件，新事件的绝对切点 = `旧切点 + 视图切点 - 1`（减 1 因为摘要消息占第 0 位），保证链式压缩时事件始终指向正确的绝对位置。
- **防御检查**：事件损坏（缺字段）→ 退回完整历史；切点越界（大于消息数）→ 只返回摘要消息。
- **请求改写与状态更新**：投影出 `modified_messages = [摘要消息] + [保留窗口]`，用 `request.override(messages=...)` 发给模型；同时返回 `ExtendedModelResponse`，把新 `_summarization_event` 和 `_summarization_session_id` 通过 `Command` 写回状态——**`state["messages"]` 本身不动**（除非溢出兜底要写回被裁剪的尾部）。

### 4.8 手动压缩：把压缩做成工具

**思路**：自动压缩只在"快满"时触发。但有时模型**自己**就知道该压缩——比如刚做完一个任务、要转向全新任务，旧上下文已无用，此时主动压缩能省大量空间。所以额外提供工具 `compact_conversation`，模型可像调用"读文件"一样调用它。为防止**过早滥用**，加一个资格门槛：对话规模至少达到"自动触发阈值的 50%"才允许真正压缩。**把能力开放给模型（灵活），用门槛约束（防滥用）**。

**细节**：

- 工具 `compact_conversation` 是**无参数**结构化工具，描述引导模型"对话变长、转向全新任务、或完成综合/抽取后"主动调用。
- **资格门槛** `_is_eligible_for_compaction`：对话达"自动触发阈值的 50%"才放行。折算：`("tokens", N)` → `0.5N`；`("messages", N)` → `0.5N` 条；`("fraction", F)` → `0.5F×max_input_tokens`；换算函数 `max(1, int(value*0.5))`；多条件：字典=AND、列表=OR。不满足 → 返回 `"Nothing to compact yet — conversation is within the token budget."`。
- **执行**：投影有效消息 → 资格检查 → 算切点（切点为 0 则"没什么可压"）→ 划分 → 生成摘要 → 外置历史。结果返回工具消息 `"Conversation compacted. Summarized N messages into a concise summary."`，同时更新事件与会话 id；异常返回 `"Compaction failed: ..."`，**绝不抛异常**。
- 该中间件还会往系统提示追加一段"建议长会话调用 compact_conversation"的提示片段（可 `system_prompt=None` 关闭）。

---

### 4.9 容错：每一步失败都不致命

**思路**：压缩是多环节流水线，任何一环都可能失败。设计原则是**逐环降级，绝不因压缩失败让主任务崩溃**。压缩是"锦上添花的优化"，不是"生死攸关的必经之路"。

**细节**（降级行为对照）：

| 环节失败 | 降级行为 |
|---|---|
| 历史归档写失败 | 照常生成摘要，但摘要不带文件路径（退化为纯摘要） |
| 媒体上传失败 | 归档里留"图片丢失"占位标记，不静默丢弃 |
| 摘要模型报错 | 返回"摘要生成失败"说明文字，不抛异常 |
| 判断不用压缩但调用超长 | 转入压缩流程重试（见 4.6） |

## 5. 完整流程：把各主题串起来

**每次模型调用前**都走这条流水线：

```
每次要把消息发给模型前：
│
├─ ① 投影视图：根据"压缩事件"把原始历史算成 [摘要] + [最近窗口]   （4.7）
│      （第一次没有压缩事件 → 视图 = 完整历史）
│
├─ ② 估算 token：系统提示 + 工具定义 + 消息，一次数完             （4.3）
│
├─ ③ 分层瘦身：够"参数截断"阈值 → 截旧消息 write_file/edit_file 大参数（4.4）
│      （截完有改动就重新数一次 token）
│
├─ ④ 判断是否摘要：                                               （4.3）
│      ├─ 没到阈值 → 直接发，若收到"输入超长"错误则转 ⑤（溢出兜底）（4.6）
│      └─ 到了阈值 → 进入 ⑤
│
├─ ⑤ 计算切点：按 keep 预算（二分找 token 预算 / 按消息数）→ 向前调"安全"（4.2）
│
├─ ⑥ 切分：旧前缀（要摘要） | 最近窗口（原样保留）                  （4.2）
│
├─ ⑦ （仅溢出）裁剪保留尾部的大工具结果 → 外置 large_tool_results/  （4.6）
│
├─ ⑧ 外置媒体：旧前缀里的图片等 → 存文件 → 换路径引用               （4.5）
│
├─ ⑨ 外置历史：旧前缀 → 追加写入归档 xxx.md（失败非致命）           （4.5）
│
├─ ⑩ 生成摘要：旧前缀（裁到 4000 token）→ 填四小节提示词 → 调模型   （4.1）
│
├─ ⑪ 组装：构造摘要消息（含归档路径）→ [摘要消息] + [最近窗口]       （4.1）
│
└─ ⑫ 发送并记录：把视图发给模型；把新"压缩事件"写回状态             （4.7）
         （原始历史不变，只是投影规则更新）
```

> 小细节：⑨ 外置历史 和 ⑩ 生成摘要 彼此独立，异步路径下会**并行**执行（`asyncio.gather`），节省等待时间。

## 6. 压缩前后对比：模型看到的消息发生了什么变化

用一个例子贯穿。任务："统计这个仓库里的 TODO 并写报告"，模型已跑很久，累计 120 条消息、估算 175k token，窗口 200k（87.5%，越过 85% 阈值）。

**压缩前**（模型收到的消息）：

```
[0]  系统提示：你的角色、可用工具说明……
[1]  用户：帮我统计这个仓库里的 TODO 并写一份报告
[2]  AI：好的，我先看下目录结构 (tool_calls: ls)
[3]  工具结果：<目录列表>
[4]  AI：我搜索一下 TODO 关键字 (tool_calls: grep)
[5]  工具结果：<几百行匹配结果>
[6]  AI：我把结果整理成报告 (tool_calls: write_file, args 里是整份报告内容)
[7]  工具结果：报告已写入 /workspace/report.md
 ... （中间还有大量往返）
[119] 工具结果：<最近一次操作的结果>
```

**压缩后**（模型收到的消息）：

```
[0]  系统提示：不变

[1]  人类消息（新生成的"摘要消息"）：
     "你现在处于一段已经被压缩的对话中。
      完整对话历史已保存到 /conversation_history/session_ab12….md，需要细节可读该文件。
      以下是压缩后的摘要：
      ┌─────────────────────────────────────────────┐
      │ ## SESSION INTENT                          │
      │   统计仓库 TODO 并产出报告                  │
      │ ## SUMMARY                                │
      │   已扫描 src/ 下 32 个 .py 文件；决定用    │
      │   grep 而非逐文件读取（更快）；             │
      │   否决了逐行手数（易错）……                  │
      │ ## ARTIFACTS                              │
      │   /workspace/report.md —— 新建，含统计表   │
      │ ## NEXT STEPS                             │
      │   把报告粘贴给用户，确认格式是否满意        │
      └─────────────────────────────────────────────┘"

[2]  AI：最近窗口内的消息（原样，未动）
[3]  工具结果：……
 ... （大约 20 条最近消息）
```

**核心变化**：

1. **旧前缀（约 100 条）整体消失**，被一条摘要消息替代；
2. 摘要消息是"人类消息"形态，标记 `lc_source="summarization"`，供链式压缩识别、跳过；
3. 摘要里**内嵌归档路径**，是"失忆时可查"的钩子；
4. **最近窗口（约 20 条 / 10%）原样保留**，一字没动；
5. 若走溢出兜底，最近窗口末尾的超大工具结果可能被替换成"结果太大已存文件，请分段读取"的桩消息；
6. **存储里的原始 120 条历史没被删**——只是发给模型的"视图"变了。

## 7. 清理机制

一句话结论：**SDK 层没有自动清理（设计如此）；清理只存在于命令行工具 dcode 层，且只覆盖历史归档这一类文件。**

**思路**：压缩中间件对归档是纯追加、对媒体和大工具结果只写不删——这是有意的取舍，**归档是"失忆时可查"的唯一恢复路径，宁可留着**。所以清理职责被放到更高层的 dcode CLI，而不是 SDK。

**细节**：

**① SDK 层**：无自动清理。想删只能靠模型/用户显式调用 `delete` 工具（且要过权限校验）。

**② dcode 层——启动归档清扫**：dcode 每次启动挂一个后台任务（`exclusive=True` 保证同时只有一个在跑），按保留天数清理历史归档：

- 默认保留 **30 天**；配置项 `history.retention_days` 或环境变量 `DEEPAGENTS_CODE_HISTORY_RETENTION_DAYS` 可调；`0` 表示**禁用清扫**；
- **只清** `conversation_history/` 目录下**直接的、`.md` 后缀、且是常规文件**的条目；
- 按**最后修改时间 mtime** 判定过期（`mtime < now - 保留天数×86400`）；
- **竞态防护**：删除前先打开文件、用 `fstat` 再确认"确实没被正在进行的压缩刷新过"才 `unlink`——因为压缩对归档是"读-追加-重写"，若清扫的删除与正在进行的重写竞争，POSIX 下会孤儿化已打开的句柄、静默丢掉刚写入的历史；先 `fstat` 观察到"重写已刷新 mtime"就保留文件。

**③ dcode 层——删会话同步删归档**：用户删某会话时，一并删除该会话归档 `{thread_id}.md`（做了路径安全校验，拒绝能逃出归档目录的伪造 id）。

**④ 明确不清理的部分**：

- **`media/` 媒体文件**：清扫只匹配归档目录的直接子 `.md`，`media/` 是子目录、且是二进制非 `.md`，**永远不被扫**；
- **`large_tool_results/` 大工具结果**：dcode 里只被**路由**到某目录，没有任何清扫/GC，**永久留存**。

> 推论：只用 SDK（不走 dcode）时，这三类文件会无限增长。长期运行纯 SDK 服务，需自行按 `conversation_history/`、`media/`、`large_tool_results/` 三个前缀做配套清理。

## 8. 一张图总结

```
                 ┌─────────────────────────────────────────────┐
                 │            原始对话（状态里，永不删除）        │
                 └───────────────┬─────────────────────────────┘
                                 │ 投影（每次发消息前）
                                 ▼
        ┌──────────────────────────────────────────────┐
        │           发给模型的"视图"                    │
        │   [摘要消息]  +  [最近窗口，原样]              │
        └──────────────────────────────────────────────┘
                                 ▲
                                 │ 由"压缩事件"决定（摘要内容 / 切点 / 归档路径）

   压缩流程（触发后执行）：
   估算token → (可选)截断大参数 → 判断阈值 → 算安全切点
   → 外置媒体 → 外置历史(.md) → 生成摘要 → 组装视图 → 发送
```

**三个关键设计理念，贯穿始终**：

1. **摘要而非丢弃**——用一次模型调用换"不重复劳动"；
2. **可恢复而非不可逆**——旧对话先落盘再替换，媒体单独存放、按路径引用；
3. **存储与呈现分离**——原始历史永不删除，只改"发出去的视图"。

## 9. 术语表

| 术语 | 通俗解释 |
|---|---|
| token | 模型计费/计量的最小文字单位，可粗略理解为"半个字或 3/4 个英文单词" |
| 上下文窗口 | 模型一次能读入的最大文字量 |
| 消息 | 对话历史的基本单元（用户消息 / AI 消息 / 工具结果消息） |
| 工具调用 | 模型在回复里请求"帮我执行某个函数" |
| 状态（state） | 智能体运行期间保存的持久数据，最核心的是累积的消息列表 |
| 视图 | 某次实际发给模型的消息集合（可从状态"投影"而来） |
| 压缩事件 | 记录"摘要内容 + 切点位置 + 归档路径"的一份元数据 |
| 后端（backend） | 智能体读写文件的存储层（磁盘 / 内存 / 沙箱等） |
| 归档（offload） | 把要丢弃的内容先写入文件，供以后按需读取 |

## 10. 配置速查

| 配置项 | 含义 | 默认值 |
|---|---|---|
| 触发阈值（trigger） | 何时开始压缩 | 有模型信息时：上下文 **85%**；否则：**170k token** |
| 保留窗口（keep） | 压缩后原样保留多少 | 有模型信息时：**10%** 上下文；否则：**6 条消息** |
| 摘要输入上限 | 参与生成摘要的消息最多多少 token | **4000** |
| 参数截断 | 旧消息里超大工具参数截多短 | 超过 **2000 字符**截断（只留开头一小截） |
| 手动压缩门槛 | `compact_conversation` 工具何时允许执行 | 达到触发阈值的 **50%** |
| 归档保留期（dcode） | 历史归档保留多久后清扫 | **30 天**（`0` 禁用） |
| 恢复建议阈值（dcode） | 恢复线程时上下文多大就建议压缩 | **400k token**（`0` 禁用建议） |
