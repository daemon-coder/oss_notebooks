# DeepAgents 上下文压缩机制

> 本文面向**完全没接触过 DeepAgents（以及 LangChain、LangGraph 这类框架）的读者**。
> 文中每一个概念都会在用到之前先用大白话解释，不预设任何背景知识。
> 为了让你读得懂，全文**刻意不写任何代码、类名、函数名、字段名**——只讲"发生了什么、为什么、参数是多少"。
>
> 配套文档：[消息排列与上下文注入](消息排列与上下文注入.md)。建议先读那份了解"一次请求由哪些部分组成"，再回来看本文。

## 1. 先建立三个最小概念

### 1.1 智能体（agent）是怎么干活的

在 DeepAgents 里，一个"智能体"大致是这样工作的：你给它一个目标（比如"统计这个仓库里的 TODO 并写报告"），它会**一轮一轮地和模型对话**：

1. 模型读到"到目前为止的全部内容"，给出回复；
2. 回复里可能包含"我要调用某个工具"（读文件、写文件、执行命令）；
3. 程序执行这个工具，把**工具结果**追加回对话；
4. 模型再读全部内容，继续下一步……

关键点：**每一轮，模型都要把整段对话重新读一遍**，才知道自己在干什么、下一步该做什么。

### 1.2 上下文窗口（context window）

模型一次能读进去的文字量是有限的。这个上限通常用 **token** 来衡量（可以粗略理解为"半个到四分之三个汉字、或者一小段英文单词"）。比如某个模型"窗口是 20 万 token"，就是一次调用最多塞 20 万 token。

我们把"某次实际发给模型的全部文字"叫**上下文**。

### 1.3 问题：对话无限增长，窗口有限

一个长任务可能产生几百上千条消息（用户的话、AI 的回复、工具调用的请求、工具返回的结果……），全部累积在历史里。**对话越长，上下文越大，迟早撞上窗口上限**，模型调用会直接报"输入超长"错，任务就崩了。

这就是本文主题——**上下文压缩**：在上下文逼近上限时主动"瘦身"，把旧对话压成更短的形式，腾出空间让任务继续。

## 2. 核心思路：一句话 + 三个取舍

### 2.1 一句话

> 当上下文快满时，把**较早的旧对话**交给模型做一次摘要，用这段摘要**替换**旧对话；被替换掉的原始旧对话**不丢弃，而是先写进文件**，摘要里带上文件路径，模型以后需要细节时可以用"读文件"把它找回来；**最近的一小段对话**则原样保留、一字不动。

```
压缩前（发给模型的全部消息）：
┌────────────────────────────────────────────────────────┐
│ [系统提示] [用户] [AI] [工具结果] [AI] [工具结果] ……       │
│  └──────────── 旧对话（可能几百条，越来越大）────────────┘  │
└────────────────────────────────────────────────────────┘

压缩后：
┌─────────────────────────────┬──────────────────────────┐
│ [一段摘要]（内含文件路径指针）│ [最近若干条，原样保留]      │
└─────────────────────────────┴──────────────────────────┘
        ▲                            ▲
   旧对话 → 摘要                 最近窗口 → 不动
        │
        └── 完整旧对话 → 先写进文件（可找回）
```

### 2.2 三个贯穿始终的取舍

| 取舍 | 放弃的做法 | 选择的做法 |
|---|---|---|
| **摘要而非丢弃** | 直接砍掉最旧的消息 | 花一次模型调用，把旧对话浓缩成摘要，保留"目标、关键决策、产物、下一步" |
| **可恢复而非不可逆** | 摘要完细节就永久丢了 | 摘要**之前**先把旧对话写进文件，摘要里带路径，随时可读回 |
| **存储与呈现分离** | 直接在存储里删旧消息 | 原始历史**一条都不删**，只在"发给模型"时临时算一份精简视图 |

第三点是全文最重要的一条，先记住：**存储里永远保留完整原始对话，发给模型的只是一份"投影出来的视图"**。后面第 9 节会展开。

## 3. 一次压缩的全过程（总览）

每次要把消息发给模型之前，都会走一遍这条流水线。下面这张图是全文的地图，每一步后面的"见第 X 节"指向详解：

```
每次发消息给模型前：
│
├─ ① 算视图：根据"压缩记录"把原始历史算成 [摘要] + [最近窗口]   （见第 9 节）
│     （第一次没有压缩记录 → 视图 = 完整历史）
│
├─ ② 估算 token：系统提示 + 工具定义 + 消息，一次数完           （见第 4 节）
│
├─ ③ 便宜瘦身：够阈值就先截掉旧消息里超大工具参数                （见第 6 节）
│     （截完有变化就重新数一次 token）
│
├─ ④ 判断要不要摘要                                            （见第 4 节）
│     ├─ 没到阈值 → 直接发；若收到"输入超长"错误则转 ⑤（兜底）（见第 10 节）
│     └─ 到了阈值 → 进入 ⑤
│
├─ ⑤ 算切点：按"保留多少"算出一道分界，再往"安全位置"微调        （见第 5 节）
│
├─ ⑥ 一切两半：旧前缀（要摘要） | 最近窗口（原样保留）           （见第 5 节）
│
├─ ⑦ （仅兜底）裁剪最近窗口末尾的超大工具结果                   （见第 10 节）
│
├─ ⑧ 外置媒体：旧前缀里的图片等 → 存成文件 → 换成路径引用       （见第 8 节）
│
├─ ⑨ 外置历史：旧前缀 → 追加写入归档文件（失败不致命）           （见第 8 节）
│
├─ ⑩ 生成摘要：旧前缀（裁到 4000 token）→ 填四段式提示 → 调模型  （见第 7 节）
│
├─ ⑪ 组装：构造摘要消息（含文件路径）→ [摘要消息] + [最近窗口]    （见第 7、9 节）
│
└─ ⑫ 发送并记录：把视图发给模型；把新"压缩记录"写回状态           （见第 9 节）
         （原始历史不变，只是投影规则更新）
```

> 小细节：⑨ 和 ⑩ 彼此独立，在异步路径下会**并行**执行，省一点等待时间。

## 4. 什么时候触发压缩

### 4.1 阈值：三种粒度，任一满足即触发

触发条件支持三种"量法"，可以组合：

| 量法 | 含义 |
|---|---|
| 按消息条数 | 消息条数达到某个数就触发 |
| 按 token 数 | 估算的 token 数达到某个值就触发 |
| 按窗口比例 | 占模型窗口的某个百分比就触发（如 80%） |

组合语义：**列表 = 任一满足（或）**；**字典 = 同时满足（与）**。比如"到 80% 或到 100 条，先到先触发"。

### 4.2 双信号：估算值 + 模型报告的真实用量

判断"要不要压"有两个 token 来源，容易混，先分清：

1. **估算值**——程序自己按字符数折算（默认约 4 个字符算 1 token，某系模型约 3.3）。不依赖模型返回，随时能算。
2. **模型报告值**——模型每次返回时，会附带这次真实用了多少 token，记在最近一条 AI 回复上。

触发判定是"两者取其一"：**估算值越阈值，或者最近一条 AI 回复报告的真实用量越阈值，满足一个就触发**。

用真实值这条路径有个防御：程序会先确认这条 AI 回复确实来自**当前这个模型**（比对模型来源），避免"用模型 A 的数字去触发模型 B 的压缩"这种串数据。

### 4.3 默认值（开箱即用）

程序会自动探测：如果这个模型能查到它的"输入上限"（很多模型会声明），就用**按比例**的默认值；查不到就用**按固定数量**的保守值：

| 场景 | 触发阈值 | 保留窗口 |
|---|---|---|
| 能查到模型输入上限 | 窗口的 **85%** | 窗口的 **10%** |
| 查不到 | **17 万 token** | **最近 6 条消息** |

> 说明：上游框架自带的默认是"保留 20 条消息"。DeepAgents 在能拿到窗口大小时改成"按比例 10%"，拿不到时用更保守的"6 条"。

### 4.4 估算值的一个已知短板

按字符折算只分了两档（某模型 3.3、其余 4.0），而且**不区分中英文**：1 个汉字和 1 个英文字母都算 1 个字符，再统一除以 4。于是**中文会被严重低估**（1 个汉字常常就约等于 1 个 token，估算却只当四分之一个）。

这个问题本可以用真实值来校正，但校正系数被限制在最多上浮 25%，补不回中文那种几倍的缺口。想精确可以自己传一个计数函数（按中文约 1 token/字、其余约 4 字符/token 加权，或用模型官方分词器）。注意：传了自定义计数函数后，它会**同时**用于"触发判定"和"算切点"两处，所以你的计数函数必须对任意切片都稳定、单调。

### 4.5 其余计数细节

- 计数范围不止消息，还包括系统提示和工具定义（这两块也占窗口）。
- 程序会探测计数函数接不接受"工具"参数：能接就把它也算进去。
- **每轮只数一次**：工具定义转成文本很贵，所以"截参数判定"和"摘要判定"共享同一次计数；只有截断真的发生时，才重新数一次。

## 5. 压缩哪一部分：滑动窗口 + 安全切点

### 5.1 思路：越近越重要

对话里**越近的消息越重要**——模型马上要做的下一步最依赖最近几条；很早以前的消息已经被后续对话覆盖和推进，更适合被摘要。所以把对话切一刀：

- **旧前缀**（早的部分）→ 拿去做摘要；
- **最近窗口**（晚的部分）→ **原样保留**，一字不动。

保留多少可配置。默认见第 4.3 节（10% 或 6 条）。

### 5.2 一个必须处理的细节：别拆散"请求 + 结果"对

一条 AI 消息会"发起"工具调用（比如"写文件"），紧接着有工具结果回来。这对"请求 + 结果"必须**成对**——如果只留结果、把发起调用的那条 AI 消息摘要掉了，模型就会看到一个"没有来由的结果"，看不懂。

所以切点必须落在"安全"位置：**宁可多摘要一点，也不拆散这对**。这是"正确性 > 省空间"的取舍。

### 5.3 切点怎么算

1. **按保留预算找目标切点**：
   - 保留按 token / 比例：算出目标 token 数（如窗口 × 10%），用二分查找找到最小的下标，使"该下标之后的消息"token 数 ≤ 预算；
   - 保留按条数：切点 = 总条数 − 保留条数。
2. **往"安全"位置微调**：如果切点落在一条"工具结果"上，就**向前找**那条"发起这些工具调用的 AI 消息"（按工具调用编号匹配），把切点移到把它包含进去；找不到对应 AI 消息（边缘情况）才向后越过这串工具结果。
3. 二分查找用的是**不带"用量缩放"**的局部计数器，保证切点计算稳定可复现。

## 6. 便宜瘦身：先截参数，再摘要

### 6.1 思路

很多时候真正撑爆上下文的是少数几条"巨型消息"——"写文件"塞了整整一个文件、"改文件"塞了巨大补丁。为这些参数做一次完整摘要有点"杀鸡用牛刀"。所以先做一道**更便宜的预瘦身**：只对**旧消息**里这两个工具的**超大参数**做截断；截完 token 降回阈值以下，就**根本不用摘要**了。

为什么只动旧消息、只动这两个工具：最近窗口是模型马上要用的，不能截；只有"写文件 / 改文件"的参数是"一次性塞大段代码/补丁"的重灾区。这是"**先用便宜手段，再用贵手段**"的分层防御。

### 6.2 细节

1. **判定是否截**：截断也有自己的触发阈值，格式和摘要触发一致（条数 / token / 比例）；没配就不截。
2. **定位截哪些**：按"保留策略"算出"老消息"的边界，边界之前的才可能截，最近保留窗口不碰。
3. **执行截断**：只对旧消息里 AI 的"写文件 / 改文件"调用参数动手——字符串值超过**2000 字符**的，替换成"前 20 个字符 + 一句'参数已截断'"。

截断有改动就重新数一次 token，再进入摘要判定。

## 7. 摘要怎么生成

### 7.1 摘要的内容：强制四段式

摘要提示词要求模型**严格按四段**输出（这是从上游默认模板继承来的结构）：

- **本次目标**（SESSION INTENT）：用户最初及演化的目标；
- **摘要**（SUMMARY）：关键决策与结论，**含被否决的方案及原因**；
- **产物**（ARTIFACTS）：创建/修改了哪些文件、改了些什么；
- **下一步**（NEXT STEPS）：接下来做什么。

### 7.2 生成摘要前的准备

1. **裁剪输入**：待摘要的旧消息先裁到最多 **4000 token**（留尾部、从"人类消息"开始、允许部分截断、包含系统提示）。裁剪异常时兜底只取**最后 15 条**。
2. **转成纯文本**：把消息格式化成纯文本，避免直接打印消息对象导致元数据撑大 token。
3. **填提示词**：在默认模板基础上，DeepAgents 额外**插入一段"媒体引用说明"**——告诉摘要模型：遇到 `<image url="..."/>` 这类路径引用要**原样保留**、别臆造视觉细节、需要时让后续模型去读那个路径。这正是因为第 8 节会把图片外置成路径引用，摘要模型看到的是路径而非原始字节。

### 7.3 摘要消息长什么样

摘要生成后，被包成一条**"人类"角色的消息**（带一个特殊标记，供后面识别、跳过）。有归档路径时是三段式：

```
你现在处于一段已经被压缩的对话中。

完整对话历史已保存到 <文件路径>，需要细节可读该文件。

以下是压缩后的摘要：

<summary>
<四段式摘要文本>
</summary>
```

没有路径（外置失败）时退化成简版："这是到目前为止的对话摘要：……"。

> 注意两个角色的区别（和第 8 节的对比）：**摘要提示词**是给"做摘要的模型"看的（要求结构化、保留关键细节）；**摘要消息**是给"接下来继续干活的模型"看的（把它当既定背景，别复述）。

## 8. 被压缩的内容如何"找得回来"

### 8.1 思路

摘要一定会丢细节（某文件当时具体写了什么）。模型之后需要细节怎么办？答案是：在"用摘要替换旧对话"**之前**，先把完整旧对话**写进文件**存成归档，再在摘要消息里**嵌入文件路径**。为什么是文件——DeepAgents 的智能体本来就带一套文件工具，归档成文件天然能被模型用既有能力访问，不需要额外机制。

媒体是次生问题：图片是二进制，塞不进文本归档。处理：把图片**解码后单独存成文件**（按内容指纹命名），归档里只留引用标签，摘要模型看到的也是引用而非原始字节。

### 8.2 两类外置

**(a) 历史归档**——一个会话一个文件，多次压缩追加到同一个文件：

- 路径形如 `对话历史/<会话编号>.md`，会话编号在**同一次对话内复用**，所以同一段对话的多次压缩**追加到同一个文件**；子智能体各自独立、互不串文件。
- **过滤**：跳过上一次的摘要消息，避免"摘要的摘要"重复存储。
- **序列化**：用 XML 格式渲染。
- **追加**：拼上一行"压缩于 <时间>"的标题追加到文件（先读旧内容再合并写入；读旧内容用"下载"而非"读文件"，因为后者返回带行号的内容、不适合拼接）。
- **失败非致命**：写失败只记日志、发警告、返回"无路径"，摘要照做（退化为纯摘要）。

文件形态（追加式日志，示意）：

```
## 压缩于 2025-06-01T12:00:00+00:00

<系统角色>你的角色……</系统角色>
<人类>帮我统计 TODO 并写报告</人类>
<AI>
  <内容>好的，我先看目录</内容>
  <工具调用 名称="列目录">{}</工具调用>
</AI>
<工具结果>src/  utils/  tests/</工具结果>
  ...（本次被压缩掉的全部消息）
```

**(b) 媒体外置**——图片等二进制单独存文件：

1. 检测三种内联图片的形态（标准 base64 字段、顶层 `data:` 地址、OpenAI 风格的图片地址）；
2. 解码：base64 载荷做 base64 解码；普通 `data:<类型>,<内容>` 做百分号解码（覆盖内联 SVG）；类型决定扩展名（猜不出用 `.bin`）；
3. **去重**：按内容指纹取前 16 位命名，同内容只存一份；
4. 上传到 `对话历史/媒体/<指纹>.<扩展名>`；
5. 重写：把内联块换成带路径的引用标签（图片/音频/视频各自映射成对应引用，其他类型退化成通用引用）；上传失败的替换成"外置失败"占位标记。

### 8.3 归档实际落到哪

SDK 层用虚拟路径（默认根 `/`），真实落盘由**存储层**决定。以命令行工具为例：`对话历史/` 有专门路由落到本机用户目录下的 `~/.deepagents/conversation_history/`（目录权限加固为仅本人可访问、跨会话保留）；沙箱/服务端模式下归档写在沙箱存储里，本地没有文件。

## 9. 最关键的一点：存储与呈现分离

### 9.1 思路

压缩之后，对话历史到底变成什么样？**上游框架的默认做法**是直接在状态里删掉全部旧消息、塞入摘要 + 保留窗口——**原始历史真的没了**。

DeepAgents 的选择：**原始历史永远保留，一个字都不删**。做法是：

- 在状态里额外记一份**压缩记录**（摘要内容、切点位置、归档路径）；
- 每次发消息给模型时，**临时算出**模型该看的视图：`[摘要消息] + 原始历史[切点之后]`；
- 只改"发出去的东西"，不改"存着的东西"。

打个比方：**原始对话是一份完整台账，永远存档；发给模型的只是从台账里"投影"出来的一份精简视图**，压缩记录就是投影规则。

### 9.2 为什么这样

- ✅ 原始日志保留，可回放、可复盘、可评测；
- ✅ 自动压缩与手动压缩共享同一份原始状态、通过同一套投影协作；
- ✅ 链式压缩不重复摘要"已经摘要过"的东西；
- ⚠️ 代价：状态持续变大，需要额外字段和换算逻辑保证投影正确。

这是"**宁可多存不多删，宁可多算不丢信息**"的设计。

### 9.3 细节

- **压缩记录**存三样：摘要消息、切点位置（在原始历史里的**绝对下标**）、归档路径（可能为空）。
- **投影**：没有记录 → 视图 = 完整历史；有记录 → 视图 = `[摘要消息] + 原始历史[切点之后]`。模型每轮看到的永远是"摘要 + 切点之后的原始消息"。
- **绝对下标换算**：视图里的"切点"和原始历史里的"切点"不是同一个数（视图第 0 位是摘要消息）。若之前已有记录，新记录的绝对切点 = `旧切点 + 视图切点 − 1`（减 1 因为摘要消息占了第 0 位），保证链式压缩时记录始终指向正确的绝对位置。
- **防御检查**：记录损坏（缺字段）→ 退回完整历史；切点越界（大于消息数）→ 只返回摘要消息。
- **请求改写与状态更新**：投影出 `[摘要消息] + [保留窗口]` 发给模型；同时把新压缩记录写回状态——**`原始历史本身不动`**（除非溢出兜底要写回被裁剪的尾部，见第 10 节）。

## 10. 失败时的兜底：溢出恢复

### 10.1 思路

即便有阈值，仍可能出意外——模型突然拒绝，抛"输入超长"错误。直接让任务崩溃吗？不。把它当作一次"被动触发压缩"的信号：先正常调用，失败后转入压缩流程重试。哲学是"**外部错误不该击穿系统，而应转化为一次自救**"。

### 10.2 细节

1. 在"判断不用摘要"的路径上直接调用模型；若抛"输入超长"错误，置一个溢出标记，转入正常压缩流程。
2. 额外动作——**裁剪保留窗口末尾的超大工具结果**：
   - 检查"保留窗口"是否**以连续一串工具结果结尾**，且合计 token 达到阈值（阈值来自保留预算；保留按条数、拿不到 token 信息时默认 **5000**）；
   - 对每条超大结果：
     - 若是"读文件"的结果：**不写新文件**（原文件本就在存储里），只把内容切到**前 4000 字符** + 一句提示"完整内容在 <原路径>，用读文件的偏移/行数参数分段读"；
     - 其他工具结果：全文写入 `超大工具结果/<调用编号>`，原位替换成一条"桩消息"：

```
工具结果太大，这次调用的结果已保存到文件：超大工具结果/<调用编号>
请用读文件分段读取（例如 offset=0, limit=100）。
下面是结果的头尾预览：
  1  <结果第一行>
  2  ...
  ... [省略 N 行] ...
  M  <结果最后一行>
```

   - 替换后的消息**保留原来的编号**，通过一次状态更新写回（按编号覆盖原消息）。

> 说明：`超大工具结果/` 目录不专属于压缩——文件中间件还有一条"工具结果超过阈值就主动驱逐"的路径也写这里（甚至执行命令的输出也能直接重定向进去）。压缩只用到"溢出兜底"这一条。

## 11. 手动压缩：把压缩做成工具

### 11.1 思路

自动压缩只在"快满"时触发。但有时模型**自己**就知道该压缩——比如刚做完一个任务、要转向全新任务，旧上下文已无用，此时主动压缩能省大量空间。所以额外提供一个工具（名字叫"压缩对话"），模型可以像调用"读文件"一样调用它。为防止**过早滥用**，加一个资格门槛：对话规模至少达到"自动触发阈值的 50%"才允许真正压缩。**把能力开放给模型（灵活），用门槛约束（防滥用）**。

### 11.2 细节

- 该工具**无参数**，描述引导模型在"对话变长、转向全新任务、或完成综合/抽取后"主动调用。
- **资格门槛**：对话达"自动触发阈值的 50%"才放行（token → 0.5 倍；条数 → 0.5 倍；比例 → 0.5 × 窗口）。多条件：字典 = 与、列表 = 或。不满足 → 返回"还没什么可压的，对话还在预算内"。
- **执行**：投影有效消息 → 资格检查 → 算切点（切点为 0 则"没什么可压"）→ 一切两半 → 生成摘要 → 外置历史。结果返回"对话已压缩，共摘要了 N 条消息"，同时更新压缩记录；异常返回"压缩失败：……"，**绝不抛异常**。
- 该层还会往系统提示追加一句"建议长会话时调用压缩工具"的提示（可关闭）。

---

## 12. 容错原则：每一步失败都不致命

压缩是多环节流水线，任何一环都可能失败。设计原则是**逐环降级，绝不因压缩失败让主任务崩溃**。压缩是"锦上添花的优化"，不是"生死攸关的必经之路"。

| 环节失败 | 降级行为 |
|---|---|
| 历史归档写失败 | 照常生成摘要，但摘要不带文件路径（退化为纯摘要） |
| 媒体上传失败 | 归档里留"图片丢失"占位标记，不静默丢弃 |
| 摘要模型报错 | 返回"摘要生成失败"说明文字，不抛异常 |
| 判断不用压缩但调用超长 | 转入压缩流程重试（见第 10 节） |

---

## 13. 多轮压缩的叠加

压缩是可重复的。下一轮压缩的范围从当前视图头部开始，**会连上一次的摘要一起再压**——也就是说摘要会被"摘要的摘要"不断浓缩（模型看不到中间版本，只看得到最新那一条）。程序会做两件事保证链式压缩正确：

- **外置时过滤**：把旧的摘要消息从"要写进归档"的内容里过滤掉（原始消息早就在归档里了，别重复存）；
- **切点换算**：用第 9.3 节的"绝对下标换算"，保证每一次的新切点都指向原始历史里的正确位置。

## 14. 谁来清理归档

一句话结论：**SDK 层没有自动清理（有意为之）；清理只存在于命令行工具层，且只覆盖"历史归档"这一类文件。**

- **SDK 层**：无自动清理。归档是"失忆时可查"的唯一恢复路径，宁可留着。想删只能靠模型/用户显式调用"删除"工具（且要过权限校验）。
- **命令行工具层——启动时清扫**：每次启动挂一个后台任务，按保留天数清理历史归档：
  - 默认保留 **30 天**；可配置，`0` 表示**禁用清扫**；
  - **只清**"历史归档"目录下**直接的、`.md` 后缀、且是常规文件**的条目；
  - 按**最后修改时间**判定过期；
  - **竞态防护**：删除前先打开文件、再确认"确实没被正在进行的压缩刷新过"才删——因为压缩对归档是"读-追加-重写"，若清扫的删除与正在进行的重写竞争，可能悄悄丢掉刚写入的历史。
- **命令行工具层——删会话同步删归档**：用户删某会话时，一并删除该会话的归档（做了路径安全校验，拒绝能逃出归档目录的伪造编号）。
- **明确不清理的部分**：
  - **媒体文件**：清扫只匹配归档目录的直接 `.md` 子文件，`媒体/` 是子目录、且是二进制非 `.md`，**永远不被扫**；
  - **超大工具结果**：只被路由到某目录，没有任何清扫，**永久留存**。

> 推论：只用 SDK（不走命令行工具）时，这三类文件会无限增长。长期运行纯 SDK 服务，需自行按"历史归档 / 媒体 / 超大工具结果"三个前缀做配套清理。

## 15. 术语表

| 术语 | 通俗解释 |
|---|---|
| token | 模型计费/计量的最小文字单位，可粗略理解为"半个字或一小段英文单词" |
| 上下文窗口 | 模型一次能读入的最大文字量 |
| 消息 | 对话历史的基本单元（用户消息 / AI 消息 / 工具结果消息） |
| 工具调用 | 模型在回复里请求"帮我执行某个函数" |
| 状态 | 智能体运行期间保存的持久数据，最核心的是累积的消息列表 |
| 视图 | 某次实际发给模型的消息集合（可从状态"投影"而来） |
| 压缩记录 | 记录"摘要内容 + 切点位置 + 归档路径"的一份元数据 |
| 存储层 | 智能体读写文件的那层（磁盘 / 内存 / 沙箱等） |
| 外置（归档） | 把要丢弃的内容先写入文件，供以后按需读取 |
| 中间件 | 一层层的加工插件，能在每次请求发给模型前拦截并改写它（详见配套文档） |

## 16. 配置速查

| 配置项 | 含义 | 默认值 |
|---|---|---|
| 触发阈值 | 何时开始压缩 | 能查到模型上限时：窗口 **85%**；否则 **17 万 token** |
| 保留窗口 | 压缩后原样保留多少 | 能查到模型上限时：**10%**；否则 **6 条消息** |
| 摘要输入上限 | 参与生成摘要的消息最多多少 token | **4000** |
| 参数截断 | 旧消息里超大工具参数截多短 | 超过 **2000 字符**截断（只留开头一小截） |
| 手动压缩门槛 | 压缩工具何时允许执行 | 达到触发阈值的 **50%** |
| 归档保留期（命令行工具） | 历史归档保留多久后清扫 | **30 天**（`0` 禁用） |
