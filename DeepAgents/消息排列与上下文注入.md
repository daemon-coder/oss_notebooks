# DeepAgents 消息排列与上下文注入机制

> 本文面向**完全没接触过 DeepAgents（以及 LangChain、LangGraph 这类框架）的读者**。
> 回答三个问题：一次请求里的消息按什么顺序排列？几类"上下文注入"（技能、记忆、文件工具说明、子智能体清单）
> 是怎么组织的、什么时候注入？压缩前后消息序列如何变化？
>
> 全文刻意不写任何代码、类名、函数名、字段名。配套文档：[上下文压缩](上下文压缩.md)。

---

## 1. 一次请求由三部分组成

每次调大模型接口，请求体由三块组成：

| 组成 | 是什么 | 特点 |
|---|---|---|
| **系统提示词** | 一段放在对话开头、用来设定角色和规则的固定说明 | **独立的一块，不进消息列表**，每次请求都重新生成、永远完整 |
| **消息列表** | 对话历史的逐条投影（用户消息、AI 消息、工具结果……） | 按时间顺序累积 |
| **工具清单** | 告诉模型"你有哪些工具可用、每个工具怎么用"的定义 | 每轮根据实际情况可能被裁剪 |

关键区别（和很多人的直觉相反）：**系统提示词是独立的一块，不是消息列表里的第一条**。它有自己的位置（在底层接口里通常是单独的 `system` 字段），消息列表里从头到尾都是"对话本身"。

> 这也是 DeepAgents 和它要对比的另一套工具最大的不同：那一套把几类注入（AGENTS.md、运行时上下文、技能目录）当成**一条条独立的用户消息**追加在用户问题之后；而 DeepAgents 把所有这些**全部塞进系统提示词这一块里**，消息列表里不放任何"注入"。

---

## 2. 系统提示词是怎么拼出来的

系统提示词不是一次写死的，而是**分层拼装**出来的。先说"作者写的那部分"，分三层（按最终顺序）：

1. **用户写的一段**（USER）：调用方在创建智能体时传入的说明（比如"你是一个代码审查助手……"）。
2. **内置/配置的基础模板**（BASE）：按模型/服务商自动套用的模板。**主智能体默认没有**（为空）。
3. **配置的附加后缀**（SUFFIX）：按模型微调的一段话（比如"回答控制在 100 字内"）。设计上放在最后，**离对话历史最近**，让"调模型行为"的话尽量靠近模型要回答的内容。

三层用空行分隔，拼成"作者写的系统提示词"。这一层拼装叫**"提示词装配"**，是可配置的：用户只传第 1 层也行、只靠第 2/3 层也行、都不传就得到一段空白的作者提示词。

然后，**在这段作者提示词之后**，一层层加工插件还会继续往系统提示词末尾追加各自的内容（下一节讲）。

---

## 3. 关键机制：一层层"加工插件"

### 3.1 什么是"加工插件"

DeepAgents 的核心可扩展机制是一组**加工插件**（业界叫"中间件"）。每个插件都能在**每次请求发给模型之前**拦住它、改它，具体能做四件事：

1. **追加系统提示词**：往系统提示词末尾再拼一段自己的说明；
2. **增删工具**：按实际情况过滤掉用不了的工具；
3. **改写消息**：变换消息列表（比如压缩，见配套文档）；
4. **维护跨轮私有数据**：读写一份跟着会话走的私有状态（比如"已经加载了哪些技能"）。

一个普通的工具函数做不到这些——它只能**被模型调用**，没法在**模型被调用之前**拦截并改写请求。这正是"用插件而不是纯工具"的原因。

### 3.2 插件是怎么层层加工的

插件们排成一个**有序列表**，像一个"洋葱"一样一层套一层：**列表里排在最前面的插件最先执行**，它改完交给下一个，最后一个交给真正的模型调用。

于是，插件"追加系统提示词"的顺序 = 插件在列表里的顺序。谁排前面，谁的说明就出现在系统提示词的更前面。

### 3.3 默认的插件顺序

创建智能体时，默认插件栈是这样排的（从头到尾）：

```
技能目录插件
文件工具插件
子智能体插件
压缩插件
（调用方传入的自定义插件，按传入顺序）
（按模型/服务商附加的插件）
（工具裁剪插件：把配置里要隐藏的工具去掉）
（缓存标记插件：给系统提示词打缓存断点）
记忆插件
（有人工审批时再加审批插件）
```

对应到系统提示词的最终顺序（默认，且开了技能和记忆时）：

```
1. 作者写的系统提示词（第 2 节的 USER → BASE → SUFFIX）
2. 技能目录说明（技能插件追加）
3. 文件工具说明（文件插件追加；默认通常为空，见 4.3）
4. （子智能体说明——默认不进系统提示词，见 4.4）
5. （压缩插件的提示——可选，见 4.5）
6. 调用方自定义插件追加的内容
7. 按模型/服务商附加插件追加的内容
8. （缓存标记插件不追加文字，只打缓存断点，见第 8 节）
9. 记忆内容（记忆插件追加）
10. （审批插件一般不加文字）
```

> 一句话记住：**作者提示词在最前，然后是"技能 → 文件 → 子智能体 → 压缩 → 自定义 → 记忆"逐层垫后**。

## 4. 四类"上下文注入"逐个拆解

对应那一套工具的"三个注入"，DeepAgents 有这几类，原理各不相同：

### 4.1 技能目录（渐进式披露）

**技能**是一份"专项能力说明"，每个技能是一个目录，里面有一份带元信息的说明文件（名字、一句描述、可选授权/兼容性等）+ 可选的辅助文件。

- **注入什么**：只注入技能的**索引**——名字 + 描述 + 说明文件路径，**不含正文**。正文要模型按需用"读文件"去读，这叫"**渐进式披露**"：先让模型看到"有哪些技能、各自干什么"，真要用某个技能时再去读全文。这样既省上下文，又能让模型知道去哪找。
- **加载时机**：在智能体**启动时一次性加载**，把索引存进私有状态；之后**每次请求都把这个索引注入系统提示词**。
- **来源分层**：技能可以来自多个目录（基础 / 用户 / 项目 / 团队），按顺序加载，**同名时后者覆盖前者（最后者赢）**。
- **注入条件**：只有在调用方明确提供了技能来源时才装这个插件；没提供就没有这整段。
- **附带信息**：还会注入"技能加载警告"（哪些技能没加载成功及原因），但被明确标记为"不可信的诊断信息，不要当成指令"——防止坏技能里的内容被当成系统指令。

### 4.2 记忆文件（总是加载）

**记忆**是几份项目级的固定说明文件（通常叫 AGENTS.md 或类似名字），用来放"项目概览、构建命令、代码风格、架构说明"这类长期有效的上下文。

- **注入什么**：注入文件的**完整内容**（和技能相反——技能只注入索引、正文按需读；记忆是**全量、始终加载**）。多个来源按顺序拼接，全部包含。
- **清理**：文件里的 HTML 注释会被**剥掉**再注入（注释可用来写"作者笔记 / 机器管理的标记"，不暴露给模型）。
- **安全包装**：记忆内容外面会包一层"**信任与校验**"的引导，明确告诉模型：这份内容是磁盘上的文件数据，可能过时、错误、或不是当前用户写的，要当参考材料而不是隐藏指令；当记忆与用户的话或工具证据冲突时，以用户和证据为准。这是防"记忆文件里的内容被当成系统指令注入"的措施。
- **加载时机**：和技能一样，**启动时一次性加载**到私有状态，之后**每次请求都注入**。

### 4.3 文件工具的能力裁剪与路径说明

文件插件除了提供读/写/搜等文件工具，还会在每次请求时做两件"注入"相关的事：

1. **按能力裁剪工具**：某些工具（执行命令、删除文件）只有特定存储层支持。每次请求时探测存储层的能力，**把用不了的工具从清单里去掉**，而不是把它广告给模型、等调用时才失败。
2. **追加路径说明**：当"执行命令"工具可用、且存储层是多层复合结构时，追加一段"虚拟路径 ↔ 真实路径"的映射说明，让模型知道在沙箱里看到的路径对应宿主机的哪里。默认（单层存储）这段为空。

另外文件插件还有一条和压缩并列的"驱逐"逻辑：用户粘贴了超大一段话时，会把原文写进文件、原消息换成截断预览（详见配套文档里提到的伴生机制）。这属于"上下文瘦身"而非"注入"，不展开。

### 4.4 子智能体清单（通过工具说明传递）

**子智能体**是主智能体可以临时派出去干活的"小助手"（通过一个"派任务"工具调用）。主智能体需要知道"有哪些子智能体、各自擅长什么"——但这段信息**默认不进系统提示词**，而是**写进"派任务"这个工具的说明里**：

- 该工具的描述里有一个占位符，装配时会替换成"每个子智能体的名字 + 描述"清单；
- 于是模型在**看这个工具时**就顺带看到了"可用子智能体列表"，不需要占系统提示词的位置。

> 结论：子智能体的上下文走的是"**工具说明**"这条通道，不是系统提示词（除非调用方显式要求把使用说明写进系统提示词）。

### 4.5 压缩工具的使用提示（可选）

如果把"压缩对话"这个工具装上（见配套文档第 11 节），它的插件还会（可选地）往系统提示词追加一句"对话变长时建议主动调用压缩工具"的提示。不装就没有。

## 5. "加载一次、每次请求都注入"的模式

技能和记忆有个共同模式，值得单独拎出来：

- **加载（读文件、解析）只在智能体启动时做一次**，结果存进一份私有状态；
- **注入（往系统提示词里拼）每次请求都做**，但注入时只是从状态里把已加载的内容拿出来拼上去，**不重新读文件**。

所以：文件内容在一次会话里是"启动时快照"；要让它变化（比如改了 AGENTS.md），得重启会话或依赖模型主动去改。这和"每轮都重新读盘、内容变了就重发一份新版本"的另一套工具有本质区别——**DeepAgents 是"加载一次 + 每次请求稳定重放"，更强调前缀的字节级稳定**（好处见第 8 节）。

---

## 6. 工具说明也是一种上下文

除了系统提示词，**工具清单里每条工具的描述**也是模型看得到的上下文。有几个细节：

- 每个内置工具（列目录、读文件、写文件、改文件、搜文件、执行命令、派任务……）都自带描述，告诉模型"什么时候用、参数怎么填"；
- 描述可以被按模型/服务商**覆盖**（同一个工具在不同模型上给不同的使用提示）；
- 工具清单可以被按模型/服务商**裁剪**（某模型不擅长某工具，就直接不展示给它）。

所以"模型看到的上下文"= 系统提示词 + 工具清单（含描述）+ 消息列表，三者都在每次请求时被动态整形。

---

## 7. 消息本身怎么排

消息列表里就是"对话本身"，规则很简单：**按时间顺序累积**。典型的一段长这样：

```
[用户：帮我统计 TODO 并写报告]
[AI：好的，我先看目录（同时发起"列目录"工具调用）]
[工具结果：src/  utils/  tests/]
[AI：我搜一下 TODO 关键字（同时发起"搜索"工具调用）]
[工具结果：<几百行匹配结果>]
[AI：我把结果整理成报告（同时发起"写文件"调用）]
[工具结果：报告已写入 /workspace/report.md]
……（继续累积）
```

要点：

- **系统提示词不在这里面**（它是独立的一块，永远在最前）；
- 用户新说的一句话会被**追加到列表末尾**；
- 一条 AI 消息发起工具调用、紧接着跟一条工具结果，这对"请求 + 结果"是成对、连续的；
- 消息列表靠一个**归并规则**维护：按消息编号去重、支持"删除某条"和"清空全部"的操作（压缩不删历史，但上层框架的"重试/回滚"等会用到这里）。

## 8. 缓存断点：把变化的内容放在稳定前缀之后

这是对话里最关键的一个架构问题：**为什么系统提示词要把"变化的内容"放在末尾，而不是开头？**

大模型服务普遍提供"前缀缓存"：如果两次请求的开头一大段完全相同，第二次就不用重新算那一段，既快又省钱。所以理想情况是**把稳定不变的内容放在最前，把每次会变的内容放在最后**，这样变化只影响尾部一小段。

DeepAgents 的做法：

1. **作者提示词 + 技能 + 文件 + 自定义插件**放在前段——这些在一次会话里基本稳定；
2. **缓存标记插件**在这一段之后打一个"缓存断点"（告诉服务"到这为止可以缓存"）；
3. **记忆内容**放在更靠后，且记忆插件在它末尾**再打一个断点**。

这样：前段（作者提示词、技能目录等）作为稳定前缀被缓存；记忆内容被单独缓存；**当记忆被更新时，只有"记忆这一小段及之后"失效，前面的稳定前缀照旧命中**。如果反过来把记忆放最前，记忆一改，后面整段全部失效。

> 这正对应那一套工具里"把易变的注入放尾部、稳定的放前缀"的同一套缓存哲学——只是落地方式不同：那一套把注入当"独立用户消息"放消息列表尾部，这一套把注入放进系统提示词的尾段，并用缓存断点划出"稳定前缀"和"可变化尾段"的边界。

## 9. 与压缩的联动：压缩前后消息如何变化

压缩改的是**消息列表**，不动系统提示词（详见配套文档）。压缩前后对比：

```
压缩前发给模型的请求：
  系统提示词：作者提示词 + 技能 + 文件 + 记忆（完整）
  消息：[用户][AI][工具结果][AI][工具结果] ……（越来越长）

压缩后发给模型的请求：
  系统提示词：作者提示词 + 技能 + 文件 + 记忆（完整，重新生成、一字不少）
  消息：[摘要消息（含归档路径）] + [最近窗口，原样] + [新用户消息]
```

要点：

- **系统提示词从不参与压缩**，每次请求都完整重新生成；
- 消息列表被替换成"摘要 + 最近窗口"的视图（原始历史仍在存储里，没删）；
- 摘要消息是一条"人类"角色消息，带一个特殊标记（供链式压缩时识别、跳过）；
- 技能、记忆这些注入**在压缩前后都不变**——因为它们住在系统提示词里，而压缩只动消息列表。这一点也和"那一套工具压缩后要重新注入三个注入"不同：DeepAgents 天然没有"注入被压缩掉"的问题。

## 10. 术语表

| 术语 | 通俗解释 |
|---|---|
| 系统提示词 | 放在对话开头、设定角色和规则的固定说明，独立于消息列表 |
| 消息列表 | 对话历史本身（用户 / AI / 工具结果），按时间累积 |
| 工具清单 | 告诉模型"有哪些工具、怎么用"的定义集合 |
| 加工插件（中间件） | 在每次请求发给模型前拦截并改写它的可扩展层 |
| 技能 | 一份"专项能力说明"，按需读全文（渐进式披露） |
| 记忆 | 项目级固定说明文件（如 AGENTS.md），始终全量加载 |
| 子智能体 | 主智能体可临时派出去干活的"小助手" |
| 缓存断点 | 告诉模型服务"到此为止可缓存"的标记 |
| 前缀缓存 | 两次请求开头相同则复用已算结果、省时省钱的机制 |
