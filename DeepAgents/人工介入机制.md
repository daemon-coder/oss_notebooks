## 1. 什么是 HITL

HITL（Human-in-the-loop，人工介入）解决一个问题：**程序跑到一半，需要人来拍板，不能自己往下走。**

比如：

- "要不要删这个文件？"（安全审批）
- "这个参数改一下行不行？"（审核）
- "用户从 A / B / C 里选哪个？"（要用户输入）

核心动作就三个词：

```
暂停 ──► 等人给答案 ──► 继续
```

听起来简单，但"暂停之后还能从原地继续"，这件事在代码里怎么实现，才是本文要讲的重点。

## 2. 从一个最小例子开始（先跑，再讲原理）

我们先不碰 DeepAgents，用**最简单的图**来讲清楚"暂停 / 继续"到底发生了什么。

### 2.1 先看一个普通节点：从上往下跑，跑完就结束

```python
def node(state):
    print("开始")
    return {"结果": "完成了"}
```

这个函数很简单：打印一行"开始"，返回一个结果。跑一次，结束。

### 2.2 加一句"问问用户"：第一次跑，它停住了

现在我在中间插一句"问问用户"：

```python
from langgraph.types import interrupt

def node(state):
    print("开始")
    答案 = interrupt("请问你几岁？")   # ← 新加的一行
    print("收到", 答案)
    return {"结果": 答案}
```

**第一次跑这个函数时，发生了什么？**

```
第 1 行  print("开始")          → 输出"开始"
第 2 行  答案 = interrupt("请问你几岁？")  → 在这里【停住】，把"请问你几岁？"抛出去
第 3 行  print("收到", 答案)     → 【没执行到】
第 4 行  return {"结果": 答案}   → 【没执行到】
```

也就是说：函数跑了两行就**停下来了**，后面的代码没执行。而你（调用方）拿到了它抛出来的那句话——**"请问你几岁？"**。

### 2.3 用户答完，第二次跑：interrupt() 这次"返回"了答案

现在假设用户回答了"18"。你再次调用，这次**带上答案**：

```python
from langgraph.types import Command

# 第二次调用：Command(resume="18")
```

这次函数会**从头再跑一遍**，但结果不同：

```
第 1 行  print("开始")          → 又输出"开始"（注意：又打印了一次！）
第 2 行  答案 = interrupt("请问你几岁？")  → 这次【不停】，直接返回 "18"
第 3 行  print("收到", 答案)     → 输出"收到 18"
第 4 行  return {"结果": 答案}   → 返回 {"结果": "18"}
```

**关键来了**：同一个 `interrupt("请问你几岁？")`，第一次跑是"停住、抛问题"，第二次跑是"直接返回答案 18"。

### 2.4 把两次连起来看

```
第一次调用（不带答案）：
    输出：开始
    然后：停住，抛出 "请问你几岁？"   ← 程序返回了，不占资源

第二次调用（resume="18"）：
    输出：开始
    输出：收到 18
    返回：{"结果": "18"}
```

这就是"暂停 → 继续"的全部本质。就这么简单。

### 2.5 一个必须知道的小细节：恢复时会"从头重跑"

你可能注意到了：**"开始"打印了两次**。

这是因为，框架"暂停"时，记住的**不是**"代码执行到第 2 行了"，而是：

> "这个节点的状态存起来了，等会儿有人给答案了，就把它从头再跑一遍。"

所以恢复时，函数**从头再跑**，只是这一次 `interrupt()` 会"感知到答案已经来了"，于是直接返回答案，而不是再次停住。

**这带来一个重要推论**：`interrupt()` 之前的代码会被执行两次。所以它前面的代码要**幂等**（跑两遍没副作用）——别在它前面做"发短信、扣款、写文件"这种只能做一次的事。

### 2.6 关键澄清：interrupt() 自己不会弹窗

你可能以为 `interrupt("请问你几岁？")` 会自己弹出一个对话框。**不是的。**

`interrupt()` 只做一件事：**把数据交给你（调用方），然后暂停**。至于"弹窗""命令行输入""发个网页请求"……这些全是**你自己的代码**在**图外面**做的。

整个东西分两半：

```
┌──────────── 图内（agent 的代码）────────────┐
│  interrupt(内容) → 交出内容 + 暂停          │  ← 就这么多，没有别的
└───────────────────────────────────────────┘
                     │ 把"内容"交出去
                     ▼
┌──────────── 图外（你自己的代码）────────────┐
│  收到内容 → 你想怎么表现就怎么表现            │
│  （弹窗？命令行输入？发网页请求？随你）        │
│  → 拿到用户答案 → resume(答案) 塞回去        │
└───────────────────────────────────────────┘
```

接着第 2.2 节的例子，完整代码是这样的：

```python
# ========== 图内：节点（agent 的代码）==========
from langgraph.types import interrupt

def node(state):
    print("开始")
    答案 = interrupt("请问你几岁？")   # 只交出这句话 + 暂停，不弹窗
    return {"结果": 答案}
```

```python
# ========== 图外：你自己的代码（服务端 / GUI 后端）==========
def 弹窗(问题):          # ← 这才是真正的弹窗，你自己写
    # 随便怎么显示"问题"、等用户输入、返回答案
    return 用户输入

# 第一次：跑到 interrupt 就返回
app.invoke({"..."}, config)

# 检查：有没有中断等着处理？
state = app.get_state(config)
if state.interrupts:
    内容 = state.interrupts[0].value     # "请问你几岁？"
    答案 = 弹窗(内容)                     # ← 弹窗发生在这里
    app.invoke(Command(resume=答案), config)
```

**关键点**：

1. `interrupt(内容)` 里的"内容"就是要丢给用户看的数据，任意类型（字符串、dict、数字……）都行；
2. "内容"通过 `get_state(config).interrupts[0].value` 拿到（用 `stream` 时则在输出里出现 `__interrupt__`）；
3. **弹窗是 100% 你的活**：`interrupt()` 管到"交数据"为止，之后"怎么给用户看、怎么收答案"全是图外你写的代码。

## 3. 这背后到底发生了什么（原理）

跑完例子，我们再回头解释"为什么能这样"。

### 3.1 interrupt 的本质：一个"能恢复的暂停"

`interrupt(内容)` 第一次被调用时，相当于**抛出一个特殊的"暂停信号"**：

- 这个信号里带着 `内容`（你要抛给用户看的东西，比如"请问你几岁？"）；
- 程序收到信号，就**停止往下执行**，把 `内容` 交还给调用方；
- 同时，程序会**把当前状态存一份**（下一节讲为什么）。

### 3.2 为什么能恢复：因为暂停时存了档

"停住"这件事，光停在内存里是不够的——万一进程重启、换台机器，就找不回来了。

所以框架在暂停时，会**把当前状态写进存档器（checkpoint）**。这个存档里记着：

- 到目前为止的完整消息历史；
- 当前停在哪个节点、有哪些任务没做完；
- 中断时抛出的那个 `内容`。

有了这份存档，之后无论隔多久、甚至重启之后，都能"找回现场"。

### 3.3 resume 的本质：加载存档 + 把答案塞回那一行

你第二次调用并带上答案（`Command(resume=答案)`）时，框架做两件事：

1. **加载存档**：把暂停时的状态原样恢复；
2. **把答案塞回去**：重新执行那个节点，但 `interrupt()` 这次直接返回 `答案`。

于是代码就"接着"跑下去了。

### 3.4 一句话串起来

> `interrupt(问题)` 第一次 = 停下 + 存档 + 把问题抛给用户；
> `Command(resume=答案)` 第二次 = 加载存档 + 重跑节点 + `interrupt()` 返回答案。

## 4. 前提：必须配存档器

从 3.2 你就懂了：暂停要"存档"，恢复要"读档"。所以**必须给图配 checkpointer（存档器）**，否则 interrupt 直接报错。

```python
from langgraph.checkpoint.memory import InMemorySaver

graph.compile(checkpointer=InMemorySaver())   # 这个不能省
```

## 5. 一个完整可跑的最小代码

把上面讲的拼起来，就是一个能跑的最小骨架：

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from typing_extensions import TypedDict


class State(TypedDict):
    question: str
    answer: str


def ask_node(state: State):
    answer = interrupt(f"请回答：{state['question']}")
    return {"answer": answer}


graph = StateGraph(State)
graph.add_node("ask", ask_node)
graph.add_edge(START, "ask")
graph.add_edge("ask", END)
app = graph.compile(checkpointer=InMemorySaver())   # 必须配存档器

config = {"configurable": {"thread_id": "会话-1"}}

# 第一次：跑到 interrupt() 停住，返回值里带 __interrupt__
first = app.invoke({"question": "你叫什么名字？"}, config=config)
# first 里能看到 __interrupt__ = "请回答：你叫什么名字？"

# 第二次：带答案恢复
result = app.invoke(Command(resume="张三"), config=config)
print(result["answer"])   # -> 张三
```

## 6. 两种使用层次

理解了底层，再往上，DeepAgents 里用 HITL 有两层：

| 层次 | 是什么 | 适合 |
|---|---|---|
| **直接调 `interrupt()`** | 你自己在工具/节点里写 `interrupt(...)` | 自定义交互、任意逻辑 |
| **`interrupt_on` 声明式** | 告诉框架"调用某工具前请人审批"，框架自动断 | 工具审批/审核/代答 |

下面分别讲。

---

## 7. 直接调 interrupt() 的用法

### 7.1 在工具里调 interrupt（工具弹框让用户选）

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from deepagents import create_deep_agent


def ask_user(options: list[str]) -> str:
    """弹框让用户从给定的选项里选一个。"""
    choice = interrupt({"question": "请选择一项", "options": options})
    return f"用户选择了：{choice}"


agent = create_deep_agent(
    model="your-model-id",
    tools=[ask_user],
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "会话-1"}}

# 第一轮：模型调用 ask_user，跑到 interrupt() 时暂停并返回
first = agent.invoke(
    {"messages": [{"role": "user", "content": "帮我问问用户想选哪个"}]},
    config=config,
)
# first 里含 __interrupt__（就是 {"question": "请选择一项", "options": [...]}）
# 你的 GUI 拿到后弹框；此刻程序已返回、不占资源

# 用户选完，恢复：
result = agent.invoke(Command(resume="方案B"), config=config)
print(result["messages"][-1].content)
```

### 7.2 一个节点多个 interrupt：按顺序匹配

```python
def node(state):
    a = interrupt("第一个问题")   # 拿到第一个 resume 值
    b = interrupt("第二个问题")   # 拿到第二个 resume 值
    return {"a": a, "b": b}
```

### 7.3 interrupt_before / interrupt_after（按节点断）

```python
agent.invoke(
    {"messages": [...]},
    config={
        "configurable": {"thread_id": "会话-1"},
        "interrupt_before": ["tools"],   # 进入 tools 节点前暂停
        # "interrupt_after": ["tools"],  # tools 节点之后暂停
    },
)
```

### 7.4 不带答案恢复

如果只 `agent.invoke(None, config)`（不带 resume 值），`interrupt()` 会返回 `None`。适合"只需人点个'继续'、不需要输入"的场景。

## 8. interrupt_on 声明式：四种决策详解

这是 DeepAgents 内置的 `HumanInTheLoopMiddleware`，让你**声明式**给工具加审批，不用自己写 interrupt。

### 8.1 配置结构

```python
agent = create_deep_agent(
    model="...",
    tools=[...],
    checkpointer=InMemorySaver(),
    interrupt_on={
        "工具名": {
            "allowed_decisions": [...],   # 允许哪些决策
            "description": "...",         # 可选：审批说明
            "when": 谓词函数,              # 可选：决定是否对这次调用中断
        },
        "另一个工具": True,               # True = 允许全部四种决策
    },
)
```

- **没列在 `interrupt_on` 里的工具，默认自动放行**，不中断。

### 8.2 四种决策逐一讲

#### ① approve（批准）—— 照常执行

| 项 | 内容 |
|---|---|
| 含义 | 人看了没问题，放行 |
| 工具是否执行 | ✅ 按原参数执行 |
| 决策体 | `{"type": "approve"}` |
| 结果 | 工具正常返回结果 |

```python
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config=config)
```

#### ② edit（编辑）—— 改参数后执行

| 项 | 内容 |
|---|---|
| 含义 | 人修改工具名字或参数后再执行 |
| 工具是否执行 | ✅ 用改后的 name + args 执行 |
| 决策体 | `{"type": "edit", "edited_action": {"name": "...", "args": {...}}}` |

```python
agent.invoke(Command(resume={"decisions": [
    {"type": "edit", "edited_action": {"name": "write_file", "args": {"path": "/safe.txt", "content": "改过了"}}}
]}), config=config)
```

#### ③ reject（拒绝）—— 不执行，告诉模型"别重试"

| 项 | 内容 |
|---|---|
| 含义 | 人否决这次调用 |
| 工具是否执行 | ❌ 不执行 |
| 决策体 | `{"type": "reject", "message": "原因"}`（message 可选） |
| 结果 | 生成一条 error 状态的消息："被拒绝 + 原因，别重试" |

```python
agent.invoke(Command(resume={"decisions": [
    {"type": "reject", "message": "这个文件不能删"}
]}), config=config)
```

#### ④ respond（代答）—— 人代替工具回答

| 项 | 内容 |
|---|---|
| 含义 | 工具不执行，人直接给出"工具结果" |
| 工具是否执行 | ❌ 不执行 |
| 决策体 | `{"type": "respond", "message": "..."}` |
| 结果 | 生成一条 success 状态的消息，内容就是 message |

```python
agent.invoke(Command(resume={"decisions": [
    {"type": "respond", "message": "用户选了方案B"}
]}), config=config)
```

**这正是"弹框让用户选"最贴合的写法**：工具不执行，人直接代答，框架自动生成干净的工具结果消息。

### 8.3 决策体速查表

| 决策 | 决策体 | 工具执行 | 生成消息 |
|---|---|---|---|
| approve | `{"type":"approve"}` | 原样执行 | 无 |
| edit | `{"type":"edit","edited_action":{...}}` | 改后执行 | 无 |
| reject | `{"type":"reject","message"?}` | 不执行 | error |
| respond | `{"type":"respond","message"}` | 不执行 | success（=message） |

## 9. 一次调用多个工具时，框架怎么处理（重点）

模型一次发出多个工具调用，其中**部分**配了 HITL，框架的处理是**批处理**。

### 9.1 流程

1. 模型发出一条 AI 消息，里面挂多个工具调用；
2. 框架扫描所有工具调用，把"需要审批的"（在 `interrupt_on` 里、且 `when` 谓词放行）**收集成一个批次**；
3. **只发一次 interrupt**，中断值是"待审批动作列表"；
4. 人工**一次给回一个决策列表**（每个待审批动作对应一条）；
5. 框架校验"决策数 == 待审批动作数"，不一致报错；
6. 按原顺序重建工具调用：
   - 审批/编辑 → 保留；
   - 拒绝/代答 → 移除，换成一条合成 ToolMessage；
   - **没配 HITL 的 → 原样保留，自动放行**；
7. 图继续：通过的工具照常执行，拒绝/代答的已有 ToolMessage、不再执行。

### 9.2 具体例子

模型一次发 3 个工具调用：`read_file`（没配）、`write_file`（配了）、`delete_file`（配了）。

```
AIMessage(tool_calls=[read_file, write_file, delete_file])
                        ↑ 自动放行    ↑ 配了       ↑ 配了
```

框架处理：

```
1. 收集待审批：write_file、delete_file
2. 发一次 interrupt，中断值 ≈ {
     "action_requests": [write_file 请求, delete_file 请求],
     "review_configs": [...]
   }
3. 人工一次给回 2 条决策（顺序对应）：
   {"decisions": [
       {"type": "approve"},                       # write_file 批准
       {"type": "reject", "message": "别删"}      # delete_file 拒绝
   ]}
4. 重建工具调用：
   read_file  → 保留（自动放行）
   write_file → 保留（批准）
   delete_file→ 移除，换成 error ToolMessage
5. 继续：read_file + write_file 并行执行，delete_file 不执行
```

### 9.3 三条关键规则

1. **一次批处理**：多个待审批工具合并成一次中断，不是各断一次；
2. **决策顺序 = 动作顺序**：决策列表第 1 条对应第 1 个待审批动作；
3. **数量必须匹配**：不一致抛 `ValueError`；
4. **没配 HITL 的工具自动放行**：根本不进入中断。

## 10. 照着本文手写一个最小实现（骨架）

如果你想从零实现 HITL，主体就下面几块。

### 10.1 核心数据结构

```
PendingAction          待审批动作
    ├─ tool_call       原始工具调用（名字、参数、id）
    └─ allowed         允许的决策集合

Decision               人工决策
    ├─ type            approve / edit / reject / respond
    ├─ edited_action?  （edit 时）改后的 name + args
    └─ message?        （reject / respond 时）附带内容

PauseRecord            暂停记录（= 一次存档）
    ├─ state           暂停时的完整状态（含消息历史）
    ├─ pending        待审批动作列表
    └─ resume_at       恢复到哪个点
```

### 10.2 核心流程（伪代码）

```
def 运行(agent, 用户输入):
    状态 = 加载存档(thread_id) 或 初始状态

    loop:
        ai_msg = 调模型(状态.消息历史)
        if ai_msg 没有工具调用:
            return ai_msg

        待审批 = [tc for tc in ai_msg.tool_calls if 需要审批(tc)]
        if 待审批:
            存档(状态, 待审批)            # 暂停：存状态 + 待审批列表
            return 中断事件(待审批)       # 交还控制权，等人工

        结果列表 = 并行执行(ai_msg.tool_calls)
        状态.消息历史 += 结果列表
        continue


def 恢复(thread_id, 决策列表):
    状态, 待审批 = 加载存档(thread_id)    # 读档
    assert len(决策列表) == len(待审批)    # 数量必须匹配

    for 动作, 决策 in zip(待审批, 决策列表):
        if 决策.type == approve:
            保留(动作.tool_call)
        elif 决策.type == edit:
            保留(用 决策.edited_action 替换 name/args)
        elif 决策.type == reject:
            移除(动作.tool_call)
            追加 ToolMessage(error, "被拒绝: " + 决策.message)
        elif 决策.type == respond:
            移除(动作.tool_call)
            追加 ToolMessage(success, 决策.message)

    结果列表 = 并行执行(保留的工具调用)
    状态.消息历史 += 结果列表
    return 运行(agent, 继续)
```

### 10.3 手写必须处理的三个难点

1. **状态持久化**：暂停时必须把"完整状态 + 待审批列表"落盘，恢复时原样加载——这是跨进程/重启恢复的关键。
2. **悬空工具调用**：reject/respond 移除了 tool_call，必须立刻补一条**带正确 tool_call_id** 的 ToolMessage，否则模型会看到"没有结果的工具调用"，行为跑偏。
3. **节点重跑语义**：恢复时暂停所在的逻辑会重跑，`interrupt()` 之前的代码必须幂等。

## 11. 常见疑问（汇总）

### 11.1 每个消息最终都会存储吗？

基本上会，但有前提：正常运行到存盘点就都存；进程在写完前崩溃、或持久化模式选 `"exit"` 且中途被杀，在途消息会丢。

### 11.2 HITL 会新增存储吗？

不会新增存储类型/新表。中断时只是**多写一次存档**（把暂停状态 + 中断值写进同一套三张表）。

### 11.3 没有 HITL，能不能 resume 加载历史？

- **resume**（从 interrupt 恢复）依赖 HITL；
- **加载/重放历史消息**不依赖 HITL，靠 checkpoint 随时可读（`get_state` / `get_state_history` / 指定 `checkpoint_id` / 带新输入 `invoke`）。

### 11.4 工具弹框：用 HITL 还是阻塞工具？

| 维度 | 不用 HITL（工具内阻塞） | 用 HITL |
|---|---|---|
| 等待期间资源 | worker 一直被占 | 完全释放 |
| 进程重启 | 丢 | 能恢复 |
| 等多久 | 受超时限制 | 想等多久等多久 |
| GUI 集成 | 自己搞回调/长连接 | 框架给 interrupt 事件 |
| 可重试/分支 | 无 | 有（换值重试） |

前后端分离场景**强烈建议用 HITL**；单进程本地脚本（如命令行 `input()`）用阻塞工具反而简单。

### 11.5 自己写循环"中断+读历史重开"，和 HITL 一样吗？

大方向类似但**不等价**，三个差别：

1. **消息语义**：HITL 自动生成正确 tool_call_id 的 ToolMessage；手动补若补成"新用户消息"会留下悬空工具调用，行为跑偏。
2. **状态完整性**：HITL 存完整图状态；只存消息历史会丢中间状态。
3. **精确续接 vs 重新推理**：HITL 从暂停点继续；重开是让模型重读全部历史重新推理。

## 12. 常见坑

1. **没配存档器**：interrupt 直接报错。
2. **悬空工具调用**：reject/respond 后没补对应 tool_call_id 的 ToolMessage，行为跑偏。
3. **resume 值类型不对**：`interrupt_on` 的 resume 是 `{"decisions": [...]}`，不是裸字符串。
4. **决策数量不匹配**：批处理中断里，决策数必须等于待审批动作数。
5. **节点重跑副作用**：`interrupt()` 之前的代码要幂等。

## 13. 术语表

| 术语 | 通俗解释 |
|---|---|
| HITL | 人工介入：AI 停下来等人拍板再继续 |
| interrupt | 暂停：停下、存档、把内容抛给调用方 |
| resume | 继续：加载存档、把答案塞回那一行接着跑 |
| 中断值 | interrupt 抛给调用方的内容 |
| 决策（decision） | 人对工具调用的处理：approve / edit / reject / respond |
| 批处理 | 一次中断审完所有待审批工具调用 |
| 存档器 | 保存图状态的组件，HITL 依赖它 |
