## 1. 先分清两件事：对话消息 ≠ 文件

进入正题前，先划清一个容易混淆的边界。一个智能体在干活时，会产生**两类完全不同的东西**：

| 东西 | 是什么 | 例子 |
|---|---|---|
| **对话消息** | 对话本身的逐条记录 | 用户的话、AI 的回答、工具执行的结果、系统设定 |
| **文件** | 智能体用"写文件"能力落盘的内容 | 它帮你生成的一份报告、一段代码 |

这两类东西的**保存方式不一样**：文件是智能体主动"写"出来的（存在哪取决于你给它配的文件后端：内存、本地磁盘、云存储等）；而**对话消息是框架自动替你保存的**，不用智能体自己操心。

本文只讲**对话消息**这一件事。文件怎么存，是另一个话题。

## 2. 消息存在哪：一个共享的"消息列表"

### 2.1 消息列表

整个智能体在运行期间，维护着一份**共享状态**，其中有一块专门放对话，叫**消息列表**。它就是一条条消息按时间顺序排成的队列：

```
[系统设定] [用户：帮我查一下] [AI：好的，我来调工具] [工具结果：……] [AI：查到了]  ……
```

每来一条新消息（不管是用户说的、AI 回的、还是工具返回的），就**往这个列表末尾追加一条**。这份列表是所有环节共享的：模型读它、工具结果写它、下一轮模型再读它。

### 2.2 关键前提：不配"存档器"，就只在内存里临时存在

这份消息列表本身只在**内存**里。如果不做任何额外配置，程序一结束，它就像没存档的游戏进度一样**彻底消失**。

要让消息"存下来、重启后还能接着聊"，你必须给智能体配一个**存档器**。存档器决定了消息最终落到哪：

| 存档器类型 | 消息存到哪 | 进程重启后 |
|---|---|---|
| 内存版 | 内存 | 没了 |
| 文件版 | 本地磁盘文件 | 还在 |
| 数据库版（如 PostgreSQL / MySQL） | 数据库表里 | 还在 |

**DeepAgents 自己不定死存哪**——它只是把"存档器"这个参数往下传，你传内存它就存内存，你传数据库它就存数据库。这也是为什么本文后面讲数据库表时，说"表是存档器建的，不是 DeepAgents 建的"。

## 3. 什么时候存：每"一步"存一次，不是每条消息

这是最容易搞错的地方，单独拎出来讲。

### 3.1 先纠正一个直觉

很多人会以为"每来一条消息就写一次库"。**不是的。** 存盘的粒度是**"一步"（一轮动作）**，不是"一条消息"。

什么叫"一步"？智能体干活的节奏大致是"模型想一步 → 执行一步 → 模型再想一步"这样的循环。每一次"模型想完"、或者每一次"工具执行完"，都算**完成了一步**。**每完成一步，才存一次**。

### 3.2 一个具体例子

假设对话是：

> 用户：北京和南京今天的温度都是多少？
> AI（一次回复里同时发两个工具调用）：查北京温度、查南京温度
> 工具结果 1：北京 20 度
> 工具结果 2：南京 23 度
> AI：北京 20、南京 30

直觉上你可能数出 6 条消息，觉得要写 6 次库。**实际上只写了 4 次**。原因有两个：

**原因一：那两个"工具调用"是同一句话，不是两句。**
模型在一次生成里，一次性输出了一条 AI 回复，里面**同时带着两个工具调用**。在存储层面这是**一条消息**（一条 AI 消息，内部挂着两个待执行的工具请求），不是两条。

**原因二：两个工具是"并行"执行的，结果一起存。**
查北京、查南京这两个工具，框架是**同时**发出去跑的。它们跑完，两个结果**合并在一起、只存一次**。

于是真实的时间线是这样的：

| 存盘次数 | 时机 | 此刻消息列表多出什么 |
|---|---|---|
| ① | 调用开始（读入用户输入） | 用户那句话 |
| ② | 模型第一次想完 | 一条 AI 消息（内含两个工具调用） |
| ③ | 两个工具**并行**跑完 | 两条工具结果 **一起**进来 |
| ④ | 模型第二次想完 | 最终那句 AI 回答 |

**一共 4 次，不是 6 次。**

## 4. 存了什么内容

从**逻辑上**看，每次存盘存的都是**"截至此刻的完整对话历史"**——也就是所有消息的：

- 每一条消息的**完整正文**；
- 每条消息的**唯一编号**（同一条消息在多次存盘里靠编号对齐、去重）；
- 附加信息（比如 AI 消息里挂着的工具调用请求、工具结果对应的那条请求编号等）。

但**"存"的方式不是每次都把全量重新抄一遍**（那样会越存越慢）。实际做法是"**全量快照 + 增量**"结合：

- **每隔约 50 步**，才把整个消息列表**全量抄一遍**（这叫一次"快照"）；
- 两次快照之间，**只记"这次新增了哪几条"**（这叫"增量"）。

所以无论哪一步，逻辑上的"完整对话"都还在——读的时候，用"最近一次快照 + 中间攒下的增量"就能拼出全量列表。这样既没丢东西，又避免了每步都全量重抄。

## 5. 存储格式：一份"存档"落在数据库的三张数据表里

> 本节是全文核心，按读者要求给出**三张表的具体定义和存储示例**（含列名与建表语句，以 MySQL 版存档器为例；PostgreSQL 结构相同，仅列类型换成对应类型）。

### 5.1 一句话

> 存到数据库里的**不是"一条条消息"**，而是**"一份份存档"**。消息只是每份存档里的一部分内容。

### 5.2 三张表的真实定义（建表语句）

```sql
-- 表一：checkpoints（存档目录）—— 每存一次档，插一行
CREATE TABLE checkpoints (
    thread_id            VARCHAR(150) NOT NULL,          -- 会话编号
    checkpoint_ns        VARCHAR(150) NOT NULL DEFAULT '',-- 子图命名空间（子智能体用）
    checkpoint_id        VARCHAR(150) NOT NULL,          -- 存档编号（单调递增）
    parent_checkpoint_id VARCHAR(150),                   -- 上一个存档，串成链
    type                 VARCHAR(150),                   -- 存档类型
    checkpoint           JSON NOT NULL,                  -- 存档的"结构"（版本号等，不含消息正文）
    metadata             JSON NOT NULL DEFAULT ('{}'),   -- 元信息（来源、第几步）
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

-- 表二：checkpoint_blobs（正文）—— 真正存消息正文的地方
CREATE TABLE checkpoint_blobs (
    thread_id     VARCHAR(150) NOT NULL,
    checkpoint_ns VARCHAR(150) NOT NULL DEFAULT '',
    channel       VARCHAR(150) NOT NULL,   -- 通道名，'messages' 就是"消息列表"
    version       VARCHAR(150) NOT NULL,   -- 该通道的版本号
    type          VARCHAR(150) NOT NULL,   -- 序列化类型（通常 'msgpack'）
    `blob`        LONGBLOB,                -- 消息列表的二进制内容
    PRIMARY KEY (thread_id, checkpoint_ns, channel, version)
);

-- 表三：checkpoint_writes（增量 / 待写入）
CREATE TABLE checkpoint_writes (
    thread_id     VARCHAR(150) NOT NULL,
    checkpoint_ns VARCHAR(150) NOT NULL DEFAULT '',
    checkpoint_id VARCHAR(150) NOT NULL,
    task_id       VARCHAR(150) NOT NULL,   -- 是哪个任务写的
    idx           INTEGER NOT NULL,        -- 该任务的第几笔写入
    channel       VARCHAR(150) NOT NULL,
    type          VARCHAR(150),
    `blob`        LONGBLOB NOT NULL,       -- 这次写入的消息（二进制）
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, idx)
);
```

> 另外还有一张 `checkpoint_migrations`（单列主键，只记录"迁移到第几版"），与消息存储无关，可忽略。

### 5.3 关键分工：谁存"结构"，谁存"正文"

一次存档落库时，有一条关键规则（来自存档器的写库实现）：

- **基本类型**（数字、字符串、布尔等）的值，**直接内联**进表一的 `checkpoint` JSON 里；
- **非基本类型**（比如整个消息列表这种"对象"），**被移出去**，单独序列化后存进表二 `checkpoint_blobs`。

所以结论是：**表一的 `checkpoint` JSON 里没有消息正文，只有版本号等"结构信息"**；消息正文在表二（快照时）和表三（增量时）。

### 5.4 表一：checkpoints（存档目录）—— 一行长这样

```
thread_id            = "thread-42"
checkpoint_ns        = ""
checkpoint_id        = "0194f8a1-3c2b-7e6d-9a10-5b4c3d2e1f00"   ← uuid6，单调递增
parent_checkpoint_id = "0194f8a0-…（上一个存档的 id）"
type                 = ""
checkpoint (JSON)    = {
    "v": 1,
    "id": "0194f8a1-3c2b-7e6d-9a10-5b4c3d2e1f00",
    "ts": "2025-08-26T10:20:31.123456+00:00",
    "channel_versions": {
        "messages": "00000000000000000001.00000000000000000000"
    },
    "versions_seen": { "__start__": { "messages": "…" } }
    // 注意：这里【没有】消息正文，只有版本号
}
metadata (JSON)      = { "source": "loop", "step": 0, "parents": {} }
```

- `checkpoint_id` 每次存档递增，`parent_checkpoint_id` 指向上一份，把整条对话的存档串成一条链；
- `channel_versions` 里 `messages` 的版本号，就是在表二里定位正文的"坐标"。

### 5.5 表二：checkpoint_blobs（正文）—— 一行长这样

```
thread_id     = "thread-42"
checkpoint_ns = ""
channel       = "messages"                                   ← 消息列表这条通道
version       = "00000000000000000001.00000000000000000000" ← 对应表一里的版本号
type          = "msgpack"
blob          = <二进制：反序列化后是"全量消息列表">
```

把 `blob` 反序列化（解包）后，得到的就是**全量消息列表**，例如：

```
[ HumanMessage("1+1等于几？"), AIMessage("等于2"), … ]
```

**关键点（结合第 4 节的"增量快照"）**：`messages` 通道**不是每次存档都往这里写**。只有"快照步"（约每 50 步）才把全量列表写进来；中间那些步，这里不新增 `messages` 记录（由表三接力）。

### 5.6 表三：checkpoint_writes（增量 / 待写入）—— 一行长这样

```
thread_id     = "thread-42"
checkpoint_ns = ""
checkpoint_id = "0194f8a1-…"   ← 属于哪次存档
task_id       = "…"            ← 哪个任务写的
idx           = 0              ← 该任务第 0 笔写入
channel       = "messages"
type          = "msgpack"
blob          = <二进制：这次新增的消息，反序列化后是 [AIMessage("等于2")]>
```

这张表是**"记账流水"**：快照之间的每一步，把"这次新增了哪几条消息"记成一行。读的时候，从最近的快照出发，把中间的流水一行行叠加上去，就拼出了完整列表。

### 5.7 一次存档怎么落进三张表（一张图）

```
每一步结束 ──► 表一：插入一行"存档目录"（版本号、父子链……）        ← 每步都有
                    │
                    ├─ 普通步：表三记"这次新增哪几条"（增量流水）    ← 中间大部分步
                    │
                    └─ 快照步（约每 50 步）：表二写入"全量消息列表"  ← 每约 50 步一次
                                               （二进制，按 会话+通道+版本 定位）
```

### 5.8 读的时候怎么拼回全量

```
读最新存档（表一）──► 拿到 messages 的版本号
        │
        ▼
往表二找"最近的快照"──► 反序列化出【全量列表】
        │
        ▼
再往表三把"快照之后的增量流水"一条条叠加──► 得到当前完整消息列表
```

## 6. 写库是同步还是异步：默认异步、后台线程

这是关于"会不会拖慢"的核心问题。结论先说：**默认是异步写库，不阻塞主流程**。

### 6.1 默认：后台线程异步写

主循环走到"该存盘了"这一步时，**并不亲自去写数据库**，而是把这个活**丢给一个后台线程**去做，然后**立刻继续跑下一步**，不等数据库返回。

用生活类比：你（主循环）在流水线上干活，每完成一件，就喊一句"存档！"——但喊完不站着等，继续做下一件；旁边一个专职助手（后台线程）听到后就默默去归档。你的速度不被归档拖住。

### 6.2 三种模式

框架提供三种持久化模式，默认是**异步**：

| 模式 | 行为 | 阻塞主流程？ |
|---|---|---|
| 异步（**默认**） | 下一步执行期间，后台线程并行写库 | 否 |
| 同步 | 下一步开始前，先写完库再继续 | 是 |
| 仅退出时 | 只在整次运行结束时写一次 | 否（但只写一次） |

除非你显式要求"同步"，否则就是异步。

### 6.3 两条"防出乱子"的保障

虽然是后台异步，但有两条保证，让你不会拿到"半成品"：

1. **顺序保证**：每个写库任务开始前，会等上一个写库任务先完成，保证存档按先后顺序落库、不会乱序。

2. **退出兜底**：当你这次调用**返回的那一刻**，框架会**等所有还没写完的存档都写完**。也就是说，函数一返回，数据一定已经全部进库了——不存在"函数都返回了、库里还缺最后一步"的情况。

### 6.4 那"重不重"？

你的担心有道理，但实际开销没那么可怕，因为有三重减负：

1. **不是每条消息写，是每步写**（见第 3 节，你那 6 条消息的场景只写 4 次）；
2. **写库在后台线程，和模型调用并行**——真正耗时大头是模型推理（秒级），一次数据库写入是毫秒级，默认异步模式下二者重叠，写库延迟基本被"藏"起来；
3. **消息通道做了"增量快照"优化**（见下一节），避免每一步都把整段历史重新打包一遍。

真正需要长期留意的是**两处累积**，而不是"每一步都在同步刷库"：

- **消息历史本身会持续增长**：每次快照里，消息列表都比上一次更长（对话在累积），长时间、多步骤的会话会越存越多，需要定期清理（框架提供保留策略，比如只留最近若干次存档）；
- **打包本身吃 CPU**：到了快照那一步，要把整份消息列表打包成二进制，这一步即使在后台线程做，也消耗 CPU。消息越大（超长工具输出、大文档），打包越慢。

## 7. 优化：增量快照

如果对话越长、还每次都全量重抄，就会越来越贵。所以消息列表这条通道用了**增量快照**策略：

- **每隔一定步数**（默认约 50 步），才存一次**全量**消息列表；
- 两次全量之间，**只存"增量"**（这段时间新增的那几条）。

读的时候，从最近一次全量出发，把中间那几步的增量叠加上去，就能拼出完整列表。这样既避免了"每步全量重写"，又把"回放历史"的深度压在了有限步数内，整体数据量从"越来越贵"压成了"线性增长"。

## 8. 长期单会话：读会越来越慢，怎么优化

前面（第 4、7 节）说过：历史总量会线性增长，每次新回合都要把**全量消息列表**从二进制解码回内存——这一步的代价和历史条数成正比。如果你的业务是"**同一个会话、长期不断新增对话**"，这个代价会随时间越来越明显。这一节讲怎么优化。

### 8.1 先看清：读的代价到底在哪

每次发一个新回合，框架的读过程是：

```
读最新存档 ──► 把【全量消息列表】从二进制解码回内存 ──► 压缩插件再切掉旧部分
                 ↑ 这一步和历史条数成正比，躲不掉
```

关键认知：**这一步跟"快照频率""写库异步与否"都无关**。因为无论怎么存，读回来时都要把 N 条消息解码成内存对象。所以"优化读"只有一个根本方向——**让 N 变小**（让存着的消息变短）。

### 8.2 方案一（最推荐）：定期"结转"到新会话

生产上处理"无限对话"的标准做法，是**不要无限期让一个会话涨下去**，而是定期开新会话，把"摘要 + 最近几条"带过去：

```
旧会话（已积累很多轮）
      │ 触发结转
      ▼
1. 取出"摘要 + 最近若干条消息"
2. 新建一个会话，用它们作为初始消息
3. 旧会话归档或删掉
```

这样每个会话的消息数被**卡在一个上限**，读的代价不再随时间无限增长。DeepAgents 的压缩其实已经把摘要和"从哪里开始裁"记了下来，可以拿来当结转种子；原始历史它也已经外置到文件了，不怕丢。

### 8.3 方案二：定期裁剪消息列表（同一会话内）

如果不想换会话，就在**同一个会话里**定期把消息列表**真正截短**——只保留"摘要 + 最近若干条"，把更早的旧消息从列表里移除（注意：DeepAgents 默认不这么做，需要手动截）。

- 截短后，存档里的消息真的变短了，下一次读就轻了；
- **保底**：被移除的原文先写进文件（压缩已经这么干了），需要时再读文件找回。

这就是"存储级压缩"——正好补上 DeepAgents 默认只做"上下文级压缩"、不缩存储的空缺。

### 8.4 方案三：换用"真正改写状态"的压缩

如果**不需要**回放、评测、可恢复（DeepAgents 默认保留全量历史就是为了这三样），可以换成另一套"压缩时真的把旧消息删掉、只留摘要 + 最近"的压缩机制。这样消息列表天然不长。

代价：丢了原始历史，无法回放/评测。

### 8.5 辅助手段：定期清理旧存档

除"减 N"外，数据库里**旧存档越堆越多**，也会让"按会话查最新存档"变慢。可以定期清理，只留最新一个。

⚠️ 但要小心：在用了"增量快照"的机制下，**贸然删旧存档可能把"重建全量列表所依赖的祖先快照/增量"删断**，导致消息读出来是空的。安全的顺序是：**先让最新存档成为一次完整的快照，再删更早的**（方案二/三裁剪后自然就是新快照点）。

### 8.6 几个"没用"的误区

| 你以为的优化 | 实际效果 |
|---|---|
| 调快照频率 | 只影响"写"的放大，不影响"读"——读还是要把 N 条消息解码出来 |
| 换成异步写库 | 只影响"写"的阻塞，不影响"读" |
| 只清理旧存档、不裁剪消息 | 减的是存储和查询延迟，**不减**"重建全量列表"的解码代价 |

---

## 9. 一句话总结

> 你每说一句话、AI 每想一步、工具每跑一步 → 消息列表变长 → 框架在**每完成一步后**写一次**存档**（默认走**后台线程、异步**，不阻塞主流程；你拿到的返回值里，数据已保证落库）。存的是**截至此刻的完整对话**，而不是单条消息——但**消息正文不是每步都全量重抄**：约每 50 步抄一次全量快照，中间只记增量。数据库里对应**三张数据表**：存档目录、正文、增量/待写入。

## 10. 术语表

| 术语 | 通俗解释 |
|---|---|
| 消息列表 | 对话历史本身（用户 / AI / 工具结果 / 系统设定），按时间累积 |
| 存档（检查点） | 对"截至此刻整个状态"的一次快照，消息列表是其中一块 |
| 存档器 | 决定存档落到哪的组件（内存 / 文件 / 数据库） |
| 一步（一轮动作） | 模型想一次、或工具执行一次，存盘的触发粒度 |
| 通道 | 状态里的一块独立区域，"消息列表"就是其中一条通道 |
| 正文表 | 三张数据表之一，真正存消息正文（二进制打包）的地方；只在快照步写全量 |
| 增量 / 待写入表 | 三张数据表之一，记快照之间的增量写入，读时靠它回放拼出全量 |
| 增量快照 | 每隔若干步存一次全量、中间只存增量的优化 |
| 异步写库 | 后台线程写库、不阻塞主流程的默认模式 |
| 结转 | 定期开新会话、把"摘要 + 最近消息"带过去，控制单个会话的消息数 |
| 存储级压缩 | 真正缩短存档里消息列表的压缩（区别于只压缩"给模型看的上下文"） |
